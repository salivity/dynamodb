How DynamoDB Executes Multi-Table Batch Retrieval

Amazon DynamoDB allows applications to fetch multiple items across different tables in a single network round trip using the BatchGetItem API operation. This article breaks down the internal mechanics of multi-table batch retrieval, covering how DynamoDB disaggregates the request, queries underlying storage partitions in parallel, calculates capacity unit consumption, and manages partial failures through unprocessed keys.

The Anatomy of a Multi-Table Request

A BatchGetItem call accepts a RequestItems map where keys represent table names, and values define the primary keys of the items to retrieve alongside optional projection expressions and consistency settings. A single batch call can retrieve up to 100 items and a maximum of 16 MB of data across any number of tables in the same AWS Region and account.

Request Routing and Disaggregation

When an application issues a BatchGetItem request, it lands on a DynamoDB Request Router (a stateless fleet layer). The router inspects the RequestItems payload and performs the following sequence:

  1. Schema Validation and Authentication: The router validates credentials, ensures the requester has dynamodb:BatchGetItem permissions for every specified table, and verifies that the requested keys match the primary key schemas of their respective tables.
  2. Decomposition: The request is split internally into individual sub-requests grouped by table and partition key.
  3. Partition Location Lookup: DynamoDB checks an internal partition map cache to determine which storage partition nodes host the requested primary keys.

Concurrent Execution Across Storage Nodes

DynamoDB does not process items or tables sequentially. Instead, the Request Router executes read operations in parallel across the underlying storage nodes:

  • Independent Storage Dispatches: Sub-requests targeting different tables—or different partitions within the same table—are dispatched concurrently via internal asynchronous remote procedure calls (RPCs).
  • Isolation of Table Workloads: Physical storage partitions for Table A operate completely independently of those for Table B. A high-latency partition or heavy load on one table does not stall reads targeted at partitions of a different table.
  • Consistency Application: Each table in the batch can have its own consistency model defined (eventually consistent by default, or strongly consistent). The storage nodes enforce the designated consistency level on a per-table basis.

Capacity Unit Consumption

Read capacity units (RCUs) are calculated and consumed independently per table, not aggregated across the batch:

  • Each item retrieved consumes capacity units based on its table's billing mode (Provisioned or On-Demand) and whether strongly consistent (1 RCU per 4 KB) or eventually consistent (0.5 RCU per 4 KB) reads were requested.
  • If Table A runs out of provisioned throughput, it experiences throttling, but this does not deduct capacity from or immediately throttle Table B.

Response Aggregation and Handling Partial Failures

Once storage nodes respond, the Request Router compiles the items back into a structured dictionary matching the format of the original request:

  • Responses Object: Items that were successfully retrieved are grouped under their respective table names in the Responses map.
  • UnprocessedKeys: If a subset of items cannot be read due to partition throttling, throughput exhaustion, or reaching the overall 16 MB response payload limit, DynamoDB does not fail the entire transaction. Instead, the successfully retrieved items are returned, and the remaining item keys are placed in the UnprocessedKeys block.
  • Retry Protocol: The client application is responsible for inspecting the UnprocessedKeys element in the response and retrying those specific keys, typically using an exponential backoff algorithm.
