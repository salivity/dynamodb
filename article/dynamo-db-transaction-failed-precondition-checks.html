DynamoDB Transaction Failed Precondition Checks

When an Amazon DynamoDB transaction encounters a failed precondition check, the entire transaction is immediately canceled to preserve strict atomicity. In transactional writes (TransactWriteItems), all specified operations succeed or fail together. If a conditional expression on any single item evaluates to false, DynamoDB rolls back every pending mutation, writes no data to the database, and returns a TransactionCanceledException containing detailed diagnostic information about which item triggered the failure.

Immediate All-or-Nothing Rollback

DynamoDB transactions enforce ACID properties. When executing a TransactWriteItems call, DynamoDB performs a validation and preparation phase. If any condition expression (precondition check) in the request fails during this phase:

  • Zero state changes occur: No items are created, updated, or deleted, even if the other operations in the transaction were valid and satisfied their respective conditions.
  • Isolation is maintained: Concurrent read operations will never observe partial updates from a canceled transaction.

Error Structure: TransactionCanceledException

When a precondition check fails, DynamoDB raises a TransactionCanceledException. The response object contains a critical array named CancellationReasons.

This array corresponds directly to the order of operations submitted in the TransactWriteItems call:

  • The operation that failed the precondition will have a Code of ConditionalCheckFailed.
  • Operations that were otherwise valid but canceled due to the failing operation will have a Code of None.
  • If an item also encountered another issue, such as a validation error, its corresponding reason will reflect that specific failure code.

By inspecting the index of the ConditionalCheckFailed entry within CancellationReasons, applications can determine precisely which item and condition caused the transaction to abort.

Consumed Capacity Impact

Precondition failures do not bypass DynamoDB pricing or throughput metrics:

  • Capacity is consumed: DynamoDB consumes read capacity units (RCUs) or write capacity units (WCUs)—or their on-demand equivalents—to evaluate condition expressions.
  • Billing for evaluation: Even though no items are committed, the transactional reads and validation checks required to determine that the precondition failed are billed to your account.

Recommended Handling Strategies

When an application receives a TransactionCanceledException due to a failed conditional check:

  1. Inspect CancellationReasons: Parse the response to verify whether the failure was an expected concurrency state (such as an optimistic locking version mismatch) or an unexpected data validation issue.
  2. Handle Optimistic Locking Conflicts: If the precondition was used to prevent race conditions (e.g., checking an item version), refresh the local state by fetching the latest item attributes and retry the transaction with updated condition parameters.
  3. Avoid Blind Retries: If the failed precondition represents an immutable business rule (e.g., checking that a bank balance is greater than zero), retrying immediately without changing the underlying request or state will continually fail and consume capacity.
