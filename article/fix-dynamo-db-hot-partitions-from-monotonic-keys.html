Fix DynamoDB Hot Partitions from Monotonic Keys

Monotonically increasing sort keys often cause severe write throttling and hot partition issues in Amazon DynamoDB when paired with static or low-cardinality partition keys. This article explores the root cause of this performance bottleneck and details the primary mitigation strategy: partition key write sharding (salting). By introducing randomized or calculated suffixes to your partition keys, you can evenly distribute write workloads across physical partitions while maintaining predictable query performance.

Understanding the Bottleneck

In DynamoDB, each physical partition has a hard throughput limit of 1,000 Write Capacity Units (WCUs) and 3,000 Read Capacity Units (RCUs). When an application writes sequential or time-series data using monotonically increasing sort keys (such as auto-incrementing IDs or current timestamps) against a single partition key, every write request hits the same physical partition.

Even if your overall table has provisioned thousands of WCUs, any workload exceeding 1,000 WCUs on that single partition key results in ProvisionedThroughputExceededException errors.

The Primary Solution: Partition Key Sharding (Salting)

The most effective strategy to resolve this issue is write sharding, also known as key salting. Instead of writing all monotonically increasing sort keys to a single partition key, you append a suffix (a "salt") to the partition key value to distribute the writes across multiple logical partitions.

1. Randomized Sharding

Randomized sharding works best for write-heavy workloads where items do not need to be queried together by exact key values immediately.

  • Implementation: Select a range of numbers (e.g., 1 to \(N\)) and append a randomly chosen number to the partition key: PartitionKey = "Order_" + random(1, N).
  • Result: Writes are distributed evenly across \(N\) distinct partitions, multiplying your write throughput limit by \(N\) (up to the physical limit of the table).
  • Query Trade-off: To fetch all records for a given logical entity, your application must perform parallel scatter-gather queries across all \(N\) partition keys and aggregate the results.

2. Deterministic (Calculated) Sharding

Deterministic sharding calculates the suffix based on an attribute value within the item, such as a user ID, hash, or rounded time block.

  • Implementation: Compute a hash or modulus of a secondary attribute to determine the shard: PartitionKey = "SensorData_" + (deviceID % N).
  • Result: All writes for a specific device or sub-group route to a predictable partition while spreading the total device population across \(N\) partitions.
  • Query Advantage: Reads for a specific sub-group require querying only a single partition key, avoiding scatter-gather operations while still eliminating single-partition write hotspots.

Time-Bucketed Partition Keys

If the monotonically increasing sort key represents time (e.g., an ISO-8601 timestamp), combining write sharding with time-bucketing is optimal. Define partition keys that roll over by hour, day, or week alongside the shard number:

PartitionKey = "Logs_2023-10-27_shard" + random(1, 10)

This prevents historical data from accumulating on the same active partition while allowing write workloads to span across the shards of the current time window.

Best Practices for Implementation

  • Choose the Smallest Viable Shard Count (\(N\)): Start with an \(N\) value calculated as Peak Required WCUs / 1,000. Over-sharding increases read latency and scatter-gather costs.
  • Handle Global Secondary Indexes (GSIs): Ensure that secondary indexes do not replicate the monotonic hot key pattern. GSIs have their own 1,000 WCU per-partition limit and can throttle the main table if writes are concentrated.
  • Leverage Scatter-Gather Reads Concurrently: When querying across salted keys, use asynchronous or parallel threads to query all partitions simultaneously rather than sequentially to maintain low read latency.
