Restrict DynamoDB Access by User ID Using IAM

Securing Amazon DynamoDB data at the individual item level is a critical security requirement for multi-tenant applications and user-facing services. To ensure users can only read or modify DynamoDB items associated with their specific identity, AWS Identity and Access Management (IAM) provides fine-grained access control through condition keys. This article explains the exact condition key used to enforce user-level item isolation in DynamoDB, how it operates on partition keys, and how to implement it within an IAM policy.

The Key: dynamodb:LeadingKeys

The specific IAM condition key used to enforce that users can only access DynamoDB items matching their user ID is dynamodb:LeadingKeys.

In DynamoDB, the "leading key" refers to the first part of an item's primary key: the partition key (also known as the hash key). When you apply dynamodb:LeadingKeys in an IAM policy statement, DynamoDB evaluates the partition key of every requested item against the allowed values specified in the policy condition. If a user attempts to read an item whose partition key does not match the authorized value, the request is denied.

How It Works

To dynamically restrict each user to their own data without creating separate IAM policies for every individual, dynamodb:LeadingKeys is paired with IAM policy variables.

Common policy variables used with dynamodb:LeadingKeys include:

  • ${aws:username}: Used for standard IAM users accessing the table directly.
  • ${cognito-identity.amazonaws.com:sub}: Used when authenticating web or mobile users via Amazon Cognito Identity Pools.
  • ${www.amazon.com:user_id} (or other OpenID Connect providers): Used when users federate through external identity providers like Login with Amazon, Google, or Facebook.

When an API call such as GetItem, Query, or BatchGetItem is made, DynamoDB compares the item's partition key attribute to the resolved variable of the authenticated caller.

Example IAM Policy

Below is an example of an IAM policy granting read access (GetItem and Query) to a DynamoDB table, strictly restricted to records where the partition key matches the caller's Cognito Identity ID:

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowUserSpecificDynamoDBReads",
            "Effect": "Allow",
            "Action": [
                "dynamodb:GetItem",
                "dynamodb:Query",
                "dynamodb:BatchGetItem"
            ],
            "Resource": "arn:aws:dynamodb:us-east-1:123456789012:table/UserDataTable",
            "Condition": {
                "ForAllValues:StringEquals": {
                    "dynamodb:LeadingKeys": [
                        "${cognito-identity.amazonaws.com:sub}"
                    ]
                }
            }
        }
    ]
}

Supported Operations and Constraints

  • Read Operations: The dynamodb:LeadingKeys condition applies directly to GetItem, BatchGetItem, and Query.
  • Write Operations: It also protects write operations, such as PutItem, UpdateItem, and DeleteItem, preventing users from writing or modifying items belonging to other user IDs.
  • Scan Limitations: The dynamodb:LeadingKeys condition cannot be applied to Scan operations because scans do not filter by a specific partition key during the read evaluation phase. Consequently, Scan permissions should generally be omitted from user policies when fine-grained access control is required.
