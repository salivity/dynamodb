How DynamoDB Processes ProjectionExpression

This article examines how Amazon DynamoDB processes data retrieval when using the ProjectionExpression parameter. You will learn the exact sequence of events DynamoDB uses to fetch and return data, how server-side attribute filtering functions, the impact on Read Capacity Unit (RCU) consumption, and the network-level benefits of retrieving specific attributes instead of entire items.

The Data Retrieval Lifecycle

When an operation such as GetItem, BatchGetItem, Query, or Scan includes a ProjectionExpression, DynamoDB follows a specific execution order:

  1. Storage Read: DynamoDB locates and reads the complete item from the underlying partition storage.
  2. Server-Side Extraction: The DynamoDB engine inspects the retrieved item and strips away all attributes that were not specified in the ProjectionExpression string.
  3. Payload Construction: DynamoDB constructs a serialized response payload containing only the requested subset of attributes.
  4. Network Transfer: The final pruned JSON response is transmitted over the network back to the client application.

Read Capacity Unit (RCU) Calculation

A common misconception is that specifying a ProjectionExpression reduces the consumed Read Capacity Units (RCUs). In DynamoDB, RCUs are calculated based on the total size of the item read from the storage layer, not the size of the data returned to the client:

  • For GetItem, DynamoDB calculates the item size by rounding up to the nearest 4 KB chunk. If a record is 6 KB and the ProjectionExpression narrows the response down to a 200-byte attribute, DynamoDB still bills for reading the full 6 KB (which consumes 2 strongly consistent RCUs, or 1 eventually consistent RCU).
  • For Query and Scan operations, the 1 MB evaluation limit applies before the projection is executed. DynamoDB reads items up to the 1 MB threshold, measures the read capacity based on the unprojected data, applies both FilterExpression and ProjectionExpression, and then returns the remaining data.

Network Performance and Serialization Benefits

While ProjectionExpression does not reduce read provisioning costs, it significantly optimizes network performance:

  • Reduced Bandwidth Consumption: By eliminating unneeded attributes (such as large binary blobs, embedded lists, or heavy text strings), the wire payload is kept as small as possible.
  • Lower Latency: Smaller payloads reduce TLS transfer time and overall round-trip latency, especially in high-throughput microservices architectures.
  • Client-Side Efficiency: Application memory overhead and JSON deserialization times drop because the SDK processes significantly smaller data structures.

Usage with Secondary Indexes

When querying a Global Secondary Index (GSI) or Local Secondary Index (LSI), ProjectionExpression behavior depends on the index's projection configuration:

  • KEYS_ONLY or INCLUDE Indexes: If you request an attribute in the ProjectionExpression that is not projected into the index, DynamoDB will reject the request with a validation exception (for GSIs) or perform an additional read against the base table (for LSIs), consuming additional base-table RCUs.
  • ALL Indexes: Any attribute can be included in the ProjectionExpression without penalty, as the index contains a complete replica of the base table's attributes.
