How DynamoDB Processes Cross-Table Transactions

Amazon DynamoDB processes transactional writes across multiple tables using the TransactWriteItems API, which enforces full ACID (Atomicity, Consistency, Isolation, Durability) guarantees. This article explains the internal mechanics of cross-table transactions in DynamoDB, detailing how the underlying coordinator orchestrates a two-phase commit protocol across distributed partitions to ensure all operations either succeed or fail together.

The TransactWriteItems Operation

When handling multiple items spanning different tables, DynamoDB requires client requests to use the TransactWriteItems API call. A single transaction can contain up to 100 write actions—including Put, Update, Delete, and ConditionCheck operations—or up to 4 MB of total data. All tables involved must reside in the same AWS account and the same AWS Region.

The Internal Two-Phase Commit Workflow

Because different tables typically reside on physically separate storage nodes (partitions), DynamoDB cannot apply writes locally in a single step. Instead, it coordinates cross-table writes using a specialized internal subsystem acting as a Transaction Coordinator:

  1. Request Intake and Routing: The client sends the TransactWriteItems payload to a DynamoDB request router. The router assigns a Transaction Coordinator to oversee the entire lifecycle of the transaction.
  2. Phase 1: Prepare and Validate:
    • The coordinator divides the request into individual item operations and routes them to the storage nodes hosting the respective partitions for each target table.
    • Each target partition validates any specified condition expressions against the item's current state.
    • If the conditions are met, the partition places an internal reservation (lock) on the item to prevent concurrent modifications, ensuring serializable isolation.
    • Each partition reports back to the coordinator whether the prepare phase succeeded or failed.
  3. Phase 2: Commit or Abort:
    • Commit: If every partition successfully validates conditions and reserves its item, the coordinator instructs all nodes to commit the changes. The data is written to the primary storage replicas, committed to the transaction logs, and the internal locks are released.
    • Abort (Rollback): If a single condition check fails, a partition is unavailable, or a concurrent transaction conflicts with a locked item, the entire transaction is rejected (TransactionCanceledException). The coordinator issues a cancellation to all participating partitions, releasing any acquired locks without applying modifications.

Isolation and Concurrency Handling

DynamoDB provides serializable isolation for transactional writes. During execution:

  • No Dirty Reads: Reads running with eventual consistency or strong consistency will not see intermediate, uncommitted states of items involved in a transaction.
  • Item-Level Contention: While the transaction is in-flight, conflicting transactional writes or standard write operations targeting the same items are rejected or queued depending on timing. To minimize latency and rollbacks, transactions should keep the number of touched items low and avoid hot keys.

Capacity and Performance Cost

Processing transactional writes across different tables incurs double the provisioned capacity compared to standard writes. Each item in the transaction consumes two Write Capacity Units (WCUs) per KB—one for the preparation phase and one for the commit phase. Additionally, because the coordinator must perform distributed network round-trips to coordinate across different table partitions, cross-table transactions exhibit slightly higher latency than standard single-item operations.
