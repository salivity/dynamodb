How DynamoDB Executes Parallel Scans

Amazon DynamoDB executes parallel scans by logically dividing a table or secondary index into multiple non-overlapping segments and allowing multiple worker threads or processes to scan these segments concurrently. By processing multiple segments simultaneously, an application can bypass the single-threaded throughput bottlenecks of a standard sequential scan, maximize consumed read capacity, and dramatically reduce the overall time required to process large datasets.

To execute a parallel scan, your client application initiates multiple independent Scan requests in parallel across different threads, processes, or compute instances. Each request must include two critical parameters: TotalSegments and Segment.

  • TotalSegments: Specifies the total number of logical partitions you want to divide the scan into. This number must be identical across all parallel workers.
  • Segment: Specifies the zero-based index (from 0 to TotalSegments - 1) that an individual worker thread is responsible for scanning.

DynamoDB uses an internal hashing algorithm based on the table's primary keys to assign data to each logical segment. This ensures that every item in the table is mapped to exactly one segment, preventing duplicate reads across concurrent workers. When a worker requests its assigned segment, DynamoDB retrieves items belonging exclusively to that segment's partition range.

Because DynamoDB spreads data across multiple physical storage partitions behind the scenes, parallel scanning aligns application threads directly with these physical partitions. If TotalSegments is set roughly equal to or greater than the number of physical partitions backing the table, the scan operations can pull data from multiple storage nodes at the same time, avoiding I/O contention on a single node.

Each parallel scan request operates with independent pagination. When a segment's scan operation reaches the 1 MB data limit or a designated page limit, DynamoDB returns a LastEvaluatedKey specific to that segment. The corresponding worker must supply this key in its subsequent request using the ExclusiveStartKey parameter to resume scanning where it left off. Because each segment progresses independently, workers do not need to coordinate with one another, and variations in segment size or network latency will not block other threads from finishing.

Parallel scans consume provisioned Read Capacity Units (RCUs) rapidly. If the cumulative read rate of all simultaneous workers exceeds the table's configured or available read throughput, DynamoDB will return ProvisionedThroughputExceededException errors. To execute parallel scans efficiently without disrupting other workloads, applications typically implement client-side rate limiting, configure exponential backoff, or schedule parallel scans during low-traffic periods.
