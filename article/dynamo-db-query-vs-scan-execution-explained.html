DynamoDB Query vs Scan Execution Explained

Amazon DynamoDB provides two distinct methods for reading collections of items: the Query operation and the Scan operation. While a Query targets specific items by searching directly against partition and sort key values, a Scan sequentially inspects every single item across an entire table or secondary index. Understanding the execution mechanics behind these two operations is essential for designing low-latency applications, minimizing consumed Read Capacity Units (RCUs), and keeping AWS infrastructure costs predictable.

How DynamoDB Executes a Query Operation

A Query operation searches an item collection directly by leveraging the table’s primary key schema.

  1. Partition Targeting: Every Query requires an equality condition on the partition key (PK = value). DynamoDB runs the partition key value through an internal hash function to identify the exact physical partition storing that data.
  2. Sort Key Traversal: If a sort key condition is provided (using operators like =, <, >, BETWEEN, or begins_with), DynamoDB traverses the sorted index structure within that specific partition to isolate the matching range.
  3. Data Retrieval: DynamoDB reads only the items that satisfy the partition and sort key conditions, up to a maximum data payload of 1 MB per request.
  4. Post-Fetch Filtering: If a FilterExpression is applied, DynamoDB evaluates it in memory after reading the indexed items from the partition and discards non-matching records before returning the payload to the client.

Because DynamoDB routes directly to the relevant partition and reads only the requested slice of data, Query operations typically execute with single-digit millisecond latency regardless of total table size.

How DynamoDB Executes a Scan Operation

A Scan operation reads all data stored in the table without relying on specific partition keys.

  1. Full Partition Iteration: DynamoDB sequentially accesses every physical partition hosting the table or index.
  2. Page-by-Page Reading: DynamoDB reads items sequentially in the order they are stored, loading up to 1 MB of raw data into memory.
  3. Post-Fetch Filtering: Just as with a Query, if a FilterExpression is defined, DynamoDB applies it to the 1 MB block of data after it has been read from storage. Non-matching items are discarded from the client response.
  4. Pagination: If more items remain in the table after reaching the 1 MB limit, DynamoDB returns a LastEvaluatedKey. The client must issue a subsequent Scan request passing this key as the ExclusiveStartKey to continue reading through the table.

Because a Scan examines the entire dataset, its execution time and resource consumption grow linearly as the table grows.

Key Operational Differences

RCU Consumption

  • Query: You are charged RCUs based only on the size of the items that match the key condition. Applying a FilterExpression does not reduce RCU consumption, but the scope of data read remains confined to the specified partition key.
  • Scan: You are charged RCUs for the total size of all items evaluated across the entire table, regardless of whether a FilterExpression discards most or all of them.

Performance and Latency

  • Query: Executes rapidly and predictably because DynamoDB looks up data directly by its physical partition location.
  • Scan: Consumes significant I/O and takes longer to complete as table size increases. Running large Scans can exhaust provisioned read throughput and throttle concurrent application requests.

Concurrency

  • Query: Operates sequentially within a single partition collection per request.
  • Scan: Supports Parallel Scans, allowing an application to divide the table into multiple logical segments and process them concurrently using background worker threads.

When to Use Each Operation

  • Use Query for almost all standard application workloads. Queries are ideal for retrieving individual records, range-based lookups (such as time-series events for a specific user), and foreign-key-style lookups via Global Secondary Indexes (GSIs).
  • Use Scan sparingly. Scans are intended for full-table operations such as exporting data to an analytics pipeline (e.g., Amazon S3 via AWS Glue), database migrations, or auditing small lookup tables where maintaining an index is unnecessary.
