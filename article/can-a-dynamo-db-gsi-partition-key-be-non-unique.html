Can a DynamoDB GSI Partition Key Be Non-Unique?

Yes, the partition key of an Amazon DynamoDB Global Secondary Index (GSI) can be non-unique. In fact, allowing non-unique partition keys is one of the primary reasons to use a GSI. This article covers how non-unique partition keys work in GSIs, how uniqueness differs between a base table and an index, and the best practices for managing high-cardinality and low-cardinality index keys.

Understanding GSI Partition Key Uniqueness

In a DynamoDB base table, the primary key must be unique:

  • If the base table uses a simple primary key (partition key only), each item must have a unique partition key value.
  • If the base table uses a composite primary key (partition key and sort key), the combination of both keys must be unique, even though individual partition keys can repeat.

A Global Secondary Index does not enforce uniqueness in any scenario. When you define a GSI, multiple items from the base table can share the exact same GSI partition key value. Furthermore, multiple items can even share the exact same combination of GSI partition key and GSI sort key.

Common Use Cases for Non-Unique GSI Keys

Non-unique GSI partition keys enable standard one-to-many lookup patterns that are difficult to achieve on base tables:

  • Status Queries: Querying records by state (for example, finding all orders where OrderStatus = "PENDING"). Thousands of orders can share the same status.
  • Parent-Child Relationships: Grouping data under a shared parent identifier (for example, retrieving all transactions where CustomerId = "CUST123").
  • Category Browsing: Organizing an inventory table by broader classifications (for example, listing all products under Department = "HomeGoods").

When you run a Query operation against the GSI using a non-unique partition key, DynamoDB returns all matching items that contain that partition key value.

Important Considerations

While non-unique partition keys provide powerful querying flexibility, consider the following performance and design factors:

  • Sparse Indexes: If an item in your base table does not contain the attribute defined as the GSI partition key, DynamoDB will not project that item into the GSI. This behavior makes GSIs naturally sparse, which saves storage and reduces write capacity consumption.
  • Hot Partitions: If a single partition key value corresponds to an overwhelmingly large percentage of your data (e.g., Status = "ACTIVE" across millions of rows), read and write operations targeting that key can overload a single physical partition. To avoid throttling, ensure workloads distribute reads evenly or apply partition sharding techniques when dealing with heavily skewed datasets.
