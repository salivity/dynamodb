Exceeding DynamoDB Transaction Size Limits

This article explains what happens when an application breaches Amazon DynamoDB transaction limits, detailing the specific constraints enforced by the service, the exact errors returned, and the resulting system behavior. It also outlines actionable strategies to handle and prevent these transactional failures, ensuring your application remains resilient and performant.

DynamoDB Transaction Limits

Amazon DynamoDB supports ACID transactions through two primary API calls: TransactWriteItems and TransactGetItems. When performing transactions, DynamoDB imposes strict hard limits:

  • Item Count Limit: A single transaction can contain a maximum of 100 actions (operations) or touch up to 100 individual items.
  • Total Payload Size Limit: The aggregate size of all items involved in a single transaction cannot exceed 4 MB.
  • Individual Item Limit: The standard DynamoDB limit of 400 KB per individual item still applies within transactions.

Immediate Consequences of Exceeding Limits

When an application sends a transaction request that violates any of these size or item constraints, DynamoDB rejects the entire request immediately at the API validation layer.

1. Request Rejection via ValidationException

If a transaction contains more than 100 operations, or if the combined size of the items exceeds 4 MB, DynamoDB returns a client-side HTTP 400 error: ValidationException. The error message will explicitly state that the request payload or action count exceeded the allowable maximum.

2. Complete Transaction Abort (Atomicity Enforced)

DynamoDB transactions are strictly atomic. If an error occurs—whether it is a ValidationException during initial validation or a TransactionCanceledException during execution—no changes are committed to the database. DynamoDB does not perform partial writes. Every single operation within that transaction is rolled back, leaving the database state completely unchanged.

3. Wasted Application Latency

Because validation rejects oversized requests, no database write capacity units (WCUs) are consumed for the uncommitted data. However, your application will still incur round-trip network latency and the compute overhead of serializing and transmitting an oversized payload over the wire.

How to Prevent and Resolve Limit Errors

To prevent transactions from failing due to size restrictions, implement the following architectural patterns:

  • Client-Side Validation: Enforce payload size checks and item counters in your application layer before making the API call. If a batch exceeds 100 items or 4 MB, split it before transmission.
  • Split into Multiple Transactions: If operations do not strictly require simultaneous atomicity across all items, partition the workload into multiple, independent transactional batches.
  • Use Amazon S3 for Large Payloads: Store large binary data or text documents in Amazon S3 and store only the resulting object URL or metadata in DynamoDB. This keeps individual item sizes well below the 400 KB limit and protects the aggregate 4 MB transaction ceiling.
  • Evaluate the Need for ACID Guarantees: If atomic consistency across items is not strictly necessary, use BatchWriteItem instead of TransactWriteItems. While BatchWriteItem is limited to 25 items and 16 MB, it handles partial completions and reduces the strict locking overhead associated with transactions.
