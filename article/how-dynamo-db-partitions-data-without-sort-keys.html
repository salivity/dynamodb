How DynamoDB Partitions Data Without Sort Keys

When an Amazon DynamoDB table is designed without a sort key, it operates using a simple primary key structure composed entirely of a partition key. This article explains how DynamoDB manages underlying physical storage, distributes read and write workloads, splits partitions dynamically, and routes operations using hash functions when sort keys are absent.

The Role of the Hash Function

In a simple primary key schema, every item in the DynamoDB table is uniquely identified by its partition key value alone. When an application issues a write or read request (PutItem, GetItem, UpdateItem, or DeleteItem), DynamoDB passes the partition key value into an internal cryptographic hash function.

The output of this hash function is an integer that falls within a fixed, deterministic numeric range. DynamoDB maps this output to a specific physical storage unit, known as a partition. Because there is no sort key to define an ordered range within that partition, the hash determines the absolute location of the item.

Physical Partition Allocation and Routing

DynamoDB distributes data across a fleet of solid-state drive (SSD) storage servers. The global hash space is divided into contiguous ranges, with each physical partition assigned responsibility for a specific slice of that range:

  1. Request Reception: An incoming request hits a DynamoDB request router.
  2. Hashing: The router hashes the item's partition key.
  3. Lookup: The router consults an internal partition map to identify which physical partition owns the corresponding hash value.
  4. Direct Routing: The request is sent directly to the three storage nodes comprising that physical partition's replication group (for high availability via Paxos consensus).

Because each partition key must be unique in tables without sort keys, multiple items can never share the exact same partition key. However, different partition keys whose hash values fall into the same numeric range will reside on the same physical partition.

Partition Splitting Triggers

A single physical partition in DynamoDB has strict operational constraints:

  • Storage Capacity: Up to 10 GB of data.
  • Throughput Capacity: Up to 1,000 Write Capacity Units (WCU) or 3,000 Read Capacity Units (RCU).

When a table grows and exceeds either the 10 GB storage boundary or the per-partition throughput threshold, DynamoDB splits the physical partition automatically. It creates a new physical partition and redistributes roughly half of the hash range from the original partition to the new one.

Because the data is organized strictly by hash value, the split divides the keys based on where their hashes land in the range, requiring no manual intervention or downtime.

Query and Access Patterns

The absence of a sort key directly impacts access capabilities:

  • Point Operations: Operations relying on the partition key locate the item in \(O(1)\) time because the hash points to an exact storage location.
  • Range Queries: The Query API requires a partition key and can only retrieve a single item in a simple primary key schema, effectively functioning like a GetItem call. You cannot query a range of items across different partition keys.
  • Scans: Retrieving multiple items without specifying exact partition keys requires a Scan operation, which reads sequentially across all physical partitions.

Workload Uniformity and Hotspots

Without sort keys to diversify data within a partition key, high-cardinality partition keys become essential. If an application repeatedly accesses a small subset of partition keys, all associated requests target the single physical partition housing those hashes.

While DynamoDB includes adaptive capacity to temporarily borrow unused read/write units from other partitions, heavily concentrated traffic on individual keys can still saturate a single partition's physical 1,000 WCU or 3,000 RCU ceiling, resulting in ProvisionedThroughputExceededException throttling errors. Selecting partition keys with millions of distinct, evenly distributed values ensures smooth distribution across all underlying partitions.
