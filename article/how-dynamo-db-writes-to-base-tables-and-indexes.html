How DynamoDB Writes to Base Tables and Indexes

When you write to an Amazon DynamoDB table that includes secondary indexes, DynamoDB separates the execution into synchronous and asynchronous operations depending on the index type. The base table write is committed first alongside any Local Secondary Indexes (LSIs) synchronously. In contrast, Global Secondary Indexes (GSIs) receive updates asynchronously through an internal storage replication stream. Understanding this split mechanism is essential for managing latency, capacity costs, and data consistency across your application.

The Base Table Write Execution

When a client sends a write request—such as PutItem, UpdateItem, or DeleteItem—to DynamoDB, the request is directed to the storage nodes hosting the target partition.

  1. Quorum Acknowledgment: DynamoDB replicates data across three facilities within an AWS Region. The write to the base table is considered successful and acknowledged to the client as soon as a quorum (at least two out of three storage nodes) confirms the write.
  2. Item Evaluation: DynamoDB evaluates whether the incoming write modifies attributes that are part of any defined secondary index keys or projected attributes. If an index is unaffected by the update, DynamoDB skips processing for that index entirely.

Local Secondary Indexes (LSIs): Synchronous Updates

Local Secondary Indexes share the same partition key as the base table item but use a different sort key. Because an LSI shares the same physical partition as the base table:

  • Atomic and Synchronous: Writes to LSIs occur in the exact same transaction as the base table write. The update to the LSI must succeed alongside the base table for the client to receive an HTTP 200 success response.
  • Failure Handling: If an LSI write fails (for example, if the 10 GB partition limit for an item collection with LSIs is exceeded), the entire write to the base table is rejected.
  • Capacity Consumption: LSIs consume Write Capacity Units (WCUs) directly from the base table's allocated capacity. A write that alters an LSI consumes additional WCUs proportional to the size of the projected attributes written to the index.

Global Secondary Indexes (GSIs): Asynchronous Updates

Global Secondary Indexes have different partition keys and sort keys from the base table, meaning they are stored on entirely separate physical storage partitions.

  • Decoupled Replication: DynamoDB does not update GSIs synchronously during the client write. Instead, once the base table write achieves quorum, DynamoDB automatically writes the mutation to an internal, highly optimized replication log.
  • Background Ingestion: Background storage processors consume this log and asynchronously apply the item mutations to the corresponding GSI partitions.
  • Eventual Consistency: Because updates are propagated asynchronously, reads against a GSI are strictly eventually consistent. There is a small propagation delay (typically a fraction of a second under normal load) before changes appear in the index.
  • Dedicated Capacity: GSIs maintain their own provisioned or on-demand write capacity. The asynchronous update consumes WCUs from the specific GSI, calculated based on the size of the projected attributes in that index.

Handling Throttling and Backpressure

Because GSI updates occur asynchronously, capacity mismatches between the base table and its GSIs can create operational issues:

  • GSI Throttling: If a GSI does not have sufficient write capacity to absorb the incoming write rate from the base table, the internal replication stream buffers the updates.
  • Backpressure on the Base Table: To prevent unbounded replication lag, DynamoDB applies backpressure. If the replication buffer fills because a GSI is severely throttled, DynamoDB throttles writes on the base table itself, even if the base table has ample available capacity.

Write Capacity Optimization

DynamoDB minimizes resource usage across indexes using the following rules:

  • Unchanged Keys: If an UpdateItem operation modifies an attribute that is neither a key nor a projected attribute in a given index, no write capacity is consumed on that index.
  • Deletes and Replaces: If a write modifies an index's key attribute, DynamoDB must perform two actions on the index: delete the old indexed entry and write the new entry. Both actions consume write capacity on the affected index.
