Handling DynamoDB Stream Failures with Dead-Letter Queues

Amazon DynamoDB Streams capture a time-ordered sequence of item-level modifications in a DynamoDB table, typically consumed by AWS Lambda functions. Because streams are organized into ordered shards, an unhandled error can halt processing for an entire shard, causing a bottleneck known as the "poison-pill" problem. Dead-letter queues (DLQs)—implemented via Amazon Simple Queue Service (SQS) or Amazon Simple Notification Service (SNS)—solve this by offloading persistent failures, allowing stream ingestion to continue uninterrupted while isolating problematic records for targeted debugging and remediation.

The Shard Blocking Problem

DynamoDB Streams guarantee strict ordering of records within each shard. When an AWS Lambda function acts as the stream consumer, default behavior dictates that any failure will cause the entire batch to be retried until the record either succeeds or reaches the 24-hour stream retention limit. This default retry behavior stops the processing of all subsequent records in the affected shard, leading to increased latency across the system and potential data staleness.

Configuring Event Source Mapping for DLQ Routing

To route failed records away from the stream without losing data, you configure failure-handling settings on the Lambda event source mapping:

  1. Maximum Retry Attempts: Limits the number of times Lambda attempts to re-process a failed batch (configurable between 0 and 10,000) before sending the data to an on-failure destination.
  2. Maximum Age of Record: Sets a maximum threshold (from 60 seconds up to 604,800 seconds) for how old an item can be before processing is abandoned.
  3. Bisect Batch on Function Error: When enabled, Lambda splits a failing batch into two smaller batches and retries each recursively. This isolates the exact offending record from the valid records in the batch, ensuring valid items still succeed.
  4. On-Failure Destination: Directs the failed metadata and payloads to an Amazon SQS queue or an Amazon SNS topic acting as the DLQ.

What the Dead-Letter Queue Receives

When the configured retry limit or record age is breached, the event source mapping bypasses the shard block and sends an invocation record to the designated DLQ target. The DLQ message contains rich metadata, including:

  • ApproximateArrivalTimestamp: The time the record was initially ingested into the stream.
  • ShardId and StreamArn: Exact references to the source DynamoDB stream and shard location.
  • ErrorMessage and ErrorCode: The specific runtime error or exception returned by the Lambda handler.
  • Payload: The DynamoDB stream record details, including keys, old images, and new images of the modified items.

Processing and Remediating Failed Records

Once records arrive in the DLQ, they must be processed to ensure eventual consistency:

  • Secondary Lambda Consumers: A separate Lambda function can consume from the SQS DLQ at a controlled rate, attempting alternative handling, data transformations, or database corrections.
  • Alerting and Monitoring: By tracking the ApproximateNumberOfMessagesVisible metric on the SQS queue using Amazon CloudWatch alarms, teams receive immediate notifications whenever stream handling fails.
  • Long-Term Storage and Replay: Unrecoverable records can be archived into Amazon S3 for compliance, manual auditing, or replaying back into DynamoDB once application bugs or schema mismatches are patched.
