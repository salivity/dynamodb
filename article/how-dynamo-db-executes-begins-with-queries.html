How DynamoDB Executes begins_with Queries

Amazon DynamoDB executes prefix searches using the begins_with function by leveraging the physical ordering of items within a partition. When applied to a sort key in a Query operation, begins_with uses an internal B-tree index to locate the lower bound of the prefix and sequentially read contiguous items until the prefix condition is no longer met. This article details the internal mechanics of prefix searches in DynamoDB, contrasts key condition execution with filter expressions, and explains how this impacts read performance and capacity consumption.

Internal Storage and Sort Key Architecture

To understand how begins_with executes, you must understand how DynamoDB stores data across partitions:

  1. Partition Key Routing: DynamoDB hashes the partition key (hash key) to determine the exact storage node and partition where the data resides.
  2. Physical Ordering by Sort Key: Within that partition, all items sharing the same partition key are stored physically together. They are ordered strictly by their sort key (range key) values using raw UTF-8 binary encoding.
  3. Local Indexing: Storage nodes maintain localized index structures (typically B-trees or similar balanced search trees) over the sort keys of each partition.

Because items inside a partition are pre-sorted, prefix matching does not require scanning the entire partition.

Query Execution in a KeyConditionExpression

When you use begins_with inside a KeyConditionExpression, the DynamoDB storage engine executes the operation as a bounded range scan:

  1. Binary Search to the Start Boundary: DynamoDB traverses the local index to find the first item whose sort key is equal to or greater than the specified prefix.
  2. Sequential Read: The storage engine reads items sequentially forward from that point. Because strings sharing the same prefix are grouped together contiguously in UTF-8 order, matching items are adjacent on disk.
  3. Termination at the End Boundary: DynamoDB stops reading immediately upon encountering the first sort key that does not begin with the target prefix.

Because the data is contiguous, disk I/O is minimized. Only the pages containing the matching records are accessed.

Read Capacity Unit (RCU) Calculation

When begins_with is used in a KeyConditionExpression, DynamoDB charges only for the items that match the condition. The total size of the matching items is aggregated, rounded up to the nearest 4 KB boundary, and billed accordingly. Items outside the prefix range are never read from disk or processed.

begins_with in FilterExpressions vs. KeyConditionExpressions

The begins_with function behaves fundamentally differently depending on where it appears in your request:

  • KeyConditionExpression (Fast and Cost-Efficient): Restricted strictly to the sort key. It leverages physical storage layout to fetch only the relevant subset of data, terminating as soon as the prefix boundary ends.
  • FilterExpression (Slow and Expensive): Applied to non-key attributes or evaluated after a primary key condition. In this scenario, DynamoDB reads all candidate items up to 1 MB into memory, consumes RCUs for the entire dataset evaluated, and only then applies the begins_with check to strip out non-matching records before returning the payload.

UTF-8 Binary Collation Mechanics

DynamoDB does not use language-specific collation rules; it evaluates begins_with using strict UTF-8 binary byte order.

  • Case Sensitivity: Uppercase characters (ASCII values 65–90) sort before lowercase characters (ASCII values 97–122). A query for begins_with(sk, "app") will not match Apple.
  • Delimiter Alignment: Common delimiters such as #, /, or : have specific ASCII values (# is 35, / is 47, : is 58). This deterministic ordering allows developers to design hierarchical sort keys (e.g., REGION#COUNTRY#STATE) where begins_with(sk, "REGION#USA#") reliably captures all child data without edge-case overlaps.
