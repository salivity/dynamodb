How DynamoDB GSIs Impact Write Latency

Amazon DynamoDB updates Global Secondary Indexes (GSIs) asynchronously, meaning that adding multiple GSIs does not directly increase the synchronous write latency of the base table under normal operating conditions. However, maintaining numerous GSIs can indirectly introduce severe write latency, client-side timeouts, and throttling if the secondary indexes are under-provisioned or misconfigured. Understanding the architectural relationship between base tables and GSIs is essential for avoiding performance degradation as your application scales.

Asynchronous Replication Mechanics

When an application performs a PutItem, UpdateItem, or DeleteItem operation on a base table, DynamoDB commits the write to storage nodes and immediately returns a success response (HTTP 200). The base table write operation does not wait for the GSIs to be updated.

Instead, DynamoDB replicates mutations to each GSI asynchronously in the background. Because of this decoupled design, the base table write latency typically remains in single-digit milliseconds regardless of whether you have one GSI or twenty, provided all indexes have adequate throughput.

The Threat of Backpressure and Throttling

The primary risk of having many GSIs is backpressure. DynamoDB requires that all GSIs keep up with the rate of writes occurring on the base table. If any single GSI lacks sufficient Write Capacity Units (WCUs)—or cannot scale quickly enough under on-demand mode—that GSI will begin to throttle.

To prevent replication lag from growing uncontrollably, DynamoDB applies backpressure to the base table. When backpressure occurs:

  • The base table begins rejecting incoming writes with a ProvisionedThroughputExceededException.
  • The AWS SDK's default behavior is to catch these exceptions and retry the write automatically using exponential backoff.
  • These repeated client-side retries cause perceived write latency to spike dramatically from milliseconds to seconds, potentially causing upstream application timeouts.

Increased Write Amplification

Every write to a base table that affects an indexed attribute triggers an automatic write to the corresponding GSI. If an item matches the partition or sort keys of five different GSIs, a single base table write generates five additional secondary writes behind the scenes.

While these happen asynchronously, creating many GSIs multiplies the probability of hitting partition key limits or capacity bottlenecks on at least one index. A hot partition key on just one GSI can bottleneck write throughput for the entire base table.

Replication Lag vs. Write Latency

It is critical to distinguish between base table write latency and GSI replication lag:

  • Base Table Write Latency: The round-trip time for a client to persist an item to the primary table.
  • Replication Lag: The duration it takes for that change to appear when querying the GSI (eventual consistency).

Having a large number of GSIs increases the overall system workload. During traffic spikes, the replication lag across these indexes can expand significantly, leading to stale data when reading from the GSIs, even if base table write latency temporarily remains stable.

How to Prevent GSI-Induced Latency

To prevent numerous GSIs from degrading write performance, follow these design practices:

  • Match or Exceed Base Capacity: If using provisioned mode, ensure every GSI has equal or higher write capacity than the base table.
  • Use Sparse Indexes: Only project items that are strictly necessary for your access patterns. If an item lacks the GSI's partition key, DynamoDB does not write to that index, reducing overall write amplification.
  • Minimize Attribute Projections: Use KEYS_ONLY or INCLUDE rather than ALL where possible to minimize the data payload replicated across the storage fleet.
  • Monitor CloudWatch Metrics: Track OnlineIndexThrottleEvents, ProvisionedWriteCapacityUnits, and SuccessfulRequestLatency to identify struggling indexes before they apply backpressure to your primary workload.
