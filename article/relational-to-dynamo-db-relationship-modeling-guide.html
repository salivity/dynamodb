Relational to DynamoDB: Relationship Modeling Guide

Migrating data from a relational database to Amazon DynamoDB requires shifting from a normalized, schema-first architecture to an access-pattern-first design. Unlike relational databases that use foreign keys and dynamic runtime joins, DynamoDB relies on pre-joined data structures, denormalization, and strategic key design to deliver consistent single-digit millisecond latency at any scale. This guide outlines how to identify access patterns, select appropriate modeling strategies for one-to-one, one-to-many, and many-to-many relationships, and leverage single-table design principles during migration.

1. Shift from Schema-First to Access-Pattern-First

In relational modeling, the primary objective is eliminating redundancy through normalization (3NF) without worrying about how data will be queried. In DynamoDB, you must define all read and write queries before designing the schema. Because DynamoDB does not support native JOIN operations, relationships must be materialized at write time to satisfy specific access patterns efficiently.

2. Modeling One-to-One (1:1) Relationships

One-to-one relationships, such as a User and a UserProfile, can be modeled in two primary ways:

  • Embedding (Attribute Level): If the related data is always retrieved together and does not exceed the 400 KB item size limit, embed the child entity directly into the parent item as a map attribute.
  • Separation (Key Level): If the entities are queried independently or updated frequently by separate services, maintain them as separate items sharing the same Partition Key (PK) with distinct Sort Keys (SK) (e.g., PK: USER#123, SK: METADATA for the user, and PK: USER#123, SK: PROFILE for the profile).

3. Modeling One-to-Many (1:N) Relationships

One-to-many relationships, such as an Order and its OrderItems, depend on whether the number of child items is bounded or unbounded:

  • Complex Attributes for Bounded Sets: When the number of child items is small and fixed (e.g., a user's delivery addresses), embed them as a list or map directly inside the parent record.
  • Item Collections for Unbounded Sets: When the relationship is unbounded (e.g., sensor readings or customer orders), use an item collection. Store both entities under the same Partition Key, differentiating them with the Sort Key:
    • Order: PK: ORDER#101, SK: METADATA
    • Order Item 1: PK: ORDER#101, SK: ITEM#A
    • Order Item 2: PK: ORDER#101, SK: ITEM#B Querying PK = ORDER#101 retrieves the parent entity and all related child items in a single request.

4. Modeling Many-to-Many (N:M) Relationships

Many-to-many relationships, such as Students and Courses, replace the traditional relational join table with an Adjacency List pattern:

  • Create an item representing the association using composite keys. For example, assign PK: STUDENT#1 and SK: COURSE#CS101.
  • To query the relationship in reverse (e.g., "Find all students in CS101"), create a Global Secondary Index (GSI) with an inverted index pattern where the original SK becomes the GSI's Partition Key and the original PK becomes the GSI's Sort Key.

5. Denormalization and Duplication

In NoSQL, data duplication is an accepted tradeoff for query performance and cost efficiency. If an attribute from a parent record is rarely updated but frequently read alongside child records (such as a customer's name on an invoice), duplicate that field directly into the child records to avoid secondary lookups. If the duplicated data changes, handle the updates asynchronously using DynamoDB Streams and AWS Lambda.

6. Embracing Single-Table Design

Relational migrations often fail when teams map one relational table to one DynamoDB table. Instead, aim to consolidate multiple related entities into a single DynamoDB table. Use generic primary key names (e.g., PK and SK of type String) and prefix-based identifiers (e.g., ORG#id, DEPT#id). This enables single-round-trip queries that fetch multiple entity types simultaneously using the Query API.
