How DynamoDB Evaluates Complex Filter Expressions

This article provides an in-depth explanation of how Amazon DynamoDB evaluates boolean logic within complex filter expressions. It covers the hierarchy of boolean operators, the role of grouping with parentheses, how missing attributes influence truth values, and the critical distinction between post-read filtering and read capacity consumption.

The Filter Expression Pipeline

DynamoDB evaluates filter expressions strictly as a post-read operation. When a Query or Scan operation executes, DynamoDB first locates items based on partition and sort key conditions, reads up to 1 MB of raw data, and only then applies the FilterExpression.

Because evaluation happens after reading, boolean logic in filter expressions does not reduce consumed Read Capacity Units (RCUs). If an item evaluates to false based on the boolean logic, it is discarded from the result set, but the capacity required to read that item from storage has already been consumed.

Boolean Operators and Precedence

DynamoDB supports three primary boolean operators in filter expressions:

  1. NOT
  2. AND
  3. OR

When an expression contains multiple operators without explicit grouping, DynamoDB evaluates them according to standard operator precedence:

  1. NOT has the highest precedence and binds tightly to the operand immediately following it.
  2. AND has the second-highest precedence.
  3. OR has the lowest precedence.

For example, consider the following expression:

attribute_exists(A) OR attribute_exists(B) AND attribute_exists(C)

DynamoDB evaluates attribute_exists(B) AND attribute_exists(C) first. The result of that conjunction is then evaluated against attribute_exists(A) using the OR operator.

Overriding Precedence with Parentheses

To enforce a specific evaluation order, enclose sub-expressions in parentheses (). DynamoDB resolves expressions inside nested parentheses from the innermost group outward.

Rewriting the previous example:

(attribute_exists(A) OR attribute_exists(B)) AND attribute_exists(C)

DynamoDB now evaluates the OR condition first. For the item to be returned, attribute C must exist, alongside at least one of attribute A or B.

Evaluation of Comparison Operators and Functions

Each terminal node in a boolean expression is typically a comparison operator (=, <>, <, <=, >, >=), a range check (BETWEEN ... AND ...), a set membership check (IN (...)), or a built-in function:

  • attribute_exists(path)
  • attribute_not_exists(path)
  • attribute_type(path, type)
  • begins_with(path, substr)
  • contains(path, operand)
  • size(path)

Each condition resolves to a boolean truth value (true or false) for a given item:

  • Missing Attributes: If an expression references an attribute that does not exist on the item (and the expression is not specifically attribute_not_exists), that comparison evaluates to false. It does not return an error or cause the entire query to fail.
  • Type Mismatches: If a comparator expects a number but encounters a string, the comparator evaluates to false.
  • Negation of Missing Attributes: NOT (attribute = :val) evaluates to true if the attribute does not exist on the item, because the inner expression attribute = :val evaluates to false, and NOT (false) yields true.

Short-Circuit Evaluation

DynamoDB utilizes short-circuit evaluation semantics:

  • In an A AND B expression, if A evaluates to false, DynamoDB does not need to evaluate B to determine that the result is false.
  • In an A OR B expression, if A evaluates to true, DynamoDB does not need to evaluate B to determine that the result is true.

While short-circuiting improves internal evaluation efficiency, all referenced attribute names and value placeholders in the entire expression must still be valid and declared in ExpressionAttributeNames and ExpressionAttributeValues. DynamoDB validates the syntax and placeholder mappings of the entire expression before reading items from disk.
