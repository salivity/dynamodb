DynamoDB Data Compression for Large Text

Amazon DynamoDB does not natively or automatically compress large text attributes on the server side prior to writing them to storage. To reduce item sizes, developers must implement client-side compression before sending payloads to DynamoDB, transforming compressed text into binary attributes. This approach avoids exceeding DynamoDB's strict item size limits, lowers read and write capacity unit consumption, and reduces overall infrastructure costs.

The 400 KB Limit and Server-Side Handling

DynamoDB imposes a strict maximum limit of 400 KB per individual item, which includes both the attribute names and values. When writing a large string attribute (S), DynamoDB stores the raw, uncompressed UTF-8 bytes. Because the database does not evaluate or alter the content of attributes during write operations, attempting to write an uncompressed string that pushes the total item size beyond 400 KB results in an ItemSizeLimitExceededException.

Implementing Client-Side Compression

Because server-side compression is unavailable, compression must take place within the application layer before calling DynamoDB APIs such as PutItem or UpdateItem.

  1. Compression: The application takes the raw string and compresses it using an algorithm suited to the workload, such as Gstandard (zstd), GZIP, Snappy, or Deflate. Gstandard and Snappy are popular choices due to their low CPU overhead and high compression speeds.
  2. Data Type Mapping: Once compressed, the data is converted from a standard text string to raw bytes. In DynamoDB, this data must be stored using the Binary attribute type (B) instead of the String type (S).
  3. Retrieval and Decompression: When the application reads the item using GetItem or Query, it retrieves the binary attribute, runs it through the decompression algorithm, and reconstructs the original string.

Performance and Cost Implications

Compressing text attributes before writing offers distinct advantages, but introduces specific architectural trade-offs:

  • Capacity Unit Savings: DynamoDB measures read and write throughput in terms of capacity units. One Write Capacity Unit (WCU) covers a write up to 1 KB, and one Read Capacity Unit (RCU) covers a strongly consistent read up to 4 KB. Compressing a 30 KB text blob down to 5 KB reduces the write cost from 30 WCUs to 5 WCUs.
  • Loss of Query Capabilities: Storing data as a binary blob removes the ability to use DynamoDB filter expressions, key condition expressions, or functions like contains() or begins_with() on the text content. The text becomes opaque to DynamoDB.
  • Client CPU Overhead: Shifting compression to the client consumes additional CPU and memory resources on the application servers during serialization and deserialization.

Handling Extreme Payloads (The S3 Pattern)

If text attributes remain near or above the 400 KB limit even after client-side compression, the standard architectural pattern is to store the compressed text object in Amazon S3. The application then stores only the resulting S3 object key or URL as a string attribute inside the DynamoDB item, bypassing the 400 KB item constraint entirely.
