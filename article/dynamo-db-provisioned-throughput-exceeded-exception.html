DynamoDB Provisioned Throughput Exceeded Exception

When an application sends request rates that surpass the allocated read or write capacity on an Amazon DynamoDB table or secondary index, DynamoDB throws the ProvisionedThroughputExceededException. This article details why this error occurs, how it manifests across operations, and the best practices for resolving and preventing it in production environments.

The Specific Error Thrown

The exact exception returned by DynamoDB is ProvisionedThroughputExceededException (HTTP status code 400: Bad Request).

This exception indicates that your request rate is too high for the configured capacity. Depending on the operation, it can apply to read requests, write requests, or operations targeting Global Secondary Indexes (GSIs).

Common Causes of the Exception

  1. Exceeding Table-Level Capacity: In provisioned mode, a table is assigned a specific number of Read Capacity Units (RCUs) and Write Capacity Units (WCUs). Consuming more units per second than provisioned triggers this exception.
  2. Hot Partitions: DynamoDB distributes data across multiple partitions based on the partition key. Each partition has a hard limit of 1,000 WCUs and 3,000 RCUs. If requests disproportionately target a single partition key, that partition can be throttled even if the overall table capacity has not been exhausted.
  3. Throttled Global Secondary Indexes: If a write operation updates an attribute projected into a GSI, DynamoDB requires write capacity on both the base table and the index. If the GSI lacks sufficient capacity, the write on the base table will fail with a ProvisionedThroughputExceededException.
  4. Sudden Traffic Spikes: While DynamoDB uses burst capacity to accommodate short-lived spikes, sustained bursts quickly deplete this reserve and result in throttling.

How to Mitigate and Resolve the Error

  • Implement Exponential Backoff and Jitter: Transient throttling can be managed by retrying failed requests with exponential backoff. Most official AWS SDKs implement this retry logic automatically, but custom implementations must ensure retries are paced with randomized jitter to prevent the "thundering herd" problem.
  • Switch to On-Demand Capacity Mode: For workloads with unpredictable traffic patterns, DynamoDB On-Demand automatically scales to accommodate traffic volume instantly without managing capacity units.
  • Enable DynamoDB Auto Scaling: For provisioned tables, auto-scaling dynamically adjusts RCUs and WCUs based on predefined target utilization metrics to match demand.
  • Improve Partition Key Design: Ensure the partition key has high cardinality (many distinct values) to distribute read and write operations uniformly across underlying partitions.
  • Implement Caching: Use Amazon DynamoDB Accelerator (DAX) for read-heavy workloads or an in-memory cache like Redis to serve repeated reads before they hit the database.
