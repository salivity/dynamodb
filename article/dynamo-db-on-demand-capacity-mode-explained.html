DynamoDB On-Demand Capacity Mode Explained

This article explains Amazon DynamoDB's on-demand capacity mode, the specific operational setting that eliminates the need to forecast read and write throughput. It outlines how on-demand capacity manages unpredictable workloads, compares the mechanism directly with traditional provisioned capacity, and details the primary technical scenarios where choosing on-demand mode optimizes cost and development velocity.

The Solution: On-Demand Capacity Mode

Amazon DynamoDB provides two capacity modes: Provisioned and On-Demand. The mode that completely eliminates the need to forecast read and write throughput is On-Demand Capacity Mode.

With on-demand mode, DynamoDB instantly accommodates workloads as they ramp up or down to any previously reached traffic level. If a workload reaches a new peak, DynamoDB automatically scales to meet the volume. You do not need to specify read capacity units (RCUs) or write capacity units (WCUs), nor do you need to configure complex auto-scaling policies.

How On-Demand Capacity Works

Instead of pre-allocating dedicated database resources, on-demand capacity operates on a pure pay-per-request model:

  • Write Request Units (WRUs): Each unit represents one write operation for an item up to 1 KB in size.
  • Read Request Units (RRUs): Each unit represents one strongly consistent read request (or two eventually consistent read requests) for an item up to 4 KB in size.

When an application issues a query, read, or write request, DynamoDB dynamically allocates the compute and storage resources required to complete the operation. If no traffic hits the database, you only pay for data storage, with zero charges for throughput.

On-Demand vs. Provisioned Capacity

To understand the operational advantage, consider the differences between the two modes:

Feature On-Demand Mode Provisioned Mode
Capacity Forecasting Not required Mandatory (RCUs and WCUs)
Pricing Model Pay-per-request Hourly rate per allocated unit
Traffic Handling Instantly scales to sudden spikes Scales according to defined thresholds; may throttle sudden spikes
Idle Costs Zero throughput cost when idle Charged continuously for provisioned units

In provisioned mode, underestimating throughput leads to throttled requests (HTTP 400 ProvisionedThroughputExceededException), while overestimating results in paying for unused capacity. On-demand mode removes this trade-off by scaling dynamically at the cost of a slightly higher per-request price point.

Ideal Use Cases for On-Demand Mode

Choosing on-demand capacity is recommended under the following conditions:

  • New Applications: When you are launching a new product and cannot accurately model user adoption or query volume.
  • Spiky or Unpredictable Traffic: Workloads with sudden, dramatic bursts of activity—such as flash sales, breaking news alerts, or IoT event ingestion—that exceed traditional auto-scaling ramp-up times.
  • Low or Infrequent Utilization: Systems that remain idle for long stretches, such as developer environments or internal business applications used only during business hours.
  • Reduced Operational Overhead: Teams that want to minimize maintenance overhead and eliminate database capacity management tasks.
