DynamoDB Restore to Different Capacity Settings

Restoring an Amazon DynamoDB backup allows you to customize the new table’s configuration, including its billing mode and provisioned read and write capacity units. When you restore a backup with different capacity settings, DynamoDB creates an entirely new table that immediately adopts the newly specified capacity configurations without affecting the integrity or speed of the restored data. This article explains how DynamoDB handles the restore process, the impact on performance and costs, and critical post-restore considerations.

How Capacity Configuration Works During Restore

DynamoDB backups—whether created via on-demand backups or Point-in-Time Recovery (PITR)—always restore to a new table. During this process, you are not forced to maintain the original table's settings. You can switch the billing mode between Provisioned and On-Demand, or you can adjust the specific Read Capacity Units (RCUs) and Write Capacity Units (WCUs).

Impact on the Restore Process

The capacity settings assigned to the target table do not affect the duration of the restore itself. DynamoDB manages the data restoration process internally using dedicated system resources.

  • No Throttling During Restore: If you restore to a provisioned table with very low capacity (such as 1 RCU and 1 WCU), the restore will not throttle or slow down.
  • Internal Throughput: DynamoDB allocates the necessary throughput behind the scenes to write the backed-up data into the new partitions as quickly as possible.

Switching Between Billing Modes

You can adjust the table's billing mode depending on your intended workload for the new table:

  • Provisioned to On-Demand: If the source table used provisioned capacity, you can restore it as an On-Demand table. The restored table will instantly handle unpredictable workloads without requiring capacity planning, charging purely on a per-request basis.
  • On-Demand to Provisioned: If the source table was On-Demand, you can restore it with provisioned RCUs and WCUs. This is common when restoring production data into a testing or staging environment where strict cost caps are required.

Global Secondary Index (GSI) Behavior

If the backup contains Global Secondary Indexes (GSIs), the capacity rules apply to them as well:

  • When restoring to an On-Demand table, all restored GSIs automatically switch to On-Demand mode.
  • When restoring to a Provisioned table, you must define the RCU and WCU allocations for each restored GSI. If you under-provision a GSI, post-restore write operations to the base table could experience throttling if index updates exceed the GSI's provisioned write limits.

Post-Restore Operational Impact

Once the restore process completes and the table status changes to ACTIVE, the new capacity settings take effect immediately:

  • Application Throttling: If you restored with lower provisioned capacity than the original table, any application traffic directed to the new table must adhere to these lower limits. Exceeding them will result in ProvisionedThroughputExceededException errors.
  • Auto Scaling Configuration: AWS Application Auto Scaling settings are not copied from the backup. If the original table relied on auto-scaling to adjust provisioned capacity dynamically, you must manually re-create the scaling policies on the newly restored table.
  • Cost Changes: Billing for the restored table immediately reflects the new settings. Provisioned tables begin incurring hourly charges based on the configured RCUs/WCUs, while On-Demand tables incur charges based on incoming read/write request volumes.
