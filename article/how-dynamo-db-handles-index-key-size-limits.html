How DynamoDB Handles Index Key Size Limits

This article provides an overview of how Amazon DynamoDB enforces key size constraints during item creation operations. When writing an item, DynamoDB evaluates the sizes of both primary keys and secondary index keys against strict byte-length thresholds. Exceeding these limits causes the operation to fail immediately with a validation error, preventing the item from being committed to the base table or its associated indexes.

DynamoDB Key Size Constraints

DynamoDB imposes fixed byte limits on attributes used as partition keys and sort keys:

  • Partition Key: The maximum length of a partition key value is 2,048 bytes for String and Binary data types.
  • Sort Key: The maximum length of a sort key value is 1,024 bytes for String and Binary data types.
  • Number Types: Numeric keys are bounded by precision rather than raw byte length (up to 38 digits of precision), keeping them well within size limits.

These constraints apply uniformly to the base table's primary key, Local Secondary Indexes (LSIs), and Global Secondary Indexes (GSIs).

Behavior During Item Creation

When an application invokes an item creation operation (PutItem or BatchWriteItem), DynamoDB validates the item synchronously before writing:

  1. Base Table Primary Key Validation: If the base table partition key exceeds 2,048 bytes or the sort key exceeds 1,024 bytes, DynamoDB aborts the request. The write is rejected with an HTTP 400 ValidationException, and no data is written to the database.
  2. Local Secondary Index (LSI) Validation: Because an LSI shares the base table's partition key and must be updated synchronously, any item containing an LSI sort key that exceeds 1,024 bytes causes the entire PutItem call to fail with a ValidationException.
  3. Global Secondary Index (GSI) Validation: If an item contains attributes mapped as the partition or sort key of a GSI, those values are also validated synchronously at write time. If the attribute intended for the GSI partition key exceeds 2,048 bytes, or the sort key attribute exceeds 1,024 bytes, DynamoDB rejects the base table write with a ValidationException.

The Sparse Index Nuance

DynamoDB secondary indexes are sparse by default. If an item being created completely lacks the attributes designated as GSI keys, DynamoDB successfully creates the item in the base table and simply omits it from the GSI. However, this omission only applies to absent attributes; supplying an attribute that exists but exceeds the byte threshold is treated as an invalid value, resulting in immediate rejection.

Local Secondary Index Size Collections

In addition to individual key size limits, LSIs enforce a 10 GB cumulative limit per partition key across the base table and all LSIs combined. If creating a new item would cause that specific partition's total footprint to surpass 10 GB, DynamoDB rejects the creation request with an ItemCollectionSizeLimitExceededException. GSIs do not have this partition collection limit.

Preventing Key Size Failures

To avoid write failures caused by key size limits, applications should:

  • Hash Large Values: If an index key is derived from a long, arbitrary string (such as a full URL or compound path), store a fixed-length cryptographic hash (like SHA-256) as the index key attribute instead.
  • Enforce Client-Side Validation: Validate the UTF-8 byte length—not just string character length—before sending write requests to DynamoDB, accounting for multi-byte characters.
  • Normalize Compound Keys: When concatenating multiple values to form a compound sort key, use concise identifiers and delimiters to keep the total payload well below the 1,024-byte boundary.
