How DynamoDB Handles GSI Synchronization Delays

Amazon DynamoDB decouples base table updates from Global Secondary Index (GSI) updates through an asynchronous replication architecture. Because mutations to the base table are committed before they reach secondary indexes, GSIs are strictly eventually consistent, meaning slight delays can occur between writing data and querying it via an index. This article details the underlying mechanisms DynamoDB uses to manage index synchronization delays, including asynchronous change propagation, backpressure mechanisms, throttling behavior, and operational monitoring.

Asynchronous Replication Architecture

When an application performs a write, update, or delete operation on a DynamoDB base table, DynamoDB persists the change to the base table's storage nodes and immediately returns a successful response to the client. Simultaneously, an internal storage engine stream captures the item mutation and queues it for propagation to any associated GSIs.

Because GSI storage partitions are physically distinct from the base table partitions, these updates must travel across the internal storage network. DynamoDB applies the changes to the GSI partitions in the exact order they occurred on the base table. Under normal operating conditions, this propagation typically completes within a fraction of a second.

Eventual Consistency by Design

To prevent index updates from increasing the latency of base table write operations, DynamoDB enforces an eventually consistent read model for all GSIs. Unlike Local Secondary Indexes (LSIs), GSIs do not support strongly consistent reads (ConsistentRead=true). Applications querying a GSI must tolerate brief windows where read operations reflect stale or missing data while the asynchronous replication stream catches up.

Handling Backpressure and GSI Throttling

A primary cause of synchronization delay is insufficient write capacity on the GSI. DynamoDB requires that the GSI consume Write Capacity Units (WCUs) whenever a base table write projects an item into that index.

If a GSI lacks the provisioned capacity to process incoming updates, DynamoDB applies backpressure:

  1. Replication Buffer Accumulation: Unapplied index updates accumulate in an internal replication buffer assigned to the base table partition.
  2. Base Table Throttling: If the GSI remains unable to catch up and the buffer approaches its limits, DynamoDB throttles writes to the base table itself, returning a ProvisionedThroughputExceededException.

This throttling prevents the replication lag from growing indefinitely and guarantees that the GSI does not fall irrevocably behind the base table.

Monitoring Synchronization Delays

DynamoDB exposes Amazon CloudWatch metrics that allow operators to detect and diagnose GSI synchronization delays:

  • ReplicationLatency: Measures the elapsed time in milliseconds between when an item is written to the base table and when it appears in the GSI. Spikes in this metric indicate that the index is falling behind.
  • OnlineIndexPercentage: Indicates the progress of an index build when a new GSI is being created on an existing table.
  • WriteThrottleEvents: Monitored at both the base table and index levels to identify whether capacity exhaustion on the GSI is causing base table write rejections.

Strategies to Prevent Synchronization Delays

To minimize replication latency and prevent backpressure issues, implementations should follow these design standards:

  • Match or Exceed Base Table Capacity: In provisioned capacity mode, ensure the GSI write capacity is equal to or greater than the base table's write capacity, accounting for sparse index projection rates.
  • Use On-Demand Capacity Mode: For unpredictable traffic patterns, on-demand capacity automatically scales GSI throughput to match the base table, minimizing throttling-induced lag.
  • Avoid Hot Partition Keys in GSIs: Uneven distribution of index partition keys can bottleneck specific GSI storage partitions, leading to localized throttling and replication delays even if total GSI capacity appears sufficient.
  • Project Only Necessary Attributes: Reducing the payload size of GSI projections (KEYS_ONLY or INCLUDE instead of ALL) decreases the total WCUs consumed per write, allowing the index to process updates more rapidly.
