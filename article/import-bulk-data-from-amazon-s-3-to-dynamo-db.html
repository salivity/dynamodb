Import Bulk Data from Amazon S3 to DynamoDB

Amazon DynamoDB offers a fully managed, native feature that allows you to import bulk data directly from an Amazon S3 bucket into a new DynamoDB table. This article explains the underlying mechanics of this import process, including how DynamoDB parses source files, utilizes an isolated distributed processing fleet to bypass write capacity limits, validates records, builds indexes, and finalizes the new table for production use.

Initiating the Import

The process begins when an import request is triggered via the AWS Management Console, AWS CLI, or DynamoDB API (ImportTable action). The request specifies the source S3 bucket, file format (CSV, DynamoDB JSON, or Amazon Ion), compression type (GZIP, ZSTD, or uncompressed), and the target table schema, including primary keys and secondary indexes.

The native import feature works exclusively with new tables. It cannot be used to load data into an existing DynamoDB table.

Managed Serverless Processing Fleet

Once the import job is triggered, DynamoDB offloads the execution to an internal, fully managed distributed compute fleet. Because this fleet operates independently of DynamoDB's normal request-routing architecture:

  • Zero Capacity Consumption: The data load does not consume any Write Capacity Units (WCU) or on-demand request units.
  • No Impact on Existing Workloads: The process is isolated, meaning heavy ingestion will not throttle or compete with other tables in your account.
  • Cost Efficiency: You are billed based on the uncompressed size of the source data in S3 rather than standard DynamoDB write operations.

Data Parsing and Validation

The internal engine reads the source files directly from S3, decompressing them on the fly if necessary. During this phase, the engine validates each record:

  • Schema Validation: Records are verified to ensure they contain the declared partition key and sort key (if applicable) and that data types match the specified schema.
  • Format Checks: The data must adhere strictly to the chosen format (e.g., properly formatted CSV headers or valid DynamoDB JSON syntax).
  • Error Logging: Any malformed records or items exceeding the 400 KB item size limit are discarded and logged to a separate error file stored back in your Amazon S3 bucket, allowing you to audit failed records without stopping the entire import.

Partition Slicing and Data Allocation

DynamoDB uses the input dataset's total volume to calculate the optimal number of storage partitions before loading begins:

  1. Pre-partitioning: Rather than dynamically splitting partitions under write pressure, DynamoDB pre-allocates partitions based on the dataset size and key distribution.
  2. Direct Bulk Writing: The compute fleet bypasses the standard API layer and streams processed records directly into the appropriate physical storage nodes.
  3. Index Generation: If the table configuration includes Global Secondary Indexes (GSIs) or Local Secondary Indexes (LSIs), DynamoDB populates these indexes concurrently alongside the base table data.

Completion and Table Activation

Throughout the import process, the target DynamoDB table remains in an IMPORTING state, rendering it unavailable for read and write operations.

Once the data transfer, validation, and index builds are complete, DynamoDB updates the table status to ACTIVE. At this point, standard table settings—such as billing mode (On-Demand or Provisioned), Auto Scaling policies, Time to Live (TTL), and DynamoDB Streams—are initialized, and the table becomes fully accessible for standard application traffic.
