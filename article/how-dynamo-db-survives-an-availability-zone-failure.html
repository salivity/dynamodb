How DynamoDB Survives an Availability Zone Failure

Amazon DynamoDB maintains high availability during an Availability Zone (AZ) failure by decoupling its architecture into distributed microservices, automatically replicating data across three distinct physical locations, and utilizing a Paxos-based consensus algorithm to ensure continuous operations. When an AZ becomes unavailable, DynamoDB automatically reroutes traffic, elects new partition leaders if necessary, and continues processing both read and write operations without data loss or administrative intervention.

Multi-AZ Data Replication

Every DynamoDB table is split into logical partitions, and each partition is replicated across storage nodes located in at least three separate Availability Zones within an AWS Region. This synchronous replication model ensures that no single data partition depends on the physical infrastructure, power, or networking of a single data center.

Quorum-Based Consensus (Paxos)

DynamoDB uses the Paxos consensus protocol to manage write operations across these replicas. A write operation does not require acknowledgment from all three replicas to be considered durable and successful; it only requires a quorum, which is a majority of two out of the three replicas. If an AZ experiences a complete outage, the remaining two replicas in the surviving AZs still satisfy the quorum requirement. Write operations continue to succeed without dropping requests or violating durability guarantees.

Automatic Leader Failover

Within each partition's replica set, one node is designated as the leader responsible for coordinating writes and strongly consistent reads, while the other two act as followers. If the failure of an AZ takes down a follower, operations continue uninterrupted because the leader and the other follower still represent a functional majority. If the failed AZ hosted the partition's leader, the surviving follower nodes detect the absence of heartbeats and automatically elect a new leader from among themselves via Paxos. This leader election process completes within seconds, minimizing latency spikes and eliminating downtime.

Request Routing and Isolation

DynamoDB's architecture separates storage from its stateless request routing tier. When an application sends a query, a Request Router directs the request to the appropriate healthy storage node. These routers continuously monitor the health of storage nodes across all zones. If an AZ fails, the routing layer automatically identifies the impaired nodes and directs subsequent traffic exclusively to the surviving replicas in healthy AZs.

Self-Healing and Redundancy Restoration

While the remaining two replicas handle active traffic during an AZ outage, DynamoDB's background storage management processes initiate automated recovery tasks. The system provisions new replacement replicas in healthy zones and synchronizes data from the active nodes. This background repair restores three-way redundancy, ensuring that the system is resilient against subsequent hardware failures even before the affected AZ is restored.
