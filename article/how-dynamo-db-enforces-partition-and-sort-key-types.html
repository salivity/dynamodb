How DynamoDB Enforces Partition and Sort Key Types

Amazon DynamoDB operates as a NoSQL database that offers flexible, schema-less item attributes while strictly enforcing schema constraints on primary keys. While non-key attributes can vary dynamically across items, the primary key—consisting of a partition key and an optional sort key—must strictly adhere to predefined rules established at table creation. This article examines the mechanisms DynamoDB uses to enforce key types, how it validates input during write operations, the constraints imposed on key values, and the errors generated when violations occur.

Schema Declaration at Table Creation

DynamoDB establishes schema constraints at the time of table creation via the KeySchema and AttributeDefinitions parameters. The KeySchema defines the role of each key attribute (either HASH for the partition key or RANGE for the sort key), while AttributeDefinitions specifies the data type for each key.

DynamoDB restricts primary key attributes strictly to three scalar data types:

  • String (S): Represents UTF-8 encoded text.
  • Number (N): Represents positive or negative numbers with up to 38 digits of precision.
  • Binary (B): Represents arbitrary binary data, such as images, compressed formats, or encrypted payloads, encoded in base64.

Complex types like Lists (L), Maps (M), Sets (SS, NS, BS), or Booleans (BOOL) cannot be used as primary keys. Once the table is created, these key attribute definitions become immutable; you cannot modify the key structure or change key data types without creating a new table and migrating the data.

Request-Time Type Validation

DynamoDB enforces key constraints at the API level during every write operation, including PutItem, UpdateItem, DeleteItem, and their batch and transactional variants. Every write request must include the declared partition key (and sort key, if applicable) formatted with the matching data type indicator.

When an operation is processed, DynamoDB performs a strict type check against the declared AttributeDefinitions:

  • Exact Type Match: If a partition key is defined as a String ("S"), providing a Number ("N") or any other type causes the request to be rejected immediately.
  • Format Correctness: For Number types, DynamoDB validates that the value is a valid numeric string representation before accepting the write. For Binary types, it checks for valid base64-encoded bytes.
  • Presence Requirement: Unlike regular attributes, primary key attributes cannot be omitted. A write operation lacking the primary key is blocked before any data is committed to storage.

Value Constraints and Size Limits

In addition to data type validation, DynamoDB enforces structural size constraints on partition and sort key values:

  • Partition Key Size: The maximum length of a partition key value is 2048 bytes.
  • Sort Key Size: The maximum length of a sort key value is 1024 bytes.
  • Empty Values: While DynamoDB permits empty string and empty binary values for non-key attributes, primary key values must not be empty. A partition key or sort key cannot contain an empty string ("") or an empty binary payload.

Error Handling for Schema Violations

When a request violates key schema constraints, DynamoDB rejects the operation synchronously and returns an HTTP 400 client error. Typical responses include:

  • ValidationException: Triggered when a key type does not match the table definition (e.g., The provided key element does not match the schema), when a required key is missing, or when key size limits are exceeded.
  • SerializationException: Triggered when the payload cannot be parsed according to the expected data format (such as an invalid binary string).

Because validation happens prior to storage execution, non-compliant requests consume no write capacity units (WCUs), protecting table throughput and maintaining data integrity.
