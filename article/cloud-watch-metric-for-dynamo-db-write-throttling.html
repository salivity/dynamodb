CloudWatch Metric for DynamoDB Write Throttling

When an Amazon DynamoDB table exceeds its allocated write capacity, Amazon CloudWatch records these rejected operations so administrators can diagnose performance bottlenecks. The primary CloudWatch metric that indicates a DynamoDB table is throttling write requests is WriteThrottleEvents. This article explains how WriteThrottleEvents works, details the related metrics you should monitor, and outlines how to configure a CloudWatch alarm to detect and mitigate DynamoDB write throttling.

The Primary Metric: WriteThrottleEvents

The definitive metric for monitoring throttled write requests in DynamoDB is WriteThrottleEvents.

Published under the AWS/DynamoDB namespace, WriteThrottleEvents measures the number of write requests that were throttled by DynamoDB because the table or Global Secondary Index (GSI) exceeded its provisioned write throughput capacity units (WCU).

Key details of this metric include:

  • Metric Name: WriteThrottleEvents
  • Namespace: AWS/DynamoDB
  • Dimensions: TableName, and optionally GlobalSecondaryIndexName
  • Standard Statistic: Sum
  • Unit: Count

Each time a PutItem, UpdateItem, DeleteItem, or BatchWriteItem request exceeds the available write throughput, DynamoDB denies the request, returns a ProvisionedThroughputExceededException, and increments the WriteThrottleEvents counter.

Related Throttling Metrics

While WriteThrottleEvents is the direct indicator for write operations, other metrics provide additional context:

  • ThrottledRequests: Measures all throttled requests (both reads and writes) across the table. It triggers when any request returns a 400-series ProvisionedThroughputExceededException. While useful for general alerting, it does not distinguish between reads and writes.
  • ConsumedWriteCapacityUnits vs. ProvisionedWriteCapacityUnits: Comparing consumed writes against provisioned capacity shows how close traffic is to the operational ceiling before throttling occurs.

How to Configure a CloudWatch Alarm for Write Throttling

To catch write throttling as soon as it happens, configure a CloudWatch alarm with the following settings:

  1. Metric Selection: Select AWS/DynamoDB > TableMetrics > WriteThrottleEvents for your specific table.
  2. Statistic: Choose Sum.
  3. Period: Set to 1 minute (or 5 minutes depending on your reporting tolerance).
  4. Threshold Type: Static.
  5. Condition: Greater than (>) 0.
  6. Alarm Action: Configure an Amazon SNS topic to notify engineering teams via email, Slack, or PagerDuty.

Setting the threshold to > 0 ensures immediate notification whenever a write request is rejected.

Common Causes of DynamoDB Write Throttles

If WriteThrottleEvents triggers an alarm, investigate the following typical causes:

  • Hot Partition Keys: DynamoDB allocates throughput evenly across underlying storage partitions. If a high volume of writes targets a single partition key value, that partition can throttle even if total consumed capacity is well below the table's total provisioned limit.
  • Throttled Global Secondary Indexes: If a table has a GSI with provisioned write capacity lower than the main table, writes to the main table will be throttled to prevent the GSI from falling behind.
  • Sudden Traffic Spikes: Bursts of write traffic that exceed the table's capacity and exhaust its burst capacity (up to 300 seconds of unused capacity) will trigger throttles.

Remediation Strategies

To eliminate write throttling indicated by WriteThrottleEvents:

  • Enable Auto Scaling: Set up DynamoDB Auto Scaling to dynamically adjust provisioned write capacity units based on utilization.
  • Switch to On-Demand Capacity Mode: If write workloads are unpredictable or have sudden, sharp spikes, consider switching the table billing mode from Provisioned to On-Demand.
  • Optimize Key Design: Ensure partition keys have high cardinality to distribute write operations evenly across partitions.
  • Align GSI Capacity: Ensure that all GSIs have write capacity equal to or greater than the base table's write capacity.
