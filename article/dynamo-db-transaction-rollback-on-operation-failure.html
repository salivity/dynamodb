DynamoDB Transaction Rollback on Operation Failure

Amazon DynamoDB supports full ACID (Atomicity, Consistency, Isolation, Durability) guarantees using its transactional APIs, primarily TransactWriteItems. When a single operation within a transactional write batch fails, DynamoDB immediately aborts the entire transaction, rejects all accompanying operations, and rolls back any staged changes so that no partial data is persisted. This article explains the internal two-phase coordination DynamoDB uses, why rollbacks occur, and how to identify and handle failed operations in your application.

The Two-Phase Transaction Process

DynamoDB uses an internal two-phase consensus protocol to execute transactions across multiple partitions and tables:

  1. Validation and Preparation Phase: DynamoDB validates all operations in the TransactWriteItems request. It verifies that the request does not exceed transactional limits (up to 100 actions or 4 MB of data), evaluates all conditional expressions, and confirms that sufficient write capacity is available across all targeted items. Items are reserved to prevent conflicting operations.
  2. Commit Phase: If every pre-condition and capacity check succeeds across all operations in the batch, DynamoDB commits the writes permanently to storage across the respective partitions.

If any single operation encounters an error during the preparation phase, DynamoDB terminates the execution pipeline immediately. Because no data is written to permanent storage until all operations pass validation, the "rollback" in DynamoDB is an automatic abort: the reserved items are released, and the tables remain in their pre-transaction states.

The TransactionCanceledException

When an operation in a batch fails, DynamoDB responds with a TransactionCanceledException. Along with this HTTP 400 error, the response payload includes a CancellationReasons array.

The CancellationReasons array maintains a strict one-to-one positional mapping with the operations submitted in the TransactWriteItems request:

  • If an action succeeded its validation check, its corresponding entry in CancellationReasons contains the code None.
  • If an action caused the rollback, its entry contains a specific failure code detailing the exact reason.

This structure allows client applications to pinpoint precisely which item and operation caused the entire batch to fail.

Common Causes of Transaction Rollback

DynamoDB triggers a transaction rollback under several specific conditions:

  • ConditionalCheckFailed: A condition expression attached to a Put, Update, or Delete operation evaluated to false. If even one item fails its condition, the entire batch is rejected.
  • TransactionConflict: Another concurrent transaction or write request attempted to modify one or more of the same items simultaneously. DynamoDB rejects the transaction to preserve isolation.
  • ProvisionedThroughputExceeded: One or more target partitions lack the provisioned or on-demand capacity required to complete the operation.
  • ValidationError / ItemCollectionSizeLimitExceeded: An operation exceeds schema constraints, data size limits, or Local Secondary Index (LSI) item collection boundaries.

Handling Transaction Rollbacks in Code

Because DynamoDB rolls back the entire batch atomically, handling failed transactions requires determining whether the failure is transient or logic-based:

  1. Inspect CancellationReasons: Parse the error response to inspect each element of the CancellationReasons list.
  2. Retry on Conflicts: If the rollback occurred due to a TransactionConflict or throughput throttling, apply exponential backoff and jitter before retrying the transaction.
  3. Correct Application State on Logic Failures: If the cancellation was caused by a ConditionalCheckFailed, retrying immediately will produce the same outcome. Fetch the latest state of the data, re-evaluate the business logic, and construct a new transaction request accordingly.
