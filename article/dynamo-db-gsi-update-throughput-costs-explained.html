DynamoDB GSI Update Throughput Costs Explained

Amazon DynamoDB calculates throughput costs for Global Secondary Index (GSI) updates separately from base table updates. When an item in a base table is created, modified, or deleted, DynamoDB automatically propagates these changes to any relevant GSIs asynchronously. The write throughput consumed on a GSI depends on whether the item's key or projected attributes were altered, the size of the projected item in the index, and whether the modification results in an insertion, deletion, or replacement.

The Mechanics of GSI Write Units

DynamoDB measures write capacity in Write Capacity Units (WCUs) for provisioned mode and Write Request Units (WRUs) for on-demand mode. For standard writes, one unit represents up to 1 KB of data written per second.

When calculating the size of a GSI write, DynamoDB includes:

  • The GSI partition key and sort key (if present).
  • The base table’s partition key and sort key (if present), which are automatically projected.
  • All other projected attributes (KEYS_ONLY, INCLUDE, or ALL).

The total byte size of these attributes is rounded up to the nearest 1 KB multiplier to determine the base unit cost.

Update Scenarios and Throughput Consumption

The exact throughput cost of an UpdateItem or PutItem operation depends on which attributes are modified:

  1. Non-Projected Attribute Updates: If an update modifies only attributes that are not projected into the GSI, DynamoDB does not write to the GSI. The throughput cost for the GSI is zero.
  2. Projected Attribute Updates: If an update modifies an attribute that is projected into the GSI without changing the GSI key schema, DynamoDB overwrites the GSI entry. This consumes write capacity corresponding to the size of the newly updated GSI entry rounded up to the nearest 1 KB.
  3. GSI Key Modifications: If an update changes a GSI partition key or sort key attribute, DynamoDB must remove the old index entry and insert a new index entry. This results in two separate writes to the GSI:
    • One delete operation to remove the old item (sized according to the old projected item size).
    • One put operation to add the new item (sized according to the new projected item size). Both operations consume separate WCUs or WRUs on the GSI.
  4. Item Deletions: Deleting an item from the base table deletes the corresponding item from the GSI, consuming write capacity equivalent to the size of the projected GSI item rounded up to 1 KB.

Backpressure and Throttling

GSIs allocate their own independent write capacity. If a base table write triggers a GSI update, but the target GSI lacks sufficient provisioned capacity (or exceeds burst limits in on-demand mode), DynamoDB throttles the write on the base table. This backpressure mechanism ensures that the index never falls permanently out of sync with the base table data.
