DynamoDB Scan Capacity on a Sparse Index

This article explains how Amazon DynamoDB calculates read capacity unit (RCU) consumption when performing a Scan operation on a sparse secondary index. You will learn the mechanics behind sparse index evaluation, the formula used to compute consumed RCUs, the impact of consistency models, and why scanning a sparse index is significantly more cost-effective than scanning a full base table.

The Mechanics of a Sparse Index Scan

In DynamoDB, a secondary index (Global Secondary Index or Local Secondary Index) is considered "sparse" when its partition key or sort key attributes are not present in every item of the base table. DynamoDB only writes an item to the index if that item contains all of the attributes defined in the index's primary key schema.

When you run a Scan operation directly against a secondary index, DynamoDB reads exclusively from the index storage. Base table items that lack the index keys are never evaluated, stored, or processed during the operation. Consequently, capacity calculations only account for the items that physically exist inside the sparse index.

Step-by-Step RCU Calculation

To calculate the Read Capacity Units consumed by a sparse index Scan, DynamoDB follows these distinct steps:

  1. Calculate the Size of Evaluated Items: DynamoDB calculates the size of each item read from the index. The size of an indexed item is not the size of the original base table item; instead, it consists of:

    • The base table’s primary key attributes.
    • The index's primary key attributes.
    • Any additional attributes projected into the index (KEYS_ONLY, INCLUDE, or ALL).

  2. Sum the Total Data Evaluated: DynamoDB aggregates the sizes of all items evaluated across the scan. If your request processes multiple items in a single read call, the total payload size is determined by summing the sizes of all items evaluated, not by rounding each item individually.

  3. Round Up to the Nearest 4 KB Boundary: DynamoDB rounds the cumulative size of evaluated data up to the nearest next 4 KB increment. For example, evaluating 6 KB of indexed data rounds up to 8 KB.

  4. Apply Consistency Rules:

    • Global Secondary Indexes (GSIs): GSIs only support eventually consistent reads. One RCU provides two eventually consistent reads per second for items up to 4 KB in size (equivalent to 1 RCU per 8 KB of data evaluated).
    • Local Secondary Indexes (LSIs): LSIs support both strongly consistent reads (1 RCU per 4 KB) and eventually consistent reads (0.5 RCU per 4 KB).

Formula for an Eventually Consistent Scan (Standard GSI): \[\text{Consumed RCUs} = \frac{\lceil \text{Total Evaluated Item Size (in KB)} / 4 \rceil}{2}\]

The Effect of Filter Expressions

A common point of confusion is how a FilterExpression impacts RCU consumption. A FilterExpression is applied only after DynamoDB reads the items from the index.

Even if an item in the sparse index is discarded by your filter and not returned to the client application, it was still read from disk. Therefore, all items evaluated by the Scan contribute to the total data size and consume capacity units, regardless of whether they meet the filter criteria.

Throughput Billing Allocation

Capacity consumed by scanning a sparse index is billed against the index itself, not the base table:

  • For a GSI, the consumed RCUs deduct directly from the provisioned or on-demand read capacity assigned to that specific GSI.
  • For an LSI, read capacity is deducted from the base table’s read throughput capacity, as LSIs share throughput with the base table.

Because sparse indexes contain a reduced subset of records and smaller projected attribute footprints, scanning a sparse index minimizes the total evaluated bytes, leading to lower capacity unit consumption compared to scanning the base table.
