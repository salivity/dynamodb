How DynamoDB Global Tables Maintain Consistency

Amazon DynamoDB Global Tables deliver fully managed, multi-Region, and multi-active database replication for globally distributed applications. This article examines the architectural mechanisms DynamoDB uses to maintain data consistency across disparate geographical locations, focusing on asynchronous replication via internal streams, the "Last Writer Wins" conflict resolution model, propagation latency, and regional read consistency guarantees.

Asynchronous Multi-Region Replication

DynamoDB Global Tables are comprised of multiple identical regional tables, known as replica tables. When an application writes an item to a table in one Region, DynamoDB automatically captures the update using native change data capture technology similar to DynamoDB Streams.

The update is then replicated asynchronously to all other participating Regions over the high-speed, private AWS global network backbone. Because replication is asynchronous, the initial write operation completes immediately in the local Region with single-digit millisecond latency, without waiting for acknowledgment from remote Regions.

Conflict Resolution via Last Writer Wins (LWW)

In a multi-active configuration where writes to the same item can happen concurrently in different Regions, write conflicts are inevitable. DynamoDB resolves these conflicts using a deterministic "Last Writer Wins" (LWW) strategy.

Every update managed by Global Tables is tagged with a precise, internal timestamp metadata attribute (aws:rep:updatetime). If two updates target the same primary key across different Regions, DynamoDB compares their timestamps. The write with the latest timestamp is applied, and older writes are discarded. This ensures that all regional replicas eventually converge to the exact same state, eliminating data divergence without requiring complex distributed locking mechanisms or two-phase commit protocols.

Cross-Region Eventual Consistency

Because cross-region replication is decoupled from the local transaction path, data across disparate locations is eventually consistent. Under normal operating conditions, data written to one Region propagates to all other replica tables typically within one to two seconds.

Applications reading from a remote Region shortly after a write occurs in another Region may observe stale data until replication completes. However, in the absence of new updates, all replicas are guaranteed to reflect identical data once in-flight updates finish processing.

Read Consistency within Global Tables

DynamoDB supports two read consistency options within an individual Region:

  • Eventually Consistent Reads: The default read mode, which maximizes read throughput and minimizes latency, though it may return recently updated data out of order.
  • Strongly Consistent Reads: Guarantees a response that reflects all successful local writes up to the moment the read was executed.

Strongly consistent reads are scoped strictly to the local Region. DynamoDB does not support cross-Region strongly consistent reads; any read executed against a replica table reflects the local state of that replica, which is subject to the asynchronous replication delay from other Regions.

Network Partitions and Resiliency

If a network disruption occurs between Regions, each local replica continues to accept reads and writes independently, prioritizing availability over immediate global consistency. DynamoDB tracks unprocessed mutations and replays them automatically once cross-Region connectivity is restored, resolving conflicts through the LWW mechanism and restoring consistency across the global topology without administrative intervention.
