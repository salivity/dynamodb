How DynamoDB Validates GSI Key Schemas

Amazon DynamoDB is predominantly a schemaless NoSQL database, but it enforces strict schema validation on the primary keys of base tables and Global Secondary Indexes (GSIs). This article explains how DynamoDB executes schema validation for GSI keys during index creation, runtime item ingestion, and background backfilling, detailing the mechanics of scalar type enforcement, sparse indexing behavior, and size constraints.

Schema Definition Validation

Validation begins when a GSI is defined using the AWS Management Console, CLI, or API (such as CreateTable or UpdateTable). DynamoDB validates the structural parameters of the GSI key schema before provisioning resources.

A GSI key schema must specify a partition key and can optionally include a sort key. DynamoDB restricts GSI key data types strictly to scalar types: String (S), Number (N), or Binary (B). If you attempt to define a key schema using complex or document types—such as Lists (L), Maps (M), or Sets (SS, NS, BS)—the request is immediately rejected with a ValidationException.

Write-Time Type Enforcement

When a client executes a write operation (PutItem, UpdateItem, or BatchWriteItem) on the base table, DynamoDB validates the incoming payload against all defined GSI key schemas.

If the item includes an attribute whose name corresponds to a GSI partition key or sort key, DynamoDB checks the data type of the supplied value against the type defined in the GSI schema. If there is a mismatch—for instance, providing a String value for a GSI key defined as a Number—DynamoDB rejects the entire write operation with a ValidationException. The write fails for the base table as well; partial writes across the base table and its secondary indexes are not permitted.

Sparse Indexing and Attribute Omission

DynamoDB does not treat missing key attributes as schema validation failures. Instead, it utilizes sparse indexing.

If an item is written to the base table without the attribute matching the GSI partition key (or sort key), DynamoDB considers this valid. It simply omits the item from the GSI while committing it to the base table. An item is only validated against the GSI schema and projected into the index if the attribute defining the GSI partition key is explicitly present in the item.

Value Size and Constraint Checks

During runtime validation, DynamoDB checks the physical size limits of the GSI key attributes:

  • Partition Key: The maximum length of a GSI partition key value is 2048 bytes.
  • Sort Key: The maximum length of a GSI sort key value is 1024 bytes.
  • Empty Values: Empty String and Binary key attributes are permitted, provided they conform to DynamoDB's general attribute constraints, but they must still strictly adhere to the designated data type.

If a write operation provides a key attribute value that exceeds these byte thresholds, DynamoDB halts execution and returns a client error indicating that the key size limit has been exceeded.

Asynchronous Backfill Validation

When creating a new GSI on an existing table with pre-existing data, DynamoDB validates items asynchronously through a background backfill process.

DynamoDB scans all existing table items to project eligible entries into the new index. If the background process encounters an item with an attribute name matching the new GSI key but holding an incompatible data type, the backfill process cannot map the item. In modern DynamoDB implementations, type mismatches detected during backfill cause the index creation state to transition to CREATING and ultimately fail, setting the index to an unusable state or deleting it.
