How DynamoDB Handles BETWEEN and IN in Queries

This article provides an overview of how Amazon DynamoDB processes complex comparison operators, specifically BETWEEN and IN, during query operations. It explains the architectural mechanics behind key condition expressions versus filter expressions, detailing where these operators are permitted, how DynamoDB evaluates them under the hood, and how their usage directly impacts query performance, pagination, and Read Capacity Unit (RCU) consumption.

The Two-Stage Query Architecture

To understand how DynamoDB handles comparison operators, you must distinguish between the two distinct processing phases of a Query operation:

  1. Key Condition Evaluation (Storage Layer): DynamoDB locates the target partition using the partition key and then navigates the physical storage index using the sort key. This step determines which physical items are read from disk into memory and directly dictates RCU consumption.
  2. Filter Expression Evaluation (Compute Layer): Once items are read into memory, DynamoDB applies any specified FilterExpression rules to eliminate unwanted items before returning the payload to the client. This step does not reduce read costs.

Because of this two-stage model, operators behave very differently depending on whether they are placed in the KeyConditionExpression or the FilterExpression.

How DynamoDB Processes the BETWEEN Operator

The BETWEEN operator evaluates whether an attribute value falls inclusively within a specified lower and upper bound (attribute BETWEEN :val1 AND :val2).

In Key Condition Expressions

DynamoDB natively supports BETWEEN on the sort key in a KeyConditionExpression. When executed:

  • Index Traversal: Because sort keys are stored in sorted order within a partition (typically using a B-tree-like structure), DynamoDB quickly locates the lower bound and reads contiguously until it hits the upper bound.
  • Cost Efficiency: Only items falling within the BETWEEN range are read from storage. RCUs are calculated strictly based on the combined size of the items within that range.
  • Data Types: BETWEEN works on numbers, strings, and binary attributes, sorting based on UTF-8 binary encoding for strings or numerical value for numbers.

In Filter Expressions

When BETWEEN is used in a FilterExpression, it can target any attribute, whether it is part of the primary key or a non-key attribute:

  • Post-Read Execution: DynamoDB reads all items matching the KeyConditionExpression into memory first.
  • Filtering: DynamoDB evaluates the condition in memory and discards items outside the range.
  • Cost Impact: You are billed for reading all matching items from the key condition phase, regardless of how many items the BETWEEN filter discards.

How DynamoDB Processes the IN Operator

The IN operator checks whether an attribute matches any value in a designated list (attribute IN (:val1, :val2, ...)).

In Key Condition Expressions (Not Supported)

DynamoDB does not support the IN operator in a KeyConditionExpression.

A query must evaluate a single contiguous range within a single partition. An IN list represents discrete, non-contiguous lookup points, which the underlying storage engine cannot process in a single contiguous index scan. To achieve the effect of an IN operator on key attributes:

  • Parallel Queries: Execute multiple distinct Query operations in parallel—one for each item in the list—and merge the results in your application code.
  • BatchGetItem: If you know both the partition key and the sort key, use BatchGetItem instead of a query to retrieve multiple discrete items in a single request.

In Filter Expressions (Supported)

The IN operator is fully supported inside a FilterExpression:

  • Evaluation: DynamoDB fetches the data via the partition key and sort key constraints, loads the results into memory, and performs an in-memory linear or set-membership scan to match the attribute against the IN list.
  • Size Limits: An IN operator can contain up to 100 values in a single expression.
  • Cost Impact: As with all filter expressions, you are billed for reading the entire dataset determined by the key condition, not just the items that match the IN criteria.

Impact on Pagination and Limits

When using BETWEEN or IN within filter expressions, DynamoDB enforces its standard 1 MB limit before evaluating the filter:

  • DynamoDB reads items until it hits the 1 MB data limit or finishes the partition.
  • It applies the FilterExpression (BETWEEN or IN).
  • It returns the filtered items along with a LastEvaluatedKey.

If the filter condition rejects all items within that 1 MB slice, DynamoDB returns an empty Items array alongside a LastEvaluatedKey. Applications must implement pagination logic to continue querying using the ExclusiveStartKey until no LastEvaluatedKey is returned.
