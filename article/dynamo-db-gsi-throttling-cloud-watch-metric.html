DynamoDB GSI Throttling CloudWatch Metric

Amazon DynamoDB base table writes can fail when an associated Global Secondary Index (GSI) lacks sufficient write capacity, causing backpressure on the main table. This article identifies the exact Amazon CloudWatch metric responsible for signaling GSI write throttling, explains how DynamoDB's index updates trigger this condition, and outlines how to diagnose and resolve the bottleneck.

The CloudWatch Metric to Monitor

The primary CloudWatch metric that indicates a Global Secondary Index is throttling is WriteThrottleEvents, evaluated using both the TableName and GlobalSecondaryIndexName dimensions.

When a GSI runs out of provisioned write capacity, DynamoDB emits the WriteThrottleEvents metric specifically for that index. Simultaneously, you will observe WriteThrottleEvents or ThrottledRequests on the base table metric dimensions, even if the base table itself has ample unconsumed Write Capacity Units (WCUs).

Why GSI Throttling Affects Base Table Writes

DynamoDB uses an asynchronous yet coordinated replication model to update GSIs. When an item is created, updated, or deleted on the base table, DynamoDB automatically applies those modifications to any affected GSIs.

However, if any GSI cannot accommodate the write volume:

  1. The GSI exhausts its allocated Write Capacity Units.
  2. DynamoDB throttles the GSI update to prevent the index data from lagging significantly behind the primary storage.
  3. DynamoDB applies backpressure to the base table, rejecting incoming write operations on the base table with a ProvisionedThroughputExceededException.

Because of this design, the base table's write performance is fundamentally constrained by the lowest provisioned throughput of any of its GSIs.

How to Diagnose the Issue in CloudWatch

To confirm that base table throttles are caused by a GSI rather than the table itself, follow these steps:

  1. Open the CloudWatch Console and navigate to Metrics > DynamoDB.
  2. Select the Table Metrics dimension and check WriteThrottleEvents for your base table.
  3. Select the Table and Secondary Index Metrics dimension.
  4. Locate the WriteThrottleEvents metric for each GSI associated with that base table.
  5. Compare the timestamps of the spikes. If the GSI's WriteThrottleEvents align with the throttles observed on the base table, the GSI is the root cause.

You can also cross-reference this with the ConsumedWriteCapacityUnits metric against the ProvisionedWriteCapacityUnits metric for that specific GSI dimension to verify that write utilization reached 100%.

Remediation Strategies

To eliminate GSI-induced base table throttling, implement the following adjustments:

  • Align Provisioned Capacity: Ensure the GSI’s provisioned Write Capacity Units equal or exceed the base table’s provisioned write capacity.
  • Enable DynamoDB Auto Scaling: Configure application auto-scaling on both the base table and all attached GSIs to dynamically adapt to traffic spikes.
  • Switch to On-Demand Capacity Mode: If traffic patterns are unpredictable or bursty, switch the table to On-Demand capacity mode so both the base table and GSIs scale instantly.
  • Optimize Index Projections: Use sparse indexes or project fewer attributes into the GSI so that writes to the base table do not always trigger an index write.
