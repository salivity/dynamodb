Prevent Stale Reads in DynamoDB: ConsistentRead

In high-concurrency applications, Amazon DynamoDB may return outdated data due to its default read consistency model. This article explains how the ConsistentRead parameter prevents reading stale data, how it functions under the hood, the API calls that support it, and the performance and cost trade-offs associated with enabling strongly consistent reads.

The ConsistentRead Parameter

To guarantee that a read operation returns the most up-to-date data following a write, you must set the ConsistentRead parameter to true.

By default, DynamoDB uses eventually consistent reads (ConsistentRead=false). When data is written to a DynamoDB table, it is replicated across multiple storage nodes in different Availability Zones. An eventually consistent read might query a replica that has not yet received the latest write, leading to stale or outdated results. Setting ConsistentRead=true instructs DynamoDB to return a strongly consistent read, which queries a quorum of nodes to guarantee that the response reflects updates from all prior successful write operations.

Supported API Operations

The ConsistentRead parameter can be included in the request payload of the following read operations:

  • GetItem: Retrieves a single item by its primary key.
  • BatchGetItem: Retrieves multiple items across one or more tables using their primary keys.
  • Query: Retrieves multiple items that share a partition key, optionally filtered by a sort key.
  • Scan: Reads every item in a table or secondary index.

Trade-offs and Considerations

While setting ConsistentRead=true solves concurrency and data staleness issues, it introduces specific trade-offs:

  1. Capacity and Cost: A strongly consistent read consumes twice the throughput of an eventually consistent read. One Read Capacity Unit (RCU) provides one strongly consistent read per second for items up to 4 KB, whereas the same RCU provides two eventually consistent reads per second.
  2. Latency: Strongly consistent reads may have slightly higher latency because the engine must confirm consistency across multiple storage replicas before returning a response.
  3. Availability: In the event of a network partition or degraded replica availability, strongly consistent reads are more likely to fail with an HTTP 500 error than eventually consistent reads.
  4. Index Constraints: Strongly consistent reads are supported on base tables and Local Secondary Indexes (LSIs). They are not supported on Global Secondary Indexes (GSIs), which are updated asynchronously and only support eventually consistent reads.
