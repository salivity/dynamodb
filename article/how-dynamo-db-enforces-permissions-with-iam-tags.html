How DynamoDB Enforces Permissions with IAM Tags

This article explains how Amazon DynamoDB leverages AWS Identity and Access Management (IAM) tags to enforce permission boundaries and access controls. By adopting Attribute-Based Access Control (ABAC), administrators can define fine-grained security policies where access to DynamoDB tables and operations is dynamically governed by matching the tags attached to IAM principals with the tags assigned to DynamoDB resources.

Attribute-Based Access Control (ABAC) in DynamoDB

DynamoDB integrates natively with IAM's policy evaluation engine to evaluate resource tags, request tags, and principal tags during API calls. Instead of listing specific Amazon Resource Names (ARNs) inside an IAM policy, access is determined by matching key-value pairs (tags). When an identity attempts an operation on a DynamoDB resource, IAM evaluates the identity's permission boundary and policies against the tags present on both the caller and the target resource.

Key IAM Condition Keys Used for Tag Enforcement

DynamoDB relies on global and service-specific IAM condition keys to validate tags:

  • aws:ResourceTag/${TagKey}: Compares the tag key and value attached to the DynamoDB resource (such as a table) with the value defined in the IAM policy.
  • aws:PrincipalTag/${TagKey}: Represents the tag attached to the IAM user or role making the request. It allows administrators to enforce rules such as: Allow access only if the principal's Environment tag matches the table's Environment tag.
  • aws:RequestTag/${TagKey}: Checks the tags passed in the request payload when creating a resource (dynamodb:CreateTable) or applying new tags (dynamodb:TagResource).
  • aws:TagKeys: Restricts which specific tag keys can be added, updated, or removed in a request.

Enforcing Table-Level Access Through Tag Matching

DynamoDB uses the aws:ResourceTag and aws:PrincipalTag keys to restrict data-plane and control-plane actions:

  1. Direct Resource Tag Matching: A policy allows operations like dynamodb:GetItem, dynamodb:PutItem, or dynamodb:UpdateTable only when the target table contains a specific tag, such as Environment = Production.

  2. Dynamic Principal-to-Resource Matching: Policies can use policy variables, such as:

    "Condition": {
  "StringEquals": {
    "aws:ResourceTag/Department": "${aws:PrincipalTag/Department}"
  }
}

    Under this rule, if an engineer with Department = Finance calls dynamodb:Query on a table tagged Department = Engineering, DynamoDB rejects the request.

Enforcing Tagging Compliance at Creation

To prevent untagged or improperly tagged resources from bypassing boundaries, IAM policies use aws:RequestTag combined with a Deny effect.

When a user calls dynamodb:CreateTable, the policy verifies that mandatory tags (such as Owner, CostCenter, or DataClassification) are included in the request. If the required tags are absent or do not meet allowed criteria, the request fails before the DynamoDB table is provisioned.

Preventing Privilege Escalation via Tag Tampering

Because permissions depend on tags, unauthorized modification of tags could allow an attacker to gain access to restricted DynamoDB tables. DynamoDB enforces security boundaries by separating tagging permissions:

  • Restricting dynamodb:TagResource: IAM policies restrict who can apply new tags or change existing tags on DynamoDB tables.
  • Restricting dynamodb:UntagResource: Policies block the removal of existing tags used for access control.
  • Condition-Based Tag Modification: Using aws:TagKeys, administrators ensure that users cannot add, modify, or delete sensitive security tags used for authorization boundaries.

Permission Boundaries as Guardrails

An IAM permission boundary sets the maximum permissions that an identity-based policy can grant to an IAM entity. When using tags within a permission boundary:

  • Delegated administrators creating IAM roles or users must attach the permission boundary.
  • The permission boundary contains rules requiring aws:ResourceTag checks on all dynamodb:* actions.
  • Even if an identity has an attached policy granting dynamodb:* on all resources ("Resource": "*"), the permission boundary overrides it, strictly limiting the principal to DynamoDB tables whose tags match the boundary's constraints.
