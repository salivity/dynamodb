DynamoDB Partition Key Capacity Calculation

This article explains how Amazon DynamoDB calculates the number of physical partitions needed to support your provisioned capacity and data footprint. It breaks down the mathematical formulas used to estimate partition counts based on Read Capacity Units (RCUs), Write Capacity Units (WCUs), and storage thresholds, while clarifying how capacity is allocated across logical partition keys.

The Two Capacity Thresholds

DynamoDB allocates underlying physical partitions based on two independent hardware and architecture constraints: total throughput and total storage volume. A single physical partition has hard limits:

  • Maximum Read Capacity Units: 3,000 RCUs
  • Maximum Write Capacity Units: 1,000 WCUs
  • Maximum Storage Size: 10 GB of data

When calculating the required partition count, DynamoDB evaluates both the throughput requirements and storage requirements, provisioning enough partitions to satisfy whichever metric demands more resources.

The Partition Count Formula

To determine the initial number of physical partitions for a provisioned table, DynamoDB calculates two values:

  1. Throughput-driven partitions: \[\text{Partitions (Throughput)} = \frac{\text{Total Provisioned RCU}}{3000} + \frac{\text{Total Provisioned WCU}}{1000}\]

  2. Storage-driven partitions: \[\text{Partitions (Storage)} = \frac{\text{Total Storage in GB}}{10\text{ GB}}\]

The final partition count is determined by taking the higher of the two values and rounding up to the nearest whole integer:

\[\text{Total Partitions} = \lceil \max(\text{Partitions (Throughput)}, \text{Partitions (Storage)}) \rceil\]

For example, if an application requires 4,000 RCUs, 2,000 WCUs, and stores 15 GB of data:

  • Throughput calculation: \((4000 / 3000) + (2000 / 1000) = 1.33 + 2.0 = 3.33\)
  • Storage calculation: \(15 / 10 = 1.5\)
  • The higher value is \(3.33\), which rounds up to 4 physical partitions.

Uniform Allocation Across Partitions

Once DynamoDB computes the required partition count, the total table-level provisioned capacity is divided uniformly across all active physical partitions:

  • RCU per partition: \(\frac{\text{Total Provisioned RCU}}{\text{Total Partitions}}\)
  • WCU per partition: \(\frac{\text{Total Provisioned WCU}}{\text{Total Partitions}}\)

Using the previous example of 4 partitions with 4,000 RCUs and 2,000 WCUs, each partition receives a baseline allocation of 1,000 RCUs and 500 WCUs.

Logical Partition Keys vs. Physical Partitions

DynamoDB uses an internal hash function (based on MD5) on the item's logical partition key value to generate an integer that determines which physical partition will store that item.

Multiple logical partition keys inevitably map to the same physical partition. Because provisioned capacity is distributed evenly at the physical partition level, all logical partition keys sharing a physical partition compete for that partition's assigned slice of RCU and WCU. If a single logical key receives disproportionate traffic, it cannot naturally exceed the hard physical partition ceiling of 1,000 WCUs or 3,000 RCUs.

Adaptive Capacity Handling

To manage uneven traffic distribution across partition keys without requiring manual re-calculation, DynamoDB employs Adaptive Capacity. This mechanism detects imbalanced workloads and automatically reallocates unused throughput from quiet partitions to active partitions. If sustained high throughput on a specific partition key exceeds normal allocation, DynamoDB can automatically split the physical partition to isolate hot partition keys, recalculating and increasing the partition count dynamically.
