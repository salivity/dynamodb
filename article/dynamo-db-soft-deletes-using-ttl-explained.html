DynamoDB Soft Deletes Using TTL Explained

Amazon DynamoDB Time to Live (TTL) is natively designed to perform automated hard deletes, but it can be leveraged alongside DynamoDB Streams to implement an automated soft delete pattern. This article covers how DynamoDB TTL functions under the hood, how to intercept system-initiated deletions via DynamoDB Streams, and how to process those events to mark data as soft-deleted or archive it without consuming primary write capacity.

How DynamoDB TTL Operates

DynamoDB TTL allows you to define a specific timestamp attribute for your items formatted in Unix epoch time (in seconds). A dedicated background process continuously scans your tables, compares this timestamp against the current time, and purges expired items.

Key characteristics of the native TTL process include:

  • Zero Consumed Throughput: TTL deletes do not consume your provisioned Read Capacity Units (RCUs) or Write Capacity Units (WCUs).
  • Eventual Deletion: TTL is not instantaneous. DynamoDB typically deletes expired items within 48 hours of their designated expiration time.
  • Hard Deletion by Default: When the background process deletes an item, it is permanently removed from the table.

Turning Hard TTL Deletions into Soft Deletes

Because native TTL results in permanent data removal, executing a soft delete requires intercepting the deletion event before the data is lost. This is achieved by combining TTL with DynamoDB Streams.

When TTL deletes an item, DynamoDB writes a REMOVE event to the table's stream. This event contains the entire deleted item (if the stream view type is configured to include the old image). You can process this stream using an AWS Lambda function to execute the soft-delete workflow.

Identifying TTL-Initiated Deletes

To avoid intercepting standard application-driven DeleteItem calls, your stream processor must distinguish between manual deletes and TTL deletes.

DynamoDB labels TTL deletions with a specific service identity within the stream record:

"userIdentity": {
    "type": "Service",
    "principalId": "dynamodb.amazonaws.com"
}

If a user or application deletes an item directly via the API, the userIdentity will contain IAM credentials or be omitted. When the principalId matches dynamodb.amazonaws.com, the deletion was triggered by the TTL process.

The Execution Workflow

The end-to-end execution of a TTL-driven soft delete operates as follows:

  1. Item Expiration: An item reaches its designated expiration timestamp in the table.
  2. Background Removal: DynamoDB's TTL process identifies the expired item and drops it from the active storage partition.
  3. Stream Emission: DynamoDB publishes a REMOVE record to the table’s DynamoDB Stream, preserving the deleted item's data in the OldImage field.
  4. Lambda Processing: An AWS Lambda function subscribed to the stream receives the batch of records.
  5. Origin Verification: The function checks each record’s userIdentity.principalId to confirm the deletion was performed by dynamodb.amazonaws.com.
  6. Soft Delete Update: The Lambda function re-writes the item back to the table with a modified state (e.g., setting an attribute isDeleted: true and removing the TTL attribute) or routes the payload to cold storage, such as Amazon S3 or an archive table.

The Reverse Pattern: TTL for Soft-Deleted Cleanup

TTL is also commonly used in reverse to manage the lifecycle of already soft-deleted records.

In this pattern, the application manually performs a soft delete by updating the item:

  • Sets an attribute such as isDeleted = true.
  • Sets a new ttl_timestamp attribute scheduled for a future date (e.g., 30 or 90 days out).

Your application filters out queries where isDeleted is true during standard operations. Once the retention period lapses, DynamoDB TTL automatically and cost-effectively hard-deletes the archived record, preventing unbounded table growth.
