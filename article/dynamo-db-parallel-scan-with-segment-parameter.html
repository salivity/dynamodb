DynamoDB Parallel Scan with Segment Parameter

This article explains how the Segment parameter enables parallel processing during an Amazon DynamoDB scan operation. By pairing the Segment parameter with TotalSegments, DynamoDB logically partitions table data across multiple independent workers, allowing simultaneous execution that significantly reduces overall scan duration for large datasets.

The Mechanics of a Parallel Scan

By default, a standard DynamoDB scan operation functions sequentially. It accesses one page of items at a time and traverses internal partitions in a single-threaded manner, which can result in high latency when querying millions of items.

To overcome this limitation, DynamoDB provides parallel scans. This mechanism relies on two complementary parameters configured within the Scan API request:

  • TotalSegments: Defines the total number of distinct, parallel workers that will scan the table concurrently.
  • Segment: Identifies the specific, zero-based slice of data assigned to an individual worker. The value ranges from 0 to TotalSegments - 1.

How the Segment Parameter Divides Data

DynamoDB distributes table items across multiple physical storage partitions using an internal hash function applied to each item's partition key.

When you provide the Segment parameter alongside TotalSegments, DynamoDB uses an internal mapping algorithm to assign a specific subset of these physical partitions to that designated segment.

Each worker process or thread issues a separate Scan request specifying its unique Segment number. Because the data subsets are mathematically mutually exclusive, every worker scans its designated segment independently without reading overlapping items.

Independent Execution and Pagination

The Segment parameter creates complete operational isolation for each worker:

  • Isolated Pagination: DynamoDB paginates results per segment. When a single Scan request returns a 1 MB limit or reaches the end of an evaluation, it returns a LastEvaluatedKey specific solely to that assigned segment.
  • Independent Checkpointing: If a worker fails, only that specific Segment needs to be restarted using its own LastEvaluatedKey, without disrupting the progress of other concurrent threads.
  • Distributed Workloads: Workers do not need to coordinate with each other in real-time. You can run segments across separate threads, containers, or distributed serverless compute environments like AWS Lambda.

Performance Impact and Considerations

Using the Segment parameter transforms the scan from an I/O-bound sequential pipeline into a scalable, distributed operation:

  • Linear Execution Speed: Scanning a large table with 10 segments can approach a 10x reduction in total wall-clock execution time compared to a single-threaded scan, provided sufficient Read Capacity Units (RCUs) are available.
  • Throughput Consumption: Parallel scans consume RCUs rapidly. The value chosen for TotalSegments should be tuned based on the table's provisioned or on-demand read capacity to avoid triggering ProvisionedThroughputExceededException errors.
