How DynamoDB Works with AWS PrivateLink

Amazon DynamoDB supports AWS PrivateLink through interface VPC endpoints, allowing you to route API requests to DynamoDB entirely within the private AWS network without traversing the public internet. By provisioning Elastic Network Interfaces (ENIs) with private IP addresses in your Virtual Private Cloud (VPC), PrivateLink enables secure, low-latency connectivity from your VPC, peered VPCs, or on-premises networks to DynamoDB. This overview explains how network traffic is routed, authenticated, and processed when using DynamoDB with AWS PrivateLink endpoints.

Step 1: DNS Resolution and Request Initiation

When an application inside your VPC or connected on-premises network initiates an API call (such as GetItem or PutItem) to DynamoDB, the request begins with a DNS lookup. Depending on your configuration, this happens in one of two ways:

  • Private DNS Enabled: The standard public regional endpoint (e.g., dynamodb.us-east-1.amazonaws.com) resolves directly to the private IP addresses assigned to the VPC endpoint's Elastic Network Interfaces (ENIs). Your application requires no code changes or endpoint overrides.
  • Endpoint-Specific DNS: If private DNS is disabled, your application must be configured to target the generated interface endpoint DNS names (e.g., vpce-xxx-yyy.dynamodb.us-east-1.vpce.amazonaws.com).

Step 2: Routing Through Elastic Network Interfaces (ENIs)

Once the destination IP is resolved, the application directs its HTTPS network packets to the local ENIs provisioned inside the VPC subnets. Because these ENIs reside inside your private subnets, outbound traffic does not require an Internet Gateway (IGW), a Virtual Private Gateway, or a NAT Gateway. Security groups attached to these ENIs act at the transport layer to control inbound and outbound traffic to and from your application instances.

Step 3: Traversal Across the AWS Private Backbone

From the ENI, the network traffic enters the AWS PrivateLink infrastructure. The traffic is encapsulated and transported securely across the AWS internal network backbone directly to the DynamoDB service fleet. This isolation guarantees that payload data and metadata remain protected from internet-routable pathways.

Step 4: Endpoint Policy Evaluation

Before the request reaches the DynamoDB service engine, AWS evaluates VPC endpoint policies attached to the interface endpoint. An endpoint policy is an IAM resource policy that controls which IAM principals can access which DynamoDB resources through that specific endpoint.

  • If the endpoint policy denies the action or does not explicitly allow it, the request is rejected immediately at the endpoint boundary.
  • If allowed, the request proceeds to standard DynamoDB authorization.

Step 5: IAM Authentication and Request Processing

After clearing the endpoint policy, the request arrives at the DynamoDB service frontend, where standard authentication occurs:

  1. Signature Verification: DynamoDB verifies the AWS Signature Version 4 (SigV4) headers using the caller's IAM credentials.
  2. IAM Policy Check: DynamoDB evaluates the caller's IAM user or role policies and any target resource policies to verify access permissions.
  3. Execution: Once authorized, DynamoDB reads or writes the requested data partitions in the storage nodes.

Step 6: Return Response

After processing the request, DynamoDB packages the response and sends it back through the same established PrivateLink connection. The data traverses the private AWS backbone back to the ENI in your VPC, which forwards the response payload directly to the client application.
