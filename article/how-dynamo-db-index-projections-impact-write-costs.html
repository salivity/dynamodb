How DynamoDB Index Projections Impact Write Costs

In Amazon DynamoDB, secondary indexes—both Global Secondary Indexes (GSIs) and Local Secondary Indexes (LSIs)—replicate data from the base table to support alternative query patterns. The projection setting (KEYS_ONLY, INCLUDE, or ALL) defines which attributes are copied from the base item into the index. This selection directly dictates write costs by determining the size of the written index item, the number of consumed Write Capacity Units (WCUs), and whether a write to the base table triggers an index update at all.

How DynamoDB Calculates Index Write Costs

Every write to an index consumes Write Capacity Units (WCUs). DynamoDB calculates write units based on 1 KB chunks:

  • Item Size Rounding: One WCU writes an item up to 1 KB in size. If an item written to an index is 1.2 KB, it rounds up to consume 2 WCUs.
  • GSI Billing: GSIs have their own provisioned or on-demand write capacity separate from the base table. An inefficient projection directly inflates the GSI's billing metrics.
  • LSI Billing: LSIs share write capacity with the base table. Larger LSI updates consume the base table's allocated capacity.

The Three Projection Types and Write Behavior

1. KEYS_ONLY

This setting projects only the index partition key, index sort key, and the base table's primary keys.

  • Impact on Write Cost: Minimal. Because only key attributes are stored, the index item size is typically well under 1 KB, consuming only 1 WCU per write.
  • Update Filtering: Modifying non-key attributes on the base table will not trigger an update to the GSI, completely eliminating index write costs for those operations.

2. INCLUDE

This setting allows you to specify an explicit list of non-key attributes to project alongside the key attributes.

  • Impact on Write Cost: Moderate and predictable. The item size increases only by the size of the specific attributes you declare. As long as the combined size of the keys and included attributes stays below 1 KB increments, WCU consumption remains controlled.
  • Update Filtering: If an update to a base table item modifies an attribute that is not in the INCLUDE list (and not a key), DynamoDB bypasses updating the GSI entirely, saving write capacity.

3. ALL

This setting replicates every attribute from the base table item into the secondary index.

  • Impact on Write Cost: Maximum. The index item mirrors the base table item's full size. If your base table item is 8 KB, writing to the GSI also consumes 8 WCUs.
  • Update Filtering: Any write or update to any attribute in the base table forces a corresponding write to the GSI. There is zero write-filtering benefit.

Write Amplification During Attribute Updates

When modifying an existing item in the base table, projection settings influence write amplification:

  • Key Changes: Changing an item's primary key or GSI key triggers a delete and a put operation on the index, doubling the WCU consumption for that event.
  • Projected Attribute Changes: Updating an attribute contained within a projection requires an index update.
  • Unprojected Attribute Changes: Updating an attribute omitted from KEYS_ONLY or INCLUDE projections costs zero WCUs on the GSI, as DynamoDB skips writing to the index.

Best Practices to Minimize Costs

  1. Avoid Defaulting to ALL: Use ALL only when access patterns require near-complete item projections and cannot tolerate the latency or cost of secondary fetches back to the base table.
  2. Favor INCLUDE for Query Coverage: Identify the specific attributes your read queries frequently retrieve and project only those. This keeps the item size within lower 1 KB boundaries and avoids index writes when other base table attributes change.
  3. Use KEYS_ONLY for High-Velocity Base Tables: If a base table experiences frequent updates on attributes that secondary queries do not need, KEYS_ONLY provides the maximum write isolation and prevents unnecessary secondary index spend.
