When to Use an LSI Over a GSI in DynamoDB

Amazon DynamoDB provides Local Secondary Indexes (LSIs) and Global Secondary Indexes (GSIs) to enable query access patterns beyond a table's primary key design. While GSIs are generally preferred for their flexibility, developers should select an LSI when they need strongly consistent reads, want to utilize the base table’s throughput capacity without paying for separate index capacity, and are querying data that shares the same partition key as the base table. This article outlines the specific architectural scenarios and trade-offs where choosing an LSI over a GSI is the optimal engineering decision.

1. Requirement for Strongly Consistent Reads

The primary technical differentiator of an LSI is read consistency.

  • Local Secondary Indexes support both eventually consistent and strongly consistent reads. If your application logic demands that a query immediately reflects the latest writes (such as inventory verification, financial ledgers, or real-time authorization checks), an LSI is the only secondary index option in DynamoDB that supports ConsistentRead = true.
  • Global Secondary Indexes only support eventual consistency. Replicating updates to a GSI occurs asynchronously, introducing replication lag that can result in stale reads.

2. Querying Across the Same Partition Key

An LSI requires the partition key to be identical to the base table's partition key, altering only the sort key.

You should choose an LSI when your access pattern strictly involves:

  • The same entity or partition boundary (same partition key).
  • An alternative attribute to sort, filter, or rank items within that entity (different sort key).

If your query requires searching across different partition keys or omitting the partition key altogether, a GSI is mandatory. However, if your access pattern naturally operates within the existing partition boundary, an LSI avoids the overhead of managing a global index.

3. Unified Capacity and Cost Efficiency

Throughput billing and capacity management differ significantly between the two index types:

  • LSIs consume capacity from the base table. Read operations on an LSI consume the Read Capacity Units (RCUs) allocated to the base table, and writes to items that affect the index consume the base table's Write Capacity Units (WCUs). This eliminates the operational overhead of provisioning, monitoring, and auto-scaling separate throughput settings.
  • GSIs require dedicated capacity. A GSI has its own provisioned or on-demand throughput. Under-provisioning a GSI can cause write throttling on the base table itself, requiring developers to carefully balance GSI throughput with table writes.

Choosing an LSI simplifies capacity planning when the workload volume against the secondary index aligns closely with the base table's overall read and write patterns.

4. Immediate Consistency Within Transactions

When executing write operations that involve DynamoDB transactions (TransactWriteItems), LSIs maintain atomicity and immediate consistency alongside the base table writes. Because the LSI data is stored in the same storage nodes (item collections) as the base table data, writes to the table and updates to the LSI are committed synchronously.

With a GSI, updates are committed asynchronously after the transaction completes on the base table. If your downstream processes rely on an index reflecting transactional writes without latency, an LSI is required.

Constraints to Consider Before Selecting an LSI

While an LSI offers consistency and cost benefits, it introduces structural constraints that must fit your system requirements:

  • Creation at Table Definition: LSIs can only be created at the time of table creation. They cannot be added, modified, or deleted afterward. If your data model evolves, adding a new index will require creating a GSI or migrating to a new table.
  • The 10 GB Item Collection Limit: When a table has one or more LSIs, all items sharing the same partition key value (known as an item collection) cannot exceed 10 GB in total size across the base table and its LSIs. If an item collection breaches 10 GB, DynamoDB rejects further writes for that partition key.
  • Index Limit: A table can have a maximum of 5 LSIs, compared to up to 20 GSIs per table by default.

Summary Checklist

Select a Local Secondary Index over a Global Secondary Index when:

  1. Your application requires strongly consistent reads on secondary query patterns.
  2. The query pattern uses the same partition key as the base table.
  3. You want the index to share the base table’s throughput rather than managing separate index capacity.
  4. Your partition size will comfortably stay under the 10 GB item collection limit.
  5. You can define the index schema upfront during table creation.
