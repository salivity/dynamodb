How DynamoDB Evaluates Condition Expressions

This article explains how Amazon DynamoDB evaluates condition expressions before executing item mutations such as PutItem, UpdateItem, and DeleteItem. By enforcing conditions at the database level, DynamoDB ensures that write operations only succeed if an item meets specific criteria, preventing data corruption, overwrites, and race conditions. Below is a breakdown of the evaluation lifecycle, atomicity guarantees, and error-handling behavior during conditional mutations.

The Evaluation Lifecycle

When a client sends a write request with a condition expression, DynamoDB processes the operation in a synchronized sequence on the storage node hosting the item's partition:

  1. Locating the Item: DynamoDB routes the request to the appropriate storage node using the item's partition key. It reads the current state of the existing item from local storage.
  2. Parsing the Expression: The engine parses the condition expression, replacing any expression attribute names (aliases for reserved words or nested paths) and expression attribute values (placeholders for actual values) with their resolved inputs.
  3. Evaluating Logic: DynamoDB evaluates the boolean expression against the existing item's attributes. Operators such as comparison operators (=, <, >), functions (attribute_exists, attribute_not_exists, begins_with, contains), and logical operators (AND, OR, NOT) are applied directly to the retrieved item data. If the item does not currently exist in the table, all attributes are treated as non-existent.
  4. Execution or Abort:
    • If the condition evaluates to true: The requested mutation is applied immediately.
    • If the condition evaluates to false: The operation halts, the item remains unchanged, and DynamoDB returns a ConditionalCheckFailedException (HTTP 400).

Atomicity and Concurrency Control

DynamoDB performs the read, condition evaluation, and subsequent write as a single atomic operation on the storage node. While the condition is being evaluated and the write is applied, the item is locked against other concurrent mutations on that partition. This strict serializability guarantees optimistic concurrency control: no other operation can modify or delete the item between the evaluation step and the commit step.

Handling Non-Existent Items

A condition expression does not require an item to exist beforehand unless explicitly defined. For example, using the attribute_not_exists(partition_key) function ensures that an item is created only if it does not already exist, effectively preventing accidental overwrites. Conversely, operations targeting an existing item can assert attribute_exists(partition_key) to ensure an update or delete fails if the target item is missing.

Capacity and Cost Impact

DynamoDB consumes write capacity units (WCUs) even when a condition check fails. Because the system must perform the internal read and evaluation work on the partition replica, a failed conditional write incurs the same capacity unit cost as if the condition had passed. If the request fails due to validation errors (such as a malformed expression) before reaching the storage node, no capacity units are consumed.
