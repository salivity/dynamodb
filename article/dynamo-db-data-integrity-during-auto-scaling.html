DynamoDB Data Integrity During Auto-Scaling

Amazon DynamoDB maintains strict data integrity during automatic table scaling through an architecture based on distributed consensus, decoupled request routing, and non-blocking partition management. Whether scaling throughput capacity in response to traffic fluctuations or splitting physical storage partitions due to data growth, DynamoDB ensures that every read, write, and transaction remains durable, consistent, and uninterrupted.

Decoupled Storage and Request Routing

DynamoDB separates its request routing layer from its storage node layer. When an application sends a read or write request, it first hits an internal Request Router. Routers do not store data; instead, they maintain a local partition map that maps partition keys to the specific storage nodes hosting the data.

If auto-scaling alters the underlying topology—such as when throughput demands cause partitions to divide—storage nodes inform routers through membership protocols. If a router attempts an operation on an outdated storage node, the node rejects the request with a configuration error. The router immediately refreshes its metadata from the centralized configuration management service and transparently retries the operation on the correct node without exposing transient errors to the client.

Partition Splitting Mechanics

When an individual partition exceeds capacity limits (10 GB of storage, 1,000 write capacity units, or 3,000 read capacity units), DynamoDB triggers an automated partition split. To prevent data corruption or loss during this transition:

  1. Replication Group Creation: DynamoDB provisions new target storage nodes across multiple Availability Zones to form child partition groups.
  2. Snapshot and Log Replay: The system takes an atomic snapshot of the parent partition’s storage engine (a variant of a log-structured merge-tree or B-tree) and copies the baseline data to the child nodes. Any mutations (writes and updates) that occur during this transfer are captured via transaction logs and continuously replicated to the new nodes.
  3. Atomic Cutover: Once synchronization reaches parity, an atomic metadata commit updates the partition key boundaries. The parent partition stops processing writes, the final delta is committed to the children, and the routing layer is instructed to direct future traffic to the child partitions. This handoff occurs within milliseconds.

Multi-AZ Replication via Paxos Consensus

Every partition in DynamoDB is replicated across at least three physical storage nodes in separate Availability Zones, forming a Paxos-based replica group. A write is only acknowledged as successful to the client once a quorum (at least two of the three nodes) writes the operation to its write-ahead log (WAL) on non-volatile media.

During scaling operations, the Paxos leader node enforces the order of incoming operations. Even if a node is reassigned or data is copied to scale out the cluster, the consensus protocol guarantees that uncommitted writes are never partially applied and committed writes cannot be lost, regardless of hardware failures or network splits occurring mid-scale.

Isolation and ACID Transaction Preservation

Automatic scaling does not compromise transactional safety. DynamoDB's transactional operations (TransactWriteItems and TransactGetItems) coordinate two-phase commits across multiple partitions. During scaling events, the internal transaction coordinator handles distributed locks and validates that all involved partitions are available. If a partition split is actively finalizing, the transaction coordinator waits for the brief metadata cutover to complete or safely rolls back the transaction, preserving full serializable isolation.
