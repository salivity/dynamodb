Redesigning DynamoDB GSI Keys for Bottlenecks

Amazon DynamoDB Global Secondary Indexes (GSIs) enable flexible querying, but poorly chosen partition keys can create severe write bottlenecks that degrade an entire application. This article outlines the critical warning signs, operational metrics, and architectural anti-patterns that signal it is time to redesign your GSI keys. By recognizing issues like hot partitions, low-cardinality keys, and base-table throttling early, you can restructure your schema to ensure predictable latency and scalable throughput.

Consistent GSI Write Throttling

The most immediate sign that a GSI key requires redesign is the presence of ProvisionedThroughputExceededException errors during write operations, specifically originating from the index rather than the base table.

In DynamoDB, writes to the base table are asynchronously propagated to all GSIs. However, if a GSI cannot accommodate a write due to exhausted capacity on a specific partition, the base table write itself will be throttled. If your base table has ample write capacity units (WCUs) but writes are failing, a GSI partition bottleneck is almost always the root cause.

Low Cardinality in the GSI Partition Key

A GSI partition key must distribute writes across physical partitions. If your GSI uses an attribute with very few distinct values—such as status, is_active, or gender—all writes containing that attribute funnel into a small number of physical partitions.

A single DynamoDB partition has a hard limit of 1,000 WCUs per second. When multiple concurrent writers update items that share the same GSI partition key value (for example, marking orders as status = "PENDING"), the 1,000 WCU threshold is quickly exceeded. If your key design relies on an attribute with low entropy, it must be redesigned immediately.

Time-Based or Monotonically Increasing Keys

Using timestamps, dates, or sequential IDs as the GSI partition key inevitably leads to write bottlenecks. When an application logs events with a GSI partition key like YYYY-MM-DD or YYYY-MM-DD-HH, all concurrent traffic for that time window targets the exact same partition.

Once the clock advances, traffic moves entirely to the next partition, leaving previously allocated partitions idle. This pattern prevents DynamoDB from effectively distributing traffic across the storage fleet.

Uneven Storage and Throughput Distribution

Amazon CloudWatch provides metrics that indicate when a key design is failing:

  • ConsumedWriteCapacityUnits vs. ProvisionedWriteCapacityUnits: High throttling events occurring while total consumed WCU is far below the provisioned limit indicates non-uniform access.
  • Storage skew across partitions: While DynamoDB abstracts physical partitions, heavily skewed item counts associated with specific partition keys inevitably lead to localized throughput exhaustion.

If these metrics show that peak write traffic cannot scale linearly with provisioned capacity, the partition key is not uniformly spreading the workload.

How to Redesign the GSI Key

When any of the above conditions occur, you should adopt one of the following remediation patterns:

  • Write Sharding (Suffixing): Append a random or deterministic integer suffix (e.g., 0 to N) to the GSI partition key upon write (e.g., PENDING_1, PENDING_2). Queries then read across all shards in parallel and merge results on the client side.
  • Compound Partition Keys: Combine two attributes to form a more granular partition key, such as combining tenant_id with status (TENANT#123_STATUS#PENDING).
  • Evaluate Sparse Indexes: If the GSI only needs to capture a small subset of items, ensure the partition key attribute is only populated on items that must appear in the index. DynamoDB skips writing to the GSI entirely for items lacking the index key.
  • Decouple with DynamoDB Streams: If high-frequency writes do not require real-time index availability, disable the GSI and stream updates via DynamoDB Streams to a dedicated aggregation store or an asynchronous processing pipeline.
