DynamoDB Parallel Scans Across Table Segments

Amazon DynamoDB processes large datasets efficiently by allowing applications to divide a table into multiple logical segments and scan them concurrently. When executing a parallel scan across non-contiguous table segments, DynamoDB decouples the application's logical segment definition from the physical storage partitions beneath it. This article explains how DynamoDB distributes these logical segments across its internal partition key hash space, how individual workers track progress through non-contiguous boundaries, and the mechanics required to maximize throughput without resource contention.

Logical Segmentation vs. Physical Partitions

In DynamoDB, data is physically distributed across storage nodes using an internal hash function applied to each item's partition key. This hash space ranges from 0x0000000000000000 to 0xFFFFFFFFFFFFFFFF. Physical partitions hold contiguous ranges of this hash space.

When an application initiates a parallel scan, it specifies two key parameters:

  • TotalSegments: The number of logical chunks the table should be divided into.
  • Segment: The specific chunk (0-indexed) that a given worker thread will process.

A logical segment does not map directly to a single physical partition. Instead, DynamoDB mathematically stripes the logical segments across the entire hash space. Because physical partitions may split, merge, or reside on separate storage nodes, the data belonging to a single logical segment is often physically non-contiguous. DynamoDB routes each scan operation to the relevant storage nodes that host the parts of the hash ring assigned to that specific logical segment.

Processing Mechanism for Non-Contiguous Segments

When a worker requests a scan for a specific segment, DynamoDB executes the following steps:

  1. Hash Space Assignment: DynamoDB uses an internal hashing algorithm to interleave the assigned keyspace for each segment. Segment \(N\) out of \(M\) is responsible for evaluating keys whose hash values align with \((Hash(Key) \pmod M) = N\). This guarantees that every item belongs to exactly one segment, preventing duplicate processing across workers.
  2. Scatter-Gather on the Storage Layer: Because the items matching the segment formula reside across multiple physical partitions, the DynamoDB request router communicates with multiple storage nodes. The router coordinates reads across these disparate partitions without requiring the underlying partitions to be adjacent.
  3. Pagination with LastEvaluatedKey: Scans return up to 1 MB of data per request. To resume processing across non-contiguous blocks, DynamoDB returns a LastEvaluatedKey. This key acts as an opaque cursor containing both the primary key and internal partition boundary tracking. The worker must supply this key in the subsequent request's ExclusiveStartKey parameter.
  4. Independent Progress Tracking: Each worker maintains its own cursor independently. A worker scanning Segment 0 can progress at a completely different rate than a worker scanning Segment 1. Non-contiguous data distribution does not block or synchronize individual segment progress.

Throughput and Provisioned Capacity Allocation

DynamoDB distributes read capacity units (RCUs) evenly across all physical partitions in a table. When parallel scans run:

  • Even Load Distribution: If TotalSegments is equal to or a multiple of the number of physical partitions, the scan requests are evenly distributed across all underlying storage nodes, maximizing RCU utilization.
  • Mitigating Hotspots: If a segment encompasses a heavily populated non-contiguous partition or high-traffic partition keys, that specific worker might exhaust partition-level throughput, resulting in ProvisionedThroughputExceededException.
  • Worker Sizing: Setting TotalSegments too high relative to the physical partition count introduces overhead, while setting it too low leaves physical partition capacity underutilized.

Best Practices for Parallel Scans

To achieve optimal performance when scanning non-contiguous segments:

  • Match Segments to Partition Count: Set TotalSegments equal to or slightly higher than the number of physical partitions the table utilizes.
  • Handle Rate Limiting: Implement exponential backoff in each worker to handle throttling at the individual partition level independently.
  • Avoid Monopolizing Throughput: Use application-level rate limiters to prevent the parallel scan workers from consuming the entirety of the table's provisioned read throughput, which could starve other real-time operational workloads.
