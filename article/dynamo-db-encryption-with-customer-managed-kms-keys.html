DynamoDB Encryption with Customer-Managed KMS Keys

Amazon DynamoDB provides native encryption at rest to protect sensitive data stored in tables, indexes, streams, and backups. When utilizing customer-managed keys (CMKs) from AWS Key Management Service (KMS), DynamoDB enforces item-level storage protection using an envelope encryption workflow coupled with AWS Identity and Access Management (IAM) and KMS key policies. This article explains the technical mechanics of how DynamoDB enforces encryption at rest using customer-managed keys, from policy-driven provisioning to cryptographic operations.

Envelope Encryption Mechanism

DynamoDB uses envelope encryption to balance cryptographic performance with granular access control:

  1. Root Key Protection: The customer-managed KMS key serves as the root key (Key Encryption Key or KEK). It remains securely within AWS KMS hardware security modules (HSMs) and never leaves the service unencrypted.
  2. Data Key Generation: When a table configured with a CMK is created or loaded, DynamoDB calls the KMS API (kms:GenerateDataKey) to request a unique plaintext Data Encryption Key (DEK) and an encrypted version of that same DEK.
  3. Item Storage Encryption: DynamoDB uses the plaintext DEK to encrypt raw item attributes, primary keys, local and global secondary indexes, and write-ahead logs using AES-256 before committing them to persistent physical storage.
  4. Key Removal from Memory: The plaintext DEK is used transiently in memory and then discarded. The encrypted DEK is stored alongside the table metadata.
  5. Decryption on Read: When reading data, DynamoDB passes the encrypted DEK to KMS via kms:Decrypt. If KMS authorizes the request, it returns the plaintext DEK to DynamoDB to decrypt the table items for the caller.

Enforcing Customer-Managed Keys via IAM and SCPs

DynamoDB does not automatically require customer-managed keys by default; it defaults to AWS-owned keys. To strictly enforce the use of CMKs across an organization or workload, administrators use IAM policies and Service Control Policies (SCPs).

Enforcement is implemented by evaluating API calls such as dynamodb:CreateTable and dynamodb:UpdateTable:

  • Restricting SSE Types: Policies can use the dynamodb:SSEType condition key to deny table creation if the encryption type is not set to KMS.
  • Restricting KMS Master Key IDs: The condition key dynamodb:KMSMasterKeyId or dynamodb:KMSMasterKeyArn can be evaluated. If a request does not specify an approved customer-managed KMS Key ARN, the action returns an AccessDeniedException.
  • Mandatory Table Tags: Organizations often require tables to include specific compliance tags during creation, which can trigger automated governance tools (such as AWS Config) to remediate or delete tables that use AWS-managed or AWS-owned keys.

KMS Key Policies and Grants

For DynamoDB to use a customer-managed key, the KMS key policy must explicitly authorize DynamoDB to perform cryptographic actions on behalf of the user.

  • Caller Permissions: The IAM identity creating or updating the table must possess kms:CreateGrant, kms:DescribeKey, and kms:Decrypt permissions on the target CMK.
  • Grants: DynamoDB creates a KMS grant associated with the CMK. This grant delegates permission to the internal DynamoDB service principal to generate data keys, decrypt existing data keys, and re-encrypt data when necessary.
  • Immediate Access Revocation: Because DynamoDB relies on the validity of this KMS grant and key, an administrator can immediately cut off access to encrypted data by disabling the CMK, modifying its key policy, or revoking the grant. Once access is severed, DynamoDB cannot decrypt data keys, and read or write operations to the table will fail.
