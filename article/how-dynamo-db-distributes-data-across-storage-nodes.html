How DynamoDB Distributes Data Across Storage Nodes

Amazon DynamoDB distributes internal data across physical storage nodes through horizontal partitioning driven by consistent hashing and partition keys. This article details the underlying architecture of DynamoDB's storage engine, explaining how the service maps item keys to physical hardware, groups storage nodes into multi-Availability Zone replication sets, handles dynamic partition scaling, and routes requests with predictable single-digit millisecond latency.

Consistent Hashing and the Partition Key

At the core of DynamoDB's data distribution is consistent hashing. When an item is written, DynamoDB takes the item's partition key value and passes it through an internal cryptographic hash function (historically a variant of MD5). This generates a 128-bit hash value that determines the item's position within a fixed, unordered keyspace.

Because the hash function distributes inputs uniformly across the keyspace, items with distinct partition keys are spread evenly across the storage infrastructure, preventing physical bottlenecks regardless of the semantic relationships between the keys.

Partitions as the Fundamental Storage Unit

DynamoDB divides a table's data into logical units called partitions. A single partition holds up to 10 GB of data and can deliver up to 1,000 Write Capacity Units (WCU) and 3,000 Read Capacity Units (RCU).

Each logical partition maps to physical hardware resources—specifically Solid-State Drives (SSDs) and dedicated compute slices—managed by storage nodes in AWS data centers. If a table contains 100 GB of data, DynamoDB allocates at least 10 partitions distributed across the physical fleet to balance storage and compute loads.

Replication Groups and High Availability

Physical storage nodes do not operate in isolation; they are organized into partition groups. A partition group typically consists of a three-node replica set spread across distinct Availability Zones (AZs) within an AWS Region:

  • Leader Node: One replica in the group is elected as the leader using a Paxos-based consensus algorithm. The leader coordinates write operations, appends writes to its local write-ahead log (WAL), and propagates changes to peer replicas.
  • Peer Replicas: The other two physical nodes replicate the write-ahead log. A write is acknowledged to the client as soon as a quorum (the leader and at least one peer replica) confirms the log has been committed to disk.
  • Read Distribution: Strongly consistent reads are served directly by the leader node, while eventually consistent reads are routed to any of the three physical replicas to balance read loads across hardware.

If a physical storage node fails, the consensus mechanism detects the failure, elects a new leader if necessary, and provisions a replacement storage node by streaming the write-ahead log from the surviving peers.

The Request Router and Partition Map

When a client makes an API call to DynamoDB, the request hits a stateless Request Router fleet. The Request Router maintains a cached copy of the global partition map, which links hash key ranges to the specific physical nodes currently hosting those ranges.

  1. The Request Router hashes the incoming request’s partition key.
  2. It evaluates its internal routing table to determine which partition group owns that hash range.
  3. It dispatches the request over low-latency internal network links directly to the physical storage node responsible for that partition.

If a router's partition map is outdated (for instance, following a partition migration), the target storage node returns an error code, prompting the Request Router to invalidate its cache, fetch the updated partition location, and transparently retry the operation.

Dynamic Partition Splitting and Heat Management

As data grows or throughput requirements increase, DynamoDB dynamically adapts without downtime through partition splitting:

  • Size-Based Splitting: When a partition approaches the 10 GB threshold, the storage layer splits it into two new child partitions. The key range is halved, and one half of the data is migrated to a new physical storage node.
  • Throughput-Based Splitting: If workload traffic on a partition consistently exceeds 1,000 WCUs or 3,000 RCUs, DynamoDB divides the hash range across multiple partitions to distribute the compute load across different physical nodes.

To mitigate transient traffic spikes on specific keys, DynamoDB incorporates adaptive capacity. This mechanism dynamically reallocates unused read and write capacity from quiet partitions to busy partitions on other physical nodes, preventing throttling caused by non-uniform access patterns across the cluster.
