Impact of High Cardinality in DynamoDB Partition Keys

Using high-cardinality attributes as partition keys in Amazon DynamoDB is one of the most effective ways to optimize performance, eliminate hot partitions, and ensure scalable data access. Because DynamoDB distributes data across physical storage nodes based on the hash value of the partition key, high cardinality ensures that reads and writes are evenly distributed across the system. This article examines how high cardinality impacts performance, partition management, throughput efficiency, and access pattern design.

What Is High Cardinality in DynamoDB?

Cardinality refers to the uniqueness of data values contained in a particular column or attribute. In DynamoDB, an attribute with high cardinality has a large number of distinct values relative to the total number of items. Common examples include:

  • Universally Unique Identifiers (UUIDs)
  • User IDs or Customer Account Numbers
  • Device serial numbers
  • Transaction IDs or Order Numbers

Conversely, attributes with low cardinality have very few unique values, such as status flags (e.g., active or inactive), binary states, or broad categories.

Even Distribution of Data and Traffic

DynamoDB uses an internal hash function to map partition keys to physical storage units called partitions. When you select a high-cardinality attribute as your partition key, the hash values are uniformly distributed across the available keyspace.

This even distribution ensures that:

  • Storage is balanced across multiple physical nodes rather than accumulating on a single partition.
  • Request traffic (both reads and writes) is spread evenly across the underlying hardware, preventing any single storage node from handling a disproportionate amount of work.

Preventing Hot Partitions and Throttling

Each physical partition in DynamoDB has strict operational limits: a maximum of 1,000 Write Capacity Units (WCUs), 3,000 Read Capacity Units (RCUs), and 10 GB of storage.

If you use a low-cardinality partition key, items with the same key are stored on the same physical partition. If a sudden surge of requests targets that key, the partition quickly exceeds its 1,000 WCU or 3,000 RCU threshold. This results in a "hot partition," causing DynamoDB to return ProvisionedThroughputExceededException errors (throttling), even if your overall table-level capacity is not exhausted.

High-cardinality partition keys prevent hot partitions by diffusing traffic across many distinct keys, ensuring that individual partition limits are rarely breached.

Efficient Throughput and Cost Optimization

DynamoDB allocates provisioned throughput across physical partitions. When traffic is concentrated on a small set of keys, you are often forced to over-provision capacity for the entire table just to handle the load on a single hot partition. By introducing high cardinality, your application utilizes provisioned read and write capacity uniformly. This reduces waste, prevents unexpected throttling spikes, and lowers operational costs in both provisioned and on-demand billing modes.

Query Limitations and Architectural Trade-Offs

While high cardinality is ideal for performance and scalability, it impacts how you query data:

  • No Multi-Item Queries on the Partition Key Alone: If every item has a unique partition key (such as a UUID) and no sort key, you can only perform single-item lookups via the GetItem, PutItem, UpdateItem, or DeleteItem APIs. You cannot use the Query API to fetch related records in a single call.
  • Composite Primary Keys: To maintain high cardinality while still querying groups of related records, combine a high-cardinality partition key with a meaningful sort key (e.g., CustomerID as the partition key and OrderDate as the sort key). This isolates query operations to a specific entity while keeping total traffic distributed across all customers.
  • Secondary Indexes: If you need to search or filter across entities using low-cardinality attributes, you should create Global Secondary Indexes (GSIs) or utilize techniques such as write sharding rather than compromising the cardinality of your base table's partition key.
