DynamoDB Client-Side Encryption Explained

This article provides an overview of client-side encryption for Amazon DynamoDB, identifying the specific mechanism used to protect data before it ever reaches the cloud. Readers will learn how the AWS Database Encryption SDK secures sensitive attributes prior to transmission, how this approach differs from default server-side encryption, and why it is essential for high-security environments.

The encryption method in DynamoDB that offers client-side protection before transmitting data is client-side encryption, implemented using the AWS Database Encryption SDK (formerly known as the Amazon DynamoDB Encryption Client).

Unlike standard server-side encryption, which encrypts data after it arrives at AWS data centers, client-side encryption processes data entirely within your local application environment. Your application encrypts sensitive attributes before sending them over the network to DynamoDB, and decrypts them only after retrieving the data back into the local environment.

How Client-Side Encryption Works

Client-side encryption introduces a zero-trust model to your database operations:

  1. Local Encryption: Before an item is written to DynamoDB via a PutItem or UpdateItem call, the SDK encrypts specific attribute values using cryptographic keys managed by your application or AWS Key Management Service (AWS KMS).
  2. Transmission in Ciphertext: The data travels across the network in ciphertext format. Even though transit is typically secured by TLS, client-side encryption guarantees that the payload remains unreadable even if TLS were somehow compromised.
  3. Storage as Ciphertext: DynamoDB receives and stores the attribute values as ciphertext. To AWS, the values are meaningless bytes.
  4. Local Decryption: When your application fetches the record, DynamoDB returns the ciphertext. The SDK decrypts the values locally using the appropriate decryption key.

Client-Side Encryption vs. Server-Side Encryption

DynamoDB enables Server-Side Encryption (SSE) at rest by default. While SSE protects data on the physical disks within AWS facilities, it requires trusting AWS with the plaintext during transit processing and key management.

Client-Side Encryption ensures end-to-end security where AWS never possesses the plaintext data or the plaintext encryption keys. This distinction is critical for meeting stringent regulatory standards such as HIPAA, PCI-DSS, or internal zero-trust architecture mandates.

Key Capabilities

  • Attribute-Level Control: You can choose which attributes to encrypt, which to sign without encrypting (allowing them to be queried), and which to leave untouched. Primary keys (partition and sort keys) must remain unencrypted so DynamoDB can index and route the data properly, but they can still be cryptographically signed.
  • Data Integrity Checks: The SDK automatically calculates digital signatures for your attributes. This ensures that any unauthorized modifications made to the stored data—whether in transit or at rest—are immediately detected upon decryption.
  • Compatibility with AWS KMS: You can back the client-side encryption with AWS KMS customer managed keys, combining localized cryptographic operations with centralized key policy enforcement and audit logging via AWS CloudTrail.
