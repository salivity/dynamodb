DynamoDB Transaction Maximum Execution Time

This article examines the maximum execution time allowed for an Amazon DynamoDB transaction request. It details the specific time limit enforced by the service, explains what occurs when a transaction exceeds this threshold, and outlines practical strategies to avoid transaction timeouts and cancellations.

The Maximum Execution Time Limit

The maximum execution time allowed for a single DynamoDB transaction request—whether using TransactWriteItems or TransactGetItems—is 2.5 seconds (2,500 milliseconds).

DynamoDB uses an optimistic concurrency model. If a transaction request cannot complete all of its read, write, and condition-checking operations within this 2.5-second window, DynamoDB automatically rejects the request and cancels the transaction.

What Happens When a Transaction Times Out

When a transaction exceeds the 2.5-second limit, the following occurs:

  • Transaction Cancellation: DynamoDB rolls back all write operations in the transaction to maintain atomicity, consistency, isolation, and durability (ACID). No partial changes are saved.
  • Error Response: DynamoDB returns a TransactionCanceledException. Within this exception, the CancellationReasons list provides specific error codes (such as TransactionConflict or ProvisionedThroughputExceeded) that explain why the individual operations took too long or failed.

Common Causes of Transaction Timeouts

Transactions rarely take 2.5 seconds under normal operational conditions. Reaching the limit typically indicates underlying bottlenecks, including:

  • High Key Contention: When multiple concurrent requests attempt to modify the same item simultaneously, transaction conflicts force coordination delays that can extend execution time beyond the threshold.
  • Throughput Throttling: If the targeted tables or partitions do not have sufficient read or write capacity units (RCUs/WCUs), operations are throttled, introducing latency.
  • Large Transaction Payloads: Although DynamoDB allows up to 100 operations or 4 MB of data per transaction, processing large payloads across multiple distributed partitions increases network and coordinator overhead.

Best Practices to Prevent Timeouts

To ensure transactions finish well within the 2.5-second execution limit:

  • Minimize Contention: Design partition keys to distribute read and write traffic evenly across your partitions. Avoid patterns that repeatedly target the same item across concurrent transactions.
  • Size Transactions Efficiently: Group only the operations that strictly require ACID guarantees into a single transaction. Keep payloads as small as possible.
  • Monitor Latency and Throttling: Track the SuccessfulRequestLatency and ThrottledRequests metrics in Amazon CloudWatch to identify partition-level bottlenecks before they cause timeouts.
  • Configure Client-Side Retries: Implement exponential backoff and jitter in your application's SDK configuration to handle transient conflicts gracefully without overwhelming DynamoDB with immediate retries.
