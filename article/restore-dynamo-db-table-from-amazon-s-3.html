Restore DynamoDB Table From Amazon S3

Restoring data from an Amazon Simple Storage Service (S3) bucket back into Amazon DynamoDB is accomplished through DynamoDB's native "Import from S3" feature. This article explains the architectural process DynamoDB uses to ingest data files from S3, create a target table, parse records without consuming write capacity, and handle errors during bulk ingestion.

Target Table Creation

The restore process requires creating a brand-new DynamoDB table; it cannot import data directly into an existing table. When an import job is initiated via the AWS Management Console, AWS CLI, or the ImportTable API, you define the target table configuration, including:

  • Primary key schema (Partition Key and optional Sort Key).
  • Billing mode (Provisioned or On-Demand).
  • Secondary indexes (Local Secondary Indexes and Global Secondary Indexes).
  • Encryption settings (AWS owned key, AWS managed key, or customer managed KMS key).

DynamoDB initializes the table in an IMPORTING state, making it unavailable for read and write operations until the restoration completes.

Supported Data Formats and Compression

DynamoDB supports source data stored in Amazon S3 in three formats:

  1. DynamoDB JSON: Standard JSON formatted with DynamoDB data type descriptors (e.g., {"S": "value"}).
  2. Amazon Ion: A superset of JSON developed by Amazon that provides rich data typing.
  3. CSV: Delimited text files, where headers define the attribute names.

Source files can be uncompressed or compressed using GZIP or ZSTD algorithms. DynamoDB automatically detects compression and processes individual or multiple objects matching the designated S3 bucket prefix.

Serverless Parallel Ingestion

Once the job starts, DynamoDB manages the ingestion entirely behind the scenes using internal distributed compute resources:

  • No Capacity Consumption: The import does not consume the table's provisioned Write Capacity Units (WCUs) or incur On-Demand write charges. It is billed separately based on the uncompressed size of the source data processed.
  • Parallel Processing: DynamoDB scales internal worker instances to read, decompress, and parse S3 objects concurrently.
  • Direct Storage Ingestion: The parsed records are loaded directly into the underlying storage nodes allocated for the new table partitions.

Error Handling and Verification

During the import, DynamoDB validates the source data against the defined schema and standard DynamoDB constraints (such as item size limits of 400 KB and primary key uniqueness).

  • If an item violates schema constraints (for example, missing a partition key or containing invalid formatting), it is rejected.
  • DynamoDB generates detailed error logs and writes them back to your S3 bucket under an error prefix, documenting the specific line or record that failed.
  • You can monitor the status and metrics—such as imported items, processed bytes, and error counts—through CloudWatch and the DynamoDB console.

Finalizing Table Availability

After all valid items from the S3 source are written to the storage nodes, DynamoDB generates any configured Global Secondary Indexes (GSIs). Once index backfilling completes, the table transitions from the IMPORTING status to ACTIVE. At this point, the restored table is fully functional and ready to accept live application reads and writes.
