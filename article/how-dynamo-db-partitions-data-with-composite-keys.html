How DynamoDB Partitions Data with Composite Keys

Amazon DynamoDB manages large-scale data by distributing items across physical storage nodes called partitions. When you define a composite primary key—consisting of a partition key and a sort key—DynamoDB uses a two-step mechanism to place and organize your records. The partition key determines the specific physical partition where the data is stored, while the sort key determines the physical order of the data within that partition. This article explains the internal hashing mechanism, the role of the sort key, partition split behavior, and how composite keys affect read and write performance.

The Mechanics of the Partition Key

The first attribute of a composite key is the partition key (historically called the hash key). When an application writes an item to DynamoDB, the service passes the partition key's value through an internal cryptographic hash function.

The output of this hash function points directly to an internal hash ring that maps to a specific physical partition. Because this calculation relies exclusively on the partition key value, all items that share the exact same partition key value map to the same physical partition or set of partitions, completely ignoring the sort key during the initial routing phase.

The Role of the Sort Key

The second attribute of a composite key is the sort key (historically called the range key). Once DynamoDB identifies the correct physical partition using the partition key's hash, it uses the sort key to store the item in sorted order.

Items sharing the same partition key are stored together as an "item collection." Within that collection:

  • Data is stored in ascending order based on the sort key's binary representation (or numerical order for number types).
  • Range queries using operators such as BETWEEN, Begins With, <, >, and <= are executed efficiently because the related data physically resides next to each other on the same storage node.

How DynamoDB Handles Partition Limits and Splits

A single DynamoDB physical partition can hold up to 10 GB of data and support a maximum of 1,000 Write Capacity Units (WCUs) or 3,000 Read Capacity Units (RCUs). When your table grows beyond these limits, DynamoDB automatically provisions additional partitions.

When composite keys are involved, partition splitting behaves in one of two ways:

  1. Tables without Local Secondary Indexes (LSIs): If a single item collection (items with the identical partition key) exceeds 10 GB, DynamoDB splits the data across multiple physical partitions based on the sort key values. It allocates contiguous sort key ranges to different physical nodes to balance the load.
  2. Tables with Local Secondary Indexes (LSIs): An item collection cannot exceed 10 GB in total size. If the limit is reached, DynamoDB rejects further writes to that partition key, returning an ItemCollectionSizeLimitExceededException.

Avoiding Hot Partitions with Composite Keys

Because the partition key alone determines physical data placement, choosing an attribute with low cardinality can lead to "hot partitions"—scenarios where a single physical partition handles an uneven amount of traffic.

To ensure optimal performance, the partition key should have high cardinality (many distinct values, such as user_id or device_id), allowing traffic to distribute evenly across all physical partitions. The sort key should then be used to model relationships or time-series data (such as timestamp or order_id) to enable fast, targeted lookups within that specific partition.
