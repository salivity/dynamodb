DynamoDB Stream View Types Explained

Amazon DynamoDB Streams capture a time-ordered sequence of item-level modifications in a DynamoDB table. The exact information included within each change record is governed entirely by the table's StreamViewType setting. This article breaks down how the four distinct stream view types control the data payload written to the stream, how different operations affect record output, and how to select the correct view type for your workload.

Understanding the StreamViewType Attribute

When you enable DynamoDB Streams on a table, you must specify the StreamViewType. This configuration dictates whether a change record includes the primary key attributes only, the entire item before the change, the entire item after the change, or both the before and after states.

The choice of StreamViewType directly affects the payload size written to the stream, downstream Lambda invocation payloads, and overall stream storage consumption.

The Four Stream View Types

DynamoDB provides four options for configuring the content of stream records:

1. KEYS_ONLY

  • Content: Writes only the partition key and sort key (if defined) of the modified item.
  • Payload Size: Minimal.
  • Best Used For: Cache invalidation workflows or notifications where downstream consumers only need to know that an item changed and can query the table directly if more data is required.

2. NEW_IMAGE

  • Content: Writes the complete item as it appears immediately after the write operation, including all of its attributes.
  • Payload Size: Moderate to high, depending on the item's size.
  • Best Used For: Replicating data to external search engines (like OpenSearch), feeding data warehouses, or aggregating data where only the latest state is relevant.

3. OLD_IMAGE

  • Content: Writes the complete item as it appeared before the write operation occurred.
  • Payload Size: Moderate to high, depending on the item's size.
  • Best Used For: Auditing, archival pipelines, or triggering rollback workflows where you need to preserve or analyze the previous state of an item.

4. NEW_AND_OLD_IMAGES

  • Content: Writes both the OldImage (the state before the write) and the NewImage (the state after the write) within the same change record.
  • Payload Size: Largest possible payload among all view types.
  • Best Used For: Event-driven architectures that require delta calculations, such as tracking inventory adjustments, sending notification emails highlighting changed fields, or enforcing state-machine transitions.

Behavior Across Database Operations

The actual data present in a change record also depends on the database event type (INSERT, MODIFY, or REMOVE):

StreamViewType INSERT Event MODIFY Event REMOVE Event
KEYS_ONLY Keys only Keys only Keys only
NEW_IMAGE Full new item Full new item Keys only (no new image exists)
OLD_IMAGE Keys only (no old image exists) Full old item Full old item
NEW_AND_OLD_IMAGES Full new item Both full old and full new items Full old item
  • Note: For INSERT operations under OLD_IMAGE, and for REMOVE operations under NEW_IMAGE, DynamoDB defaults to returning only the key attributes because the corresponding image does not exist.

Choosing the Right View Type

Selecting the proper view type requires balancing downstream data requirements against efficiency:

  • Bandwidth and Processing: Passing complete images when consumers only need keys creates unnecessary network traffic and memory usage in consumer applications like AWS Lambda.
  • Idempotency and Diffing: If consumers must verify what specific attribute triggered an event, NEW_AND_OLD_IMAGES eliminates the need for the consumer to maintain its own state or perform secondary reads against DynamoDB.
  • Cost Efficiency: While DynamoDB Streams read request units are billed separately from table operations, smaller record payloads reduce latency and memory consumption across the entire processing pipeline.
