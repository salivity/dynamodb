How DynamoDB Handles Null and Empty String Values

Amazon DynamoDB enforces specific rules regarding how it stores and indexes empty strings and null values. While older versions of the database imposed strict limitations on empty strings, DynamoDB now natively supports empty string values across non-key and key attributes, alongside an explicit NULL scalar data type. This article details how DynamoDB processes these two data states, highlights key restrictions for primary keys and secondary indexes, and explains the behavior of set and document types.

The Explicit NULL Data Type

DynamoDB provides a dedicated scalar data type for null: NULL. In low-level DynamoDB JSON format, this is represented as:

"AttributeName": { "NULL": true }

A NULL attribute represents an unknown, undefined, or missing state for a non-key attribute. It is distinct from an empty string ("") or an empty collection.

Empty String Support

Historically, DynamoDB rejected empty string values ("") for String (S) attributes, throwing a ValidationException. In May 2020, AWS updated DynamoDB to natively support empty strings in String attributes.

An empty string is stored as a valid String type with a length of zero:

"AttributeName": { "S": "" }

Empty strings are fully supported in non-key attributes, Maps, and Lists.

Rules for Primary Keys (Partition and Sort Keys)

The handling of null and empty values differs significantly when applied to primary key attributes:

  • Empty Strings as Keys: DynamoDB allows empty strings to serve as partition keys and sort keys. However, using an empty string as a partition key is generally considered an anti-pattern because it concentrates records onto a single partition, potentially leading to hot partition throttling.
  • NULL as Keys: DynamoDB strictly prohibits the NULL data type as a partition key or a sort key. Primary keys must be of type String (S), Number (N), or Binary (B). If an item requires a null-like state for a key, the attribute must instead be populated with a predefined placeholder value (such as "UNKNOWN" or "N/A").

Behavior in Global and Local Secondary Indexes

Secondary indexes follow the same data type rules as base table keys:

  • GSI/LSI Keys: Secondary index partition and sort keys can be empty strings, but they cannot use the NULL data type.
  • Sparse Indexing: In DynamoDB, secondary indexes are sparse by default. If an item completely omits the attribute used as an index key, that item is not indexed. Storing an empty string ("") in an index key attribute will cause the item to be indexed. Storing a NULL data type in that attribute will cause the write operation to fail if that attribute acts as an index key.

Complex and Set Types

DynamoDB applies distinct validation rules for collections and complex data structures:

  • Sets (SS, NS, BS): Sets cannot be empty. A String Set (SS) must contain at least one element. While an individual element within a String Set can be an empty string, the set itself cannot exist with zero elements.
  • Lists (L) and Maps (M): Unlike sets, lists and maps can be completely empty (represented as [] and {}). Lists can also contain NULL data types and empty strings as valid elements.
