How DynamoDB Verifies API Request Signatures

Amazon DynamoDB authenticates incoming client requests using the AWS Signature Version 4 (SigV4) cryptographic protocol. When an API client sends a request to DynamoDB, it must include a digital signature created using its AWS secret access keys. DynamoDB authenticates the request by independently reconstructing the same signature on the server side and comparing it to the client's signature. This process validates the caller's identity, protects data integrity in transit, and safeguards against replay attacks before any database operations are executed.

Step 1: Receiving and Parsing the Request

Every HTTP request sent to DynamoDB includes authentication metadata, typically placed inside the Authorization header or passed as query string parameters. Upon receiving a request, DynamoDB extracts several key components:

  • Access Key ID: Identifies the AWS identity making the request.
  • Credential Scope: Specifies the date, target AWS Region, and target service (dynamodb/aws4_request).
  • Signed Headers: A semicolon-separated list of HTTP headers included in the signature calculation.
  • Signature: The 64-character hexadecimal HMAC-SHA256 hash generated by the client.
  • Timestamp: Extracted from the x-amz-date or Date header.

Step 2: Timestamp and Replay Defense

Before performing cryptographic calculations, DynamoDB inspects the timestamp of the request. The service compares the provided date and time against the current server time. If the timestamp differs from the server's clock by more than 15 minutes, DynamoDB drops the request and returns an InvalidSignatureException or RequestTimeTooSkewed error. This mechanism prevents malicious actors from intercepting valid requests and replaying them at a later time.

Step 3: Reconstructing the Canonical Request

To confirm that the payload and headers were not tampered with during transmission, DynamoDB rebuilds the "canonical request" using the raw HTTP request data. The canonical format normalizes the request by assembling:

  1. The HTTP request method (e.g., POST).
  2. The canonical URI (e.g., /).
  3. The canonical query string parameters (sorted alphabetically).
  4. The canonical headers (lowercased, trimmed of excess whitespace, and sorted alphabetically).
  5. The list of signed headers.
  6. The SHA-256 hash of the request body (the JSON payload containing the DynamoDB operation, such as GetItem or PutItem).

DynamoDB then generates a SHA-256 hash of this reconstructed canonical request.

Step 4: Constructing the String to Sign

Next, DynamoDB builds the standardized "string to sign." This string binds the canonical request to a specific context and time. It consists of:

  • The algorithm identifier: AWS4-HMAC-SHA256.
  • The request timestamp from the headers (formatted as YYYYMMDD'T'HHMMSS'Z').
  • The credential scope string (e.g., 20260330/us-east-1/dynamodb/aws4_request).
  • The SHA-256 hash of the canonical request calculated in Step 3.

Step 5: Deriving the Signing Key and Computing the Signature

DynamoDB retrieves the Secret Access Key associated with the client's Access Key ID via AWS Identity and Access Management (IAM).

Using this secret, DynamoDB derives a scoped signing key through a series of sequential HMAC-SHA256 hashing operations:

  1. kDate = HMAC-SHA256("AWS4" + SecretAccessKey, Date)
  2. kRegion = HMAC-SHA256(kDate, Region)
  3. kService = HMAC-SHA256(kRegion, "dynamodb")
  4. kSigning = HMAC-SHA256(kService, "aws4_request")

Once kSigning is derived, DynamoDB computes the final signature by calculating the HMAC-SHA256 hash of the string to sign using kSigning as the key.

Step 6: Constant-Time Comparison and Authorization

DynamoDB compares its locally generated signature against the signature sent in the client’s Authorization header using a constant-time comparison algorithm to prevent timing attacks.

  • If the signatures match, the client is successfully authenticated, and the integrity of the payload is verified. DynamoDB passes the request context to the IAM policy engine to evaluate whether the authenticated entity has permissions to perform the requested operation on the specified table.
  • If the signatures do not match—indicating invalid credentials, an incorrect timestamp, or altered payload data—DynamoDB rejects the request immediately with an HTTP 403 SignatureDoesNotMatch response.
