DynamoDB Streams Event Filtering Explained

Amazon DynamoDB Streams captures item-level modifications in near real-time, but processing every insert, update, and delete can lead to unnecessary consumer invocations and increased operational costs. This article explains how AWS Lambda Event Source Filtering allows you to filter DynamoDB stream records natively before they trigger downstream consumers, eliminating the need to write custom filtering logic inside your application code.

The Feature: AWS Lambda Event Source Filtering

The capability that enables filtering DynamoDB change streams before invoking downstream consumers is AWS Lambda's Event Source Mapping Filter Criteria.

When using Amazon DynamoDB Streams as an event source for AWS Lambda, this feature applies filter criteria directly at the stream poller level. If an incoming record does not match the predefined filter rules, Lambda drops the record immediately without invoking your Lambda function.

How It Works

DynamoDB Streams records all data modifications (INSERT, MODIFY, and REMOVE) and serializes them into JSON payloads containing the event metadata, Keys, OldImage, and NewImage.

Lambda's event filtering evaluates these JSON payloads against up to five filter criteria defined on the event source mapping. Each criteria uses JSON rule syntax to match patterns such as:

  • Event Type: Triggering consumers only on INSERT or REMOVE events, while ignoring MODIFY.
  • Attribute Values: Triggering consumers only when a specific attribute matches a condition (for example, when an order's Status changes to COMPLETED).
  • Numeric and String Comparisons: Matching prefixes, exact values, existence of attributes, or numeric ranges within the DynamoDB stream record.

Because filtering occurs in the event source mapping layer, non-matching records do not count toward your Lambda invocation metrics, concurrency limits, or execution costs.

Benefits of Native Stream Filtering

  • Cost Optimization: You avoid paying for Lambda invocations that immediately exit because the incoming record is not actionable.
  • Reduced Concurrency Pressure: High-throughput tables will not exhaust your downstream Lambda concurrency limits with irrelevant events.
  • Simplified Consumer Code: Developers no longer need boilerplate logic at the start of a function to inspect records and exit early.
  • Lower Operational Latency: Downstream systems only process relevant messages, reducing execution queues and pipeline backlog.

Implementation Example

You can configure filter criteria using the AWS Management Console, AWS CLI, AWS CloudFormation, or AWS CDK.

A sample filter pattern to process only INSERT events where a status attribute equals PENDING looks like this:

{
  "Filters": [
    {
      "Pattern": "{ \"eventName\": [\"INSERT\"], \"dynamodb\": { \"NewImage\": { \"Status\": { \"S\": [\"PENDING\"] } } } }"
    }
  ]
}

By placing this filtering rule on the DynamoDB stream mapping, your downstream Lambda function executes only when relevant data changes occur, streamlining data processing workflows natively.
