Why Querying DynamoDB LSI Uses Base Table Capacity

Querying a Local Secondary Index (LSI) in Amazon DynamoDB consumes read capacity from the base table because LSIs do not have their own allocated throughput and share the same physical storage partitions as the base table. This article breaks down the architectural reasons behind this shared throughput model, explains how DynamoDB manages LSI read operations, and details why fetching non-projected attributes introduces additional capacity costs from the base table.

Shared Capacity Architecture

Unlike Global Secondary Indexes (GSIs), which maintain independent read and write capacity settings, a Local Secondary Index relies entirely on the provisioned or on-demand capacity of its base table. DynamoDB does not allow you to configure separate Read Capacity Units (RCUs) or Write Capacity Units (WCUs) for an LSI. Every read, write, update, or delete operation that involves an LSI draws directly from the base table’s throughput pool.

Partition Colocation

An LSI must use the same partition key as the base table, differing only by sort key. Because both the base table items and the index entries share the exact same partition key, DynamoDB stores them together in the same physical storage partition, referred to as an item collection. Since the physical infrastructure serving requests to the LSI is the same infrastructure serving the base table, DynamoDB meters the operations against the single shared capacity pool assigned to that partition.

The Cost of Projected vs. Non-Projected Attributes

When querying an LSI, the amount of base table capacity consumed depends on the attributes requested and the index's projection type:

  • Projected Attributes: If the query requests only attributes that are projected into the LSI (via KEYS_ONLY, INCLUDE, or ALL), DynamoDB reads the data directly from the index. The base table still incurs the RCU cost, but the cost is calculated strictly based on the size of the index entry (rounded up to the nearest 4 KB).
  • Non-Projected Attributes (Base Table Fetch): If a query requests attributes that were not projected into the LSI, DynamoDB must perform an automatic lookup back to the base table to fetch the missing data. This results in two reads: one against the LSI to find the matching keys, and a second read against the base table to retrieve the full item. This operation significantly increases base table RCU consumption and adds latency to the query.

Read Consistency Impact

LSIs support both eventually consistent reads and strongly consistent reads, unlike GSIs which only support eventually consistent reads. If you request a strongly consistent read when querying an LSI, DynamoDB consumes one full RCU per 4 KB of data read directly from the base table's capacity allocation. Eventually consistent reads consume half that amount (0.5 RCU per 4 KB), but both pull directly from the base table's limits.
