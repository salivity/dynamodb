DynamoDB Item Creation During Write Auto Scaling

When Amazon DynamoDB auto scaling actively adjusts provisioned write capacity, item creation requests are evaluated strictly against the table's currently available capacity rather than the pending target capacity. Because DynamoDB auto scaling uses CloudWatch alarms and Application Auto Scaling to adjust limits asynchronously, changes are not instantaneous. If item creation rates surge while scaling is underway, DynamoDB absorbs the excess traffic using burst capacity; if burst capacity is depleted, it rejects incoming write requests with a ProvisionedThroughputExceededException, requiring client-side retry mechanisms to manage the load until the new capacity is active.

The Asynchronous Nature of Auto Scaling

DynamoDB Auto Scaling does not instantly increase Write Capacity Units (WCUs). When write traffic spikes, the following sequence occurs:

  1. Metric Aggregation: CloudWatch collects consumed capacity metrics over consecutive evaluation periods (typically taking several minutes).
  2. Alarm Trigger: Once sustained high utilization breaches the target threshold, CloudWatch triggers an Application Auto Scaling policy.
  3. Capacity Update: DynamoDB asynchronously allocates additional partitions or provisioned throughput to the table.

During this transition period—which can take several minutes—the table continues operating under its existing provisioned WCU limit. DynamoDB does not maintain an internal, server-side queue for writes awaiting scale-up completion.

The Role of Burst Capacity

To handle short-term spikes during the auto scaling lag, DynamoDB utilizes built-in burst capacity. The service automatically stores unused capacity from quiet periods for up to 300 seconds (5 minutes).

When you issue write operations like PutItem or BatchWriteItem that exceed the current provisioned WCUs, DynamoDB automatically consumes this burst reserve. If the scale-up event finishes before the burst capacity is exhausted, all item creation requests succeed seamlessly with no observable latency impact or errors.

Request Throttling

If write demand exceeds the provisioned WCUs and completely drains the 5-minute burst pool before auto scaling finishes provisioning higher limits, DynamoDB begins throttling item creation.

  • The service immediately returns a ProvisionedThroughputExceededException (HTTP status code 400).
  • Throttling occurs on a per-request basis and does not corrupt or partially write single-item transactions.
  • The table remains fully available; it simply rejects the volume of requests exceeding the current throughput boundary.

Handling Writes on the Client Side

Because DynamoDB rejects excess writes rather than holding them, the client application is responsible for managing the traffic during active scaling adjustments:

  • SDK Exponential Backoff: The standard AWS SDKs include built-in retry logic that uses exponential backoff and jitter. When an item creation request encounters a ProvisionedThroughputExceededException, the SDK automatically pauses and retries the write, often allowing time for burst capacity to replenish or auto scaling to finish.
  • Dead-Letter Queues (DLQs) and Buffers: For high-throughput ingestion pipelines, decoupling write operations using an intermediate buffer (such as Amazon SQS or Amazon Kinesis) ensures that unwritten items are retained and processed once DynamoDB finishes increasing provisioned write capacity.
