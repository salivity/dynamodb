Representing Foreign Keys in DynamoDB Single-Table Design

Transitioning from a relational database to Amazon DynamoDB requires fundamentally rethinking how relationships are modeled. Because DynamoDB does not support native declarative foreign key constraints or SQL joins, relationships are handled strictly through access-pattern modeling. This guide explains how foreign keys are translated into single-table design using item collections, Global Secondary Indexes (GSIs), adjacency lists, and selective denormalization.

The Conceptual Shift: References Without Constraints

In a relational schema, a foreign key enforces referential integrity at the database layer. In DynamoDB, referential integrity is moved entirely to the application layer. Foreign keys no longer function as automated guardrails; instead, they serve as addressing mechanisms to group related data physically together or to index items across different partitions.

1. One-to-Many Relationships: Item Collections

The primary way to represent a parent-child relationship (such as a customer having multiple orders) is through an item collection sharing the same Partition Key (PK), differentiated by the Sort Key (SK).

  • Partition Key (PK): Contains the parent entity's unique identifier (e.g., CUSTOMER#123).
  • Sort Key (SK): Contains the entity type and the child identifier (e.g., METADATA for the customer record, and ORDER#987 for an order).

In this pattern, the foreign key (CUSTOMER#123) is embedded directly into the partition key of the child item. This groups the parent and all related child entities on the same physical storage partition, allowing a single Query operation to retrieve the parent and all its children simultaneously.

2. Secondary Lookup Patterns: Global Secondary Indexes (GSIs)

When an item's primary key must remain unique to itself (e.g., PK: ORDER#987, SK: ORDER#987), the foreign key is stored as a distinct item attribute (e.g., CustomerId: CUSTOMER#123).

To query items by their foreign key:

  1. Store the foreign key attribute in the item.
  2. Create a Global Secondary Index (GSI) where the foreign key attribute acts as the GSI's partition key (GSI1PK = CUSTOMER#123).
  3. Set the GSI sort key (GSI1SK) to the child's identifier or a timestamp for sorting.

This mirrors a traditional relational foreign key index, allowing the application to look up all items referencing a specific foreign entity.

3. Many-to-Many Relationships: Adjacency Lists and Inverted Indexes

Many-to-many relationships (e.g., users and roles, or courses and students) are represented using an adjacency list pattern.

  1. Target Item Representation: Store two types of items—the main entities and the relationship (edge) items.
  2. Inverted Index: Design a GSI that swaps the PK and SK:
    • Base Table: PK: USER#123, SK: ROLE#Admin
    • GSI1: GSI1PK: ROLE#Admin, GSI1SK: USER#123

Querying the base table returns all roles assigned to a user, while querying GSI1 returns all users assigned to a specific role.

4. Denormalization and Duplication

In relational models, foreign keys avoid data duplication by pointing to a single source of truth. In DynamoDB single-table design, denormalization is often preferred to satisfy read patterns in a single request.

Attributes from the parent entity that rarely change (such as CustomerName) can be copied directly into the child order items. While this requires the application to handle distributed updates if the parent data changes, it removes the need to query the foreign key target entirely for standard read operations.

Enforcing Referential Integrity

Because DynamoDB will not prevent orphan records or validate foreign key existence upon insert:

  • Transactions: Use TransactWriteItems to atomically create a child item and verify or update the parent record simultaneously.
  • Cascading Operations: Cascading deletes must be implemented programmatically using transactions or asynchronous event-driven pipelines (e.g., DynamoDB Streams triggering an AWS Lambda function to delete associated records).
