DynamoDB Authentication with AWS Signature Version 4

Amazon DynamoDB uses AWS Signature Version 4 (SigV4) to authenticate inbound API requests, verify sender identity, and guarantee data integrity during transit. This authentication framework relies on keyed-hash message authentication codes (HMAC-SHA256) and AWS Identity and Access Management (IAM) credentials to cryptographically sign HTTP requests. By requiring every request to contain a verifiable cryptographic signature, DynamoDB ensures that the request originates from a known identity, has not been tampered with by an intermediary, and cannot be captured and replayed maliciously.

The Components of a SigV4 Request

When a client sends an API call to DynamoDB (such as PutItem or Query), the request must include authentication data, which is typically transmitted in the HTTP Authorization header. This header contains four key elements:

  • Algorithm: Identifies the hashing algorithm used, standardly AWS4-HMAC-SHA256.
  • Credential Scope: A formatted string that binds the request to a specific date, AWS region, and target service (e.g., 20231025/us-east-1/dynamodb/aws4_request), along with the caller's AWS Access Key ID.
  • Signed Headers: A semicolon-separated list of HTTP headers included in the signature calculation.
  • Signature: The calculated hexadecimal HMAC-SHA256 digest that authenticates the request.

The Signing Process

To generate the signature, the client completes four sequential steps:

  1. Create a Canonical Request: The client standardizes the incoming HTTP request format. This includes the HTTP method (e.g., POST), the canonical URI, query parameters, canonicalized headers, signed header names, and a SHA-256 hash of the JSON payload body. Standardizing ensures that both the client and DynamoDB evaluate the exact same text string.

  2. Create the String to Sign: The client concatenates the algorithm name, the request timestamp (from the x-amz-date header), the credential scope, and the SHA-256 hash of the canonical request created in step one.

  3. Calculate the Signing Key: Rather than using the raw AWS Secret Access Key directly, the client derives a scoped signing key through a series of chained HMAC-SHA256 operations using the secret key, current date, AWS region, and the service name (dynamodb). This scoping limits exposure if a transient signing key is compromised.

  4. Calculate the Signature: The client computes an HMAC-SHA256 hash of the "string to sign" using the derived signing key. The resulting hash is converted to a lowercase hexadecimal string and appended to the request in the Authorization header.

Server-Side Verification by DynamoDB

When DynamoDB receives the HTTP request, it validates authentication before evaluating access control policies:

  • Replay Attack Check: DynamoDB checks the timestamp in the x-amz-date or Date header. If the timestamp deviates by more than 15 minutes from the server's clock, the request is rejected immediately.
  • Signature Recreation: DynamoDB uses the Access Key ID from the credential scope to look up the caller's secret key from the internal IAM directory. It reconstructs the canonical request and the string to sign using the exact headers and payload received over the wire. It then derives the signing key and computes its own version of the signature.
  • Comparison: DynamoDB compares the signature it calculated with the signature provided in the client's Authorization header. If the values match, identity and payload integrity are confirmed. Any discrepancy—caused by an invalid credential, network payload tampering, or an expired session token—results in an InvalidSignatureException or AccessDeniedException.

SDK Automation

While SigV4 can be implemented manually, standard deployments rely on official AWS Software Development Kits (SDKs) or the AWS Command Line Interface (CLI). These tools automatically retrieve credentials (including temporary credentials from IAM roles or AWS STS), structure canonical requests, calculate the required HMAC hashes, and append the Authorization and date headers seamlessly in the background for every DynamoDB call.
