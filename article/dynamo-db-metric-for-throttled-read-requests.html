DynamoDB Metric for Throttled Read Requests

This article identifies the specific Amazon CloudWatch metric used to track throttled read requests in Amazon DynamoDB, explains how it functions, and outlines strategies to resolve and prevent read throttling on your tables.

The Metric: ReadThrottleEvents

The primary CloudWatch metric that tracks the number of throttled read requests in DynamoDB is ReadThrottleEvents.

When an application attempts to perform a read operation (such as GetItem, Query, Scan, or BatchGetItem) that exceeds the provisioned Read Capacity Units (RCUs) allocated to a DynamoDB table or Global Secondary Index (GSI), DynamoDB throttles the request and emits data points to the ReadThrottleEvents metric.

Key Characteristics of ReadThrottleEvents

  • Unit: Count.
  • Scope: Available at the table level and the Global Secondary Index (GSI) level.
  • Statistic to monitor: The SampleCount or Sum statistic indicates the total number of throttled read requests within a given time period.
  • Behavior: A non-zero value indicates that requests are exceeding the allocated read throughput or that requests are concentrated on a specific partition ("hot partition"), exceeding partition-level limits (typically 3,000 RCUs per partition).

ReadThrottleEvents vs. ThrottledRequests

While ReadThrottleEvents specifically isolates read operations, DynamoDB also provides the ThrottledRequests metric.

  • ReadThrottleEvents: Measures events where read requests specifically exceeded available read throughput.
  • ThrottledRequests: An aggregate metric that counts all requests rejected with a ProvisionedThroughputExceededException, combining both read and write operations.

For targeted troubleshooting of read bottlenecks, ReadThrottleEvents is the more precise metric to analyze.

How to Prevent and Mitigate Throttled Read Requests

If ReadThrottleEvents is firing, implement one or more of the following solutions:

  1. Switch to On-Demand Capacity Mode: If traffic patterns are unpredictable or experience sudden spikes, on-demand capacity automatically scales read throughput to match application demand.
  2. Increase Provisioned RCUs or Enable Auto Scaling: If using provisioned capacity, raise the allocated RCUs or configure DynamoDB Auto Scaling with target utilization tracking to automatically adjust throughput.
  3. Implement Caching with DynamoDB Accelerator (DAX): Place DAX or an in-memory cache like Amazon ElastiCache in front of the table to serve repeated reads directly from memory, reducing read pressure on the table.
  4. Resolve Hot Partitions: Redesign the partition key schema to distribute read access evenly across partitions, ensuring individual partition limits are not exceeded.
  5. Use Exponential Backoff and Jitter: Configure the AWS SDK's built-in retry mechanism to gracefully handle intermittent throttling without failing the client-side operation.
