DynamoDB LSIs and Item Collection Size Limits

When designing an Amazon DynamoDB schema, creating a Local Secondary Index (LSI) imposes a strict 10 GB size limit on any single item collection. An item collection consists of all the items in a table and its LSIs that share the same partition key value. This article explores how this 10 GB ceiling affects data modeling, the risks of hitting write rejections, and strategic alternatives such as Global Secondary Indexes (GSIs).

Understanding the 10 GB Item Collection Limit

In a standard DynamoDB table with only Global Secondary Indexes or no secondary indexes at all, there is no limit to the amount of data that can share the same partition key value. However, the moment an LSI is added during table creation, DynamoDB enforces an item collection limit: the sum of the base table items and all corresponding LSI items with identical partition key values cannot exceed 10 GB.

This 10 GB ceiling is a hard quota that AWS does not increase. It includes the raw data, primary keys, attribute names, and indexed attributes across both the base table and every LSI defined on the table.

Operational Impact: Write Rejections

When an item collection reaches the 10 GB boundary, DynamoDB rejects any subsequent PutItem, BatchWriteItem, or UpdateItem operations that attempt to add new items or increase the size of existing items within that collection. These rejected calls trigger an ItemCollectionSizeLimitExceededException.

Read operations, deletes, and updates that decrease the item size continue to work normally. However, for write-heavy applications, hitting this limit effectively freezes new data ingestion for that specific partition key, leading to application downtime or data loss if not handled appropriately.

Schema Design Implications

The 10 GB limitation fundamentally dictates how partition keys must be structured:

  • Unbounded Growth Anti-Pattern: Modeling unbounded datasets with an LSI is an anti-pattern. Workloads like user activity logs, IoT sensor feeds, or audit trails—where items accumulate endlessly under an entity ID—will eventually breach the 10 GB threshold.
  • High Cardinality Requirements: Partition keys must have sufficiently high cardinality to guarantee that data distribution remains balanced. Coarse-grained partition keys (such as grouping by Status or a broad Category) concentrate too much data into a single collection, dramatically accelerating the time it takes to hit the limit.
  • Proactive Lifecycle Management: If LSIs are required for a dataset with steady writes, the schema must incorporate data purging strategies, such as Time to Live (TTL) or scheduled archiving workflows, to systematically purge older items and keep the collection below 10 GB.

LSIs vs. GSIs in Architecture Decisions

The primary historical advantage of an LSI is support for strongly consistent reads, which GSIs did not traditionally offer. However, this consistency comes at the cost of the 10 GB boundary and the inability to add or delete LSIs after table creation.

Global Secondary Indexes do not have item collection size limits. A single partition key can scale to terabytes of data across base tables and GSIs without size-related write rejections. Unless strong read consistency on secondary attributes is a non-negotiable architectural requirement, modern DynamoDB design favors GSIs to avoid the operational risk and scaling ceiling imposed by item collections.
