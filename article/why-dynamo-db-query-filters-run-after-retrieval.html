Why DynamoDB Query Filters Run After Retrieval

In Amazon DynamoDB, query filter expressions run after items are fetched from storage rather than during the initial lookup phase. This article explains the architectural and performance reasons behind this design, how DynamoDB uses partition routing to locate data, the impact on Read Capacity Units (RCUs) and payload limits, and how developers should properly design schemas to avoid common performance pitfalls.

The Partitioned Storage Engine

DynamoDB achieves predictable, single-digit millisecond latency at any scale by relying on horizontal partitioning. Data is distributed across distinct storage partitions governed by a partition key (hash key).

When a query is executed:

  1. The partition key is hashed to locate the exact storage node hosting the data.
  2. The storage engine reads the items that match the partition key and optional sort key (range key) conditions directly from disk or memory.
  3. Because data on a partition is strictly organized and sorted by the primary key schema, DynamoDB can read this contiguous block of data with extreme efficiency.

Attributes outside the primary key are not indexed in this primary B-tree structure. The storage engine has no direct index path to search by arbitrary attributes without inspecting every item.

Why Filters Are Evaluated Post-Fetch

DynamoDB decouples storage retrieval from result filtering to maintain guaranteed execution time. The process works in two distinct stages:

  1. Storage Read: The database engine scans the primary index matching the partition key and sort key expression up to a maximum read boundary of 1 MB of data.
  2. Filter Evaluation: The retrieved items are passed to an in-memory compute layer. This layer evaluates the FilterExpression, discards any items that do not evaluate to true, and packages the remaining items into the response payload.

Evaluating filter expressions directly on the storage layer without secondary indexes would require arbitrary disk scanning. This would introduce non-deterministic I/O operations, breaking DynamoDB's core promise of predictable response times.

Implications for Cost and Limits

Because filtering occurs strictly after reading, developers must account for two major operational constraints:

  • Read Capacity Units (RCUs): DynamoDB calculates consumed RCUs based on the total size of items read from the storage layer, not the size of the filtered results returned to the client. If a query reads 100 KB of data and the filter expression discards 95 KB, the user is still billed for reading 100 KB.
  • The 1 MB Result Limit: A single Query operation can evaluate a maximum of 1 MB of data. If a query matches 1 MB of data on the primary key, but the filter expression eliminates every single item, DynamoDB returns an empty list along with a LastEvaluatedKey. The client must continue paginating to process the next set of data.

Filters vs. Indexes

A FilterExpression is designed primarily to reduce network bandwidth and client-side processing, not database read consumption. It prevents sending unnecessary data over the wire to the application layer.

To minimize consumed capacity and bypass the post-fetch filtering behavior, attributes must be modeled into the primary key schema or indexed using Global Secondary Indexes (GSIs) or Local Secondary Indexes (LSIs). By indexing the target attributes, DynamoDB can use its storage-level B-tree routing to read only the qualifying items, eliminating the need to read and discard unindexed records.
