DynamoDB Transactional Write Throughput Costs

Amazon DynamoDB calculates throughput costs for transactional write requests by consuming double the standard write capacity units required for normal write operations. This article explains how DynamoDB measures item sizes, applies the 2x multiplier for ACID transaction guarantees, accounts for both provisioned and on-demand capacity modes, and calculates costs for conditional checks included in write transactions.

The Standard vs. Transactional Multiplier

Standard write operations (PutItem, UpdateItem, and DeleteItem) consume one Write Capacity Unit (WCU) in provisioned mode, or one Write Request Unit (WRU) in on-demand mode, for every 1 KB of data written per second.

Because transactional writes (TransactWriteItems) provide atomicity, consistency, isolation, and durability (ACID) across multiple items, DynamoDB performs a two-phase consensus mechanism under the hood. To account for the overhead of preparing and committing these transactions, DynamoDB charges 2 write units for every 1 KB of data written per item.

How Item Sizes Are Calculated

Throughput for transactional writes is calculated on an item-by-item basis rather than aggregated across the entire transaction:

  1. Calculate Item Size: The total size of the item is determined by adding the attribute name lengths and the attribute value sizes.
  2. Round Up to the Nearest 1 KB: Each item in the transaction is rounded up to the next whole kilobyte increment before applying throughput math.
  3. Apply the 2x Multiplier: The rounded kilobyte size is multiplied by 2 to determine the total WCUs or WRUs consumed by that specific item.

For example, if a transaction modifies an item of 500 bytes, the size rounds up to 1 KB, requiring 2 WCUs/WRUs. If an item is 2.2 KB, it rounds up to 3 KB, requiring 6 WCUs/WRUs (3 KB × 2).

Multi-Item Transactions

A TransactWriteItems call can contain up to 100 actions and operate on up to 4 MB of data in total. To compute the total throughput cost of the transaction, compute the cost for each individual item and sum them together.

Consider a transaction containing three actions:

  • Item A: 800 bytes → Rounds to 1 KB → 2 write units
  • Item B: 1.5 KB → Rounds to 2 KB → 4 write units
  • Item C: 3.1 KB → Rounds to 4 KB → 8 write units

Total Throughput Consumed: 2 + 4 + 8 = 14 WCUs or WRUs.

Condition Checks Within Write Transactions

The TransactWriteItems API also allows ConditionCheck operations, where an item's state is validated without writing new data to it.

Condition checks within a write transaction consume transactional read capacity rather than write capacity. A condition check consumes 2 Read Capacity Units (RCUs) in provisioned mode, or 2 Read Request Units (RRUs) in on-demand mode, for each 4 KB increment of the evaluated item.

Billing Across Capacity Modes

  • On-Demand Mode: You are charged per transactional WRU consumed. Since a transactional write requires 2 WRUs per 1 KB, each kilobyte costs twice the standard on-demand write rate.
  • Provisioned Mode: Your table must have sufficient allocated WCUs to absorb the burst. If a transaction requires 20 WCUs and your table only has 10 unreserved WCUs available in that second, the entire transaction will fail with a TransactionCanceledException due to throttling, unless managed via DynamoDB burst capacity or client-side retries.
