Amazon DynamoDB Global Secondary Index Limits

Amazon DynamoDB relies on Global Secondary Indexes (GSIs) to enable flexible querying across non-primary key attributes, but AWS imposes specific architectural boundaries on their usage. This article outlines the default limits on the number of GSIs allowed per table, the process and viability of requesting quota increases, and the operational limitations that arise when scaling the number of indexes on a single table.

The Per-Table GSI Limit

By default, Amazon DynamoDB allows a maximum of 20 Global Secondary Indexes per table.

This limit is a default soft quota. If your application architecture requires more than 20 GSIs on a single base table, you can request a quota increase through the AWS Service Quotas console or AWS Support. AWS evaluates quota increase requests based on use case, account history, and resource availability.

Key Schema and Attribute Restrictions

Each GSI on a table comes with specific configuration rules that limit how it can be structured:

  • Key Schema: Every GSI must have a partition key (HASH). A sort key (RANGE) is optional. The index key attributes can be of type String, Number, or Binary.
  • Projected Attributes: A GSI must use one of three projection types:
    • KEYS_ONLY: Includes only the index partition key, index sort key, and the base table’s primary key.
    • INCLUDE: Includes the keys plus a specified list of non-key attributes.
    • ALL: Projects all attributes from the base table into the index.
  • Size Limits: An individual item in a GSI cannot exceed the standard DynamoDB item size limit of 400 KB, including the attribute names and values projected into the index.

Operational and Performance Constraints

While you can attach up to 20 or more GSIs to a single table, scaling the number of indexes introduces several operational limitations:

  • Sequential Index Creation: Although DynamoDB allows you to add or delete GSIs on existing tables without downtime, you can only create or delete one GSI at a time per table. You must wait for the index to reach the ACTIVE status before initiating another creation or deletion.
  • Write Amplification: Writing or updating an item in the base table automatically updates every GSI that includes the modified attributes. Having many GSIs multiplies the number of write capacity units (WCUs) consumed per base table write, leading to significantly higher costs.
  • GSI Throttling Impacts the Base Table: When using provisioned capacity, if any GSI lacks sufficient write throughput to process incoming updates, it becomes throttled. This backpressure can cause write operations on the base table itself to be rejected or throttled, regardless of the base table's provisioned capacity. On-demand capacity mitigates this risk by scaling automatically, but it can quickly drive up billing if write traffic spikes.
  • Storage Overhead: Every GSI maintains its own copy of the projected data. Adding multiple GSIs with the ALL projection type will multiply your storage usage by the number of indexes created.
