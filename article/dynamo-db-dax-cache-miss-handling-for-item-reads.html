DynamoDB DAX Cache Miss Handling for Item Reads

This article explains how Amazon DynamoDB Accelerator (DAX) manages cache misses during item read operations. When applications issue read requests like GetItem or BatchGetItem through DAX, the accelerator uses an inline, read-through caching mechanism to fetch, populate, and return data seamlessly whenever a requested item is not already present in memory.

The Read-Through Process for GetItem

DAX operates as an inline cache sitting directly between your application and the DynamoDB tables. When an application performs a GetItem operation, DAX processes the request in the following sequence during a cache miss:

  1. Cache Lookup: DAX evaluates its in-memory Item Cache using the partition key and sort key (if applicable) provided in the read request. It detects that the item is absent.
  2. Read-Through to DynamoDB: Rather than returning an empty response or an error to the client, DAX immediately routes the request to the underlying DynamoDB table on behalf of the application.
  3. Fetching the Item: DynamoDB fulfills the read request and sends the item data back to the DAX cluster.
  4. Cache Population: Before returning the item to the client, DAX writes the retrieved item into its Item Cache.
  5. Response Delivery: DAX sends the item back to the calling application.

Any subsequent GetItem requests for the same key will register as a cache hit, serving the data directly from memory with microsecond latency until the item expires or is evicted.

Handling BatchGetItem Requests

When an application issues a BatchGetItem call, the request may contain a mix of cached and non-cached items:

  • Partial Hits: DAX retrieves all matching items already present in the Item Cache.
  • Miss Delegation: DAX compiles the remaining keys that were not found in the cache and submits a consolidated read request directly to DynamoDB.
  • Reassembly and Caching: The items returned by DynamoDB are added to the DAX Item Cache, merged with the items retrieved from the initial cache hit, and returned to the application as a single response payload.

Cache Eviction and Expiration

Items loaded into DAX following a cache miss are governed by two retention controls:

  • Time-to-Live (TTL): When creating or configuring a DAX cluster, an Item Cache TTL is specified. Items remain in the cache until this TTL elapses, at which point DAX treats future requests for that key as a miss and re-fetches the item from DynamoDB.
  • Least Recently Used (LRU) Eviction: If the DAX node runs out of memory before an item's TTL expires, DAX evicts older, less-frequently accessed items using an LRU algorithm to make room for newly fetched items.

Strongly Consistent Reads

DAX only caches eventually consistent reads. If an application requests a strongly consistent read (ConsistentRead = true), DAX does not check the Item Cache, nor does it write the fetched item into the cache. Instead, it passes the request directly through to DynamoDB, retrieves the authoritative item, and returns it to the client without modifying the cache state.
