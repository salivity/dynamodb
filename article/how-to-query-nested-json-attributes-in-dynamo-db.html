How to Query Nested JSON Attributes in DynamoDB

Amazon DynamoDB enables developers to store deeply nested JSON data using Map and List data types. To query, filter, or retrieve these nested attributes directly without reshaping your data model, DynamoDB provides a feature called document paths. This article explains what document paths are, how they function within DynamoDB expressions, and how to utilize them alongside PartiQL for direct access to nested JSON elements.

Understanding Document Paths

Document paths represent the native DynamoDB syntax used to traverse and reference attributes inside nested Maps and Lists. Instead of downloading an entire nested JSON document to parse it in your application code, you can use document paths inside DynamoDB expressions to pinpoint specific nested values directly at the database layer.

Document paths use two primary syntax conventions:

  • Dot notation (.) for Maps: Accesses child attributes inside a nested Map (for example, Address.City).
  • Bracket notation ([n]) for Lists: Accesses specific elements within an array by their zero-based index (for example, PhoneNumbers[0]).

Using Document Paths in Expressions

Document paths can be integrated into several DynamoDB expression types to evaluate or extract nested values:

  1. Projection Expressions: Retrieve only the specific nested fields you need, reducing network payload and read throughput costs.
    • Example: Specifying ProjectionExpression="UserProfile.Settings.Theme" returns only the Theme value from the nested map.
  2. Filter Expressions: Filter Query or Scan results based on the contents of nested JSON fields.
    • Example: Setting FilterExpression="Orders[0].Status = :status" checks the status of the first order in an array.
  3. Update Expressions: Modify or add a single nested value without overwriting the parent object.
    • Example: Using SET UserProfile.LastLogin = :timestamp updates only the LastLogin key within the UserProfile map.

Handling Reserved Words with Expression Attribute Names

DynamoDB reserves certain keywords (such as Date, Status, or Year). If your nested keys use reserved words or contain special characters such as hyphens or dots, you must alias them using Expression Attribute Names (prefixed with #).

For example, to navigate to a nested attribute named Status inside Metadata:

  • Path reference: #meta.#stat
  • Mapping definition: ExpressionAttributeNames={"#meta": "Metadata", "#stat": "Status"}

Querying with PartiQL

DynamoDB also supports PartiQL, a SQL-compatible query language that fully supports nested document paths. You can execute standard SQL statements directly against nested JSON structures using standard dot notation:

SELECT Address.City 
FROM Customers 
WHERE Address.PostalCode = '98101'

Key Limitations to Consider

While document paths allow direct referencing and filtering of nested JSON in FilterExpression, ProjectionExpression, and UpdateExpression, you cannot use document paths directly as Partition Keys or Sort Keys in a KeyConditionExpression. To query nested attributes efficiently with indexed lookups, you must elevate the nested field to a top-level attribute or copy its value into a Global Secondary Index (GSI).
