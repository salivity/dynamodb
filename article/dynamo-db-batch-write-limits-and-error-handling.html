DynamoDB Batch Write Limits and Error Handling

Amazon DynamoDB processes bulk operations using the BatchWriteItem API, but the outcome of a batch request depends entirely on the type of limit an individual write exceeds. When individual writes violate hard validation constraints—such as the maximum item size limit—DynamoDB rejects the entire batch immediately without processing any items. Conversely, if an individual write fails due to transient or capacity-related thresholds, such as provisioned throughput limits, DynamoDB processes the valid items and isolates the throttled writes into a response payload for subsequent retries.

Hard Limit Violations: Total Batch Rejection

DynamoDB enforces strict operational boundaries on every individual write operation inside a BatchWriteItem call. The most prominent constraint is the individual item size limit, which cannot exceed 400 KB (including attribute names and values).

When an individual item within a batch exceeds this 400 KB limit, DynamoDB does not partially execute the batch. Instead, the service fails the request at the validation stage:

  • Exception Type: The API immediately returns a client error: ValidationException.
  • Atomicity of Validation: Pre-execution validation applies to the entire HTTP payload. If even one item out of a 25-item batch violates schema requirements, key definitions, or size limits, zero items are written to the table.
  • HTTP Status Code: A 400 Bad Request is returned to the client.

The same complete failure occurs if the collective size of all operations in the batch exceeds the 16 MB payload limit, or if the request contains more than 25 individual PutItem or DeleteItem actions.

Dynamic Limit Violations: Partial Processing via UnprocessedItems

A different mechanism governs situations where individual writes exceed operational or infrastructure capacity rather than static size limits. This happens when individual partition throughput is saturated or table-level Write Capacity Units (WCUs) are exhausted:

  1. Partial Success: DynamoDB processes as many individual items in the batch as capacity allows.
  2. Identification of Failures: Items that exceed provisioned throughput or encounter high partition contention are not discarded. Instead, DynamoDB leaves them unprocessed.
  3. The UnprocessedItems Response: The response payload returns an HTTP 200 OK along with an UnprocessedItems map containing the exact operations that could not be completed.
  4. No Aggregate Failure: The overall call does not throw a ProvisionedThroughputExceededException unless every single item in the batch failed to process.

Recommended Handling Strategy

To successfully manage batches containing operations that risk exceeding individual thresholds:

  • Client-Side Validation: Calculate item byte sizes before calling BatchWriteItem. If any item exceeds 400 KB, compress the payload, split the data across related records, or store the object in Amazon S3 and store only the metadata reference in DynamoDB.
  • Exponential Backoff: When handling dynamic throughput rejections, inspect the UnprocessedItems field in the response. Resubmit only those specific items in a subsequent request using an exponential backoff algorithm with jitter to prevent persistent partition throttling.
