DynamoDB BatchWriteItem Payload Size Limits

Amazon DynamoDB limits the total payload size of a BatchWriteItem operation to ensure predictable latency, throughput, and resource allocation across its distributed architecture. A single BatchWriteItem call can contain up to 25 individual PutItem or DeleteItem requests, but the aggregate size of all operations combined cannot exceed 16 MB. This article details the exact technical mechanisms DynamoDB uses to evaluate, enforce, and reject requests that breach these payload boundaries.

The 16 MB Total Size Limit

The primary boundary for BatchWriteItem is a strict 16 MB total payload ceiling. In addition to this aggregate limit, DynamoDB enforces an individual item limit of 400 KB. While 25 items at the maximum 400 KB size would only total approximately 10 MB—well below the 16 MB threshold—the aggregate cap exists to protect against overhead anomalies, serialized wire formats, and multi-table batches.

How DynamoDB Calculates the Payload Size

When DynamoDB evaluates a BatchWriteItem request, it measures the size of the entire payload based on the attributes of each item:

  • Attribute Names: The length of the attribute name in UTF-8 bytes.
  • Attribute Values: The raw byte size of the attribute value depending on data type (e.g., strings are measured in UTF-8 bytes, binary data in raw bytes, numbers as variable-length representations up to 38 digits).
  • Structural Overhead: The structural framing overhead for collections like Maps and Lists, including element types and nesting levels.

For DeleteItem actions, the size calculation includes the primary key attributes (partition key and sort key if present) identifying the item to remove. For PutItem actions, every attribute included in the new or replaced item is factored into the total.

Pre-Execution Validation and Error Handling

DynamoDB enforces the payload size limits synchronously at the request parsing layer before any storage-node execution takes place:

  1. Immediate Rejection: If the incoming JSON payload exceeds 16 MB, or if the total number of operations exceeds 25, DynamoDB immediately halts processing.
  2. Atomic Failure: Unlike operational write failures—which return an UnprocessedItems map containing items that failed due to throttling—payload size violations reject the entire batch atomically. None of the operations in the batch are executed.
  3. ValidationException: The service returns an HTTP 400 Bad Request with a ValidationException error code, notifying the client that the batch size criteria were violated.

Client-Side Management Best Practices

Because DynamoDB rejects the entire batch upon limit violation, client applications must manage batch sizes proactively. Applications should track both the item count (max 25) and the cumulative byte size of the items being prepared. When appending items to a batch queue, the client should calculate the serialized size of each item and flush the batch whenever either the 25-item count or a safe byte threshold (such as 10 MB to 14 MB to account for protocol overhead) is reached.
