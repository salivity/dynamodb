How DynamoDB Calculates Nested Attribute Sizes

Amazon DynamoDB enforces a strict maximum item size limit of 400 KB, which includes both attribute names and their corresponding values. For complex schemas containing nested document types, DynamoDB uses a deterministic formula to calculate the byte consumption of lists and maps, including structural overhead for each container and element. Understanding this calculation is essential for optimizing storage, avoiding item size exceptions, and controlling consumed Read and Write Capacity Units.

Basic Data Type Sizing

Before calculating container sizes, individual scalar values within lists and maps are evaluated by their standard byte weights:

  • Strings: Length of the string encoded in UTF-8 bytes.
  • Numbers: Approximately 1 byte per two significant digits, plus 1 byte for the exponent/sign, up to a maximum of 21 bytes.
  • Binary: The total raw byte length of the binary payload.
  • Boolean: 1 byte.
  • Null: 1 byte.

Sizing Rules for List Attributes

A List (L) stores an ordered collection of values. DynamoDB evaluates the size of a list attribute using the following components:

  1. Top-Level Attribute Name: The length of the attribute name in UTF-8 bytes (applied once per top-level attribute).
  2. Container Overhead: Exactly 3 bytes of fixed overhead for the list itself.
  3. Element Sizing: The byte size of each element stored inside the list according to its data type.
  4. Per-Element Overhead: Exactly 1 byte for each element contained in the list.

The formula for a list is: List Size = 3 bytes + Σ (Element Size + 1 byte)

For example, a list containing two strings—"cat" (3 bytes) and "dog" (3 bytes)—consumes:

  • 3 bytes (container overhead)
  • (3 bytes + 1 byte) for "cat" = 4 bytes
  • (3 bytes + 1 byte) for "dog" = 4 bytes
  • Total: 11 bytes (plus the UTF-8 length of the top-level attribute name).

Sizing Rules for Map Attributes

A Map (M) stores an unordered collection of key-value pairs. Similar to lists, maps incur base container overhead and per-entry overhead, with the additional requirement of accounting for the map's internal keys:

  1. Top-Level Attribute Name: The length of the attribute name in UTF-8 bytes.
  2. Container Overhead: Exactly 3 bytes of fixed overhead for the map itself.
  3. Key Sizing: The UTF-8 byte length of each key name within the map.
  4. Value Sizing: The byte size of each value associated with the key.
  5. Per-Entry Overhead: Exactly 1 byte for each key-value pair.

The formula for a map is: Map Size = 3 bytes + Σ (Key Name Length in Bytes + Value Size + 1 byte)

For example, a map with a single entry {"status": "active"} consumes:

  • 3 bytes (container overhead)
  • 6 bytes for the key "status"
  • 6 bytes for the string value "active"
  • 1 byte (entry overhead)
  • Total: 16 bytes (plus the UTF-8 length of the top-level attribute name).

Sizing Deeply Nested Structures

DynamoDB supports nesting documents up to 32 levels deep. When lists or maps are placed inside other lists or maps, the sizing rules compound recursively.

Each inner container contributes its own 3-byte container overhead, plus its internal elements and their respective 1-byte overheads, to the parent container's element size. The parent container then treats that total inner size as a standard element, adding an additional 1-byte entry overhead to it.

Capacity Unit Implications

The cumulative byte count of all top-level attributes, nested containers, keys, and values constitutes the total item size. DynamoDB rounds this total up to the next 4 KB boundary for standard read operations and the next 1 KB boundary for write operations. Because structural overhead compounds with large numbers of small nested elements, flattening unnecessary structures or shortening key names inside maps directly reduces consumed capacity units.
