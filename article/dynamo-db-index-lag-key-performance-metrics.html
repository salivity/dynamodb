DynamoDB Index Lag: Key Performance Metrics

Amazon DynamoDB updates Global Secondary Indexes (GSIs) asynchronously, which can cause an index to fall behind base table updates when write capacity is insufficient. While DynamoDB does not publish a direct "replication lag" duration metric for operational GSIs, the primary performance metric indicating that an index is lagging or struggling to keep up is WriteThrottleEvents measured at the GSI dimension. Additionally, during initial GSI creation, the OnlineIndexPercentageProgress metric indicates backfill progress and lag relative to the base table.

Primary Metric for Active GSIs: WriteThrottleEvents

Global Secondary Indexes rely on an asynchronous replication mechanism to copy updates from the base table. DynamoDB requires that the GSI have equal to or greater write capacity than the base table. If the GSI does not have enough write capacity to process these incoming changes:

  • WriteThrottleEvents (GSI Dimension): This CloudWatch metric records the number of write requests rejected due to insufficient capacity on the index. When write throttle events occur on a GSI, index replication begins to queue and lag. If the throttling persists, DynamoDB will eventually throttle write activity on the base table itself to prevent the index from falling indefinitely behind.
  • ConsumedWriteCapacityUnits vs. ProvisionedWriteCapacityUnits: Comparing these two metrics for the target GSI highlights when the index is operating at or near its provisioned threshold, signaling that lag is imminent.

Metric During Index Creation: OnlineIndexPercentageProgress

When adding a new Global Secondary Index to an existing table, DynamoDB must backfill historical data while simultaneously applying new live updates:

  • OnlineIndexPercentageProgress: This metric tracks the percentage completion of the online index backfill process. A stalled or slowly increasing percentage indicates that the index build is lagging behind live base table modifications, often due to heavy base table writes consuming available provisioning.

Related DynamoDB Lag Metrics

Depending on the architecture used to synchronize DynamoDB data, other metrics serve as indicators of update delays:

  • ReplicationLatency (Global Tables): Used exclusively for DynamoDB Global Tables replicating across AWS Regions. It measures the elapsed time in milliseconds from when an item is written to a base table in one region until it appears in replica tables.
  • IteratorAgeMilliseconds (DynamoDB Streams): Used when maintaining external search indexes (such as Amazon OpenSearch Service) via DynamoDB Streams and AWS Lambda. It measures the age of the last processed record, directly reflecting how far behind the consumer is from the base table.

Preventing DynamoDB Index Lag

To ensure indexes remain closely synchronized with base table updates:

  1. Match Provisioned Capacity: Configure the GSI provisioned write capacity units (WCU) to match or exceed the base table WCU.
  2. Use On-Demand Capacity Mode: If traffic patterns are spiky or unpredictable, switch the base table and its GSIs to On-Demand mode to allow automatic scaling.
  3. Set CloudWatch Alarms: Create alarms on WriteThrottleEvents scoped specifically to the GlobalSecondaryIndexName dimension to detect replication bottlenecks before base table operations are impacted.
