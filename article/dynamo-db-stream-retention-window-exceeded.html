DynamoDB Stream Retention Window Exceeded

When an Amazon DynamoDB Streams consumer falls behind the retention time window, it permanently loses access to unprocessed records, triggering a TrimmedDataAccessException. DynamoDB Streams enforces a strict, non-configurable 24-hour data retention limit. Once this window elapses for unread modifications, DynamoDB automatically purges the expired records from the stream. Consequently, consumers cannot catch up sequentially, leading to silent data gaps or failed processing pipelines unless explicit recovery mechanisms are put in place.

The 24-Hour Retention Limit

DynamoDB Streams captures time-ordered sequences of item-level modifications in a DynamoDB table. Unlike Amazon Kinesis Data Streams, which allows retention periods to be extended up to 365 days, DynamoDB Streams hardcodes the data lifespan to exactly 24 hours. Once a record reaches the 24-hour mark, it is trimmed and deleted from the stream regardless of whether any consumer has read it.

Shard Iterator Expiration and Exceptions

Stream consumers track their position using shard iterators. When a consumer requests data older than 24 hours:

  • TrimmedDataAccessException is thrown: The DynamoDB Streams API returns this error when the consumer attempts to read from a position that points to already-purged data.
  • Shard Iterator Becomes Invalid: The current shard iterator cannot be advanced incrementally. The consumer's standard sequential processing loop breaks because the expected starting point no longer exists.

Downstream Impact

The primary consequence is data inconsistency. Because the stream records represent table mutations (inserts, updates, deletes), any downstream system relying on the stream—such as an Elasticsearch index, an analytics data lake, or a secondary database—will miss these intermediate states.

If consumers are not built to gracefully catch TrimmedDataAccessException, the consumer application may enter a crash loop, continually attempting to read from the expired iterator and failing repeatedly.

Handling and Recovery

When a consumer falls behind the retention horizon, manual or automated intervention is required to resume processing:

  1. Re-initializing the Iterator: The consumer must discard the expired shard iterator and request a new one using either TRIM_HORIZON (which points to the oldest available, non-trimmed record) or LATEST (which skips all backlog and processes only new incoming modifications).
  2. Reconciling Lost Data: Skipping trimmed records creates a data gap. To restore consistency, you must perform a full or targeted scan of the underlying DynamoDB table to synchronize the downstream target with the current state of the database.
  3. Handling Deletions: Because scans of the main table only reveal current items, hard-deleted items that were purged from the stream cannot be identified via a simple table scan. Reconstructing deleted records requires querying backups, point-in-time recovery (PITR), or application audit logs.

Prevention and Monitoring

To avoid falling behind the retention window:

  • Monitor IteratorAgeMilliseconds: Use Amazon CloudWatch to track the IteratorAgeMilliseconds metric. Set alarms to trigger alerts well before this value approaches 86,400,000 milliseconds (24 hours).
  • Scale Consumer Capacity: If using AWS Lambda, increase concurrency limits or optimize function execution times. If using the Kinesis Client Library (KCL) or custom workers, scale the compute fleet horizontally to match the shard count and ingestion rate.
  • Use Kinesis Data Streams for DynamoDB: If your architecture frequently requires longer backlogs or extended processing delays, enable Amazon Kinesis Data Streams for DynamoDB instead of native DynamoDB Streams, allowing configurable retention windows of up to one year.
