DynamoDB Streams Maximum Retention Period

Amazon DynamoDB Streams capture a time-ordered sequence of item-level modifications in a DynamoDB table. This article covers the maximum data retention period for these stream change logs, explains how the automated expiration mechanism operates, and outlines practical options if your architecture requires storing change records for a longer duration.

The maximum retention period for change logs in DynamoDB Streams is strictly 24 hours. From the exact moment a modification occurs and is recorded, the log entry remains available to stream consumers for exactly 24 hours. After this time window elapses, the records are automatically trimmed and permanently deleted by AWS.

This 24-hour retention limit is a fixed service quota. Unlike other streaming services, it cannot be adjusted, extended, or configured through the AWS Management Console or API. Consequently, consuming applications—such as AWS Lambda functions or custom workers utilizing the Kinesis Client Library (KCL)—must read and process the stream records within this rolling 24-hour window to prevent data loss.

If your application requires retaining change data capture (CDC) logs for longer than 24 hours, consider the following alternatives:

  • Amazon Kinesis Data Streams for DynamoDB: Instead of using native DynamoDB Streams, you can route table change events directly to Amazon Kinesis Data Streams. Kinesis supports configurable retention periods ranging from 24 hours up to 365 days.
  • Archiving to Amazon S3: You can configure an AWS Lambda function or Amazon Data Firehose to consume the DynamoDB Stream and write the raw change records to an Amazon S3 bucket for long-term, cost-effective storage and analysis.
