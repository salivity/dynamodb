DynamoDB GSI Throttling During Table Writes

When a write operation occurs on an Amazon DynamoDB base table, the service asynchronously replicates that write to any associated Global Secondary Indexes (GSIs). If a GSI does not have sufficient write capacity to handle the incoming data, it throttles the write request. Consequently, DynamoDB rejects the write operation on the base table itself, even if the base table has ample provisioned write capacity units. Understanding this mechanism is vital for maintaining application reliability and designing effective capacity management strategies.

The Direct Impact: Base Table Throttling

DynamoDB uses an internal asynchronous mechanism to update GSIs. However, to prevent data divergence and buffer overruns, the system will not allow the replication backlog between the base table and a secondary index to grow indefinitely.

When a GSI runs out of Write Capacity Units (WCUs) or encounters a hot partition, it pushes back against the base table. DynamoDB immediately begins throttling writes to the base table to protect the GSI. As a result, the application receives a ProvisionedThroughputExceededException on the base table PutItem, UpdateItem, DeleteItem, or BatchWriteItem call. The write fails entirely; the item is not written to the base table or the index.

Why DynamoDB Enforces This Behavior

DynamoDB decouples base table storage from GSI storage, but it guarantees eventual consistency for secondary indexes. If DynamoDB allowed base table writes to succeed while a GSI was overwhelmed, the replication delay could stretch to minutes or hours, or internal replication buffers could exhaust their memory. By throttling the base table, DynamoDB limits replication lag and ensures that indexes remain reasonably up to date with the primary dataset.

Identifying GSI Throttling

Because the error is returned on the base table operation, it often appears as a standard base table capacity issue. To determine if a GSI is the root cause, monitor Amazon CloudWatch metrics:

  • WriteThrottleEvents on the Base Table vs. GSI: Check if WriteThrottleEvents is spiking on the index while base table write utilization remains below its provisioned threshold.
  • OnlineIndexPercentageProgress and ReplicationLatency: Elevated replication latency often precedes GSI throttling.
  • Partition Key Distribution: Review CloudWatch Contributor Insights to detect hot partition keys within the GSI that might exhaust individual partition limits (1,000 WCUs per partition).

Prevention and Mitigation Strategies

  1. Match or Exceed Base Table WCU: Ensure the GSI has at least as much write capacity as the base table. If a base table write causes multiple index updates or spans different partition boundaries, the GSI may require even more capacity.
  2. Enable DynamoDB Auto Scaling: Configure application auto-scaling on both the base table and all GSIs. Ensure that the scale-up thresholds and policies are aligned so the GSI scales alongside the base table.
  3. Adopt On-Demand Capacity Mode: For unpredictable or spiky workloads, on-demand capacity automatically accommodates varying traffic loads without requiring manual capacity planning for each index.
  4. Avoid Hot Keys in the Index: A GSI with a low-cardinality partition key (such as a status flag or boolean) concentrates writes onto a small number of physical partitions, leading to throttling even when overall index WCU appears sufficient. Ensure GSI partition keys have high cardinality.
