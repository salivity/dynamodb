Modeling One-to-Many Relationships in DynamoDB

Modeling one-to-many (1:N) relationships in Amazon DynamoDB requires moving away from relational normalization and designing around specific application access patterns. Depending on the cardinality of the relationship, the volume of data, and how the data is queried, DynamoDB offers several distinct strategies: embedding data directly, using item collections via composite primary keys, leveraging Global Secondary Indexes (GSIs), and denormalization. This guide outlines these core patterns to help you implement efficient, scalable data models.

1. Embedded Lists or Maps (Document Type)

Embedding represents the simplest way to model a one-to-many relationship by storing the "many" items inside a List or Map attribute directly within the parent item.

  • When to use: Use this approach for bounded relationships where the number of child items is small and predictable (e.g., a user with up to five shipping addresses), and the child data is always read alongside the parent.
  • Limitations: DynamoDB enforces a strict 400 KB limit per item. If the number of child items grows indefinitely or if individual children need to be queried or updated frequently in isolation, this pattern becomes inefficient and risks hitting size limits.

2. Item Collections via Composite Primary Keys

An item collection is a group of items that share the same Partition Key (PK) but have different Sort Keys (SK). This is the standard single-table design approach for unbounded or large one-to-many relationships.

  • How it works:
    • The parent item uses the entity ID for the PK (e.g., PK: ORDER#101) and a static or type-based SK (e.g., SK: METADATA).
    • Each child item shares the parent's PK (e.g., PK: ORDER#101) but uses a unique identifier for the SK (e.g., SK: ITEM#A, SK: ITEM#B).
  • Querying: You can retrieve the parent and all related child records in a single round-trip using the Query API on the partition key. You can also fetch only the parent, or a specific subset of children, by applying the begins_with() expression on the Sort Key.
  • When to use: Ideal when the number of child items is unbounded, or when you need to fetch the parent and its children together efficiently.

3. Global Secondary Indexes (GSI) with Parent Referencing

When child items need their own independent primary key in the base table, you can model the relationship by referencing the parent's ID in an attribute and projecting it via a Global Secondary Index (GSI).

  • How it works:
    • In the base table, each child item has its own primary key (e.g., PK: ITEM#A).
    • The child item includes a reference attribute containing the parent ID (e.g., OrderId: ORDER#101).
    • Create a GSI where OrderId serves as the GSI Partition Key.
  • Querying: Querying the GSI using OrderId = ORDER#101 returns all children related to that parent.
  • When to use: Best suited for cases where child items are queried independently of the parent by their own unique identifiers, or when the base table schema cannot accommodate a shared partition key.

4. Denormalization and Duplication

In read-heavy architectures where joining or secondary querying introduces unwanted read units or latency, denormalizing parent data across child records is an effective pattern.

  • How it works: Commonly accessed parent attributes (such as an author's name or a product's title) are duplicated directly onto each child record (such as comments or order line items).
  • When to use: Use when the duplicated data rarely changes, and child records are frequently read in isolation while requiring context from the parent.
  • Trade-offs: Updating the duplicated data requires updating multiple items, leading to higher write costs and eventual consistency considerations.

Choosing the Right Approach

To select the most efficient pattern:

  1. Check cardinality: If the child count is small and fixed, use Embedded Lists.
  2. Evaluate read patterns: If you frequently need both the parent and children simultaneously, use Item Collections.
  3. Evaluate child lookups: If children are accessed individually by their own IDs, use a Global Secondary Index.
  4. Assess mutation rates: If parent data is immutable or rarely updated, apply Denormalization to optimize read performance.
