DynamoDB BatchGetItem Limits: How Many Items Allowed?

Amazon DynamoDB's BatchGetItem operation enables applications to retrieve multiple items across one or more tables using their primary keys in a single network request. While this operation significantly reduces HTTP overhead compared to individual GetItem requests, it enforces strict operational constraints. This article outlines the primary constraints governing BatchGetItem, specifically the maximum item count, cumulative response size limits, and the mechanisms used to handle partial results.

The 100-Item Request Limit

A single BatchGetItem operation can retrieve a maximum of 100 items. This limit applies to the cumulative total of items requested across all tables included in the single call. For example, you can request 100 items from a single table, 50 items from two different tables, or any combination that does not exceed 100 total primary keys. Submitting a request with more than 100 items results in a validation exception from the DynamoDB API.

The 16 MB Data Size Limit

In addition to the item count constraint, a single BatchGetItem response cannot exceed 16 MB of data. Even if you request fewer than 100 items, the operation halts once the cumulative payload reaches 16 MB. Because an individual DynamoDB item can be up to 400 KB in size, retrieving 100 large items could quickly surpass this payload threshold.

Handling UnprocessedKeys

When a BatchGetItem request hits the 16 MB payload limit, or encounters provisioned throughput limits (throttling), DynamoDB does not fail the entire operation. Instead, it returns a partial result:

  • Responses: Contains the items that were successfully retrieved before reaching the size limit or throttling threshold.
  • UnprocessedKeys: Contains the primary keys that DynamoDB was unable to process during the execution of the call.

If the UnprocessedKeys element in the response is not empty, your application must send subsequent BatchGetItem calls containing those remaining keys until all items are retrieved. Implementing exponential backoff is recommended when retrying unprocessed keys due to throughput constraints.

Best Practices for Staying Within Limits

  • Chunk Requests Manually: When fetching more than 100 items, split your list of keys into batches of 100 or fewer in your application logic before invoking the API.
  • Use Projection Expressions: Specify only the necessary attributes using a ProjectionExpression. While this does not change the 100-item count limit, it reduces the overall data transferred, helping prevent the response from reaching the 16 MB cap.
  • Always Check for Unprocessed Keys: Never assume a single call returned every requested item. Always inspect the UnprocessedKeys map in the API response to ensure complete data retrieval.
