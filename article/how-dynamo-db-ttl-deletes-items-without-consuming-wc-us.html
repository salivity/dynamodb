How DynamoDB TTL Deletes Items Without Consuming WCUs

Amazon DynamoDB Time-to-Live (TTL) allows you to define an expiration timestamp on items so they are automatically removed once they become obsolete. A major benefit of this feature is that DynamoDB deletes these expired records without consuming any of your table’s provisioned Read Capacity Units (RCUs) or Write Capacity Units (WCUs). This article explains the underlying architectural mechanisms DynamoDB uses to track, process, and permanently purge expired data in the background without affecting your provisioned throughput or application performance.

Dedicated Internal Maintenance Capacity

In standard DynamoDB operations, deleting an item requires allocating WCUs because the database must locate the partition, update storage trees, and replicate the change across storage nodes. However, TTL deletions bypass this user-facing accounting entirely.

DynamoDB decouples normal user-driven traffic from internal database management tasks. Every DynamoDB storage node reserves a dedicated pool of system-level resources—independent of customer-allocated partitions and provisioned capacity—to handle fleet-wide health, replication, and data maintenance. TTL deletions run on this internal operational capacity, ensuring that administrative tasks never compete with your read/write allocations.

Background Scavenger Architecture

Instead of running continuous, resource-heavy checks against the primary index, DynamoDB employs a low-priority, asynchronous background scanning process often referred to as a scavenger or garbage collector.

  1. Epoch Timestamp Evaluation: When an item is written with an enabled TTL attribute, DynamoDB stores the expiration time as an integer representing seconds since the Unix epoch.
  2. Asynchronous Partition Traversal: The background process periodically scans partition storage to identify items whose TTL timestamp is older than the current time.
  3. Low-Priority Execution: The sweeper is engineered with low CPU and I/O priority. If a partition experiences a surge in regular application requests, the internal scheduler yields system resources to your user-driven traffic, preventing database latency spikes.

The 48-Hour Deletion Window

Because TTL runs as an asynchronous, best-effort background service to protect customer performance, deletion is not strictly instantaneous. DynamoDB typically deletes expired items within 48 hours of their expiration timestamp.

During the window between when an item expires and when the background process actually purges it, the item can still appear in query or scan results unless you explicitly filter it out in your read requests. If you update or delete the item manually through the API before the scavenger arrives, regular capacity units will apply to your request.

Stream Integration Without Write Overhead

When DynamoDB's background scavenger removes an expired item, it can still publish a deletion event to DynamoDB Streams if the stream is enabled.

Even though the deletion did not consume WCUs on the source table, the event is recorded in the stream with a metadata flag marking it as a system-generated deletion ("principalId": "dynamodb.amazonaws.com"). This allows downstream architectures—such as AWS Lambda functions or archival pipelines—to react to expired records without paying table write fees for the initiating deletion.
