DynamoDB Stream Order Guarantee in a Single Partition

Amazon DynamoDB Streams provides a time-ordered sequence of item-level modifications in any DynamoDB table. Within the context of a single partition, DynamoDB guarantees that all item create, update, and delete events are strictly ordered and processed chronologically. This article explains how DynamoDB Streams enforces this strict ordering within an individual partition, how shards manage stream records, and what consumers must do to maintain this guarantee.

Partition Keys and Shard Assignment

DynamoDB uses the partition key of an item to determine the physical storage partition where the data resides. When an item is modified, the change is recorded in a DynamoDB Stream.

Stream records are organized into shards, which are containers for groups of stream records. Changes made to items that share the same partition key are always directed to the same shard at any given point in time. Because all mutations for that partition flow into a single shard, DynamoDB can maintain an absolute, strictly sequential record of changes for those items.

Sequence Numbers and Strict Serialization

Every modification within a single partition receives an internal, monotonically increasing sequence number. This sequence number reflects the exact order in which DynamoDB committed the transactions to the storage engine.

When records are placed into the shard, they are ordered strictly by this sequence number. This ensures that:

  • Successive updates to the same item are never inverted (e.g., an update will never appear before an item creation).
  • Interleaved updates among different items sharing the same partition key retain their exact chronological commit order.

Shard Splits and Lineage

As traffic or data volume increases, DynamoDB may split a storage partition or a stream shard. Even during a shard split, ordering within a partition is preserved through shard lineage:

  1. When a shard splits, it closes and produces one or more child shards.
  2. New modifications for the partition are routed exclusively to the appropriate child shard.
  3. Stream consumers are required to read all records from the parent shard until it is completely drained (trim horizon to shard end) before processing the child shard.

By following this parent-child hierarchy, consumers ensure that older events from the parent shard are processed before newer events from the child shard.

Consumer-Side Processing Requirements

While DynamoDB guarantees ordering within the stream shard, the consuming application must also respect this order:

  • Single-Threaded Shard Consumption: A single shard must be processed by only one worker thread at a time. If multiple consumers read from the same shard concurrently, race conditions will break the ordering guarantee.
  • Failure Handling: If an error occurs while processing a batch of records, the consumer must retry the failed batch until it succeeds or route it to a dead-letter mechanism deliberately. Skipping a failed batch and processing the next one violates sequential consistency.

Managed services like AWS Lambda (with DynamoDB event source mapping) and the Kinesis Client Library (KCL) automatically handle shard lineage, sequential shard reads, and single-concurrency per shard to preserve DynamoDB's native ordering guarantees.
