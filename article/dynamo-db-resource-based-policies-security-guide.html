DynamoDB Resource-Based Policies Security Guide

Amazon DynamoDB supports resource-based policies directly attached to tables, indexes, and streams, allowing administrators to define fine-grained access control directly on the data resource itself. This article outlines how DynamoDB evaluates and enforces these security policies, how they interact with identity-based policies, and how they simplify cross-account access and data perimeter defense.

Understanding Resource-Based Policies in DynamoDB

A resource-based policy is a JSON document attached directly to a DynamoDB resource, such as a table, a global secondary index (GSI), or a DynamoDB stream. Unlike identity-based policies (which are attached to IAM users, groups, or roles), resource-based policies specify:

  • Principal: Which IAM entities, accounts, or services can access the table.
  • Action: Which API operations are permitted or forbidden (e.g., dynamodb:GetItem, dynamodb:PutItem, dynamodb:UpdateTable).
  • Effect: Whether the specified action is allowed (Allow) or explicitly denied (Deny).
  • Condition: Specific requirements that must be met for the policy to take effect, such as caller IP, VPC source, or item-level attribute constraints.

Policy Enforcement and Evaluation Logic

DynamoDB adheres to standard AWS policy evaluation logic when determining whether to authorize a request:

  1. Explicit Deny Overrides All: If any policy (identity-based, resource-based, service control policy (SCP), or permission boundary) contains an explicit Deny for the requested action, the request is immediately rejected.
  2. Same-Account Evaluation: When the caller and the DynamoDB table belong to the same AWS account, access is granted if either an identity-based policy or a resource-based policy permits the action, assuming no explicit deny exists.
  3. Cross-Account Evaluation: When the caller is from an external AWS account, DynamoDB enforces cross-account authorization. A resource-based policy allows direct cross-account access without requiring the caller to assume an IAM role in the resource owner's account. Access is granted if the resource-based policy in the table's account grants permission and the caller's account does not explicitly block it.

Fine-Grained Access Control (FGAC) Enforcement

DynamoDB enforces item-level and attribute-level security directly through condition blocks in resource-based policies:

  • Primary Key Restrictions: Using the dynamodb:LeadingKeys condition key, policies can restrict callers to only access items where the partition key matches specific criteria, such as the caller’s user ID (${aws:username}).
  • Attribute-Level Protection: Using the dynamodb:Attributes and dynamodb:Select condition keys, administrators can limit reads and writes to specific columns, preventing unauthorized access to sensitive fields like personally identifiable information (PII).

Enforcing Network and Transport Controls

Resource-based policies allow organizations to implement robust data perimeters directly on the database:

  • Enforce TLS Encryption in Transit: By using the aws:SecureTransport condition key set to true, tables will automatically block any unencrypted HTTP requests.
  • VPC Endpoint Restrictions: Conditions using aws:sourceVpce or aws:sourceVpc restrict access exclusively to traffic originating from authorized Amazon Virtual Private Clouds (VPCs), ensuring that data cannot be queried over the public internet.

Simplified Security Operations

By attaching policies directly to tables, security teams gain decentralized control without granting broad IAM permissions. Table administrators can manage who accesses their specific resources without modifying central IAM roles, reducing privilege creep and minimizing the operational complexity of cross-account data sharing.
