How DynamoDB Prevents Cross-Tenant Data Access

Amazon DynamoDB isolates customer workloads within a shared physical infrastructure using a defense-in-depth security model. This multi-tenant architecture prevents cross-tenant data access through strict request authentication via AWS Identity and Access Management (IAM), stateless request routing, internal unique resource identifiers, cryptographic isolation with AWS Key Management Service (AWS KMS), and software-level data containment on underlying storage nodes.

Authentication and Request Validation

Every request entering the DynamoDB fleet must be cryptographically signed using AWS Signature Version 4 (SigV4). When an application sends an API call, the DynamoDB endpoint validates the signature and resolves the caller’s identity via IAM.

IAM evaluates the associated policies to ensure that the principal has explicit permission to perform the requested operation on the target resource Amazon Resource Name (ARN). If the signature is invalid, expired, or unauthorized for the specified ARN, the request is immediately rejected at the network perimeter before reaching any storage tier.

Stateless Request Routers

DynamoDB separates its architecture into a request routing fleet and a storage fleet. Incoming requests first land on stateless Request Routers. These routers inspect the validated request, look up the partition metadata, and determine which storage nodes host the exact partition for the requested item.

Request Routers do not permit arbitrary query parameters or raw storage scans across arbitrary disks. The router enforces strict boundary checks: it translates public table names into internal, immutable system identifiers and routes the request solely to the specific partition replicas holding that tenant's data.

Internal Unique Identifiers

To prevent namespace collision and identifier spoofing, DynamoDB does not manage data on storage nodes using customer-facing table names. Instead, the control plane assigns globally unique internal identifiers (UUIDs) to accounts, tables, and partitions.

Even if two different customers name their tables "Users," the storage engine tracks them under entirely distinct internal IDs. All read and write operations inside the storage engine reference these internal IDs, ensuring that memory structures, B-trees, and write-ahead logs never blend records from different tenants.

Partition-Level Data Isolation on Storage Nodes

DynamoDB uses a custom storage engine where physical SSD storage nodes host replicas of partitions belonging to different customers. The storage node software enforces data isolation at the process level:

  • Memory Bounds: Item caches and in-memory indexes validate the table and partition IDs for every look-up. A query scoped to Partition A cannot traverse adjacent memory blocks assigned to Partition B.
  • Storage Immutability: Data written to persistent storage (transaction logs and B-tree data files) is tagged with metadata headers containing the internal partition and table IDs. During reads, the storage engine asserts ownership matching the request token; mismatched records trigger an internal fault and drop the operation.

Cryptographic Separation with AWS KMS

DynamoDB encrypts all customer data at rest by default. Customers can use AWS-owned keys, AWS-managed keys, or customer-managed keys (CMKs) in AWS KMS.

When using distinct KMS keys, data is cryptographically isolated. Even in the theoretical event of a physical or logical isolation failure where a tenant's raw blocks were read by another process, the data remains unreadable without the corresponding tenant-specific KMS decryption key. Access to the KMS key is independently governed by KMS key policies, creating a separate authorization boundary.

Network and Transport Security

Traffic within the DynamoDB fleet is fully segregated. Communication between Request Routers and Storage Nodes occurs over private, internal networks using mutual TLS (mTLS) with internal service identity certificates. Tenants cannot inject network packets into the DynamoDB internal fabric, eliminating the risk of direct packet-level sniffing, IP spoofing, or cross-tenant network traversal.
