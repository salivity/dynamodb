How DynamoDB Accelerator Handles Node Failures

Amazon DynamoDB Accelerator (DAX) provides high availability and fault tolerance for in-memory caching through automated node health monitoring, seamless failover mechanisms, and automatic replacement processes. When a node within a DAX cluster encounters a hardware or software failure, DAX minimizes application downtime by redistributing client traffic, electing new primary nodes when necessary, and provisioning replacement instances without requiring manual intervention from administrators.

DAX Cluster Architecture Overview

A DAX cluster consists of one primary node and up to nine read replicas. The primary node manages write operations and updates to the cache, while read replicas scale read throughput across the cluster. Because DAX utilizes this decoupled primary-replica topology, the system handles failures differently depending on whether the affected instance is the primary node or a read replica.

Handling Primary Node Failures

When the primary node in a DAX cluster fails:

  1. Failure Detection: DAX continuously monitors the health of all nodes within the cluster. If the primary node stops responding to health checks, the service automatically initiates a failover process.
  2. Leader Election and Promotion: DAX automatically selects an existing read replica and promotes it to become the new primary node. During the election and promotion phase—typically taking less than a minute—write requests to the cache will briefly fail or fall back to DynamoDB directly, depending on client configuration.
  3. Replacement Provisioning: Once the replica is promoted, DAX automatically provisions a new instance to replace the promoted replica. This ensures that the cluster returns to its designated instance count.
  4. Cache State: The promoted replica already contains cached data, reducing the impact of cold-start read performance degradation.

If a single-node DAX cluster experiences a failure, failover is not possible. DAX instead terminates the unhealthy instance and provisions a new primary node from scratch, resulting in a cold cache and temporary unavailability during provisioning.

Handling Read Replica Failures

The failure of a read replica has minimal impact on the operational continuity of the cluster:

  1. Traffic Re-routing: Upon detecting that a replica is unhealthy, DAX marks it as unavailable. The remaining healthy read replicas and the primary node absorb the read traffic.
  2. Node Replacement: DAX provisions a new replica instance in the background to restore cluster capacity.
  3. Cache Warming: The replacement replica boots with an empty cache. It populates its cache organically as it begins serving read-through queries dispatched by the DAX client.

Client-Side Handling and Topology Discovery

The DAX client SDK interacts with the cluster via a discovery endpoint. When node membership changes due to a failure:

  • The DAX client periodically polls the cluster's configuration endpoint to receive real-time topology updates.
  • If a request to a failed node times out or encounters a network error, the client updates its internal routing table to bypass the faulty instance.
  • Write requests are redirected to the newly elected primary node once failover completes, while read requests are distributed across the surviving healthy nodes.

Multi-AZ Resilience

To maximize resilience against infrastructure-level failures, DAX nodes can be deployed across multiple Availability Zones (AZs) within an AWS Region. In a multi-AZ deployment, DAX ensures that if an entire zone experiences an outage, a replica in an alternate AZ is promoted to primary, maintaining application availability and read performance.
