DynamoDB Write Capacity: PutItem vs UpdateItem

Understanding how Amazon DynamoDB computes consumed write capacity units (WCUs) for PutItem and UpdateItem is essential for optimizing database costs and performance. While both operations consume write capacity based on 1 KB increments rounded up, the key difference lies in which state of the item is measured: PutItem calculates capacity exclusively based on the size of the newly written item, whereas UpdateItem calculates capacity based on the larger of the item's size before the update or after the update.

The Baseline: How DynamoDB Measures Write Capacity

DynamoDB measures write capacity in Write Capacity Units (WCUs):

  • 1 WCU represents one write per second for an item up to 1 KB in size.
  • Any operation that writes data calculates the target item size in bytes, divides by 1,024 bytes (1 KB), and rounds up to the nearest whole integer.
  • For on-demand mode, the calculation uses Write Request Units (WRUs), which follow the exact same size-rounding formulas as provisioned WCUs.

Write Capacity for PutItem

The PutItem operation either creates a completely new item or replaces an existing item in its entirety with a new one.

  • Calculation: DynamoDB evaluates only the final size of the item being stored.
  • Formula: Consumed WCUs = ceil(Size of New Item in KB)
  • Example: If you overwrite an existing 8 KB item with a new item that is 1.5 KB, DynamoDB charges for the 1.5 KB payload. The calculation rounds 1.5 KB up to 2 KB, consuming 2 WCUs. The size of the prior item is disregarded.

Write Capacity for UpdateItem

The UpdateItem operation edits an existing item's attributes or inserts a new item if the primary key does not yet exist.

  • Calculation: DynamoDB evaluates both the item's size immediately before the update and immediately after the update. The operation consumes capacity based on whichever size is greater.
  • Formula: Consumed WCUs = ceil(max(Size Before Update, Size After Update) in KB)
  • Example 1 (Modifying a large item): Suppose an item is currently 5.5 KB. You use UpdateItem to modify a single boolean flag, bringing the final size to 5.51 KB. DynamoDB compares 5.5 KB and 5.51 KB, takes the larger value (5.51 KB), and rounds it up to 6 KB, consuming 6 WCUs. Even though only a few bytes changed, you pay for the entire item.
  • Example 2 (Shrinking an item): Suppose an item is 4.2 KB. You remove several attributes using UpdateItem, reducing the item size to 0.8 KB. DynamoDB compares 4.2 KB (before) and 0.8 KB (after), selects 4.2 KB, and rounds up to 5 KB, consuming 5 WCUs.
  • Example 3 (Item does not exist): If UpdateItem targets a primary key that does not exist, there is no pre-existing item size. DynamoDB charges solely based on the size of the newly created item, identical to a PutItem call.

Capacity Consumption for Failed Conditional Writes

Both PutItem and UpdateItem support condition expressions (e.g., ensuring an attribute equals a specific value before writing).

  • If the condition expression fails on a standard write request, DynamoDB consumes 1 WCU for the evaluation, provided the request did not use transactional APIs.
  • If a conditional write succeeds, capacity is consumed normally based on the standard PutItem or UpdateItem sizing rules.

Secondary Index Considerations

When using either operation on a table with Global Secondary Indexes (GSIs) or Local Secondary Indexes (LSIs):

  • Local Secondary Indexes: If the base table item changes, the LSI consumes write capacity proportional to the LSI projection size, following similar before-and-after rules for updates.
  • Global Secondary Indexes: A GSI consumes write capacity only if the operation updates an attribute that is indexed by or projected into that GSI, or if the update moves the item into or out of the GSI. PutItem always writes to all relevant GSIs, whereas UpdateItem only writes to a GSI if the attributes relevant to that specific GSI are affected.
