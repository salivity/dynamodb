How DynamoDB Exports Tables to Amazon S3

Amazon DynamoDB allows you to export full table data directly to Amazon S3 without impacting production traffic or consuming read capacity units. This article explains the underlying mechanism of DynamoDB table exports, covering the role of continuous backups, data formatting options, zero-impact architecture, and how the export process executes from initiation to the delivery of data and manifest files in your target S3 bucket.

The Role of Point-in-Time Recovery (PITR)

The foundation of the DynamoDB export mechanism is Point-in-Time Recovery (PITR). To export table data to Amazon S3, PITR must be enabled on the source table.

When PITR is active, DynamoDB continuously captures changes and backs up table data to an internal, highly durable storage tier. Rather than querying the live database partition nodes that handle your read and write requests, the export feature extracts data directly from these continuous system backups. This allows you to export data from any point in time within the preceding 35 days, down to the second.

Zero Impact on Table Performance and Capacity

Because DynamoDB reads from the internal PITR backup storage rather than the live database tables:

  • No Read Capacity Units (RCU) are consumed: Your provisioned or on-demand read capacity remains completely untouched.
  • No latency spikes: Your production application experiences zero performance degradation or throttling during the export process, regardless of table size.

The Export Execution Process

When you initiate an export via the AWS Management Console, AWS CLI, or the ExportTableToPointInTime API call, the following sequence takes place:

  1. Validation and Configuration: DynamoDB validates the target Amazon S3 bucket, permissions (IAM policies), and configuration parameters, including the designated point in time, data format (DynamoDB JSON or Amazon Ion), and encryption keys (AWS KMS or Amazon S3-managed keys).
  2. Distributed Extraction: DynamoDB assigns an internal fleet of distributed workers to read the snapshot data corresponding to the requested timestamp. Because the extraction workload is distributed across multiple workers, the export can scale efficiently even for multi-terabyte tables.
  3. Serialization and Compression: The workers serialize the table items into the requested format (DynamoDB JSON or Amazon Ion). Each data file is automatically compressed using GZIP to reduce network transfer time and storage footprint.
  4. Writing to Amazon S3: The compressed files are written in parallel directly to the specified S3 bucket and prefix.

Output Structure and Manifest Files

Once the data writing process completes, DynamoDB outputs a structured directory inside your target S3 bucket containing two main components:

  • Data Files: Located in the data/ subfolder, these are the GZIP-compressed files containing the serialized table items.
  • Manifest Files: DynamoDB generates a manifest-summary.json file at the root of the export directory, along with a manifest-files.json file. The summary manifest provides metadata such as the export ARN, start and end times, item count, and schema details. The files manifest lists the S3 keys and checksums for all individual data files generated, enabling downstream services like AWS Glue, Amazon Athena, or Amazon EMR to easily ingest and verify the exported data.
