How DynamoDB Processes Write Request Batching

This article explores how Amazon DynamoDB handles write request batching via the BatchWriteItem API to significantly reduce network round trips. By consolidating up to 25 individual write operations into a single network payload, applications can decrease latency, minimize connection overhead, and optimize data ingestion pipelines. Below is a detailed breakdown of how DynamoDB receives, unpacks, executes, and responds to batched write requests.

The BatchWriteItem Mechanism

DynamoDB uses the BatchWriteItem API action to group multiple write actions—specifically PutItem and DeleteItem—into a single HTTP request. A single batch can contain up to 25 individual items, with a total payload limit of 16 MB. Each individual item within the batch can be up to 400 KB. This operation can target a single table or span multiple tables simultaneously within the same AWS region and account.

Eliminating Network Round Trips

In standard point-in-time writes, saving 25 items requires 25 separate network interactions. Each individual call incurs the cost of establishing or reusing an HTTP connection, TLS overhead, serialization, network latency, and waiting for an acknowledgment.

By contrast, write request batching packages all 25 actions into a single serialized JSON or binary payload sent over one HTTP connection. The request arrives at a DynamoDB request router (part of the DynamoDB frontend fleet). This frontend service unpacks the grouped items and routes them to their respective storage partitions over AWS's high-speed, internal network. By replacing external network traversals with ultra-fast internal routing, overall application-side latency and CPU utilization drop substantially.

Internal Parallel Processing

Although sent as a single collection, DynamoDB does not execute batched write requests sequentially. Once the request router receives the batch, it separates the items based on their primary keys and dispatches them in parallel to the appropriate storage partition replicas. This parallel execution ensures that processing a batch of 25 items takes roughly the same backend execution time as processing a single item, bounded only by internal partition throughput and consensus replication.

Non-Atomic Execution and Error Handling

BatchWriteItem is not an atomic transaction. If one item in the batch fails, the entire batch does not roll back. Instead, DynamoDB executes as many valid requests as possible and returns an HTTP 200 status code containing an UnprocessedItems object in the response.

Items generally remain unprocessed due to:

  • Exceeding the table’s provisioned write capacity or on-demand throughput limits.
  • Exceeding the partition-level write threshold (1,000 WCUs per second per partition).
  • Transient infrastructure bottlenecks.

Because the response explicitly identifies which operations failed, the client does not need to retransmit the entire batch. Modern AWS SDKs automatically detect UnprocessedItems and implement exponential backoff algorithms to retry only the failed writes, preventing unnecessary network traffic for items that were already committed.

Capacity and Cost Efficiency

Write request batching optimizes network communication and application throughput, but it does not reduce DynamoDB capacity consumption. DynamoDB calculates Write Capacity Units (WCUs) individually for each item in the batch, rounding up to the nearest 1 KB increment per item just as it would for discrete PutItem or DeleteItem calls. The primary efficiency gained is entirely operational and architectural: fewer TCP connections, reduced thread blocking, lower serialization costs, and a dramatic reduction in network round-trip overhead.
