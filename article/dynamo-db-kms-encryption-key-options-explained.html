DynamoDB KMS Encryption Key Options Explained

Amazon DynamoDB provides built-in encryption at rest to protect sensitive data using encryption keys stored in AWS Key Management Service (AWS KMS). When configuring encryption at rest for a DynamoDB table, you can choose from three key management options: AWS owned keys, AWS managed keys, and customer managed keys. This guide details how each KMS encryption option operates, along with their key differences in management, visibility, and cost, enabling you to select the right configuration for your compliance and architectural needs.

1. AWS Owned Key (Default)

The AWS owned key option is the default encryption setting for all DynamoDB tables.

  • Management and Visibility: These keys are not stored within your AWS KMS account. Instead, they belong to a collection of KMS keys that AWS owns and manages across multiple AWS accounts to protect DynamoDB infrastructure. You cannot view, configure, audit, or track the usage of these keys in AWS KMS or AWS CloudTrail.
  • Cost: There are no additional fees for using AWS owned keys. You do not incur KMS request fees or monthly key storage charges.
  • Best Use Case: Ideal for general workloads and applications where baseline data protection is required without specific compliance needs for custom key rotation, key access policies, or CloudTrail auditing.

2. AWS Managed Key

The AWS managed key is a KMS key created in your AWS account and managed directly by AWS on your behalf.

  • Management and Visibility: This key appears in your KMS console under the alias aws/dynamodb. AWS automatically creates this key the first time you select this option, and AWS manages its key rotation and basic permissions. While the key resides in your account, you cannot modify its key policy or delete it.
  • Auditing and Metrics: Because the key exists within your account, all cryptographic requests made to KMS are recorded in AWS CloudTrail, providing an audit trail of key access.
  • Cost: The key itself does not incur a monthly KMS storage fee, but standard AWS KMS API request charges apply when DynamoDB accesses the key to encrypt or decrypt data.
  • Best Use Case: Suitable for organizations that require visibility into cryptographic calls via CloudTrail for auditing purposes, but prefer to avoid the administrative overhead of managing key policies and rotation schedules.

3. Customer Managed Key (CMK)

Customer managed keys are KMS keys that you create, own, and administer entirely within your AWS account.

  • Full Control: You have complete control over the lifecycle of the key. This includes defining and editing key policies to enforce fine-grained access control, enabling or disabling the key, configuring automatic key rotation, and setting up deletion windows.
  • Auditing and Compliance: All API operations involving the key are fully tracked and visible in AWS CloudTrail. You can monitor exactly which roles and identities access the key, set up Amazon CloudWatch alarms for policy violations, and integrate access controls with your organization's governance standards.
  • Cost: Customer managed keys incur a monthly KMS key storage fee in addition to standard KMS API request charges generated by table operations.
  • Best Use Case: Essential for regulated workloads subject to strict compliance frameworks (such as HIPAA, PCI-DSS, or FedRAMP) that mandate strict cryptographic control, custom key rotation intervals, or explicit separation of duties between key administrators and data users.

Summary of Differences

Location AWS internal account Your AWS account Your AWS account
Cost Free KMS API requests only Monthly key fee + KMS API requests
Key Policy Control None None Full control
Key Rotation Managed by AWS Managed by AWS (every 1 year) Configurable (every 1 year) or on-demand
CloudTrail Logging No Yes Yes
