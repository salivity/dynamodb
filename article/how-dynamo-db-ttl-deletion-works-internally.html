How DynamoDB TTL Deletion Works Internally

Amazon DynamoDB Time to Live (TTL) provides an automated mechanism to expire and delete items without consuming provisioned read or write throughput. This article explores the internal architecture behind DynamoDB's TTL feature, explaining how background processes identify expired timestamps, the mechanics of non-blocking storage reclamation, how deletions propagate to secondary indexes and DynamoDB Streams, and why deletions occur asynchronously rather than instantaneously.

The Background Sweeper Process

DynamoDB uses continuous, low-priority background sweeps to identify and delete expired items. These sweeps run as asynchronous background tasks across the storage nodes hosting partition replicas.

The background scanner evaluates the TTL attribute specified on the table. It compares the Unix epoch timestamp (in seconds) stored in that attribute against the current system time. If the attribute contains a valid number that is less than the current epoch time, the item is flagged as expired and queued for deletion.

Resource Isolation and Capacity Consumption

TTL deletions are designed to have zero impact on application workloads:

  • Zero RCU/WCU Consumption: TTL deletions do not consume Read Capacity Units (RCUs) or Write Capacity Units (WCUs), nor do they consume on-demand request units.
  • Low-Priority Execution: The background deletion sweeps run with lower scheduling priority than standard read and write requests. If a partition experiences high application traffic, the storage node deprioritizes TTL processing to ensure that user-facing latency and throughput SLAs are not degraded.

Timing and Deletion Windows

Because TTL deletion runs as a background process rather than an inline trigger, item deletion does not happen the exact second an item expires. DynamoDB typically removes expired items within 48 hours of their designated expiration time.

Until the background worker physically deletes the item:

  • The item remains visible to read requests (GetItem, Query, Scan) unless filtered out at the application layer using filter expressions that check the timestamp against the current time.
  • The item still consumes storage space until the background process completes the removal.

Storage Reclamation and Index Management

When the background worker processes an expired item, the deletion propagates through the internal storage engine:

  1. Partition Log and B-Tree Compaction: The item is removed from the partition's internal storage structures. The storage space is marked as free and reclaimed during regular storage compaction cycles.
  2. Global Secondary Index (GSI) Cleanup: The deletion initiates an internal replication event that automatically removes the corresponding entry from all Global Secondary Indexes and Local Secondary Indexes (LSIs).
  3. DynamoDB Streams Event Generation: If DynamoDB Streams is enabled on the table, the deletion generates a standard REMOVE stream record. The record includes a system attribute, userIdentity, indicating that the deletion was initiated by the DynamoDB TTL service (PrincipalId: "dynamodb.amazonaws.com"), allowing downstream systems to distinguish between manual user deletions and automatic expirations.
