DynamoDB BatchGetItem Partial Success Handling

Amazon DynamoDB's BatchGetItem operation retrieves up to 100 items and up to 16 MB of data across multiple tables in a single API call. When DynamoDB cannot process all requested items due to throughput throttling or response size limits, it does not fail the entire operation. Instead, it returns an HTTP 200 OK status code accompanied by a partial success response. This article explains why partial successes occur, how DynamoDB formats the returned payload, and the best practices for handling unprocessed keys in application code.

Why Partial Success Occurs

A BatchGetItem operation returns a partial success under two primary conditions:

  1. Provisioned Throughput Exceeded: One or more underlying partitions or tables experience throttling because consumption exceeds provisioned read capacity units (RCUs) or on-demand limits. DynamoDB processes the items it can and defers the throttled items.
  2. Response Size Threshold: A single BatchGetItem response cannot exceed 16 MB. If the total size of the requested items crosses this threshold, DynamoDB retrieves items until the limit is approached and leaves the remaining items unprocessed.

Because individual item failures do not cause the entire operation to abort, DynamoDB does not raise an exception or return a 4xx/5xx status code.

Structure of the Response

A partial success response splits the output into two main top-level attributes:

  • Responses: A map containing the successfully retrieved items, grouped by table name. Each entry contains a list of attribute maps corresponding to the fetched items.
  • UnprocessedKeys: A map containing the items that DynamoDB could not process. The structure of UnprocessedKeys is identical to the RequestItems parameter used in the original request. It includes the primary keys of the remaining items, along with any projection expressions or read consistency parameters specified originally.

If all items are retrieved successfully, UnprocessedKeys will be empty or omitted from the response.

Implementing the Retry Loop

Because UnprocessedKeys matches the input structure expected by BatchGetItem, handling unprocessed items requires passing this map directly into a subsequent request.

Proper handling involves the following steps:

  1. Inspect the Output: After executing BatchGetItem, evaluate whether UnprocessedKeys exists and contains elements.
  2. Re-invoke BatchGetItem: Use the returned UnprocessedKeys object directly as the RequestItems parameter for the next call.
  3. Apply Exponential Backoff and Jitter: If the unprocessed status was caused by throughput throttling, immediate retries will likely fail. Introduce a backoff algorithm that increases delay exponentially with each retry and includes randomized jitter to avoid synchronization spikes against the database.
  4. Enforce Retry Limits: Define a maximum number of retry attempts or a timeout ceiling to prevent infinite loops in the event of persistent infrastructure saturation or hard partition limits.
  5. Aggregate Results: Accumulate the items from the Responses map across each iteration until UnprocessedKeys is completely empty or the retry limit is reached.
