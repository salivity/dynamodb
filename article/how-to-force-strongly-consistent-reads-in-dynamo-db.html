How to Force Strongly Consistent Reads in DynamoDB

Amazon DynamoDB defaults to eventually consistent reads to maximize read throughput and minimize latency, but certain applications require access to the most up-to-date data immediately after a write. To force a strongly consistent read in DynamoDB, you must set the ConsistentRead parameter to true in your API request. This article explains how the ConsistentRead parameter works, which operations support it, and the associated trade-offs in cost and performance.

The ConsistentRead Parameter

When querying or retrieving items from DynamoDB, setting ConsistentRead=true guarantees that the response reflects all successful write operations that occurred prior to the read. If this parameter is omitted or explicitly set to false, DynamoDB returns an eventually consistent read, which might return stale data if a write recently occurred.

Supported API Operations

The ConsistentRead parameter is supported in data retrieval operations targeting DynamoDB tables and Local Secondary Indexes (LSIs). The primary operations include:

  • GetItem: Retrieves a single item by primary key.
  • BatchGetItem: Retrieves up to 100 items from one or more tables.
  • Query: Finds items based on primary key attribute values.
  • Scan: Reads every item in a table or secondary index.

Note: Strongly consistent reads are not supported on Global Secondary Indexes (GSIs). Requests targeting a GSI must use eventual consistency. Additionally, strongly consistent reads are not supported across multiple AWS regions via DynamoDB Global Tables.

Cost and Latency Implications

Enabling strongly consistent reads impacts both throughput consumption and performance:

  • Read Capacity Units (RCU): An eventually consistent read of up to 4 KB consumes 0.5 RCUs. A strongly consistent read of the same size consumes 1 full RCU, effectively doubling the read capacity cost.
  • Latency: Strongly consistent reads may experience slightly higher latency because the request queries multiple storage nodes to verify the latest data state before returning.
  • Availability: In the rare event of a network partition or node outage, strongly consistent reads might fail with a 500-series error where an eventually consistent read could still succeed.

Implementation Example

In the AWS SDK (such as the Python boto3 library), you apply the parameter directly to the read call:

import boto3

dynamodb = boto3.client('dynamodb')

response = dynamodb.get_item(
    TableName='Users',
    Key={
        'UserId': {'S': '12345'}
    },
    ConsistentRead=True
)

By providing ConsistentRead=True, DynamoDB bypasses eventual consistency and ensures your application receives the latest written state for the specified item.
