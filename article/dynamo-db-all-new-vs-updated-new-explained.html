DynamoDB ALL_NEW vs UPDATED_NEW Explained

When modifying records in Amazon DynamoDB using the UpdateItem API, the ReturnValues parameter dictates what attribute data the service sends back to your application. Two of the most common options are ALL_NEW and UPDATED_NEW. This article explains the fundamental differences between these two parameters, highlights their performance and bandwidth implications, and outlines the ideal use cases for each.

Understanding the ReturnValues Parameter

By default, an UpdateItem operation does not return any item attributes (NONE). To inspect the state of an item after an update without making a separate, read-capacity-consuming GetItem call, you can supply a ReturnValues parameter. Both ALL_NEW and UPDATED_NEW reflect the item's state after the update has successfully executed.

How ALL_NEW Works

The ALL_NEW option instructs DynamoDB to return the entire item, including all attributes as they appear after the update completes.

  • Response Content: It includes the primary key(s), the attributes altered or added by the update expression, and all existing attributes that were left untouched.
  • Network Payload: Because it serializes the entire item, the network payload size corresponds to the full size of the item.
  • Primary Key: The partition key and sort key (if applicable) are always included in the response.

Example

If an item has the attributes { "id": "123", "name": "Alice", "status": "pending", "loginCount": 5 } and an update increments loginCount by 1:

Specifying ALL_NEW returns:

{
  "id": "123",
  "name": "Alice",
  "status": "pending",
  "loginCount": 6
}

How UPDATED_NEW Works

The UPDATED_NEW option instructs DynamoDB to return only the attributes that were explicitly modified or added during the update operation, in their new post-update state.

  • Response Content: It omits any attributes that were not affected by the update expression.
  • Network Payload: The response payload is minimal because it only serializes the changed fields.
  • Primary Key: The primary key attributes are omitted from the returned payload unless they were explicitly part of the update expression (which is rarely valid since primary keys are immutable).

Example

Using the same item { "id": "123", "name": "Alice", "status": "pending", "loginCount": 5 } and updating loginCount by 1:

Specifying UPDATED_NEW returns:

{
  "loginCount": 6
}

Key Differences

Feature ALL_NEW UPDATED_NEW
Returned Attributes All attributes in the item Only the attributes modified or created
Primary Keys Included Yes No (unless modified, which is generally not allowed)
Payload Size Larger (scales with full item size) Smaller (scales only with updated fields)
Bandwidth Usage Higher Lower

When to Use ALL_NEW

  • Cache Invalidation and Updates: When maintaining an in-memory cache (like Redis or a local application cache), ALL_NEW provides the complete entity so you can replace the cached item directly.
  • Full Object Hydration: When downstream code expects a fully hydrated domain model or Data Transfer Object (DTO) to continue execution.
  • State Synchronization: When broadcasting full state changes to event buses, WebSockets, or UI layers that require the complete entity state.

When to Use UPDATED_NEW

  • Atomic Counters: When implementing distributed counters, rate limiters, or sequence generators, UPDATED_NEW lets you retrieve the new numerical value without loading unnecessary object data.
  • Large Items: If an item contains large text fields, binary data, or long lists, UPDATED_NEW avoids the overhead of serializing and transmitting large, unchanged data across the network.
  • Optimized Bandwidth: In high-throughput microservices where minimizing serialization overhead and network I/O reduces latency and compute resource consumption.
