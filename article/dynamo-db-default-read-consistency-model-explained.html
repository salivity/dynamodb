DynamoDB Default Read Consistency Model Explained

Amazon DynamoDB uses eventually consistent reads as its default read consistency model across read operations, including queries. This article breaks down how the default consistency model operates, how it compares to strongly consistent reads, its impact on application performance and costs, and important architectural limitations such as secondary index behavior.

Understanding Eventually Consistent Reads

When an application performs a Query, GetItem, or BatchGetItem operation without specifying consistency parameters, DynamoDB automatically executes an eventually consistent read.

In a distributed system like DynamoDB, data is automatically replicated across multiple physical storage servers within an AWS Availability Zone to ensure high availability and durability. When a write operation completes, all replicas are updated. An eventually consistent read queries one of these replicas:

  • Latency and Throughput: It maximizes read throughput and offers the lowest possible read latency.
  • Staleness Window: The response might not immediately reflect the results of a recently completed write operation. Consistency across all replicas is typically achieved within a fraction of a second.
  • Potential for Repeating Reads: Reading the same key multiple times in rapid succession might occasionally return outdated data before returning updated data.

Strongly Consistent Reads

If an application requires immediate visibility of previous writes, you must explicitly set the ConsistentRead parameter to true in the API call.

A strongly consistent read returns a response with the most up-to-date data, reflecting all successful write operations that occurred prior to the read. However, strong consistency introduces specific trade-offs:

  • Latency: It can have slightly higher latency than an eventually consistent read.
  • Availability: Strongly consistent reads might not be available during certain network delay or partition scenarios.

Cost and Capacity Implications

Read consistency directly impacts your consumed Read Capacity Units (RCUs) in both provisioned and on-demand pricing models:

  • Eventually Consistent Read: One RCU provides two reads per second for items up to 4 KB in size (0.5 RCU per 4 KB).
  • Strongly Consistent Read: One RCU provides one read per second for items up to 4 KB in size (1 RCU per 4 KB).
  • Transactional Read: Consumes two RCUs per read for items up to 4 KB in size (2 RCUs per 4 KB).

Using the default eventually consistent model cuts read capacity costs in half compared to strongly consistent queries.

Global Secondary Index (GSI) Behavior

The default consistency rule carries a critical exception when querying Global Secondary Indexes (GSIs). DynamoDB updates GSIs asynchronously from the base table. Consequently, queries against a GSI only support eventual consistency; you cannot set ConsistentRead=true on a GSI query. Local Secondary Indexes (LSIs), by contrast, support both eventually consistent and strongly consistent reads.

Summary

The default read consistency for DynamoDB queries is eventually consistent. It provides optimal performance and halves read costs, making it ideal for use cases where reading slightly stale data for a few hundred milliseconds does not break business logic. For workloads requiring immediate write-to-read guarantees, developers must deliberately opt into strongly consistent reads.
