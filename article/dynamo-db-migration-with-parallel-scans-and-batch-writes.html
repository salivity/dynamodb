DynamoDB Migration with Parallel Scans and Batch Writes

Migrating data structures in Amazon DynamoDB requires specialized strategies due to its distributed, schemaless architecture. This article explains how to execute large-scale schema migrations in DynamoDB by leveraging parallel scans to extract datasets concurrently across physical partitions and using batch write operations to ingest transformed items efficiently while managing provisioned throughput and error handling.

The Need for DynamoDB Schema Migrations

Although DynamoDB is schemaless at the item level, application logic dictates a rigid schema. Common migration triggers include adding composite keys for new access patterns, reformatting attributes to support new Global Secondary Indexes (GSIs), normalizing existing fields, or backfilling default values across millions of records.

Because DynamoDB does not offer a native ALTER TABLE statement, migrations generally follow an Extract-Transform-Load (ETL) pattern:

  1. Scan existing items from the source table.
  2. Transform item attributes in-memory according to the new schema design.
  3. Write the transformed items back to the existing table (in-place) or into a newly provisioned table.

Step 1: Extracting Data Using Parallel Scans

A standard Scan operation reads an entire table sequentially via a single worker, which quickly becomes an I/O bottleneck on large datasets. DynamoDB addresses this through Parallel Scans, allowing an application to divide the table logically into multiple segments and scan them concurrently.

How Parallel Scans Work

When issuing a parallel scan, the client application specifies two parameters in the API call:

  • TotalSegments: The total number of parallel workers scanning the table simultaneously.
  • Segment: The specific segment number (zero-indexed) that a given worker is responsible for reading.
{
  "TableName": "SourceTable",
  "TotalSegments": 8,
  "Segment": 0,
  "Limit": 500
}

DynamoDB distributes table data across multiple physical storage partitions based on partition key hashes. Parallel scans allow workers to target disjoint segments of partitions simultaneously.

Implementing Parallel Scans Efficiently

  • Worker Sizing: Match TotalSegments to the available compute resources (e.g., AWS Lambda instances, ECS tasks, or an AWS Glue job). A common starting point is one segment per 2–4 GB of data, or matching the physical partition count.
  • Pagination Handling: Each worker must continue scanning its assigned segment using the LastEvaluatedKey returned in the response until the response contains no further pagination token.
  • Rate Limiting: Adjust the Limit parameter and worker count to prevent exceeding the table's Read Capacity Units (RCUs), which leads to ProvisionedThroughputExceededException.

Step 2: Transforming Items In-Memory

Once a segment worker retrieves a page of items:

  • The transformation process updates, adds, or deletes attribute values.
  • Data types can be converted (e.g., converting a numeric timestamp to an ISO-8601 string).
  • Compound attributes can be generated (e.g., combining tenant_id and status into a single partition or sort key).

Transformations occur locally in memory within the worker process before buffering items for writing.

Step 3: Loading Data Using Batch Writes

Writing items individually using PutItem introduces excessive network overhead and latency. Instead, migrations aggregate transformed items and flush them using the BatchWriteItem API.

Mechanics of BatchWriteItem

  • Payload Limits: A single BatchWriteItem call can contain up to 25 PutRequest or DeleteRequest actions, with a maximum aggregate payload size of 16 MB.
  • Atomic Processing: The operation does not execute as a single transaction; individual item writes succeed or fail independently.
  • Throughput Optimization: Grouping writes into batches minimizes HTTP request overhead and saturates available Write Capacity Units (WCUs) predictably.

Handling Unprocessed Items

DynamoDB may reject some items in a batch if the table lacks sufficient write throughput or experiences temporary storage partition splits. When this occurs, the API response returns an UnprocessedItems map.

A robust migration worker must:

  1. Check the response for UnprocessedItems.
  2. Extract the uncommitted write requests.
  3. Retry those items using an exponential backoff and jitter algorithm to avoid overwhelming the target table.

Best Practices for Migration Execution

  • Isolate Capacity: For live production systems, set table capacity mode to Provisioned with explicit RCU/WCU limits during the migration to prevent background tasks from starving real-time application traffic. Alternatively, write to an entirely new table.
  • Ensure Idempotency: Design the transformation logic so that re-running the migration over the same item multiple times yields the exact same state without creating duplicate data or corrupting state.
  • Dual-Writing: If migrating to a new table with zero downtime, enable dual-writing in the application layer or capture real-time changes via DynamoDB Streams to replicate modifications made while the historical migration job runs.
