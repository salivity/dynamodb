DynamoDB Secondary Index Projection Trade-Offs

When designing secondary indexes in Amazon DynamoDB, projecting all attributes eliminates the need for expensive base-table lookups during queries, but it introduces significant drawbacks. The primary trade-off of choosing the ALL projection type is significantly increased storage cost and higher write amplification, as every attribute is duplicated and every update to the base table consumes additional Write Capacity Units (WCUs) on the index.

The Trade-Off: Read Performance vs. Write and Storage Costs

In DynamoDB, Global Secondary Indexes (GSIs) and Local Secondary Indexes (LSIs) allow you to query data using alternate partition and sort keys. When you define an index, you must choose which attributes from the base table to project into it: KEYS_ONLY, INCLUDE (specific attributes), or ALL.

Choosing ALL maximizes read efficiency. When an index contains every attribute from the parent table, queries against the index are completely self-contained. The application never needs to perform a secondary "fetch" (a GetItem or read against the base table) to retrieve non-indexed data. This minimizes read latency and simplifies query logic.

However, this convenience comes at a steep price across two major dimensions:

1. Increased Write Capacity Consumption (Write Amplification)

When an index projects ALL attributes, any update, insert, or delete operation on the base table automatically synchronizes to the secondary index.

  • Every time a write occurs in the base table, DynamoDB consumes write capacity units (WCUs) on both the base table and any affected GSIs.
  • With ALL projection, an update to any attribute—even one not used as the index’s partition or sort key—triggers a write to the index.
  • If the index only projected KEYS_ONLY or a subset via INCLUDE, writes that do not modify the indexed keys or projected attributes might avoid updating the index altogether, saving substantial WCU costs.

2. Doubled Storage Footprint

Projecting ALL effectively duplicates the entire base table's dataset within the secondary index.

  • DynamoDB charges for the storage used by both the base table and all secondary indexes.
  • If a base table is 500 GB and has two GSIs that both use ALL projections, total storage usage balloons to roughly 1.5 TB.
  • This duplication directly scales up monthly storage billing without providing any new data.

When to Avoid Projecting All Attributes

Using ALL is an anti-pattern for write-heavy workloads with large items. If items contain large payloads (such as large text blobs or JSON documents) that are frequently updated, the operational cost of syncing those items to the index will rapidly outpace any performance benefit gained during reads.

To optimize cost and performance, project only the specific attributes your access patterns strictly require using the INCLUDE projection type, or use KEYS_ONLY if your application can tolerate occasional fetches against the base table.
