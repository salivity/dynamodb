Preventing DynamoDB Lost Updates with Version Numbers

In distributed database environments like Amazon DynamoDB, concurrent operations can inadvertently overwrite each other's changes, leading to an issue known as a lost update. Implementing optimistic locking through item version numbers combined with conditional writes is the industry standard for preventing this problem. This article explains the mechanics of lost updates, how version attributes work, and how to execute DynamoDB conditional writes to guarantee data integrity across concurrent transactions.

The Lost Update Problem

A lost update occurs when two separate processes retrieve the same item simultaneously, modify it independently, and write it back to the database. DynamoDB's default behavior operates on a "last writer wins" basis. Consequently, the second process to write will silently overwrite the changes made by the first process, permanently erasing that data without generating an error.

For example, consider an item tracking inventory with a quantity of 10:

  1. Process A reads the item (quantity: 10).
  2. Process B reads the same item (quantity: 10).
  3. Process A decrements the quantity by 2 and writes back 8.
  4. Process B decrements the quantity by 1 and writes back 9.

Process B's write overwrites Process A's update. The final recorded inventory is 9, instead of the correct value of 7, causing a lost update.

How Version Numbers Solve the Issue

Version numbers resolve this concurrency conflict using an approach called optimistic concurrency control (or optimistic locking). Instead of locking the record while reading and preparing an update, you assume conflicts are rare, but verify that the record has not changed before applying the write.

To implement this:

  1. Every DynamoDB item includes a dedicated version attribute (e.g., version, initialized to 1 when the item is created).
  2. Whenever an application updates the item, it increments this version attribute (e.g., from 1 to 2).
  3. The update command includes a condition requiring the version in the database to match the version originally retrieved by the application.

Executing Conditional Writes in DynamoDB

DynamoDB provides the ConditionExpression parameter to enforce requirements that must be met for a write operation (PutItem, UpdateItem, or DeleteItem) to succeed.

The update flow follows these explicit steps:

  1. Read the Item: Retrieve the item and store its current version number along with the data.
    • Example item state: { "id": "item123", "stock": 10, "version": 1 }
  2. Modify the Item Locally: Prepare the payload with the updated data and an incremented version number.
    • Intended new state: { "id": "item123", "stock": 8, "version": 2 }
  3. Execute with a Condition Expression: Issue the write request with a condition that verifies the existing version.
    • Condition: ConditionExpression: "version = :expectedVersion"
    • Expression Attribute Values: { ":expectedVersion": 1, ":newVersion": 2, ":newStock": 8 }

Handling Success and Failure

When DynamoDB evaluates the conditional write:

  • If the version matches: No other process has modified the item since it was read. DynamoDB executes the write atomically, persisting the new data and setting version to 2.
  • If the version does not match: Another process has already updated the item and incremented its version (e.g., to 2). DynamoDB rejects the write request entirely and returns a ConditionalCheckFailedException.

When your application catches a ConditionalCheckFailedException, it knows a concurrent collision occurred. The standard resolution pattern is to reload the latest version of the item, re-apply the business logic against the fresh data, and retry the conditional write. This cycle guarantees that no intermediate state is overwritten blindly.
