DynamoDB Encryption with AWS KMS Customer Keys

Amazon DynamoDB integrates natively with AWS Key Management Service (AWS KMS) to provide robust, transparent encryption at rest using Customer Managed Keys (CMKs). This article explains how DynamoDB utilizes AWS KMS customer keys to manage encryption lifecycles, enforce granular access controls, and execute envelope encryption to secure table data, local and global secondary indexes, streams, and backups without degrading database performance.

Customer Managed Keys vs. AWS Managed Keys

When configuring encryption at rest in DynamoDB, you can choose between an AWS owned key, an AWS managed key, or a Customer Managed Key (CMK). A CMK gives you full ownership over the encryption key's lifecycle. With a customer key, you define and manage:

  • Key Policies: Define who can administer or use the key through IAM policies and KMS key policies.
  • Key Rotation: Enable automatic annual rotation or manually create and rotate to new key material.
  • Auditing: Monitor every cryptographic request and administrative action through AWS CloudTrail logs.
  • Cryptographic Operations: Enable, disable, or delete keys instantly to revoke access to DynamoDB tables.

Envelope Encryption Mechanism

DynamoDB uses an envelope encryption strategy with AWS KMS to optimize performance and prevent KMS API rate-limiting. Rather than sending every database read and write request to AWS KMS, the process operates as follows:

  1. Requesting a Data Key: When a DynamoDB table encrypted with a CMK is created or loaded, DynamoDB sends a kms:GenerateDataKey request to AWS KMS, referencing your specified KMS Key ARN.
  2. Generating the Key Pair: AWS KMS generates a unique Data Encryption Key (DEK). It returns two versions to DynamoDB: a plaintext copy and an encrypted copy (cipherblob) encrypted under your root KMS CMK.
  3. Encrypting Table Data: DynamoDB uses the plaintext DEK in memory with an industry-standard algorithm (AES-256) to encrypt user data before writing it to storage media (solid-state drives).
  4. Storing the Encrypted Key: DynamoDB stores the encrypted version of the DEK alongside the table metadata. The plaintext DEK is securely purged from memory as soon as it is no longer actively needed.
  5. Decrypting Data: When reading data after a cache expiration or system restart, DynamoDB submits the encrypted DEK back to AWS KMS via a kms:Decrypt call. Once KMS returns the plaintext key, DynamoDB decrypts the table blocks.

Data Key Caching and Performance

Directly invoking AWS KMS for every read or write would introduce latency and rapidly exhaust KMS request quotas. To prevent this, DynamoDB caches the plaintext data keys in memory within an isolated security boundary.

Cached keys are tied to the table's security context and are retained temporarily for ongoing transactions. They are periodically discarded and refreshed, forcing re-authentication and re-authorization against the KMS key policy.

AWS KMS Grants and Permissions

DynamoDB interacts with your customer key using AWS KMS Grants. A grant is an advanced permission mechanism that allows DynamoDB to use your KMS key programmatically on your behalf without requiring permanent alterations to your KMS key policies.

To establish this:

  • The principal creating or updating the DynamoDB table must have permissions for kms:CreateGrant, kms:DescribeKey, and cryptographic operations (kms:Encrypt, kms:Decrypt, kms:GenerateDataKey*).
  • DynamoDB creates a grant specifically for the table, allowing its internal service principals to call KMS APIs to generate and decrypt the table's data keys.
  • If you revoke the grant or modify the KMS key policy to deny the service principal, DynamoDB loses access to decrypt the data keys, rendering the table inaccessible once memory caches expire.

Key Lifecycle Events and Impact on DynamoDB

Managing a customer key directly impacts the availability of the associated DynamoDB resources:

  • Key Rotation: When automatic key rotation is enabled, AWS KMS generates new key material annually. Existing data keys remain decryptable using the previous key material, while newly generated data keys use the updated key material. DynamoDB handles this transition seamlessly without requiring table re-encryption.
  • Disabling or Revoking Keys: If you disable or delete a CMK in KMS, DynamoDB can no longer decrypt data keys. As active cached keys expire (typically within minutes), all subsequent read and write requests to the table fail with an error indicating the key is unavailable.
  • Audit Trails: Every operation—from initial grant creation to individual GenerateDataKey and Decrypt calls—is recorded in AWS CloudTrail, providing an immutable audit log of when and how DynamoDB accessed your encryption keys.
