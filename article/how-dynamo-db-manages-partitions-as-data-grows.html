How DynamoDB Manages Partitions as Data Grows

Amazon DynamoDB automatically manages data growth and performance by dynamically allocating underlying storage units known as partitions. As an application writes more data to a table, DynamoDB monitors storage metrics and initiates partition splitting to distribute data and throughput evenly across multiple physical servers. This article details the triggers for partition reallocation, the internal mechanics of partition splitting, and how read and write resources are redistributed to maintain predictable, low-latency performance without downtime.

Partition Limits and Allocation Triggers

DynamoDB distributes table data across multiple Solid State Drives (SSDs) backed by storage nodes. Each individual partition has hard architectural constraints:

  • Storage Limit: A single partition holds a maximum of 10 GB of data.
  • Throughput Limit: A single partition supports a maximum of 1,000 Write Capacity Units (WCUs) or 3,000 Read Capacity Units (RCUs).

When an application's data volume increases and pushes an existing partition near the 10 GB storage boundary, DynamoDB triggers an automated resource reallocation process to prevent storage exhaustion and performance degradation.

The Partition Splitting Process

Resource reallocation driven by storage growth relies on an automated background process called partition splitting. DynamoDB accomplishes this using the following steps:

  1. Detection: Internal storage management monitors detect that a partition is approaching the 10 GB storage limit.
  2. Provisioning: DynamoDB provisions a new partition on a separate storage node within the fleet.
  3. Key Range Division: DynamoDB uses consistent hashing to assign items to partitions based on their partition key value. During a split, the hash range assigned to the parent partition is divided into two distinct sub-ranges.
  4. Data Migration: Data from the parent partition is distributed between the two new child partitions according to the new hash ranges.
  5. Pointer Update: DynamoDB's request routers update their partition mapping metadata. Once updated, incoming read and write requests for keys in the divided hash space route directly to the appropriate new partition.
  6. Decommissioning: Once all data is migrated and confirmed, the original parent partition is retired, and its physical space is reclaimed by the cluster.

This operation occurs entirely in the background using continuous replication and consensus algorithms, ensuring zero downtime and no disruption to ongoing database reads or writes.

Throughput Reallocation and Adaptive Capacity

When a partition splits strictly due to data growth, the provisioned read and write capacity allocated to the original parent partition is divided between the two new child partitions:

  • Capacity Distribution: If a table with provisioned capacity has a partition allocated 1,000 WCUs and 3,000 RCUs, splitting that partition originally halved the provisioned throughput across the child partitions (500 WCUs and 1,500 RCUs each).
  • Adaptive Capacity: To prevent partition-splitting from causing "hot partition" throttling (where one child receives more traffic than the other), DynamoDB utilizes Adaptive Capacity. This mechanism continuously monitors traffic patterns and instantly moves unused capacity from idle partitions to busier ones, ensuring that increased storage does not compromise the throughput of unbalanced workloads.

Global Secondary Indexes (GSIs)

Data growth on the base table often causes proportional growth in Global Secondary Indexes. DynamoDB treats each GSI as an independent table with its own partition layout. When data volume increases on base table attributes that are projected into a GSI, DynamoDB independently monitors and splits GSI partitions as they reach the 10 GB limit, applying the same automated reallocation process without impacting the base table's partition topology.
