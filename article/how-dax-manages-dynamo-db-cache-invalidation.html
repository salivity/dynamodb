How DAX Manages DynamoDB Cache Invalidation

Amazon DynamoDB Accelerator (DAX) provides an in-memory caching tier designed to reduce read latencies to microseconds. When updates occur on underlying DynamoDB tables, DAX handles cache invalidation and consistency differently depending on whether write operations are routed directly through the DAX cluster or applied straight to DynamoDB, as well as whether the cached data resides in the Item Cache or the Query Cache.

Write-Through Caching for Direct Writes

DAX operates primarily as a write-through cache. When your application issues a write request (PutItem, UpdateItem, or DeleteItem) directly to the DAX cluster endpoint:

  1. DAX writes the update to the target DynamoDB table first.
  2. Upon receiving a successful confirmation from DynamoDB, DAX updates or removes the corresponding item in its own Item Cache.
  3. DAX then returns a success response to the client.

Because this write-through process applies to the Item Cache across all nodes in the DAX cluster, subsequent point reads (GetItem and BatchGetItem) routed through DAX immediately reflect the newly updated or deleted item.

Item Cache vs. Query Cache Invalidation

DAX maintains two separate internal caches with distinct invalidation behaviors:

  • Item Cache: Stores individual items retrieved by primary key lookups (GetItem, BatchGetItem). When an update is routed through DAX, the Item Cache is updated or invalidated synchronously.
  • Query Cache: Stores the parameter sets and result sets for Query and Scan operations. Updates made through DAX do not automatically invalidate or update matching entries in the Query Cache. DAX does not evaluate write operations against cached query parameters to identify overlapping result sets. Instead, entries in the Query Cache remain until their configured Time to Live (TTL) expires.

Bypassing DAX: Updates Made Directly to DynamoDB

If an application updates or deletes data directly in DynamoDB instead of issuing the write request through DAX, DAX has no direct awareness of the underlying data change. DAX does not consume DynamoDB Streams automatically to synchronize its cache with external updates.

In this scenario:

  • Data stored in both the Item Cache and Query Cache becomes stale.
  • Stale entries remain in the cache until their TTL expires, after which the next read fetches fresh data from DynamoDB.
  • To avoid stale reads, all writes to tables cached by DAX must consistently be routed through the DAX client endpoint.

Eviction Mechanisms: TTL and LRU

In addition to write-through invalidation, DAX relies on two background eviction mechanisms to manage cache staleness and memory pressure:

  • Time to Live (TTL): Every item written to either the Item Cache or Query Cache has a TTL (default is 5 minutes, configurable down to 0). Once an item's TTL expires, DAX evicts it from the cache. If TTL is set to 0, DAX only reads through to DynamoDB and caches nothing.
  • Least Recently Used (LRU): When a DAX node reaches its memory capacity, it automatically evicts the least recently accessed items to make room for new data, regardless of whether their TTL has expired.
