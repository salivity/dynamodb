Key Condition vs Filter Expression in DynamoDB

When querying Amazon DynamoDB, filtering data efficiently is critical for minimizing latency and controlling operational costs. This article explains the fundamental differences between key condition expressions and filter expressions, focusing on how they process data, their impact on Read Capacity Units (RCUs), and how to apply each effectively when working with table and index queries.

Key Condition Expressions

A key condition expression determines which items DynamoDB physically reads from the table or index. It acts as the primary access mechanism during a Query operation.

  • Execution Timing: Applied before data is read. DynamoDB uses the partition key and optional sort key values to pinpoint the exact storage partition and retrieve only the relevant items.
  • Allowed Attributes: Limited strictly to the partition key (using equality operators) and the sort key (using operators such as =, <, >, <=, >=, BETWEEN, or begins_with).
  • Cost Impact: Highly cost-effective. You are billed in Read Capacity Units (RCUs) only for the items that match the key condition.
  • Performance: Provides predictable, single-digit millisecond latency because the engine navigates directly to the target partition without scanning unnecessary data.

Filter Expressions

A filter expression refines the results of a query after the initial data retrieval has already occurred.

  • Execution Timing: Applied after the query reads the data from disk, but immediately before the final response is returned to the client application.
  • Allowed Attributes: Can evaluate any attribute within the item, including non-key attributes and complex nested data types.
  • Cost Impact: Does not reduce consumed RCUs. DynamoDB charges for all items located by the key condition, regardless of whether the filter expression excludes them from the final result.
  • Pagination and Limits: DynamoDB enforces a maximum payload limit of 1 MB per query operation. This limit is evaluated before the filter expression runs. Consequently, a query can consume an entire 1 MB page and return an empty result set along with a LastEvaluatedKey, requiring client-side pagination to fetch remaining matches.

Core Differences Compared

Feature Key Condition Expression Filter Expression
Processing Stage Pre-read (locates data) Post-read (prunes data)
Permitted Fields Partition and Sort Keys only Any attribute
RCU Consumption Charged only for matching items Charged for all items read before filtering
1 MB Limit Impact Determines what data enters the 1 MB block Evaluated within the already-read 1 MB block
Network Egress Returns matched data Reduces payload size sent over the network

Best Practices

To optimize performance and minimize costs in DynamoDB:

  1. Rely on Key Conditions for Volume: Design your primary keys, Global Secondary Indexes (GSIs), and Local Secondary Indexes (LSIs) so that the bulk of your selective filtering happens through key conditions.
  2. Use Filter Expressions for Payload Optimization: Treat filter expressions as a tool to save network bandwidth and client-side processing, rather than a mechanism to save database read costs.
  3. Handle Empty Result Pages: When using filter expressions, implement recursive pagination logic in your application to handle scenarios where DynamoDB reads items that fail the filter, producing an empty result set alongside a pagination token.
