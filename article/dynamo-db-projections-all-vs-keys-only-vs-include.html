DynamoDB Projections: ALL vs KEYS_ONLY vs INCLUDE

When creating secondary indexes in Amazon DynamoDB—whether a Global Secondary Index (GSI) or a Local Secondary Index (LSI)—the projection setting dictates which attributes from the base table are duplicated into the index. Selecting the right projection type (ALL, KEYS_ONLY, or INCLUDE) is critical because it directly influences query latency, read capacity usage, storage footprint, and write costs. This guide explains how each projection type operates, outlines their performance and cost trade-offs, and provides clear criteria for choosing the best option for your workload.

What Are DynamoDB Projections?

A DynamoDB secondary index functions as an alternate view of your data with a different partition key and optional sort key. Whenever an item is written or updated in the base table, DynamoDB automatically synchronizes the change to the secondary index. The projection type specifies the exact set of attributes copied into that index.

DynamoDB provides three projection types:

  1. KEYS_ONLY
  2. INCLUDE
  3. ALL

1. KEYS_ONLY

The KEYS_ONLY projection copies only the minimal set of keys into the index:

  • The index partition key and sort key.
  • The base table partition key and sort key (to link back to the source item).

No non-key attributes from the base table are duplicated into the index.

Trade-Offs

  • Storage and Cost: Consumes the absolute minimum storage and write capacity units (WCUs). Updates to non-key attributes in the base table do not trigger writes to a KEYS_ONLY index.
  • Query Limitations: If your application queries the index and requires non-key attributes, it must perform a secondary read (GetItem) against the base table using the retrieved keys. This introduces additional network hops, increases latency, and consumes extra read capacity units (RCUs).

When to Use

  • You only need to verify an item's existence or retrieve primary keys based on secondary criteria.
  • The index is used solely for count queries or sorting.
  • Secondary attributes are rarely accessed, making occasional base table lookups acceptable.

2. INCLUDE

The INCLUDE projection replicates the index keys, the base table keys, and a designated list of non-key attributes that you explicitly specify at creation time.

Trade-Offs

  • Storage and Cost: Moderate. It only incurs storage and write costs for the explicitly defined attributes, avoiding unnecessary duplication of large or rarely queried fields.
  • Write Behavior: The index is only updated when changes occur to the index keys or to any of the projected attributes in the include list.
  • Query Latency: Fast and predictable. Queries that only request the projected attributes can be served entirely from the index without fetching from the base table.
  • Flexibility: Low. Once an index is created, you cannot modify the projected attribute list. Adding a new attribute requires creating a new secondary index and deleting the old one.

When to Use

  • Your query patterns are well-defined, and your queries consistently request a specific subset of attributes.
  • Your items contain large payloads (such as JSON blobs, logs, or descriptions) that you do not need in search results.
  • You need optimal read latency for specific fields without the cost of duplicating the entire item.

3. ALL

The ALL projection replicates every attribute from the base table into the secondary index.

Trade-Offs

  • Storage and Cost: Highest. The index essentially duplicates the entire base table's data. Any write or update to the base table—regardless of which attribute changes—triggers a corresponding write to the secondary index, driving up WCU consumption.
  • Query Latency: Lowest. Every query against the index can return full item data immediately without ever requiring an additional lookup to the base table.
  • Flexibility: High. You do not need to predict which attributes future queries will need, and schema additions are automatically reflected in the index.

When to Use

  • The workload is read-heavy and cannot tolerate the latency penalty of back-fetching from the base table.
  • The base table items are relatively small, minimizing the storage cost penalty.
  • Query access patterns are ad-hoc or frequently changing, requiring access to diverse attributes.

Direct Comparison

Feature KEYS_ONLY INCLUDE ALL
Projected Attributes Primary keys only Primary keys + specific chosen attributes All attributes from the base table
Storage Usage Lowest Medium Highest
Write Cost (WCU) Lowest Low to Medium Highest
Read Latency High (if non-key data is needed) Low (for projected attributes) Low (for all attributes)
Base Table Fetch Needed? Yes, for any non-key data Yes, if querying unprojected data No, never
Schema Flexibility High Low (requires rebuilding index to change) High

Summary of Decision Criteria

To determine the correct projection:

  1. Use KEYS_ONLY if your application only needs to discover IDs or check for the presence of records.
  2. Use INCLUDE if your queries need specific data fields and you want to prevent large, unneeded attributes from inflating index storage and write costs.
  3. Use ALL if read speed is the top priority and your access patterns require full items on every query.
