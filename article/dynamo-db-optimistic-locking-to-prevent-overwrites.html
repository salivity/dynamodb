DynamoDB Optimistic Locking to Prevent Overwrites

Optimistic locking in Amazon DynamoDB prevents overwrite race conditions by ensuring that a write operation only succeeds if the underlying item has not been modified since it was last read. Instead of locking the database record during a read-modify-write cycle, DynamoDB uses a version attribute combined with conditional writes. If two processes attempt to update the same record simultaneously, the first write updates the version number and succeeds, while the second write fails because its expected version number no longer matches, thereby protecting against data loss from concurrent updates.

The Race Condition Problem

In distributed applications, race conditions commonly occur during read-modify-write workflows. For example, two independent clients might read an account balance of $100 at the exact same moment. Client A subtracts $20, preparing to write back $80. Client B adds $50, preparing to write back $150. If Client B writes its update immediately after Client A, Client A's transaction is completely overwritten and lost—a scenario known as the "last-write-wins" race condition.

How Optimistic Locking Works in DynamoDB

Optimistic locking assumes that multiple transactions can frequently complete without interfering with each other. Rather than placing a pessimistic lock on the record—which would block other readers and writers and degrade DynamoDB's distributed throughput—DynamoDB implements optimistic concurrency control through client-managed versioning and conditional expressions.

The strategy relies on three main components:

  1. A Version Attribute: Each item in the table includes a specific attribute used to track state changes, commonly named version, versionNumber, or a timestamp.
  2. Conditional Writes (ConditionExpression): When writing an update back to DynamoDB, the client specifies a condition requiring the item’s current version to match the version read at the start of the transaction.
  3. Version Increment: In the same update expression, the version number is incremented by one.

The Execution Lifecycle

  1. Read Item: A client issues a GetItem request to retrieve the target item and notes its current version (for example, version = 1).
  2. Modify Item: The client performs its business logic locally without holding any lock in the database.
  3. Conditional Update: The client issues an UpdateItem or PutItem operation with a ConditionExpression stating version = :current_version. In the UpdateExpression, the client sets version = version + 1.
  4. Validation:
    • Success: If no other process altered the item, DynamoDB writes the changes, increments the version to 2, and returns a success response.
    • Failure: If another process modified the item in the interim, the version in DynamoDB will already be 2. DynamoDB rejects the update atomically and returns a ConditionalCheckFailedException.

Handling Concurrency Collisions

When a ConditionalCheckFailedException is raised, the failed client must not simply force the write. Instead, the application layer typically catches the exception and initiates a retry loop using an exponential backoff with jitter strategy.

During the retry, the client re-reads the updated state (now containing the newest version and the previous writer's data), re-evaluates the business logic against the fresh data, and attempts the conditional write again with the new version number. This ensures all state transitions remain atomic, consistent, and safe from overwrite corruption without introducing database deadlocks.
