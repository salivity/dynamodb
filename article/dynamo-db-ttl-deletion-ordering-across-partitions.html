DynamoDB TTL Deletion Ordering Across Partitions

Amazon DynamoDB Time-to-Live (TTL) automatically removes expired items from tables at no extra cost, but its execution model across partitions is often misunderstood. This article explains how DynamoDB manages background TTL sweeps, why item deletion ordering across different partitions is entirely non-deterministic, and how this behavior affects downstream systems like DynamoDB Streams.

The Distributed Mechanics of DynamoDB TTL

DynamoDB TTL operates as an asynchronous, background sweeper running with low priority so it does not consume provisioned read or write throughput. Rather than maintaining a single, global queue of expiring items, DynamoDB delegates cleanup tasks locally across its distributed architecture.

A DynamoDB table is split into multiple physical storage units called partitions. Each partition manages a distinct segment of the table's data based on partition key hashes. Because partitions operate independently, the TTL scanning mechanism runs autonomously across these separate partitions without a centralized coordinator directing the precise order of eviction.

Lack of Cross-Partition Ordering

Because partition sweeps happen independently and in parallel:

  • No Global Expiration Sequence: An item on Partition A with an expiration timestamp of 12:00 PM may be deleted after an item on Partition B with an expiration timestamp of 12:15 PM. The absolute expiration timestamp does not dictate when the actual deletion occurs.
  • Variable Sweep Intervals: The background garbage collection process inspects partitions at variable intervals depending on node load, table size, and overall system activity. One partition's sweep may finish significantly faster than another's.
  • No Synchronization Overhead: Enforcing a global order across partitions would require expensive distributed locks and cross-node communication. To maintain high throughput and low latency, DynamoDB intentionally avoids any cross-partition deletion coordination.

DynamoDB only guarantees that marked items are typically deleted within 48 hours of expiration; it provides no guarantees regarding the order of deletion across partitions or even within the same partition.

Impact on DynamoDB Streams

When DynamoDB TTL deletes an item, it can emit a REMOVE event to DynamoDB Streams. The event record includes the system metadata identity showing that the deletion was initiated by the DynamoDB TTL service (principalId: "dynamodb.amazonaws.com").

Because cross-partition ordering does not exist:

  1. Shard Independence: In DynamoDB Streams, each stream shard aligns closely with underlying table partitions. Stream records are only strictly ordered within a single shard for a specific partition key.
  2. Out-of-Order Downstream Events: Lambda functions or worker services consuming the stream will receive TTL delete events out of order relative to the original expiration timestamps. Applications should never assume that events appearing in the stream correspond chronologically to the passage of expiration time.

Designing Around TTL Non-Determinism

Applications requiring strict time-based behavior across items must implement safeguards rather than relying on TTL deletion mechanics:

  • Filter in Read Queries: Because an item can remain in the table for up to 48 hours past its expiration, all client read operations (GetItem, Query, Scan) should include a condition or filter expression (e.g., AttributeExists(ttl) AND ttl > :current_time) to filter out logically expired data before it is physically deleted.
  • Decouple Event Workflows: If business logic requires actions to execute in a strict chronological sequence across multiple entities, do not trigger that logic from TTL stream events. Instead, use an explicit scheduling service such as Amazon EventBridge Scheduler or AWS Step Functions to trigger events precisely when required.
