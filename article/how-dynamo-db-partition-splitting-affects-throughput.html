How DynamoDB Partition Splitting Affects Throughput

This article examines the relationship between Amazon DynamoDB partition splitting, throughput allocation, and hot partitions. When DynamoDB splits a partition due to storage growth or high traffic, it fundamentally alters how Read Capacity Units (RCUs) and Write Capacity Units (WCUs) are distributed across the underlying physical storage nodes. Understanding this process clarifies why partition splitting does not inherently resolve performance bottlenecks caused by hot partition keys, how adaptive capacity mitigates throughput starvation, and where the hard limits of DynamoDB’s scaling model lie.

Understanding DynamoDB Partition Splitting

DynamoDB stores table data across multiple physical storage units called partitions. Each partition has hard capacity constraints:

  • Storage Limit: Up to 10 GB of data.
  • Throughput Limit: Up to 1,000 Write Capacity Units (WCUs) and 3,000 Read Capacity Units (RCUs).

A partition split occurs under two primary conditions:

  1. Size-based splitting: The data stored in a single partition exceeds 10 GB.
  2. Throughput-based splitting: The traffic directed to a partition consistently exceeds its maximum hardware allocation (1,000 WCUs or 3,000 RCUs).

When a split occurs, DynamoDB allocates an additional partition node and divides the hash range (or the items within that hash range) between the old and new physical locations.

Throughput Allocation Across Splits

Historically, DynamoDB divided a table's total provisioned throughput equally across all partitions. Under this legacy model, if a table had 4 partitions and 4,000 RCUs, each partition received 1,000 RCUs. If one partition split into two, the table now had 5 partitions, effectively diluting the baseline throughput of the child partitions to 800 RCUs each.

To fix this structural limitation, DynamoDB introduced Adaptive Capacity. Adaptive capacity decouples throughput distribution from rigid mathematical division. When a partition splits:

  • The baseline provisioned throughput is still calculated across partitions, but DynamoDB dynamically shifts unused capacity from idle partitions to busier ones.
  • Adaptive capacity responds within seconds, reallocating available table-level throughput to meet localized spikes.

However, adaptive capacity cannot bypass the physical hardware limit of a single partition.

The Impact on Hot Partitions

A "hot partition" occurs when access patterns disproportionately target a specific partition key. The effect of a partition split on a hot partition depends directly on the table's primary key design.

1. Simple Primary Key (Partition Key Only)

In a table with only a partition key (hash key), all items with the same partition key must reside on the same physical partition.

  • The Split Mechanism: If a partition splits because a single partition key generates extreme traffic, the partition key cannot be divided. DynamoDB moves other partition keys to the new child partition, isolating the hot partition key on its own dedicated partition.
  • The Throughput Result: Splitting does not dilute or multiply the capacity of the hot key. The hot key remains constrained by the hard ceiling of a single partition: 1,000 WCUs and 3,000 RCUs. If the incoming traffic exceeds this limit, the request will be throttled regardless of how many times the table splits.

2. Composite Primary Key (Partition Key and Sort Key)

In a table configured with a partition key and a sort key (range key), DynamoDB can split data across sort key boundaries.

  • The Split Mechanism: If a single partition key contains multiple gigabytes of data or high traffic across a wide range of sort keys, DynamoDB can split the sort key range across multiple partitions.
  • The Throughput Result: In this scenario, partition splitting genuinely improves throughput distribution. Traffic for that single partition key is now distributed across multiple physical nodes, effectively allowing total operations for that partition key to scale beyond the 1,000 WCU / 3,000 RCU limit, provided the traffic accesses different sort key ranges.

Potential Bottlenecks Post-Split

While partition splitting isolates high-traffic data, it can cause transient performance issues:

  • Cold Partition Allocation: Immediately following a split, adaptive capacity may take a brief period to detect the concentrated demand on the new child partition containing the hot key, resulting in brief bursts of ProvisionedThroughputExceededException errors.
  • Global Secondary Index (GSI) Bottlenecks: A split on the base table does not trigger a corresponding split on a GSI. If the hot write traffic propagates to an index that has not split, the GSI becomes the throttling bottleneck, throttling the base table writes as a consequence.

Summary

DynamoDB partition splitting manages storage scaling and isolates heavy traffic, but it is not an automatic cure for hot partitions. If workload concentration stems from a single partition key without a distributed sort key, splitting merely isolates the key to a dedicated node capped at 1,000 WCUs and 3,000 RCUs. Resolving hot partition bottlenecks ultimately requires application-level strategies, such as write sharding, random suffixing, or caching layers, rather than relying on partition splits.
