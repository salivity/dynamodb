DynamoDB Schema Evolution in Single-Table Design

Single-table design in Amazon DynamoDB optimizes performance and cost by consolidating multiple entity types into one physical table, but evolving data structures within this pattern requires deliberate planning. While DynamoDB is fundamentally schemaless at the attribute level, the access patterns, composite primary keys, and Global Secondary Indexes (GSIs) create an implicit schema that must be managed. This article explains how to handle schema and data format evolution in a single-table architecture using strategies like application-layer transformations, item versioning, lazy migrations, and managed index updates.

The Dual Nature of Schema in DynamoDB

DynamoDB only enforces data types on the primary key attributes (Partition Key and Sort Key) and any configured index keys. All other attributes within an item are entirely schemaless.

In a single-table design, data format changes fall into two distinct categories:

  1. Payload Evolution: Changes to standard attributes (e.g., renaming a field, changing a data type, adding/removing properties).
  2. Key and Access Pattern Evolution: Changes that affect how items are identified, queried, or indexed via Partition Keys (PK), Sort Keys (SK), or Global Secondary Indexes (GSIs).

Handling Payload Attribute Evolution

When changes do not affect primary keys or index attributes, DynamoDB requires no physical table alterations. The application handles the evolution using several techniques.

Application-Layer Adapters and Defaulting

The most resilient way to handle attribute changes is within the application's data access layer (DAL) or object-relational mapping (ORM) layer.

  • Tolerant Reader Pattern: Ensure the application accepts missing fields, unexpected fields, and deprecated formats without failing.
  • Sensible Defaults: If a new required field is introduced, the application layer should fall back to a default value when reading legacy items that lack the attribute.
  • Type Normalization: When changing data types (e.g., moving from a string timestamp to an epoch integer), the application read path should check the attribute type and convert it to the internal domain model automatically.

Lazy Migration (Read-Repair)

Rather than executing a bulk update across millions of records, lazy migration updates items as they are naturally accessed:

  1. The application reads an item in the old format.
  2. The domain layer transforms the item to the new format.
  3. Upon any subsequent write or explicit update call, the item is persisted back to DynamoDB in the new format.

Over time, active data naturally migrates to the latest format without incurring the compute costs or read/write capacity spikes of batch migration jobs.

Explicit Item Versioning

When an entity undergoes a structural change too complex for simple fallback defaults, store a schema version attribute on the item:

{
  "PK": "USER#123",
  "SK": "METADATA",
  "SchemaVersion": 2,
  "FullName": "Jane Doe"
}

Legacy records might feature "SchemaVersion": 1 with "FirstName" and "LastName" split. The application reads SchemaVersion and routes the payload to the corresponding deserialization strategy.

Handling Primary Key and Index Evolution

When an evolution requires altering the primary key structure (PK/SK) or supporting a new access pattern, the data format change becomes structural. Because DynamoDB primary keys are immutable once an item is written, existing keys cannot simply be updated.

Adding New Entities and Prefixes

Single-table design inherently supports non-breaking additions. Because primary keys typically use generic names (e.g., PK and SK) with prefixed values (e.g., CUSTOMER#<ID>, ORDER#<ID>), introducing a new entity type or relationship requires only defining a new prefix pattern. Existing entities and queries remain completely unaffected.

Dual-Writing for Key Migrations

If an existing entity’s key composition must change to support an altered access pattern:

  1. Update the Application: Deploy code that reads from the old key structure but writes to both the old and new key structures simultaneously (dual-writing).
  2. Backfill Historical Data: Use an asynchronous worker, AWS Glue, or an Amazon EMR job to scan the table, transform legacy keys into the new format, and write the new records.
  3. Switch Reads: Update the application to read from the new key structure.
  4. Remove Dual-Writing and Clean Up: Decommission writes to the legacy format and delete the obsolete records using DynamoDB's Time to Live (TTL) or a batch deletion script.

Using Global Secondary Indexes (GSIs) for New Patterns

If access patterns change but the primary data does not need key restructuring, use sparse GSIs:

  • GSIs can be created or deleted on an existing table at any time without downtime.
  • By populating new GSI attributes on target items, only the relevant records project into the new index.
  • DynamoDB automatically backfills existing data into a newly created GSI as long as the projection attributes exist on the base items.

Asynchronous Transformation via DynamoDB Streams

For high-traffic systems where live dual-writing introduces unwanted latency or transaction overhead, use DynamoDB Streams coupled with AWS Lambda:

  1. Continue writing data using the legacy format.
  2. A Lambda function processes the stream of modifications, transforms the items into the new format, and writes them back to the table under the new key pattern.
  3. Once backfilling and stream processing are synchronized, switch the read and write paths directly to the new format.
