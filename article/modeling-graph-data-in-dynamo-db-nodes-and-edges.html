Modeling Graph Data in DynamoDB: Nodes and Edges

Amazon DynamoDB can efficiently store and query graph data structures by implementing the adjacency list pattern within a single-table design. While DynamoDB is natively a key-value and document database, mapping graph elements to its partition key and sort key schema allows for predictable, low-latency graph traversals. This article explains how to represent nodes and edges as distinct items, store their properties, and configure secondary indexes for bidirectional graph queries.

The Adjacency List Design Pattern

In graph theory, an adjacency list represents a graph as a collection of vertices (nodes), where each vertex stores a list of its adjacent vertices via connecting links (edges). In DynamoDB, this pattern is implemented by co-locating a node and its outgoing edges within the same partition key (PK), distinguishing between node metadata and edge connections using the sort key (SK).

Representing Nodes

A node represents an entity in the graph (such as a user, device, or category). In a single table, a node is represented as an item where the partition key uniquely identifies the node, and the sort key acts as a designated self-identifier or metadata tag.

  • Partition Key (PK): Contains the node identifier, typically prefixed by entity type (e.g., USER#123 or DEVICE#456).
  • Sort Key (SK): Identifies the item as node metadata (e.g., METADATA#USER#123 or simply NODE).
  • Attributes: Specific properties belonging to the node itself, such as names, creation dates, or status flags.

For example, a user node item appears as:

  • PK: USER#101
  • SK: METADATA
  • Name: Alice
  • Type: User

Representing Edges

An edge represents a directed relationship from an origin node to a destination node (such as "follows", "purchased", or "connected_to"). In DynamoDB, an edge is stored as a separate item that shares the origin node's partition key, while the sort key points to the target node.

  • Partition Key (PK): Matches the origin node's ID (e.g., USER#101).
  • Sort Key (SK): Contains the target node's ID, often prefixed with the relationship type (e.g., FRIEND#USER#202).
  • Attributes: Properties specific to the relationship, such as relationship strength, weight, or timestamps.

For example, an edge indicating that Alice follows Bob appears as:

  • PK: USER#101
  • SK: FOLLOWS#USER#202
  • Since: 2023-01-15
  • TargetType: User

Querying Outgoing Relationships (Forward Traversal)

Because the origin node and all its outgoing edges share the same partition key, retrieving a node and its direct connections requires a single Query operation:

  • Set PK = USER#101
  • Use key condition expressions to filter the sort key. Querying SK begins_with("FOLLOWS#") retrieves all the users that Alice follows. Querying without a sort key condition retrieves both the node metadata and all outgoing edges of every type.

Representing Incoming Relationships (Reverse Traversal)

Graph queries often require traversing relationships in reverse (e.g., finding all users who follow Alice). Because standard DynamoDB queries can only search by partition key, reverse traversal requires a Global Secondary Index (GSI) using an inverted index pattern.

  • GSI Partition Key (GSI_PK): Set to the target node's identifier (the base table's SK value, or a dedicated attribute like TargetID).
  • GSI Sort Key (GSI_SK): Set to the origin node's identifier (the base table's PK value).

When an edge item is written:

  • Base Table: PK = USER#101, SK = FOLLOWS#USER#202
  • GSI: GSI_PK = USER#202, GSI_SK = USER#101

Querying the GSI where GSI_PK = USER#202 returns all incoming edges pointing to Bob, effectively listing Bob's followers without requiring full table scans.
