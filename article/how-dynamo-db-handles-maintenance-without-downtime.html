How DynamoDB Handles Maintenance Without Downtime

Amazon DynamoDB maintains continuous availability during internal hardware maintenance through a combination of multi-Availability Zone (AZ) data replication, automated leader election, intelligent request routing, and non-blocking fleet management. By decoupling logical storage partitions from physical infrastructure, DynamoDB seamlessly replaces, upgrades, and retires physical servers without causing application downtime or violating strict latency service-level agreements.

Multi-AZ Partition Replication

DynamoDB stores data in partitions, which are automatically distributed across storage nodes. For high availability, every partition is replicated across at least three physical storage nodes located in distinct Availability Zones (AZs). This three-way replication forms a replica group. Because the data resides simultaneously in geographically separated data centers, any single physical machine can undergo scheduled maintenance or unexpected failure without putting the data at risk.

Paxos Consensus and Graceful Failovers

Within each three-node replica group, one node acts as the leader, while the other two act as followers. The leader processes write requests and writes them to a write-ahead log, requiring a quorum (two out of three nodes) to acknowledge the write using the Paxos consensus algorithm.

When hardware hosting a follower node requires maintenance, it can be taken offline immediately because the remaining two nodes still satisfy the write quorum and can handle strongly consistent reads. If the leader node resides on a machine scheduled for maintenance, DynamoDB initiates a graceful handoff. The leader steps down, and the remaining nodes elect a new leader using Paxos in a matter of milliseconds, preventing any interruption to read or write traffic.

Automated Node Replacement and Synchronization

When physical servers near end-of-life or require hardware component updates, DynamoDB’s internal orchestration system replaces the storage nodes:

  1. Provisioning: A new replica is initialized on healthy, modern hardware within the same Availability Zone.
  2. Log Catch-Up: The new replica streams snapshot data and transaction logs from the existing healthy replicas.
  3. Membership Update: Once the new node is fully synchronized with the rest of the replica group, the internal membership is updated to include it.
  4. Decommissioning: The old node on the legacy or faulty hardware is removed from the replica set and safely shut down.

Intelligent Request Routing

DynamoDB separates storage from the compute layer that receives client traffic. Applications interact with a fleet of stateless Request Routers. These routers continuously receive real-time topology maps indicating the health and status of every partition replica. If a storage node is being taken down for maintenance, the routers dynamically redirect incoming client requests exclusively to active, healthy nodes, avoiding failed connection attempts and eliminating client-side errors.
