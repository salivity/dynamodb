How DynamoDB GSI Backfilling Works

When you create a Global Secondary Index (GSI) on an existing Amazon DynamoDB table, DynamoDB initiates an asynchronous backfilling process to populate the new index with your historical data. This article breaks down the phases of the GSI backfilling lifecycle, how data is synchronized from the base table to the index, the impact on read and write capacity, and the potential performance risks to be aware of during the operation.

The GSI Lifecycle Phases

When adding a GSI to an existing table, the index transitions through three distinct status phases:

  1. CREATING: DynamoDB allocates the underlying storage partitions required to host the new index data based on the projected volume and specified throughput settings.
  2. BACKFILLING: DynamoDB scans the base table and copies relevant items into the newly allocated GSI storage partitions. During this phase, it also buffers and applies ongoing mutations.
  3. ACTIVE: The backfilling process is complete, data is fully synchronized, and the index is available to serve read queries.

The Mechanics of the Backfill

The backfill operation consists of two simultaneous processes: historical data ingestion and real-time mutation streaming.

1. Scanning Historical Data

DynamoDB reads data across all partitions of the base table. As it reads each item, it checks whether the item contains the partition key (and optional sort key) defined for the new GSI:

  • If the item contains the index key attributes, DynamoDB projects the configured attributes (KEYS_ONLY, INCLUDE, or ALL) and writes the record to the GSI.
  • If the item lacks the index key attributes, it is skipped.

2. Processing Real-Time Writes

While the historical scan is underway, your application continues to perform PutItem, UpdateItem, and DeleteItem operations on the base table. DynamoDB tracks these concurrent changes and applies them directly to the new GSI. This ensures that by the time the historical scan finishes, the GSI reflects all current data without dropping any real-time changes.

Capacity Consumption and Throttling Risks

The backfilling process consumes resources differently across the base table and the new index:

Base Table Read Capacity

DynamoDB performs the historical table scan using internal system capacity. In most scenarios, this scan does not consume the base table’s provisioned Read Capacity Units (RCUs), minimizing the impact on your normal read workloads.

GSI Write Capacity

The backfill process writes data to the new index, which directly consumes the GSI’s Write Capacity Units (WCUs):

  • On-Demand Mode: DynamoDB automatically scales the write capacity of the new GSI to accommodate the backfill rate alongside incoming writes.
  • Provisioned Mode: You must allocate sufficient WCUs to the GSI. If the provisioned WCU is too low, the backfill will take significantly longer to complete.

The Base Table Throttling Risk

In provisioned mode, if incoming write traffic to the base table exceeds the write throughput of the backfilling GSI, the base table's write requests can be throttled. Because DynamoDB guarantees that an active write must be committed to both the base table and any attached GSI (even while building), a bottleneck in the GSI write capacity directly impacts the write availability of the base table.

Monitoring the Process

You can track the state of the backfilling operation using the AWS Management Console, the AWS CLI (describe-table), or Amazon CloudWatch.

  • The OnlineIndexPercentageProgress metric reports the progress of the backfill operation from 0% to 100%.
  • Monitor WriteThrottleEvents on both the base table and the index to ensure that the GSI has sufficient write allocation during the build phase.
