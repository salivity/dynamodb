DynamoDB Partition Keys and Physical Storage Nodes

Amazon DynamoDB achieves horizontal scale by mapping partition keys to physical storage nodes through an automated hashing mechanism. This article explores how DynamoDB processes a partition key, hashes its value to assign data to logical partitions, and ultimately maps those partitions across a distributed fleet of replicated storage nodes to deliver consistent, single-digit millisecond latency at any scale.

The Role of the Partition Key and Hashing

Every item stored in a DynamoDB table requires a primary key. When using a simple primary key (partition key only) or a composite primary key (partition key and sort key), the partition key acts as the input to an internal, deterministic hash function.

When a read or write request enters DynamoDB, the service runs the partition key through this hashing algorithm. The resulting 128-bit hash value determines the specific logical partition responsible for storing that item. Because identical partition key values always produce identical hash outputs, all items sharing the exact same partition key are guaranteed to reside on the same logical partition.

Logical Partitions vs. Physical Storage Nodes

To understand DynamoDB architecture, you must distinguish between logical partitions and physical storage nodes:

  • Logical Partitions: A logical partition is an allocation of storage (up to 10 GB) and performance capacity (up to 1,000 write capacity units or 3,000 read capacity units).
  • Physical Storage Nodes: A storage node is an underlying server equipped with Solid State Drives (SSDs) running the DynamoDB storage engine. A single physical storage node hosts multiple logical partitions from various tables and customers.

A logical partition does not map to a single isolated physical server. Instead, it maps to a Replication Group consisting of three physical storage nodes distributed across multiple Availability Zones (AZs) in an AWS Region. One node acts as the Paxos leader responsible for coordinating writes, while the other two act as replicas.

The Request Routing Mechanism

DynamoDB decouples the application layer from physical hardware using an internal routing fleet:

  1. Request Router: When an application sends a query, read, or write command, it hits a stateless DynamoDB Request Router.
  2. Partition Map Lookup: The Request Router hashes the partition key and checks an internal routing cache (the Partition Map) to see which logical partition covers that hash range.
  3. Physical Forwarding: The router identifies the replication group of physical storage nodes assigned to that logical partition and forwards the request directly to the appropriate physical node (the leader for writes, or any healthy node for eventually consistent reads).

Partition Splitting and Node Reallocation

As a table grows, DynamoDB automatically scales without service interruption through partition splitting. A partition split occurs when:

  • The data allocated to a logical partition exceeds 10 GB.
  • The workload on a partition exceeds 1,000 WCUs or 3,000 RCUs.

When a split happens, DynamoDB allocates a new logical partition, divides the hash space, and rebalances the data. The new logical partition is often placed on a different replication group across different physical storage nodes. This dynamic reallocation spreads the compute and I/O workload across a wider footprint of physical hardware.

Architectural Implications for Key Design

Because physical nodes are assigned based on hash distribution, uniform partition key access is critical. If your application concentrates traffic on a small subset of partition keys—known as a "hot key" scenario—requests funnel into a single logical partition mapped to a single physical replication group.

Even though DynamoDB uses adaptive capacity to temporarily shift unused throughput from other partitions, severe hot keys will eventually exhaust the throughput limits of the physical storage nodes serving that partition. Designing high-cardinality partition keys ensures that the hash values distribute evenly across the entire range of logical partitions and physical storage nodes.
