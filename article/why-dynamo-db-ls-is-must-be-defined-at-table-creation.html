Why DynamoDB LSIs Must Be Defined at Table Creation

This article explains the architectural reasons why Amazon DynamoDB requires Local Secondary Indexes (LSIs) to be defined exclusively at table creation time. While Global Secondary Indexes (GSIs) can be created, updated, or deleted at any stage of a table's lifecycle, LSIs remain permanently bound to the initial schema. Below, we examine the underlying storage mechanisms, synchronous write requirements, and partition constraints that dictate this restriction.

Shared Storage Partitions and Colocation

The primary reason an LSI cannot be added later is physical data colocation. An LSI uses the same partition key as the underlying base table, only altering the sort key.

In DynamoDB's distributed architecture, all items that share the same partition key are stored together on the same physical storage node (partition). When you configure an LSI, the index data is written directly to the exact same partition where the base table items reside. Because the index data must physically live inside the existing table's partitions alongside the main item collection, DynamoDB cannot simply allocate a separate set of nodes to backfill the data later.

Synchronous Write Operations and Strong Consistency

Unlike GSIs, which are updated asynchronously, LSIs support strongly consistent reads. To provide strong consistency, any PutItem, UpdateItem, or DeleteItem call on the base table must synchronously update the LSI within the same transaction-like boundary on that storage node.

Retroactively adding an LSI to an existing table would require:

  • Locking or pausing writes to prevent data divergence while indexing existing data.
  • Rewriting data structures directly inside live, populated storage partitions across a distributed cluster.

Because DynamoDB is designed for predictable, single-digit millisecond latency at any scale, performing a resource-heavy, synchronous backfill within live data partitions is fundamentally opposed to its design principles.

The 10 GB Item Collection Limit

When a table has one or more LSIs, DynamoDB enforces a strict 10 GB size limit on any single "item collection" (all items sharing the same partition key).

If you were permitted to add an LSI to an existing table, DynamoDB might encounter existing item collections that already exceed 10 GB. An index cannot be applied to collections that violate this limit, which would cause an unresolvable conflict without deleting or rejecting pre-existing data. Defining the LSI at creation ensures that the 10 GB constraint is enforced from the very first write.

Alternatives When Schema Requirements Change

If your application requires a new index on an existing DynamoDB table, you must use one of the following approaches:

  1. Use a Global Secondary Index (GSI): GSIs can be created at any time on an active table. A GSI can use the same partition key as the base table with a different sort key, functioning similarly to an LSI, though it only supports eventually consistent reads and consumes its own provisioned or on-demand throughput.
  2. Table Migration: If an LSI and strong consistency are strictly required, you must create a new DynamoDB table with the desired LSI defined from the start, then migrate your existing data to the new table using tools such as AWS Application Migration Service, DynamoDB Streams with AWS Lambda, or AWS Glue.
