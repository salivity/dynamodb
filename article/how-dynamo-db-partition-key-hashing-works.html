How DynamoDB Partition Key Hashing Works

Amazon DynamoDB relies on consistent hashing algorithms and an internal hash ring architecture to distribute data and throughput evenly across distributed physical storage nodes. When an item is written or queried, DynamoDB generates an internal hash value from the partition key, places that value onto a fixed 128-bit integer space, and maps it directly to a specific physical storage partition. Understanding this internal calculation reveals how DynamoDB manages horizontal scaling, partition splits, and ultra-low latency routing without global locking or cluster-wide rebalancing.

The Internal Hash Function and Token Space

When an item is processed, DynamoDB extracts the partition key attribute and computes a 128-bit hash value using an internal variant of the MD5 hashing algorithm. This computation outputs a scalar integer within an immutable token space ranging from 0 to \(2^{128} - 1\).

This uniform numerical range represents a closed hash ring. Because the hashing function provides pseudo-random distribution, partition key values—even sequential or lexicographically similar ones—are dispersed evenly across the entire 128-bit spectrum, minimizing the probability of accidental data clustering.

Partition Boundaries and the Hash Ring

A DynamoDB table is divided into multiple storage partitions, each responsible for a contiguous, non-overlapping segment of the 128-bit hash ring.

  1. Range Assignment: Each physical storage partition is assigned an upper and lower hexadecimal boundary on the ring.
  2. Key Placement: When an item's hash is evaluated, DynamoDB identifies the partition whose assigned segment covers that specific hash integer.
  3. Storage Group Mapping: Partitions are not single servers; each range corresponds to a three-node replication group distributed across Availability Zones operating under a Paxos consensus model.

Request Routers and the Partition Map

Client requests do not hit storage nodes directly. Instead, they land on stateless Request Routers within the DynamoDB fleet:

  • Hash Evaluation: The Request Router hashes the incoming partition key locally in microseconds.
  • Partition Map Lookup: The router consults an in-memory cache of the table's "Partition Map." This map translates the calculated 128-bit integer into the specific storage replica group responsible for that token range.
  • Direct Routing: The router immediately directs the read or write request to the appropriate node (the Paxos leader for strong consistency/writes, or any healthy replica for eventually consistent reads).

Partition Splits and Dynamic Range Management

As tables grow in data size (exceeding 10 GB per partition) or provisioned throughput (exceeding 1,000 WCUs or 3,000 RCUs per partition), DynamoDB splits partitions automatically. The hash ring architecture accommodates this without rehashing the entire table:

  • Range Bisection: A partition range \([A, B]\) is split into two child ranges: \([A, M]\) and \([M+1, B]\), where \(M\) is typically the midpoint of the token space or a point calculated to split the existing data volume evenly.
  • Local Data Migration: Only the data residing in the newly designated half \([M+1, B]\) is transferred to a newly allocated partition group.
  • Map Propagation: The internal Partition Map Service updates the table metadata. The Request Routers invalidate their local caches and update their boundaries asynchronously, ensuring requests route to the new endpoints with zero downtime.

This localized splitting preserves the integrity of the remaining hash ring, allowing DynamoDB to scale linearly to virtually unlimited throughput and storage capacity.
