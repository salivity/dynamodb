DynamoDB Limits on Global Secondary Indexes per Table

Amazon DynamoDB places specific quotas on the number of Global Secondary Indexes (GSIs) a single table can support to ensure predictable performance and resource allocation. This article explains the default limits on GSIs, how DynamoDB validates and enforces these thresholds through its control plane APIs, and how developers can manage or design around these limits.

The GSI Limit per Table

By default, DynamoDB enforces a quota of 20 Global Secondary Indexes per table. This is a soft limit managed through AWS Service Quotas, meaning AWS accounts can request an increase—often up to 50 or more, depending on approval and region availability.

How DynamoDB Enforces the Quota

DynamoDB uses control plane validation mechanisms to actively enforce index limits during table creation and modification:

1. Control Plane API Validation

DynamoDB validates index limits whenever a client issues a CreateTable or UpdateTable API request.

  • During CreateTable, DynamoDB counts the objects within the GlobalSecondaryIndexes array. If the total exceeds the table's allocated quota, the request is rejected immediately before any resources are provisioned.
  • During UpdateTable, DynamoDB inspects the existing active indexes alongside the proposed additions. If the addition would cause the total count to exceed the quota, the API call fails.

2. Synchronous Exception Handling

When a request breaches the configured threshold, DynamoDB does not queue or partially process the request. Instead, it rejects the operation synchronously with a client-side error:

  • ValidationException: Returned when the request payload contains more indexes than permissible.
  • LimitExceededException: Returned if the account or table has reached the maximum permitted capacity for metadata modifications or total indexes.

3. Concurrent Creation Restrictions

In addition to the total index count limit, DynamoDB enforces limits on concurrent GSI lifecycle operations:

  • When using UpdateTable, you can only create or delete one GSI at a time per table.
  • Attempting to add a new GSI while another is in the CREATING or DELETING state triggers a ResourceInUseException.

Why DynamoDB Enforces GSI Quotas

The enforcement of GSI limits is rooted in the underlying storage and replication architecture:

  • Write Amplification: Every write, update, or delete to a primary table must be asynchronously replicated to all its GSIs. Each additional index multiplies the consumed write capacity and processing overhead.
  • Resource Management: Each GSI is provisioned as an independent storage structure across DynamoDB partitions. Limiting the total indexes helps prevent storage and partition sprawl for a single dataset.

Working Within GSI Limits

When an application approaches the index ceiling, two approaches are available:

  1. Request a Quota Increase: Submit a service quota increase request via the AWS Service Quotas console for the metric "Global secondary indexes per table."
  2. GSI Overloading: In single-table designs, reuse generic partition key and sort key names (such as GSI1PK and GSI1SK) to store different entity types within the same index, drastically reducing the total number of GSIs required.
