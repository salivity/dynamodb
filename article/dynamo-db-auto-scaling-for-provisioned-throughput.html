DynamoDB Auto Scaling for Provisioned Throughput

Amazon DynamoDB auto scaling dynamically adjusts provisioned throughput capacity in response to actual traffic patterns using the AWS Application Auto Scaling service. This mechanism enables tables and global secondary indexes to handle sudden workload increases without throttling while scaling down capacity during periods of low activity to minimize costs. Configuring these policies requires defining target tracking metrics, capacity boundaries, and cooldown timers that dictate how and when capacity adjustments take place.

The Target Tracking Policy

Auto scaling in DynamoDB is governed by a target tracking scaling policy. Instead of defining manual step-based scaling rules, you set a target utilization percentage for your provisioned throughput. Utilization is calculated as the ratio of consumed capacity units to provisioned capacity units over a given period:

\[\text{Utilization} = \frac{\text{Consumed Capacity Units}}{\text{Provisioned Capacity Units}} \times 100\]

A common target utilization is 70%. If traffic increases and consumed capacity exceeds 70% of the provisioned level, DynamoDB automatically increases provisioned capacity to bring the ratio back down. If traffic drops and utilization falls below 70%, the service reduces provisioned capacity accordingly.

Core Configuration Parameters

When applying an auto scaling policy to provisioned throughput, you must configure the following settings:

  • Scaling Metric: Auto scaling policies are applied separately to Read Capacity Units (RCUs) and Write Capacity Units (WCUs). A table can have different scaling behaviors for reads versus writes.
  • Target Utilization: The desired percentage of consumed capacity relative to provisioned capacity (recommended between 50% and 80%).
  • Minimum Capacity Units: The lower bound of capacity the table will maintain, regardless of how low the traffic drops. This guarantees a baseline level of performance.
  • Maximum Capacity Units: The upper bound of throughput the table can scale to. This protects against unexpected traffic spikes or runaway application queries driving up operational costs.
  • Scale-Out Cooldown Period: The duration (in seconds) the system waits after a capacity increase before allowing another scale-out action. This ensures recent adjustments have taken effect before adding more capacity.
  • Scale-In Cooldown Period: The duration (in seconds) the system waits after a capacity reduction before allowing another scale-in action. This prevents rapid capacity fluctuations ("thrashing") when traffic patterns are erratic.

Global Secondary Index (GSI) Considerations

Auto scaling policies must be applied explicitly to Global Secondary Indexes in addition to the base table. While a base table and its GSIs can have independent policies, a GSI's write capacity should always be provisioned to scale along with the base table's write throughput. If a GSI lacks sufficient write capacity to accommodate updates from the base table, write throttling will occur on the base table itself.

The Scaling Execution Workflow

Once an auto scaling policy is active, the operational flow follows an automated cycle:

  1. Monitoring: DynamoDB continuously publishes consumed throughput metrics to Amazon CloudWatch.
  2. Alarm Trigger: CloudWatch manages target tracking alarms based on your utilization percentage. If actual utilization consistently breaches the target, an alarm is triggered.
  3. Capacity Modification: CloudWatch notifies AWS Application Auto Scaling, which calculates the exact capacity units required to restore the target utilization.
  4. Table Update: Application Auto Scaling issues an UpdateTable request to DynamoDB, altering the provisioned RCUs or WCUs within your specified minimum and maximum thresholds.
