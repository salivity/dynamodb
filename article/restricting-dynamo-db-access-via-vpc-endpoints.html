Restricting DynamoDB Access via VPC Endpoints

Restricting Amazon DynamoDB API calls to private networks is a fundamental practice for securing sensitive cloud workloads. This article details the primary security controls used to restrict DynamoDB access to specific Virtual Private Clouds (VPCs). It focuses on VPC endpoint policies and AWS Identity and Access Management (IAM) condition keys, explaining how these mechanisms work in tandem to prevent unauthorized data access and limit traffic strictly to designated endpoints.

The Primary Control: VPC Endpoint Policies

The core security control that restricts DynamoDB access at the network boundary is the VPC Endpoint Policy.

DynamoDB uses a Gateway VPC Endpoint to allow instances within a private subnet to communicate with DynamoDB without crossing the public internet. By default, a DynamoDB VPC endpoint allows full access (*) to all DynamoDB actions and resources. However, you can attach an endpoint policy directly to the VPC endpoint to restrict this traffic.

An endpoint policy is a JSON-based resource policy that determines:

  • Principals: Which IAM users, roles, or AWS accounts can send requests through the endpoint.
  • Actions: Which DynamoDB API operations (such as dynamodb:GetItem or dynamodb:PutItem) are permitted.
  • Resources: Which specific DynamoDB table Amazon Resource Names (ARNs) can be accessed.

By scoping down the endpoint policy, you ensure that even if an identity has administrative DynamoDB permissions in IAM, it cannot use that specific VPC endpoint to interact with unauthorized tables or perform restricted actions.

Enforcing VPC Origin with IAM Condition Keys

While an endpoint policy dictates what traffic can pass out of a VPC to DynamoDB, the complementary control that enforces access only through a VPC endpoint is the IAM Policy Condition Key.

To guarantee that requests to a DynamoDB table originate solely from a specific VPC endpoint, administrators must use the aws:sourceVpce condition key within IAM policies or DynamoDB resource-based policies.

How aws:sourceVpce Works

By adding a condition block with aws:sourceVpce, you can explicitly deny or restrict DynamoDB API calls unless the request passes through the designated VPC endpoint ID (e.g., vpce-1a2b3c4d).

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RestrictDynamoDBToVpce",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "dynamodb:*",
      "Resource": "arn:aws:dynamodb:region:account-id:table/MySecureTable",
      "Condition": {
        "StringNotEquals": {
          "aws:sourceVpce": "vpce-1a2b3c4d"
        }
      }
    }
  ]
}

Alternatively, the aws:sourceVpc condition key can be used to restrict calls to an entire VPC ID rather than a specific endpoint ID, though aws:sourceVpce provides more granular control.

Combining Controls for Defense-in-Depth

Achieving comprehensive security requires using both controls simultaneously:

  1. VPC Endpoint Policies prevent data exfiltration by ensuring that workloads inside the VPC can only reach authorized DynamoDB tables.
  2. IAM Policies with aws:sourceVpce prevent unauthorized access from external networks by ensuring that the targeted DynamoDB table rejects any API call that does not originate from the approved VPC endpoint.
