DynamoDB Rate Limiting Across Multiple Apps

When multiple applications share a single Amazon DynamoDB table, rate limiting is enforced centrally at the table and partition levels rather than on an application-by-application basis. DynamoDB manages throughput by measuring total consumed Read Capacity Units (RCUs) and Write Capacity Units (WCUs)—or On-Demand Request Units—against the table's total provisioned or allocated limits. Because the database engine does not inherently distinguish between traffic origins for quota enforcement, all connected applications draw from the same shared pool of throughput. When the collective demand exceeds the table's configured capacity, DynamoDB uniformly throttles excessive requests using a token bucket algorithm.

The Token Bucket Algorithm

DynamoDB uses the token bucket algorithm to enforce read and write limits:

  • Token Generation: DynamoDB continuously adds tokens to a table's "bucket" at a fixed rate determined by the provisioned RCUs and WCUs.
  • Token Consumption: Every read or write operation consumes a specific number of tokens based on the size of the item and the consistency model (e.g., strongly consistent vs. eventually consistent).
  • Depletion and Throttling: When requests arrive faster than tokens are replenished, the bucket empties. Any application attempting an operation when insufficient tokens are available receives a ProvisionedThroughputExceededException (HTTP 400).

Partition-Level Allocation

DynamoDB divides table data across multiple physical storage partitions based on item partition keys. Throughput is distributed across these underlying partitions:

  • Capacity Distribution: Total table throughput is divided among all physical partitions.
  • Partition Throttling: If Application A sends a high volume of requests targeting the same partition key, it can exhaust the capacity assigned to that specific physical partition.
  • Impact on Other Apps: If Application B attempts to read or write data located on that same physical partition, Application B will also be throttled, regardless of how few requests it makes overall.

Adaptive Capacity and Burst Management

To prevent uneven traffic from immediately degrading performance across shared applications, DynamoDB includes automated capacity safeguards:

  • Burst Capacity: DynamoDB retains up to 300 seconds (5 minutes) of unused read and write capacity to accommodate sudden, temporary traffic spikes from any connected application.
  • Adaptive Capacity: If one application causes continuous, disproportionate traffic on a specific partition, DynamoDB automatically shifts unallocated capacity from quieter partitions to the hot partition, minimizing throttling across other workloads.

Global Secondary Indexes (GSIs)

Rate limits are also enforced on Global Secondary Indexes associated with the shared table:

  • If any application performs a write operation to the base table that updates an indexed attribute, DynamoDB automatically writes that update to the GSI.
  • If the GSI lacks sufficient write capacity, the write on the base table is throttled, halting operations for all applications attempting to write to that table.

Multi-Tenant Isolation Constraints

DynamoDB does not natively offer per-client, per-IAM-role, or per-application rate limiting on a single table. Because throughput is strictly accounted for at the resource level:

  • A single misconfigured application can consume the entire token allocation (a "noisy neighbor" scenario).
  • Applications requiring strict quality-of-service guarantees must implement rate-limiting upstream (such as via Amazon API Gateway, AWS WAF, or an application-level token bucket) or isolate their data into dedicated tables.
