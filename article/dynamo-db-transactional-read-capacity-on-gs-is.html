DynamoDB Transactional Read Capacity on GSIs

Amazon DynamoDB provides strict consistency and isolation through transactional operations, but capacity calculations depend entirely on the target resource and operation type. This article explains the capacity consumption rules for transactional reads, why transactional read operations cannot be executed against Global Secondary Indexes (GSIs), how transactional read capacity is calculated on base tables, and how transactions impact GSI capacity during write operations.

Transactional Reads on Global Secondary Indexes

Amazon DynamoDB does not support transactional read operations (TransactGetItems) on Global Secondary Indexes (GSIs). Consequently, DynamoDB does not calculate or consume Read Capacity Units (RCUs) for transactional reads on GSIs because the operation is fundamentally unsupported.

GSIs in DynamoDB are updated asynchronously and only support eventually consistent reads. Because transactional read requests require serializable isolation and strong consistency, they can only target base tables. If an application attempts to perform a TransactGetItems request against a GSI, DynamoDB returns a ValidationException.

How DynamoDB Calculates Capacity for Transactional Reads

Transactional reads are executed on base tables using the TransactGetItems API. When DynamoDB processes a transactional read, capacity is calculated as follows:

  • Two RCUs per 4 KB: DynamoDB consumes two Read Capacity Units for each 4 KB chunk of data read per item. This is double the capacity of a standard strongly consistent read (which consumes one RCU per 4 KB) and four times that of an eventually consistent read (which consumes 0.5 RCU per 4 KB).
  • Per-Item Rounding: Each item read within the transaction is rounded up to the nearest 4 KB boundary before doubling. For instance, reading an item of 3 KB consumes 2 RCUs, while reading an item of 6 KB consumes 4 RCUs.
  • On-Demand Mode: For tables using on-demand capacity mode, DynamoDB charges two Read Request Units (RRUs) per 4 KB read per item.

GSI Capacity Consumption During Transactional Writes

While transactional reads cannot run against GSIs, transactional writes (TransactWriteItems) frequently affect them.

When a TransactWriteItems call creates, updates, or deletes an item in a base table that alters an attribute projected into a GSI, DynamoDB updates the GSI asynchronously. The capacity consumed on the GSI is calculated as follows:

  • Two WCUs per 1 KB: A transactional write consumes two Write Capacity Units (WCUs) per 1 KB of data written to the GSI.
  • Update Costs: If an update modifies a GSI key attribute, DynamoDB performs two operations on the GSI: a delete of the old index entry and a put of the new index entry. Both actions consume transactional write capacity on the GSI.

Workarounds for Consistent Reads on Secondary Attributes

If an application requires transactional or strongly consistent reads on attributes other than the base table's primary key:

  1. Query the GSI for Primary Keys: Perform an eventually consistent read against the GSI to retrieve the base table's partition and sort keys.
  2. Execute TransactGetItems on the Base Table: Use the retrieved keys to perform a transactional read against the base table, ensuring strong consistency and serializable isolation for the retrieved data.
  3. Table Redesign: Utilize single-table design strategies, such as inverted indexes or overloaded primary keys, to allow the required data to be read directly from the base table using primary key lookups.
