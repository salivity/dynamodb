How DynamoDB Orders Items with Same Partition Key

Amazon DynamoDB maintains order among items sharing the same partition key by utilizing a secondary attribute known as the Sort Key, historically referred to as a Range Key. When a table uses a composite primary key—composed of a partition key and a sort key—all items with identical partition key values are co-located on the same physical storage node and stored in sorted order according to the sort key. This article explains the underlying mechanisms DynamoDB uses to organize, store, and retrieve ordered data within a shared partition.

Storage and Colocation

DynamoDB uses the partition key value as an input to an internal hash function. The output of this hash function determines the specific storage partition (or node) where the item will reside.

When multiple items share the same partition key value, they are assigned to the exact same partition. On that physical partition, the storage engine organizes the items in an internal data structure—typically an indexed B-tree or Log-Structured Merge-tree (LSM-tree)—ordered entirely by the sort key attribute. Because items sharing a partition key are physically clustered and presorted on disk, DynamoDB does not need to perform an in-memory sort operation when reading them.

Data Type Sorting Rules

DynamoDB orders items based on the data type defined for the sort key:

  • String (S): Strings are ordered based on the UTF-8 binary encoding bytes of each character. This results in standard lexicographical (dictionary-like) ordering based on character code points.
  • Number (N): Numbers are stored and sorted by their exact mathematical value, regardless of precision or scale. Negative numbers precede zero, and zero precedes positive numbers.
  • Binary (B): Binary attributes are compared and ordered byte-by-byte in unsigned ascending order.

Retrieving Ordered Items with the Query API

DynamoDB exposes this intrinsic ordering through the Query API. A Query operation requires a partition key and searches only the collection of items that share that key.

  • Default Sort Direction: By default, a query returns results in ascending order according to the sort key.
  • Reversing Order: Setting the ScanIndexForward parameter to false instructs DynamoDB to traverse the storage structure in reverse, returning items in descending order without incurring a performance penalty.
  • Key Conditions: Applications can narrow the ordered results by using key condition expressions (such as =, <, <=, >, >=, BETWEEN, or begins_with) on the sort key. Because the data is already physically ordered, DynamoDB can quickly seek to the starting point of the range and read forward or backward sequentially.

Local and Global Secondary Indexes

The same ordering principle applies to secondary indexes:

  • Local Secondary Indexes (LSIs): An LSI uses the same partition key as the base table but defines a different sort key. It maintains a separate, automatically synchronized sorted view of the items within the same partition.
  • Global Secondary Indexes (GSIs): A GSI allows both a different partition key and a different sort key, redistributing items across partitions and ordering them according to the new sort key defined for that index.
