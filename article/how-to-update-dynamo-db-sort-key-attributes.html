How to Update DynamoDB Sort Key Attributes

Amazon DynamoDB treats primary key attributes as immutable, meaning you cannot directly update a sort key using standard update operations. This article covers how DynamoDB reacts when an update request attempts to modify both base attributes and a sort key, the specific errors returned, and the architectural pattern required to achieve the intended data modification safely and atomically.

Primary Key Immutability in DynamoDB

In Amazon DynamoDB, an item's primary key—composed of either a partition key alone or a partition key combined with a sort key—uniquely identifies the physical location and identity of that item within the storage architecture. Because the primary key dictates data distribution and indexing, all key attributes are strictly immutable once written.

When an application issues an UpdateItem API call, DynamoDB inspects the request parameters. If the update expression attempts to modify any attribute designated as part of the primary key schema, DynamoDB will reject the request outright.

What Happens During an Update Attempt?

If an UpdateItem request attempts to modify both a non-key attribute (a base attribute) and a sort key attribute within the same operation:

  1. Request Validation: DynamoDB validates the update expression against the table's key schema prior to making any modifications.
  2. Rejection: DynamoDB immediately halts the execution and rejects the entire request.
  3. Error Response: The API returns a ValidationException with an error message stating: Cannot update attribute <SortKeyName>. This attribute is part of the key.
  4. No Partial Updates: Because the validation fails at the request boundary, no attributes are updated. The base attributes remain unchanged in the original item.

The Standard Pattern: Delete and Recreate

To effectively change a sort key along with base attributes, you must delete the existing item and create a new item that contains the desired sort key and updated base attributes.

Using Atomic Transactions

To prevent race conditions, data duplication, or data loss, use the TransactWriteItems API. This ensures that the deletion of the old record and the creation of the new record occur atomically. If either part of the transaction fails, the entire operation rolls back.

A standard transaction for this operation includes two synchronous actions:

  1. Put: Writes the new item containing the original partition key, the new sort key, all unmodified base attributes, and any modified base attributes.
  2. Delete: Removes the original item using the original partition key and original sort key.

Handling Secondary Indexes

When replacing an item to modify a sort key:

  • Global Secondary Indexes (GSIs): DynamoDB automatically cleans up and updates GSIs asynchronously. The old projected entry is removed, and the new entry is added.
  • Local Secondary Indexes (LSIs): Because LSIs share the partition key with the base table, changes applied via the transaction will immediately reflect within the localized index structure.

By orchestrating a transactional delete-and-put operation, applications maintain strict data integrity while achieving the functional outcome of an updated sort key and modified base attributes.
