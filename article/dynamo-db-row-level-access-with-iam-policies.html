DynamoDB Row-Level Access with IAM Policies

Implementing row-level security in Amazon DynamoDB allows organizations to restrict a user's access strictly to items containing specific partition key values. This article covers the specific AWS Identity and Access Management (IAM) condition key used to achieve row-level authorization, how it functions with database partition keys, and how to implement it within an IAM policy.

The IAM Condition Key: dynamodb:LeadingKeys

The primary IAM policy condition key that allows restriction of DynamoDB access based on row-level (item-level) attributes is dynamodb:LeadingKeys.

In DynamoDB, the first attribute of a primary key is the partition key (historically referred to as the hash attribute). The dynamodb:LeadingKeys condition key represents this partition key. By using this condition in an IAM policy, you can control which specific items a user or role can create, read, update, or delete based on the value of that partition key.

How dynamodb:LeadingKeys Works

When a client application makes a request to DynamoDB—such as GetItem, PutItem, UpdateItem, DeleteItem, BatchGetItem, BatchWriteItem, or Query—DynamoDB checks the partition key provided in the request against the value defined in the dynamodb:LeadingKeys condition.

If the partition key in the request matches the allowed value defined in the policy, DynamoDB authorizes the operation. If it does not match, DynamoDB denies the request.

This condition is frequently paired with context keys such as ${aws:username} or federated identity variables like ${cognito-identity.amazonaws.com:sub} to ensure that users can only access rows that belong directly to them.

Example IAM Policy for Row-Level Access

The following policy allows an authenticated user to perform read and write operations only on rows where the partition key matches their unique Cognito identity ID:

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowAccessToOnlyIndividualUserRows",
            "Effect": "Allow",
            "Action": [
                "dynamodb:GetItem",
                "dynamodb:PutItem",
                "dynamodb:UpdateItem",
                "dynamodb:DeleteItem",
                "dynamodb:Query"
            ],
            "Resource": "arn:aws:dynamodb:us-east-1:123456789012:table/UserData",
            "Condition": {
                "ForAllValues:StringEquals": {
                    "dynamodb:LeadingKeys": [
                        "${cognito-identity.amazonaws.com:sub}"
                    ]
                }
            }
        }
    ]
}

In this policy:

  • Resource specifies the target DynamoDB table.
  • dynamodb:LeadingKeys inspects the table's partition key.
  • ${cognito-identity.amazonaws.com:sub} dynamically resolves to the user's ID at runtime.
  • ForAllValues:StringEquals ensures that all partition keys requested in batch operations or single-item operations strictly match the specified identity.

Row-Level vs. Column-Level Restrictions

It is important to distinguish dynamodb:LeadingKeys from other DynamoDB condition keys:

  • dynamodb:LeadingKeys: Provides row-level security by evaluating the partition key value of an item.
  • dynamodb:Attributes: Provides column-level (attribute-level) security by restricting which specific attributes a user can view or modify within an item.
  • dynamodb:Select: Controls the projection type allowed during Query or Scan operations (such as enforcing SPECIFIC_ATTRIBUTES).

To build a fully restricted security model, administrators often combine dynamodb:LeadingKeys with dynamodb:Attributes to control both the specific rows a user can access and the exact fields within those rows they are permitted to read or write.
