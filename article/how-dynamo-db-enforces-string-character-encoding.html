How DynamoDB Enforces String Character Encoding

Amazon DynamoDB strictly mandates UTF-8 character encoding across all String (S) attribute types to ensure cross-platform compatibility and predictable data handling. DynamoDB enforces these standards by validating incoming requests at the API boundary, immediately rejecting malformed byte sequences, measuring item sizes based on UTF-8 byte length rather than character length, and performing sort operations strictly by UTF-8 byte order. This architecture guarantees that every string stored in DynamoDB complies with the Unicode standard without silent data corruption.

Strict UTF-8 Validation at the API Layer

DynamoDB does not perform automatic transcoding or character conversion on incoming data. Instead, it enforces encoding integrity right at the request parsing layer through AWS SDKs and the underlying HTTPS JSON API:

  • Malformed Sequence Rejection: When an application calls operations like PutItem, UpdateItem, or BatchWriteItem, DynamoDB's request parser decodes the payload. If an attribute declared as a String contains invalid UTF-8 byte sequences or unassigned surrogate code points, DynamoDB rejects the request, returning a SerializationException or a ValidationException (HTTP 400 Bad Request).
  • Empty String Handling: In earlier versions, DynamoDB rejected empty strings (""). In current versions, empty strings are accepted as valid zero-byte UTF-8 inputs for non-key attributes and key attributes where supported.
  • Control Characters: All characters within the valid UTF-8 Unicode space—including standard control characters—are permitted, provided they conform to valid JSON and UTF-8 formatting rules.

Size Calculation by Byte Footprint

To prevent memory overflows and accurately meter capacity, DynamoDB calculates the size of String attributes by their UTF-8 encoded byte count rather than the number of characters.

The storage cost for a string attribute is determined by adding the number of bytes required to represent the attribute name to the number of bytes representing the attribute value. Because UTF-8 is a variable-width encoding:

  • Standard ASCII characters (code points U+0000 to U+007F) consume 1 byte.
  • Latin-based characters with diacritics, Greek, and Cyrillic consume 2 bytes.
  • Most Asian scripts (CJK) consume 3 bytes.
  • Supplemental characters and emojis consume 4 bytes.

If a single item exceeds the 400 KB limit because multi-byte UTF-8 characters expand the total byte payload, DynamoDB rejects the write request with an ItemSizeTooLargeException.

Lexicographical Sorting via UTF-8 Byte Values

When a String attribute serves as a sort key, DynamoDB enforces character rules through binary byte comparison. Comparison operators (such as <, >, BETWEEN, and begins_with) evaluate strings based strictly on the ASCII/UTF-8 byte values of each character:

  • Characters are evaluated byte-by-byte from left to right.
  • Uppercase ASCII letters sort before lowercase ASCII letters because their byte values are lower (e.g., A [0x41] comes before a [0x61]).
  • Multi-byte UTF-8 characters sort according to the numeric value of their successive encoded bytes.

This deterministic byte-level evaluation ensures that sort keys behave identically across all programming languages, avoiding regional locale discrepancies.

Storing Non-UTF-8 Data via the Binary Type

Because DynamoDB strictly limits String attributes to UTF-8, it does not support legacy or alternate encodings such as ISO-8859-1, Windows-1252, or UTF-16 inside a String attribute.

When an application must store arbitrary byte streams, compressed data, or strings with alternative encodings, DynamoDB requires using the Binary (B) or Binary Set (BS) attribute types. When using the Binary type, DynamoDB bypasses UTF-8 string validation entirely, treating the data as a raw Base64-encoded byte array.
