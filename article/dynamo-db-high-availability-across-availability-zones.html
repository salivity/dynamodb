DynamoDB High Availability Across Availability Zones

Amazon DynamoDB maintains high availability and durability by automatically replicating data synchronously across at least three distinct Availability Zones (AZs) within an AWS Region. This article explains the underlying architecture that enables DynamoDB to survive AZ failures without data loss or service disruption, focusing on its use of storage partitioning, the Paxos consensus algorithm, automated leader election, and intelligent request routing.

Synchronous 3-AZ Replication

When a table is created in DynamoDB, the service automatically allocates storage resources across at least three physically isolated Availability Zones within the target region. Each AZ runs on independent power, cooling, and network infrastructure. DynamoDB automatically replicates table data across these three zones synchronously, ensuring that the loss of an entire data center or AZ does not compromise data durability or availability.

Partitioning and Replica Sets

DynamoDB distributes table data into smaller storage segments called partitions based on partition key hash values. For high availability:

  • Each logical partition consists of a replica set containing three physical replicas.
  • Each of the three replicas is hosted on separate physical storage servers located in a different AZ.
  • This one-partition-per-AZ distribution ensures that no single zone outage can affect more than one replica in a given replica set.

Paxos Consensus and Quorum Writes

To ensure strong consistency and prevent split-brain scenarios, DynamoDB uses a consensus algorithm based on the Paxos protocol:

  • Write Operations: For a write operation to succeed, a write quorum must be achieved. Because each replica set consists of three nodes, a quorum requires confirmation from a majority—at least two out of the three replicas.
  • Resilience to Failure: If one AZ experiences an outage, the remaining two replicas in the other two AZs still constitute a majority (2 of 3). As a result, write operations continue without interruption, and the service remains fully operational.

Leader Election and Failover

Each replica set elects a leader replica using Paxos:

  • Leader Responsibilities: The leader replica is responsible for coordinating write operations and serving strongly consistent read requests.
  • Automated Failover: If the leader replica resides in an AZ that fails or becomes unreachable, the remaining two peer replicas detect the absence of heartbeats and initiate a new election. A new leader is elected from the healthy AZs in milliseconds, requiring no manual intervention and causing no noticeable downtime for client applications.

Read Consistency Strategies

DynamoDB supports two read consistency models to optimize performance and availability across AZs:

  • Eventually Consistent Reads (Default): These reads can be served by any of the three replicas across any AZ. This spreads the read workload, lowers latency, and ensures reads can proceed even if communication with the leader node is temporarily degraded.
  • Strongly Consistent Reads: These reads are routed directly to the leader replica (or validated via quorum) to guarantee that the response reflects all previously successful write operations.

Self-Healing and Node Replacement

Beyond AZ-level fault tolerance, DynamoDB continuously monitors the health of individual storage nodes:

  • Automated Repair: When a replica fails or becomes permanently degraded, DynamoDB's control plane automatically provisions a replacement replica on a healthy node in the appropriate AZ.
  • Log Catch-Up: The new replica restores data from the write-ahead logs of the surviving replicas to bring itself back into synchronization without impacting active transactions.

Stateless Request Routers

Client requests to DynamoDB pass through a fleet of stateless request routers. These routers continuously track the state of storage partitions, leader assignments, and zone health. If an AZ goes down, the routing layer automatically shifts traffic away from the impacted zone and directs incoming API calls directly to the healthy replicas in the operational zones.
