Switching DynamoDB Capacity Modes Explained

Switching an Amazon DynamoDB table between On-Demand and Provisioned capacity modes allows you to adapt to changing workload patterns and optimize costs without disrupting application traffic. This article explains the underlying mechanics of how DynamoDB processes capacity mode updates, how the system handles the transition state, and the rules governing these changes.

The Transition Mechanism

When you switch a table’s billing mode via the AWS Management Console, AWS CLI, or the UpdateTable API, DynamoDB executes the update asynchronously:

  1. Table State Transition: The table’s status changes from ACTIVE to UPDATING.
  2. Zero Downtime: Throughout the update process, the table remains fully operational. Read and write operations continue without dropped requests, throttles caused by the migration itself, or data loss.
  3. Partition Preservation: DynamoDB does not repartition data immediately simply because of a mode switch. Instead, it reconfigures the metadata and throttling policies associated with the existing partitions.
  4. Completion: Once DynamoDB updates internal control plane settings, the table status returns to ACTIVE.

Switching from Provisioned to On-Demand

When transitioning from Provisioned mode to On-Demand mode:

  • Initial Capacity Baseline: DynamoDB uses the previous provisioned Read Capacity Units (RCUs) and Write Capacity Units (WCUs) as the baseline for the new on-demand table. If the previous settings were high enough to establish multiple partitions, the table immediately sustains traffic up to the previous peak throughput without cold-start throttling.
  • Global Secondary Indexes (GSIs): All GSIs attached to the table automatically switch to On-Demand mode alongside the base table. You cannot maintain a mixed configuration where a base table is On-Demand and an index is Provisioned.
  • Auto Scaling: Any existing AWS Application Auto Scaling policies attached to the table or its GSIs are deleted or disabled, as capacity is now managed automatically per request.

Switching from On-Demand to Provisioned

When transitioning from On-Demand mode back to Provisioned mode:

  • Required Parameters: You must explicitly define target RCUs and WCUs for the base table and every existing GSI in the update request.
  • Provisioning Allocation: DynamoDB sets the requested capacity and enforces the new fixed thresholds immediately once the status returns to ACTIVE. If traffic exceeds these values, requests will be throttled unless Application Auto Scaling is configured.
  • Auto Scaling Reconfiguration: Auto Scaling policies are not restored automatically; you must recreate or re-enable them to handle future demand spikes.

Operational Constraints and Rules

  • Frequency Limitation: You can switch a table from Provisioned to On-Demand mode only once every 24 hours. Conversely, you can switch from On-Demand to Provisioned mode at any time without a 24-hour waiting period.
  • Uniformity: The billing mode is table-wide. The base table and all of its secondary indexes must share the same capacity mode at all times.
