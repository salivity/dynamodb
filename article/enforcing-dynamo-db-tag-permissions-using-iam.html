Enforcing DynamoDB Tag Permissions Using IAM

Amazon DynamoDB enforces table-level tag permissions through Attribute-Based Access Control (ABAC) defined within AWS Identity and Access Management (IAM) policies. By utilizing IAM condition keys that evaluate resource tags, administrators can dynamically grant or restrict access to specific DynamoDB tables without modifying policies every time a new table is deployed. This article explains the mechanisms, condition keys, and policy structures required to implement tag-based access control for DynamoDB tables.

The Mechanism: Attribute-Based Access Control (ABAC)

DynamoDB integrates with IAM to evaluate tags attached to tables during every API request. When a principal (user or role) attempts an action on a DynamoDB table, IAM evaluates the table's existing metadata tags against the conditions defined in the caller's IAM policy. If the condition logic matches, the action is permitted; otherwise, it is denied by default.

This enforcement relies on matching tags applied directly to the DynamoDB resource with conditions defined in the policy statement.

Key Condition Keys for Tag Enforcement

DynamoDB uses global and service-specific IAM condition keys to govern tag permissions:

  • aws:ResourceTag/${TagKey}: Compares the tag key-value pair existing on the target DynamoDB table with the value specified in the policy.
  • aws:RequestTag/${TagKey}: Checks the tag key-value pair passed in the request payload when creating a table (dynamodb:CreateTable) or modifying tags (dynamodb:TagResource).
  • aws:TagKeys: Restricts which specific tag keys can be applied or removed in a request.

Enforcing Table Access Based on Existing Tags

To restrict table operations (such as data plane actions like GetItem and PutItem, or control plane actions like DeleteTable), the aws:ResourceTag key is used in the Condition block of an IAM policy.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAccessByEnvironmentTag",
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:UpdateItem",
        "dynamodb:Query",
        "dynamodb:Scan"
      ],
      "Resource": "arn:aws:dynamodb:*:*:table/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/Environment": "Production"
        }
      }
    }
  ]
}

In this scenario, IAM checks the target table's tags before executing the operation. If the table does not have an Environment tag with the value Production, access is denied.

Enforcing Tags at Creation Time

To ensure new DynamoDB tables inherit required governance tags upon creation, use aws:RequestTag combined with a Deny or Allow statement on dynamodb:CreateTable.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RequireEnvironmentTagOnCreate",
      "Effect": "Allow",
      "Action": [
        "dynamodb:CreateTable",
        "dynamodb:TagResource"
      ],
      "Resource": "arn:aws:dynamodb:*:*:table/*",
      "Condition": {
        "StringEquals": {
          "aws:RequestTag/Environment": ["Production", "Development"]
        }
      }
    }
  ]
}

If an API call to CreateTable lacks the Environment tag, the request fails, preventing untagged tables from entering the environment.

Preventing Tag Tampering and Privilege Escalation

Tag-based enforcement is only secure if principals cannot modify the tags granting them access. To protect table tags:

  1. Restrict dynamodb:TagResource and dynamodb:UntagResource: Prevent unauthorized users from altering tags to gain elevated access.
  2. Enforce Tag Immutability: Use explicit Deny rules for tag removal on production resources.
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyModifyingProductionTags",
      "Effect": "Deny",
      "Action": [
        "dynamodb:TagResource",
        "dynamodb:UntagResource"
      ],
      "Resource": "arn:aws:dynamodb:*:*:table/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/Environment": "Production"
        }
      }
    }
  ]
}

Policy Evaluation Workflow

When an IAM identity calls an operation on a DynamoDB table:

  1. Request Inspection: IAM intercepts the API request and determines the requested action (e.g., dynamodb:DeleteTable) and target ARN.
  2. Tag Retrieval: IAM retrieves the current tags attached to the DynamoDB table.
  3. Condition Matching: IAM compares the table tags against aws:ResourceTag conditions in the user's applicable policies.
  4. Authorization: If the action matches an explicit Allow statement and meets all tag conditions without hitting an explicit Deny, the request succeeds.
