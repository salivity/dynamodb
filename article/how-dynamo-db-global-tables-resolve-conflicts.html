How DynamoDB Global Tables Resolve Conflicts

Amazon DynamoDB global tables provide a fully managed, multi-region, multi-active database architecture that allows applications to read and write locally across multiple AWS regions. When concurrent updates happen to identical keys across different regions at the same time, DynamoDB resolves the collision using a native "Last Writer Wins" (LWW) conflict resolution strategy. This article explains how DynamoDB determines the prevailing write, how timestamps are handled under the hood, and the key architectural implications of this model.

The "Last Writer Wins" Strategy

DynamoDB global tables resolve concurrent writes at the item level using a Last Writer Wins algorithm. If two updates to the same primary key occur simultaneously in Region A and Region B, DynamoDB compares the timestamps of each write. The update with the most recent timestamp is propagated to all replicas, overwriting the earlier write.

Key aspects of this process include:

  • Entire Item Replacement: Conflict resolution evaluates the item as a whole rather than merging individual attributes. If Region A updates attribute X and Region B simultaneously updates attribute Y, the update with the later timestamp overwrites the entire state of the item. As a result, the earlier update to the other attribute will be lost unless your application logic specifically merges states.
  • Internal Timestamps: DynamoDB uses internal, service-generated metadata timestamps to evaluate the order of operations, not client-side application timestamps. AWS synchronizes physical clocks across its global infrastructure using high-precision time services (such as the Amazon Time Sync Service) to keep cross-region clock drift to a minimum.
  • Tie-Breaking: In the rare event that two simultaneous writes across different regions share the exact same timestamp, DynamoDB uses an internal deterministic tie-breaker to ensure all replicas converge on the exact same version of the item.

Eventual Consistency and Replication

Global tables rely on asynchronous, active-active replication. While write replication typically completes within a single second, the brief replication window means reads in different regions may temporarily reflect divergent states until all tables synchronize.

Because replication is asynchronous:

  • Local writes succeed immediately without waiting for cross-region consensus.
  • Conditional writes only evaluate the local table’s state at the moment of execution. If two regions execute conflicting conditional updates concurrently, both conditions may evaluate as true locally, but DynamoDB's LWW mechanism will still overwrite one with the other during replication.

Mitigating Concurrent Write Conflicts

Because Last Writer Wins can lead to silent overwrites in high-concurrency environments, applications with sensitive data models often implement specific architectural patterns:

  • Regional Routing (User Affinity): Route requests for specific partitions, users, or datasets to a designated "home" region using tools like Amazon Route 53 latency-based routing. This eliminates multi-region write contention on the same primary keys.
  • Optimistic Locking: Include a version number attribute within the item. While local conditional writes do not prevent remote replication overwrites, they do protect against concurrent updates within the same region.
  • Idempotent and Additive Writes: Structure data to append events or log entries rather than mutating a shared aggregate item concurrently across regions.
