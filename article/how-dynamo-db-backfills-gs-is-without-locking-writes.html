How DynamoDB Backfills GSIs Without Locking Writes

Amazon DynamoDB creates and populates Global Secondary Indexes (GSIs) online without interrupting or locking writes on the base table. This article explores the internal multi-phase mechanism DynamoDB uses to achieve this—specifically how it provisions resources, reads historical data through low-priority background scans, continuously applies concurrent mutations using internal replication streams, and resolves data conflicts to transition the index to an active state safely.

The Challenge of Online Indexing

In traditional relational databases, creating a secondary index on a large table often involves locking the table or placing it into a read-only state to maintain data consistency during the build process. Because DynamoDB is designed for high-availability, mission-critical workloads, it relies on a decoupled, asynchronous background process that allows standard base table read and write operations to continue at normal throughput and latency while the new GSI is constructed.

Phase 1: Resource Provisioning and Allocation

When an application issues an UpdateTable request to add a GSI, DynamoDB sets the index status to CREATING. In the background, the storage management layer provisions the necessary partition infrastructure for the GSI across multiple Availability Zones. This setup includes allocating dedicated storage, compute nodes, and partition routing metadata based on the provisioned or on-demand throughput settings configured for the index.

Phase 2: Historical Data Scanning

Once the GSI storage partitions are provisioned, DynamoDB begins backfilling existing data. Background processes initiate a parallel scan across the base table's physical storage partitions. To prevent this historical scan from impacting customer workloads:

  • Resource Isolation: The scan relies on internal system capacity and operates at a lower priority than real-time application requests.
  • Non-Blocking Storage Access: DynamoDB's underlying storage architecture reads storage replicas without taking row- or partition-level write locks. Base table write operations continue to commit to storage nodes simultaneously.

Phase 3: Capturing Real-Time Concurrent Mutations

While the historical scan runs, client applications continue writing, updating, and deleting items in the base table. DynamoDB captures these in-flight mutations in real time using an internal storage-level replication stream (analogous to the engine powering DynamoDB Streams).

When a base table write succeeds, the mutation is routed not only to the base table's storage nodes but also to an asynchronous ingest buffer for the newly requested GSI. This decouples user write latency from GSI processing latency.

Phase 4: Stream Merging and Conflict Resolution

Because the historical scan and real-time mutation streams run concurrently, race conditions can occur. For instance, an item could be updated by a client and written to the GSI via the stream before the historical scan reaches that item's previous version.

DynamoDB resolves this using internal write ordering and timestamps:

  1. Ordering Guarantees: Mutations processed through the replication log carry monotonic sequence numbers and commit timestamps.
  2. Idempotent Writes: When writing scanned historical items to the GSI, the ingestion layer evaluates whether a newer mutation has already been applied. If an incoming scan record is older than the current state written by the stream, the stale scanned write is discarded.

Phase 5: Stream Catch-Up and Activation

As the base table scan concludes, the backfilling process transitions into a catch-up phase. The system applies any remaining buffered real-time mutations until the replication lag between the base table writes and the GSI reaches near-zero latency.

Once the GSI is fully synchronized with the base table:

  • The index state flips from CREATING to ACTIVE.
  • The DynamoDB request routers begin directing incoming query and scan requests to the new index.
  • Subsequent base table writes are automatically propagated to the active GSI via standard asynchronous replication.
