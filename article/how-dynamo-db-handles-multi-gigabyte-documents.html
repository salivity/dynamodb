How DynamoDB Handles Multi-Gigabyte Documents

Amazon DynamoDB cannot natively store multi-gigabyte document attributes due to a strict, hard item size limit of 400 KB. Consequently, DynamoDB handles write requests containing multi-gigabyte attributes by rejecting them outright with a client error. To store and manage multi-gigabyte documents alongside DynamoDB data, architects rely on an architectural pattern known as the Claim Check pattern, which offloads the large payload to Amazon Simple Storage Service (Amazon S3) while maintaining pointers and metadata inside DynamoDB.

The 400 KB Item Limit

DynamoDB enforces an absolute maximum item size of 400 KB, which includes the attribute name and value sizes for the entire item combined. This limit is fundamental to DynamoDB's design:

  • Predictable Latency: By keeping item sizes small, DynamoDB guarantees single-digit millisecond response times for read and write operations at any scale.
  • Storage and Memory Management: Small items prevent large single-item reads or writes from monopolizing SSD throughput, memory caches, and internal partition bandwidth.
  • API Enforcement: If an application attempts to write an item that exceeds 400 KB using operations like PutItem or UpdateItem, DynamoDB immediately aborts the operation and returns a ValidationException stating that the item size has exceeded the allowed limit.

Because of this hard architectural constraint, DynamoDB does not provide internal storage allocation mechanisms, such as automatic paging, offloading, or disk segment chaining, for individual large documents or multi-gigabyte attributes.

The Solution: The Claim Check Pattern

To manage multi-gigabyte documents within a DynamoDB-driven architecture, you must decouple the document's payload from its structured metadata using the Claim Check pattern.

1. Payload Offloading to Amazon S3

Instead of transmitting the multi-gigabyte document directly to DynamoDB, the application uploads the file directly to Amazon S3. S3 is designed specifically for object storage, natively supporting individual files up to 5 TB in size with high durability and cost-effective tiered storage classes.

2. Storing Pointers in DynamoDB

Once the document is stored in S3, the application writes an item to DynamoDB containing:

  • The primary key (partition key and optional sort key).
  • The S3 reference URI (bucket name and object key).
  • Searchable metadata, such as file size, MIME type, upload timestamp, and ownership details.
  • Indexable attributes required for querying, filtering, and access control.

3. Retrieving the Document

When retrieving data:

  1. The client queries DynamoDB to fetch the document's metadata and S3 location.
  2. The client uses the retrieved S3 key to download the file directly from S3, often using pre-signed URLs to maintain secure, direct-to-storage downloads without routing large payloads through an intermediate API layer.

Why Other Approaches Fail at Scale

Techniques commonly used for moderately sized attributes do not work for multi-gigabyte data:

  • Compression: Compressing text, JSON, or binary data using algorithms like Gzip or Zstandard can reduce data size, but it cannot shrink gigabyte-scale payloads to under 400 KB.
  • Item Chunking: Splitting a document into multiple 400 KB items spread across multiple rows is impractical for gigabyte-scale documents. A 2 GB document would require over 5,000 separate items, resulting in excessive write capacity unit (WCU) consumption, expensive read assembly, high latency, and complex transaction management.
