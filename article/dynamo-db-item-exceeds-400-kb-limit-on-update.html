DynamoDB Item Exceeds 400 KB Limit on Update

Amazon DynamoDB enforces a hard limit of 400 KB per individual item, which includes both attribute names and attribute values. When an update operation causes an item to exceed this 400 KB threshold, DynamoDB immediately rejects the request with a client error, leaving the existing item in its original state. Understanding the mechanics of this failure and implementing design patterns like data compression or Amazon S3 offloading is essential for maintaining application reliability.

The Immediate Error Response

When an update operation—such as UpdateItem or a conditional PutItem—results in an item size greater than 400 KB, DynamoDB aborts the operation and returns an HTTP 400 Bad Request error. The specific exception thrown is a ValidationException, accompanied by an error message indicating that the item size has exceeded the maximum allowed size.

Because DynamoDB operations are atomic, the update fails entirely. No partial data is written, and the existing item remains unchanged in the table. If the update was part of a TransactWriteItems request, the entire transaction will be cancelled, causing all other operations in that batch to fail as well.

How Item Size Is Calculated

The 400 KB limit applies to the cumulative size of all binary and UTF-8 string lengths of both the attribute names and attribute values within the item. This includes:

  • The length of all attribute names in UTF-8 bytes.
  • The size of attribute values (e.g., strings are measured by UTF-8 byte length, numbers are measured based on variable precision, and booleans/nulls consume 1 byte).
  • Structural overhead for complex types like Lists and Maps (3 bytes per nested element, plus the element data).

If an UpdateItem action appends elements to a list, increments attributes, or sets new values, the final evaluated size of the combined item must remain at or below 400 KB (409,600 bytes).

Solutions and Workarounds

To handle data that naturally grows beyond the 400 KB boundary, you can implement several architectural patterns:

  • The Claim Check Pattern (Amazon S3): Store the large payload or bulky attributes in an Amazon S3 bucket, and store only the S3 object URL or key within the DynamoDB item. This retains DynamoDB's fast indexing and metadata querying while leveraging virtually unlimited S3 storage.
  • Compression: Compress large text or JSON payloads using algorithms like GZIP or Snappy before saving them as Binary (B) data types in DynamoDB. This often reduces the payload size by 60% to 80%.
  • Item Splitting: Normalize or partition the data across multiple items. For instance, split historical records, logs, or large nested arrays into separate items using a one-to-many relationship with a common partition key and unique sort keys.
