DynamoDB PITR: Preserving Table Configurations

Amazon DynamoDB Point-in-Time Recovery (PITR) provides continuous backups of table data, enabling restoration to any single second within the past 35 days. When executing a recovery, DynamoDB creates an entirely new table rather than overwriting the existing one. This article explains how DynamoDB handles existing table settings during this process, detailing which configurations are automatically carried over, which settings require manual reconfiguration, and how administrators can modify parameters during the restore operation.

How the Restore Process Works

DynamoDB PITR restores data by provisioning a brand-new target table with a unique Amazon Resource Name (ARN). Because it does not modify or overwrite the source table, the restoration process reads the historical state of the source table's metadata and data at the requested timestamp, applying the foundational architecture to the newly provisioned table.

Configurations Preserved Automatically

During a point-in-time recovery, DynamoDB automatically recreates core structural and capacity settings to ensure data integrity and immediate operational readiness:

  • Primary Key Schema: The partition key (and sort key, if applicable) and their respective data types are replicated exactly as they were at the restore timestamp.
  • Secondary Indexes: Both Global Secondary Indexes (GSIs) and Local Secondary Indexes (LSIs) are automatically created on the new table. The projected attributes and key schemas for these indexes match the state of the source table at the specified recovery point.
  • Billing Mode and Capacity Units: The billing mode (On-Demand or Provisioned) is preserved. If the table was in Provisioned mode, the provisioned Read Capacity Units (RCUs) and Write Capacity Units (WCUs) of the table and its GSIs are matched to the selected point in time.
  • Server-Side Encryption: By default, the restored table inherits the encryption type of the source table, whether encrypted with an AWS Owned Key, AWS Managed Key, or a Customer Managed Key (CMK) via AWS KMS.

Configurations Requiring Manual Setup

Certain operational, event-driven, and resource-level features are not automatically restored to the new table. These must be manually reconfigured after the restoration finishes:

  • Time to Live (TTL): While the TTL attribute data remains present within the restored items, the TTL background process is disabled by default on the restored table and must be re-enabled.
  • DynamoDB Streams: Streams are not activated on the restored table. If downstream systems rely on change data capture (CDC), you must enable DynamoDB Streams on the new table and update any consumer triggers (such as AWS Lambda functions) with the new stream ARN.
  • Auto Scaling Policies: While static provisioned capacity is restored, Application Auto Scaling policies (such as target tracking configurations for RCUs and WCUs) are not copied over.
  • Point-in-Time Recovery (PITR): PITR is not automatically enabled on the newly created table. Continuous backups must be explicitly turned on to protect the new table moving forward.
  • Tags and Alarms: Resource tags, Amazon CloudWatch alarms, and associated metric filters do not transfer to the new resource.
  • IAM Policies: Because the restored table receives a new ARN, any identity-based or resource-based IAM policies referencing the old table ARN must be updated to grant permissions to the restored table.

Modifying Configurations During Restoration

DynamoDB allows you to override certain table configurations directly during the restore API call, AWS CLI command, or Management Console workflow. You can opt to change the billing mode (for example, switching from Provisioned to On-Demand to accommodate initial catch-up workloads), modify the encryption key to a different KMS key, or exclude specific Global Secondary Indexes from being created, thereby optimizing provisioning costs and recovery speed.
