How to Model Real-Time Leaderboards in DynamoDB

Designing real-time leaderboards in Amazon DynamoDB requires balancing high-throughput writes with fast, sorted read operations. This article covers how to structure primary keys and Global Secondary Indexes (GSIs), mitigate hot partition limits using write sharding, and implement sparse indexes to deliver low-latency global and periodic rankings.

Base Table Primary Key Structure

The base table should prioritize distributed writes and direct point lookups for individual player data.

  • Partition Key (PK): UserID or PlayerID (String)
  • Sort Key (SK): GameID or a static entity identifier like METADATA (String)

This primary key design ensures that writes (score updates) are distributed uniformly across DynamoDB's physical partitions, preventing single-partition write limits (1,000 WCU per second) on the base table.

Global Secondary Index (GSI) for Rankings

DynamoDB only sorts data within a single partition using the Sort Key. To sort players across the entire game, you must aggregate them within a Global Secondary Index (GSI).

  • GSI Partition Key (GSI-PK): GameID or LeaderboardID (String)
  • GSI Sort Key (GSI-SK): Score (Number)

To retrieve the highest scores, query the GSI by GameID, set ScanIndexForward to false (to sort descending), and apply a Limit (e.g., Top 100).

Mitigating Hot Partitions with Write Sharding

Using a static GameID as the GSI-PK causes a hot partition bottleneck if thousands of players update scores simultaneously. To scale beyond the 1,000 WCU limit on the GSI, apply write sharding:

  1. Assign Shards on Write: When writing or updating a score, append a random shard identifier to the GSI partition key attribute:
    • GSI-PK = GameID#SHARD_<0-N> (e.g., GAME_01#SHARD_4)
    • GSI-SK = Score
  2. Scatter-Gather on Read: To retrieve the top players:
    • Query all \(N\) shards in parallel using the application layer.
    • Fetch the top \(K\) items from each shard (ScanIndexForward = false, Limit = K).
    • Merge and sort the aggregated results in memory to produce the final top \(K\) leaderboard.

For high-concurrency systems, 10 to 20 shards are usually sufficient to handle tens of thousands of writes per second.

Modeling Time-Bound Leaderboards

For daily, weekly, or seasonal leaderboards, embed the timeframe directly into the GSI Partition Key:

  • Daily GSI-PK: GAME_01#DAILY#2024-10-25 (or GAME_01#DAILY#2024-10-25#SHARD_<N> if sharded)
  • GSI-SK: Score

When the timeframe concludes, the partition transitions into a static, read-only state. You can leverage DynamoDB Time to Live (TTL) on the base table items to automatically purge historical rankings if they are no longer needed.

Optimizing with Sparse Indexes

If you only need to display the "Top 500" or players above a certain tier, avoid projecting every score update into the GSI.

  1. Create a conditional attribute, such as RankEligibleScore, on the base table.
  2. Only populate this attribute if a player's score crosses a specific threshold.
  3. Use RankEligibleScore as the GSI-SK.

DynamoDB will only populate the GSI for items containing this attribute, significantly reducing GSI storage costs and write consumption.
