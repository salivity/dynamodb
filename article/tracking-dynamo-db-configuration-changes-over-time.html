Tracking DynamoDB Configuration Changes Over Time

Tracking configuration changes to Amazon DynamoDB tables is essential for maintaining security posture, ensuring regulatory compliance, and troubleshooting unexpected application behavior. The primary mechanism for recording and auditing these changes over time is AWS Config, which continuously monitors and stores the state of DynamoDB resources. Complemented by AWS CloudTrail for API-level auditing, AWS Config provides a detailed timeline of metadata and schema updates, enabling administrators to visualize historical configurations and verify compliance against predefined governance rules.

The Core Mechanism: AWS Config

AWS Config is fully integrated with Amazon DynamoDB to deliver continuous resource tracking. When enabled, AWS Config detects any create, update, or delete operations that modify a DynamoDB table's properties and generates a Configuration Item (CI). A Configuration Item represents a point-in-time snapshot of the resource’s configuration attributes, relationships, and metadata.

AWS Config tracks a wide range of DynamoDB configuration parameters, including:

  • Billing Mode and Capacity Settings: Transitions between On-Demand and Provisioned capacity modes, as well as modifications to read and write capacity units (RCUs and WCUs).
  • Secondary Indexes: The addition, modification, or removal of Global Secondary Indexes (GSIs) and Local Secondary Indexes (LSIs).
  • Security Settings: Encryption at rest settings (AWS KMS key management) and point-in-time recovery (PITR) configurations.
  • Feature Configurations: Changes to Time to Live (TTL), DynamoDB Streams, and table-level tags.

Viewing Historical Configurations

AWS Config stores recorded Configuration Items in an Amazon S3 bucket and provides a visual timeline within the AWS Management Console. Users can select any DynamoDB table and view its complete configuration timeline. This timeline displays:

  1. State Diffs: A side-by-side comparison of the resource state before and after a modification.
  2. Associated Events: The specific CloudTrail event that triggered the change.
  3. Compliance History: How configuration updates affected compliance with active AWS Config rules (such as checking whether tables are encrypted using customer-managed keys).

The Role of AWS CloudTrail

While AWS Config records the state of the table before and after a change, AWS CloudTrail provides the context surrounding the change. CloudTrail logs the control-plane API calls responsible for modifying DynamoDB table configurations, including calls such as CreateTable, UpdateTable, DeleteTable, UpdateTimeToLive, and TagResource.

Through CloudTrail, teams can identify the specific IAM user or role that initiated the change, the source IP address, and the exact timestamp. When used together, AWS Config and AWS CloudTrail provide a complete audit trail: CloudTrail reveals who made the request, and AWS Config reveals how the table's state changed as a result.

How to Enable DynamoDB Tracking

To track table modifications, navigate to the AWS Config console and configure the recorder to include the AWS::DynamoDB::Table resource type. Once recording is active:

  1. AWS Config delivers daily configuration snapshots and change notifications to your designated Amazon S3 bucket and Amazon SNS topic.
  2. You can query past configuration states programmatically using the AWS CLI or SDKs via the GetResourceConfigHistory API.
  3. You can set up managed rules (such as dynamodb-pitr-enabled or dynamodb-table-encrypted-kms) to automatically flag non-compliant configuration changes as they occur.
