Role of DynamoDB DDL in Defining Schemas

Amazon DynamoDB is often categorized as a schemaless NoSQL database, but it relies heavily on Data Definition Language (DDL) concepts to establish critical foundational structures. This article explores how DDL operations—executed via the AWS SDKs, AWS CloudFormation, the AWS CLI, or PartiQL—define primary keys, secondary indexes, and operational configurations, establishing the explicit boundaries that govern how data is indexed, partitioned, and accessed.

The Concept of DDL in a Schemaless Database

Unlike relational database management systems (RDBMS) that require a strict column-by-column schema definition, DynamoDB enforces a schema only on the attributes used to index and retrieve data. Non-key attributes are flexible and dynamic; different items within the same table can possess entirely different attributes and data types.

In DynamoDB, DDL is primarily executed through administrative API operations such as CreateTable, UpdateTable, and DeleteTable, as well as PartiQL statements like CREATE TABLE. The role of DDL is not to govern the payload of each item, but to define how data is distributed across physical storage partitions and made queryable.

Defining Primary Keys

The most critical role of DynamoDB DDL is specifying the primary key during table creation. The primary key uniquely identifies each item and dictates partition placement. DDL requires the explicit declaration of attribute names and data types (String, Number, or Binary) for these key components:

  • Partition Key (Simple Primary Key): A single attribute that DynamoDB uses as an input to an internal hash function. The output determines the physical partition where the item is stored.
  • Partition Key and Sort Key (Composite Primary Key): A combination of two attributes. All items with the same partition key are stored together in sorted order according to the sort key, enabling range queries within a specific partition.

Once defined via DDL at table creation, primary key definitions are immutable. They cannot be altered without recreating the table or migrating data.

Declaring Secondary Indexes

DDL allows developers to define alternative query paths through Global Secondary Indexes (GSIs) and Local Secondary Indexes (LSIs). Because DynamoDB queries are restricted to primary key configurations, indexes must be defined to support additional access patterns.

  • Local Secondary Indexes (LSIs): Must be defined at table creation via DDL. An LSI uses the same partition key as the base table but a different sort key, facilitating alternate range queries within the same partition.
  • Global Secondary Indexes (GSIs): Can be defined during table creation or added later using DDL UpdateTable actions. A GSI can have a partition key and an optional sort key that are completely different from the base table.

Through DDL, administrators also specify the attribute projection for each index (such as KEYS_ONLY, INCLUDE, or ALL), determining which non-key attributes are replicated to the index storage to balance query performance and cost.

Configuring Operational Schemas

DynamoDB DDL extends beyond keys to configure table-level operational characteristics. These configurations form the operational contract for the table:

  • Capacity Modes: DDL specifies whether the table uses On-Demand capacity or Provisioned capacity with defined Read Capacity Units (RCUs) and Write Capacity Units (WCUs).
  • DynamoDB Streams: DDL enables or disables change data capture and sets the view type (e.g., keys only, new image, old image, or both).
  • Time to Live (TTL): DDL defines the specific attribute name that marks items for automatic expiration and deletion.
  • Encryption and Point-in-Time Recovery (PITR): DDL specifies the encryption provider (AWS-managed or customer-managed KMS keys) and backup strategies.

DynamoDB DDL defines the rigid scaffolding required for high performance and horizontal scaling, while leaving individual item payloads adaptable to changing application requirements.
