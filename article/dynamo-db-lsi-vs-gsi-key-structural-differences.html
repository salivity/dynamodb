DynamoDB LSI vs GSI: Key Structural Differences

Amazon DynamoDB provides two types of secondary indexes—Local Secondary Indexes (LSIs) and Global Secondary Indexes (GSIs)—to enable flexible querying beyond a table's primary key design. This article explains the primary structural difference between LSIs and GSIs, focusing on their partition key architecture, data scoping, throughput allocation, and lifecycle constraints.

The Primary Difference: Partition Key Architecture

The fundamental structural difference between an LSI and a GSI lies in the partition key:

  • Local Secondary Index (LSI): Must use the same partition key as the base table, but defines a different sort key. Because it shares the base table's partition key, an LSI is "local" to a specific partition.
  • Global Secondary Index (GSI): Can define a completely different partition key and an optional alternative sort key. It can index data across the entire table regardless of the original partition key, making it "global."

Data Scoping and the 10 GB Item Collection Limit

Because an LSI shares the base table's partition key, all items sharing that partition key form an "item collection." DynamoDB enforces a strict structural limit on item collections: the total size of all base table items and their associated LSI entries sharing the same partition key cannot exceed 10 GB. If this limit is reached, write operations for that partition key will fail.

A GSI does not create item collections with the base table. It maintains its own independent partition structure, meaning there is no 10 GB size restriction tied to the base table's partition key.

Provisioned Throughput and Storage

The structural independence of a GSI extends to its capacity management:

  • LSIs share capacity: Reads and writes to an LSI consume the Read Capacity Units (RCUs) and Write Capacity Units (WCUs) of the underlying base table.
  • GSIs require dedicated capacity: A GSI operates as a separate data store behind the scenes. It requires its own provisioned or on-demand throughput settings. If a GSI experiences throttling due to insufficient write capacity, it can throttle writes to the base table.

Index Lifecycle and Flexibility

The tight structural coupling of an LSI also dictates when it can be created:

  • LSIs must be defined at table creation. Once the table exists, you cannot add, modify, or delete an LSI.
  • GSIs can be created, updated, or deleted dynamically at any point during the table’s lifecycle without needing to recreate the table.

Read Consistency

Structurally, LSIs reside within the same storage nodes as the base table partition. As a result, LSIs support both eventually consistent and strongly consistent reads.

GSIs replicate data asynchronously from the base table across distinct partitions. Consequently, GSIs only support eventually consistent reads.
