DynamoDB Throughput Exceeded HTTP Error Code

When Amazon DynamoDB request rates exceed the allocated read or write capacity, the service rejects the request and returns an HTTP 400 status code accompanied by a ProvisionedThroughputExceededException. This article explains the exact error response DynamoDB provides during throttling events, the common causes behind throughput limits being breached, and practical techniques to resolve and mitigate the issue.

The HTTP Status Code and Error Response

DynamoDB returns an HTTP 400 Bad Request status code when provisioned throughput is exceeded. Within the JSON error payload of the response, the __type field specifies com.amazonaws.dynamodb.v20120810#ProvisionedThroughputExceededException.

An HTTP 400 response is used because AWS classifies throughput throttling as a client-side error, indicating that the client application is sending requests faster than the provisioned capacity limits allow.

Causes of ProvisionedThroughputExceededException

The error occurs when the workload exceeds the configured limits in one of the following scenarios:

  • Exceeding Table-Level Capacity: The total number of Read Capacity Units (RCUs) or Write Capacity Units (WCUs) per second surpasses the provisioned threshold for the table or global secondary index (GSI).
  • Hot Partitions: DynamoDB partitions data across physical storage nodes based on partition key values. If access patterns heavily favor a specific partition key, that single partition can exceed its 1,000 WCU or 3,000 RCU limit, triggering a throttling exception even if the overall table capacity is not exhausted.
  • Exhausted Burst Capacity: DynamoDB provides burst capacity to accommodate short-term spikes. Once this temporary reserve is drained, subsequent spikes will immediately trigger HTTP 400 errors.

How to Resolve and Mitigate Throttling

To minimize or eliminate ProvisionedThroughputExceededException errors, implement the following best practices:

  • Retry with Exponential Backoff: Use the official AWS SDKs, which automatically retry throttled requests using exponential backoff and jitter algorithms. If writing custom API calls, implement backoff logic to prevent overwhelming the database.
  • Enable Auto Scaling: Configure DynamoDB Auto Scaling to dynamically adjust provisioned read and write capacity based on specified utilization targets.
  • Switch to On-Demand Mode: For unpredictable or spiky workloads, switch the billing mode from Provisioned to On-Demand. On-demand mode accommodates sudden spikes instantly without manual capacity management.
  • Optimize Partition Keys: Design partition keys with high cardinality (e.g., UUIDs, timestamps with random suffixes) to distribute read and write operations uniformly across all partitions.
  • Implement Caching: Deploy Amazon DynamoDB Accelerator (DAX) or an in-memory cache such as Redis to serve frequent, read-heavy queries off-cluster, drastically reducing RCU consumption.
