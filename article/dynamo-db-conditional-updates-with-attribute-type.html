DynamoDB Conditional Updates with attribute_type

Amazon DynamoDB supports conditional updates to ensure write operations only occur when items satisfy specific criteria. The attribute_type function evaluates whether an attribute exists and matches a declared DynamoDB data type prior to executing an update. This article explains the mechanics of the attribute_type function, its supported data types, practical use cases, and how to implement it within a condition expression.

Understanding the attribute_type Function

The attribute_type function is evaluated within a ConditionExpression during write operations such as PutItem, UpdateItem, and DeleteItem. It validates the type of an attribute on an existing item stored in DynamoDB before modifying or deleting it.

Syntax

attribute_type(path, type)
  • path: The document path to the target attribute (e.g., status or a nested attribute like metadata.version).
  • type: A string literal representing the DynamoDB data type code to check against.

If the attribute exists and its type matches the provided type code, the function evaluates to TRUE. If the attribute does not exist or has a different type, it evaluates to FALSE.

Supported Data Types

DynamoDB uses single-letter or short string abbreviations to define its types. When using attribute_type, pass the corresponding type code:

  • Scalar Types:
    • "S": String
    • "N": Number
    • "B": Binary
    • "BOOL": Boolean
    • "NULL": Null
  • Document Types:
    • "M": Map
    • "L": List
  • Set Types:
    • "SS": String Set
    • "NS": Number Set
    • "BS": Binary Set

Execution Flow of a Conditional Update

When a client submits an update request containing an attribute_type check:

  1. Item Retrieval: DynamoDB retrieves the existing item using its partition and sort keys.
  2. Type Evaluation: DynamoDB evaluates the condition expression against the current state of the item. It inspects the binary descriptor of the target attribute to see if its tag matches the specified type parameter.
  3. Execution or Rejection:
    • If the condition evaluates to TRUE, the write operation completes atomically.
    • If the condition evaluates to FALSE, the transaction halts, and DynamoDB returns a ConditionalCheckFailedException (HTTP 400). No data is modified.

Common Use Cases

1. Safe List Appends

Before using list_append in an UpdateExpression, verifying that the target attribute is indeed a List ("L") prevents runtime errors that occur if the attribute is missing, null, or a different type.

2. Schema Enforcement in NoSQL

Because DynamoDB is schemaless, different microservices or legacy versions may inadvertently write incompatible types to the same field name. The attribute_type check enforces strict data contracts at the database level.

3. Progressive Data Migrations

When migrating an attribute from one type to another (for example, converting a legacy String timestamp "S" to an epoch Number "N"), conditions can target items that still have the legacy type.

Example Implementation

The following example demonstrates an UpdateItem request using the AWS CLI. The update increases an account balance only if the balance attribute currently exists and is stored as a Number ("N").

aws dynamodb update-item \
    --table-name Accounts \
    --key '{"AccountId": {"S": "ACC1001"}}' \
    --update-expression "SET balance = balance + :val" \
    --condition-expression "attribute_type(balance, :expected_type)" \
    --expression-attribute-values '{
        ":val": {"N": "50"},
        ":expected_type": {"S": "N"}
    }'

In this operation:

  • The ConditionExpression invokes attribute_type(balance, :expected_type).
  • :expected_type resolves to "N".
  • If balance is missing, is a String, or is any type other than Number, the operation fails without modifying the record.
