DynamoDB Streams View Types and Lambda Memory Usage

Selecting the appropriate DynamoDB Streams view type directly governs the payload size delivered to downstream AWS Lambda functions, which substantially influences Lambda memory consumption. This article explains how the four stream view types—KEYS_ONLY, NEW_IMAGE, OLD_IMAGE, and NEW_AND_OLD_IMAGES—impact the size of incoming event batches, how runtime deserialization scales memory pressure, and how to configure stream settings to avoid out-of-memory errors while minimizing execution costs.

Understanding DynamoDB Stream View Types

When enabling a DynamoDB Stream, you must choose one of four StreamViewType settings:

  • KEYS_ONLY: Emits only the partition key and sort key of the modified item.
  • NEW_IMAGE: Emits the entire item as it appears after the write operation.
  • OLD_IMAGE: Emits the entire item as it appeared before the write operation.
  • NEW_AND_OLD_IMAGES: Emits both the previous and updated representations of the item.

Each record in a stream contains metadata along with the specified item attributes. Because DynamoDB items can reach up to 400 KB in size, the choice of view type dictates the potential size of individual stream records.

Direct Impact on Lambda Memory Usage

When AWS Lambda polls a DynamoDB Stream, it reads records in batches and passes them to the function handler inside the event parameter. The stream view type impacts Lambda memory in three distinct ways:

1. In-Memory Payload Deserialization

Before your handler code executes, the Lambda runtime deserializes the incoming JSON batch into language-native objects. The memory overhead of this deserialization is proportional to the raw byte size of the payload:

  • KEYS_ONLY produces minimal memory overhead. Even at the maximum batch size of 1,000 records, the raw JSON payload rarely exceeds a few hundred kilobytes, requiring minimal runtime memory to parse and retain.
  • NEW_IMAGE or OLD_IMAGE carries complete item structures. If an item is near the 400 KB limit, a single record can require significant heap allocation once parsed into an object tree.
  • NEW_AND_OLD_IMAGES doubles the item data footprint by including both states. A single record containing two full 400 KB representations can approach 800 KB of raw data, creating substantial heap usage during parsing and object instantiation.

2. Batch Sizing Multipliers

Lambda event source mappings allow a batch size between 1 and 10,000 records. Lambda memory consumption scales as:

\[\text{Memory Footprint} \approx \text{Average Record Size} \times \text{Batch Size} \times \text{Runtime Deserialization Overhead}\]

Using NEW_AND_OLD_IMAGES with a high batch size (e.g., 100 or higher) on heavily populated items can push the combined batch payload toward the 6 MB event size limit. In languages with higher memory overheads (such as Java or .NET), parsing a multi-megabyte batch of nested JSON attributes can easily exhaust standard 128 MB or 256 MB Lambda memory allocations.

3. Heap Retention and Garbage Collection Pressure

When downstream logic processes a stream, both the initial event payload and any newly created transformation objects reside concurrently in memory. With NEW_AND_OLD_IMAGES, applications frequently compute delta changes by diffing both states, holding old, new, and diff objects simultaneously in the heap. This causes sharp spikes in peak memory usage before the runtime's garbage collector can reclaim the unreferenced payloads.

Optimizing Stream Configuration for Lambda

To keep Lambda memory usage lean and predictable:

  • Use KEYS_ONLY when processing only requires identifiers: If the processing logic simply needs to trigger an external cache invalidation or push IDs to an asynchronous queue, do not send item attributes.
  • Avoid NEW_AND_OLD_IMAGES unless diffing is required: If your application only cares about the current state, use NEW_IMAGE. Only choose NEW_AND_OLD_IMAGES if your function must evaluate specific attribute transitions.
  • Pair Verbose View Types with Smaller Batch Sizes: If NEW_AND_OLD_IMAGES is required, reduce the Lambda event source BatchSize (e.g., down to 10–50 records) to ensure that large items do not cause out-of-memory crashes.
  • Tune Lambda Memory to Peak Heap Requirements: Monitor the MaxMemoryUsed metric in AWS CloudWatch. If using image-heavy streams, size your Lambda memory allocation based on worst-case payload scenarios rather than average throughput.
