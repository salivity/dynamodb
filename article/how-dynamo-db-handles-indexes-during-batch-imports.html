How DynamoDB Handles Indexes During Batch Imports

Amazon DynamoDB manages index maintenance during high-volume batch imports differently depending on whether you are writing to Local Secondary Indexes (LSIs) or Global Secondary Indexes (GSIs). While LSIs are updated synchronously alongside the base table, GSIs rely on an asynchronous, decoupled replication mechanism. Understanding how these update models handle throughput, capacity consumption, and potential throttling is essential for maintaining optimal ingestion performance and preventing base table write failures.

Local Secondary Indexes: Synchronous Maintenance

Local Secondary Indexes share the same partition key as the base table and are updated synchronously within the same transaction as the base item write.

  • Capacity Consumption: When an item is written or updated during a batch import, DynamoDB automatically consumes additional Write Capacity Units (WCUs) from the base table to update every affected LSI.
  • Throttling Risks: Because LSI maintenance is synchronous, an item write will fail completely if there is insufficient write capacity on the base table. Furthermore, the 10 GB partition size limit applies to any item collection containing LSIs, which can lead to partition-level throttling during high-volume targeted imports.

Global Secondary Indexes: Asynchronous Maintenance

Global Secondary Indexes have distinct partition keys and sort keys from the base table. DynamoDB decouples GSI maintenance from base table writes using an internal, stream-based log architecture.

  • Replication Flow: When a batch write hits the base table, DynamoDB acknowledges the write as soon as it is committed to storage. An internal replication engine immediately reads the change and applies it to the corresponding GSI asynchronously.
  • Independent Provisioning: GSIs have their own provisioned or on-demand write capacity. Ingested data generates write activity on the GSI only if the ingested attributes match the GSI's partition schema or projection list.
  • Replication Lag: During massive data ingestion, the time difference between base table updates and GSI updates—known as replication lag—can increase temporarily while DynamoDB works through the log queue.

Backpressure and Base Table Throttling

A critical aspect of DynamoDB’s index architecture is backpressure protection. While GSI updates are asynchronous, DynamoDB does not allow an index's replication queue to grow indefinitely.

If a GSI lacks sufficient write capacity to keep up with the batch import rate on the base table, DynamoDB throttles the base table writes. Even if the base table has ample write capacity remaining, requests like BatchWriteItem or PutItem will receive ProvisionedThroughputExceededException errors until the GSI catches up.

Best Practices for Batch Imports

  • Create GSIs After Ingestion: For initial data population, import data into a table with no GSIs. Once the import completes, create the GSIs. DynamoDB will backfill the indexes using managed internal capacity without impacting your operational table limits.
  • Pre-Scale Capacity: If writing to existing tables with GSIs, match or exceed the base table’s WCU on all affected GSIs. If using On-Demand mode, gradually ramp up traffic or contact support to pre-warm the partitions if the import involves an immediate, massive burst.
  • Leverage Native S3 Import: Use DynamoDB’s native "Import from S3" feature for initial bulk loads. This service parses data from Amazon S3 directly into a new DynamoDB table, building the base table and secondary indexes simultaneously without consuming provisioned write capacity or triggering standard throttling mechanisms.
