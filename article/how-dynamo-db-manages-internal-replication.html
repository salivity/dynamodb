How DynamoDB Manages Internal Replication

Amazon DynamoDB ensures high availability, durability, and fault tolerance by automatically dividing data into partitions and replicating those partitions across multiple storage nodes. Within the storage architecture, each partition is represented as a replica group consisting of a primary (leader) node and multiple secondary (follower) storage nodes. This article explains how DynamoDB coordinates these nodes using consensus algorithms, enforces write quorums through write-ahead logging, and manages node failures and state synchronization without downtime.

Partition Replicas and the Storage Group

DynamoDB distributes table data into physical partitions based on partition key hashes. To prevent single points of failure, every partition does not reside on a single machine; instead, it is deployed as a replication group consisting of multiple storage nodes (typically a three-way replica set).

Within each replica set, one node functions as the primary or leader, while the remaining nodes act as secondaries or peers. The primary node is responsible for sequencing all incoming write operations and coordinating state across the group, while secondary nodes maintain synchronized copies of the partition's data.

Leader Election via Paxos

To manage leadership and prevent split-brain scenarios, DynamoDB utilizes the Paxos consensus algorithm. The nodes within a partition group communicate continuously using heartbeats to monitor health and reach consensus on cluster state.

If the active primary node crashes, fails a health check, or becomes network-isolated, the remaining secondary nodes detect the failure and initiate a new leader election round using Paxos. A candidate node must secure a majority vote from the replica set to become the new primary. This transition typically completes in milliseconds, ensuring minimal disruption to incoming traffic.

The Synchronous Write Path and Quorum

When a write request (such as PutItem, UpdateItem, or DeleteItem) reaches a DynamoDB Request Router, it is directed to the primary storage node for that specific partition. The primary executes the following replication workflow:

  1. Transaction Generation: The primary assigns an monotonically increasing transaction sequence number to the operation.
  2. Local Logging: The primary appends the update to its local write-ahead log (WAL).
  3. Replication Broadcast: The primary concurrently sends the log entry to all secondary storage nodes in the group.
  4. Quorum Acknowledgment: Each secondary persists the update to its own local write-ahead log and sends an acknowledgment (ACK) back to the primary.
  5. Commit: Once the primary receives an ACK from a quorum (a strict majority, such as 2 out of 3 nodes, including the primary itself), the write is committed.
  6. Client Response: The primary reports success back to the request router, which then returns a 200 OK to the client.

Because commits only require a majority rather than unanimous agreement, the storage group can tolerate the slowness or failure of a secondary node without delaying write latency.

Asynchronous Catch-Up and Anti-Entropy

The secondary node that did not acknowledge the write during the critical path does not remain outdated permanently. DynamoDB handles catch-up through asynchronous log streaming and anti-entropy background processes:

  • Log Streaming: The lagging secondary continuously pulls missing log records from the primary or peer secondaries as soon as its connection stabilizes.
  • Anti-Entropy Verification: DynamoDB employs background verification processes that cross-reference Merkle trees (hash trees) across replicas. If discrepancies or corrupted segments are detected, the system transfers the specific missing data blocks from healthy peers to repair the out-of-sync node.
  • Node Replacement: If a storage node fails permanently or suffers prolonged disconnection, the DynamoDB partition management service provisions a new, healthy node, adds it to the replica set, and streams a snapshot of the partition's current state followed by recent transaction logs.

Read Consistency Mechanics

The primary-secondary replication structure directly dictates how DynamoDB services read operations:

  • Strongly Consistent Reads: The request router routes the query strictly to the current primary node. Because the primary coordinates all writes and holds the authoritative quorum state, it guarantees the most recent version of the item.
  • Eventually Consistent Reads: The request router can dispatch the query to any replica—primary or secondary. If the request hits a secondary node that has not yet processed the latest log entries, the response may reflect a slightly stale state until the node finishes catching up.
