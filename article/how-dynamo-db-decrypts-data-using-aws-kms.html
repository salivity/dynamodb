How DynamoDB Decrypts Data Using AWS KMS

This article provides an overview of how Amazon DynamoDB integrates with AWS Key Management Service (AWS KMS) to decrypt table data encrypted at rest. It explores the underlying envelope encryption model, the step-by-step cryptographic interaction between the two services during read operations, the role of encryption contexts, and how data key caching minimizes latency and KMS request costs.

The Envelope Encryption Foundation

DynamoDB secures data at rest using envelope encryption. Instead of encrypting every individual table item directly with an AWS KMS key, DynamoDB uses a two-tier key hierarchy:

  1. KMS Key (Key Encryption Key): A customer-managed key, AWS-managed key, or AWS-owned key stored in AWS KMS.
  2. Data Encryption Key (DEK): A unique cryptographic key generated by KMS that DynamoDB uses to directly encrypt and decrypt the physical data blocks housing your table items, indexes, and streams.

When data is written, DynamoDB stores the encrypted version of the DEK alongside the encrypted data blocks. When data is read, DynamoDB must first decrypt this DEK using AWS KMS before the underlying table items can be accessed.

Step-by-Step Decryption Workflow

When an authorized client submits a read request—such as GetItem, Query, or Scan—DynamoDB manages the decryption process automatically through the following sequence:

  1. Request Ingestion: DynamoDB receives the read request via an encrypted TLS connection. The service validates the caller’s AWS Identity and Access Management (IAM) permissions to ensure they are authorized to read from the target table.
  2. Key Retrieval and Cache Check: DynamoDB locates the encrypted data partition housing the requested item. To read the encrypted block, it requires the plaintext DEK. DynamoDB checks its internal, secure in-memory cache to determine if an unexpired plaintext DEK for that table partition already exists.
  3. AWS KMS Decryption Call: If the plaintext DEK is not cached, DynamoDB initiates an internal API call to AWS KMS using the kms:Decrypt operation. The request payload includes:
    • The ciphertext of the encrypted DEK.
    • The ARN of the KMS key associated with the table.
    • An Encryption Context, which acts as additional authenticated data (AAD) cryptographically binding the DEK to the specific DynamoDB table ARN and AWS Account ID.
  4. Policy Evaluation in KMS: AWS KMS evaluates the key policy, any relevant IAM policies, and grant permissions. It verifies that the principal or the DynamoDB service acting on behalf of the principal has the kms:Decrypt permission for the specified key. KMS also confirms that the provided encryption context matches the context supplied when the DEK was originally generated.
  5. Returning the Plaintext Key: Once authenticated and verified, the AWS KMS Hardware Security Module (HSM) decrypts the encrypted DEK and returns the plaintext DEK back to DynamoDB over a secure internal channel.
  6. Data Decryption and Return: DynamoDB uses the plaintext DEK (typically utilizing 256-bit Advanced Encryption Standard, AES-256) to decrypt the storage block containing the requested attributes.
  7. Client Delivery: DynamoDB strips away the storage-level wrappers, extracts the requested item or attributes, and sends the plaintext response back to the client over the secure TLS network session.

The Role of Encryption Context

The encryption context is a set of key-value pairs that DynamoDB passes to AWS KMS during decryption. For DynamoDB, this context typically contains the table ARN and the AWS account ID.

AWS KMS cryptographically binds this context to the ciphertext of the DEK during encryption. When DynamoDB attempts to decrypt the DEK, AWS KMS checks this context against the ciphertext. If the context does not match identically, the decryption request fails. This mechanism prevents ciphertext from being moved between tables or accounts, protecting against unauthorized substitution or replay attacks.

Data Key Caching and Performance

Invoking AWS KMS for every single row read would create severe performance bottlenecks and exhaust KMS API rate limits. To prevent this, DynamoDB caches the decrypted DEKs in memory across its storage nodes.

  • Short Lifespan: Cached keys are retained temporarily and refreshed periodically in alignment with AWS internal security policies.
  • Cost and Latency Optimization: Because the plaintext DEKs are cached locally in memory, the vast majority of individual item reads do not trigger an external network call to AWS KMS. This keeps read latencies at single-digit milliseconds while significantly reducing KMS per-request costs.

Permissions and Key Types

The permissions required to complete decryption depend on the KMS key type configured for the table:

  • AWS Owned Key (default): DynamoDB manages the key entirely. Users do not need KMS permissions in their IAM policies; having DynamoDB read permissions is sufficient.
  • AWS Managed Key (aws/dynamodb): The key is stored in your account, and AWS manages it. The IAM principal reading the table must have permissions to use the key for decryption via key policies or IAM permissions.
  • Customer Managed Key (CMK): You retain full control over key rotation and policies. The IAM principal executing the read request must possess explicit kms:Decrypt permissions on that specific CMK. If the principal lacks KMS decryption rights, the DynamoDB read request returns an AccessDeniedException.
