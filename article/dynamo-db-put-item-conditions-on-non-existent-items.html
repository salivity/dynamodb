DynamoDB PutItem Conditions on Non-Existent Items

When executing a PutItem request with a condition expression on an item that does not yet exist, Amazon DynamoDB evaluates the condition against a null or empty state. Because no prior record exists, any condition requiring an attribute to equal a value, exist, or satisfy a comparative constraint evaluates to false, while checks expecting the absence of attributes evaluate to true. Understanding this evaluation flow is essential for implementing patterns like idempotent creates and preventing accidental overwrites.

The Read-Before-Write Evaluation

Before writing data, DynamoDB internally attempts to locate the item using the primary key specified in your PutItem payload. If no item matches that primary key:

  1. DynamoDB treats the target item as an empty set of attributes.
  2. The ConditionExpression is evaluated against this empty state before the new item replaces it.
  3. If the expression evaluates to true, DynamoDB writes the new item.
  4. If the expression evaluates to false, DynamoDB aborts the write and throws a ConditionalCheckFailedException.

How Common Expressions Behave

The outcome of the condition check depends on the specific functions and comparison operators used in the expression:

  • attribute_not_exists(path): Evaluates to true. When targeted at the partition key or any other attribute path, DynamoDB confirms the attribute is not present. This is the standard approach to ensure a PutItem call creates a new item without overwriting an existing one.
  • attribute_exists(path): Evaluates to false. Because the item is missing, the specified path cannot exist. This prevents PutItem from executing unless an item is already present (effectively enforcing an "update-only via overwrite" policy).
  • Value Comparisons (=, <>, <, <=, >, >=): Evaluate to false. Comparisons such as version = :expected_version fail automatically because the referenced attribute does not exist on the table.
  • String and Set Functions (contains(), begins_with()): Evaluate to false. Functions expecting a value to operate on will fail when targeted against a non-existent item.
  • size(path): Results in a validation or evaluation failure because the function cannot compute the size of a non-existent attribute.

Boolean Logic and Negation

DynamoDB supports combining conditions using AND, OR, and NOT:

  • NOT (attribute_exists(pk)): Evaluates to true, behaving identically to attribute_not_exists(pk).
  • OR Chains: If an expression checks attribute_not_exists(pk) OR version = :v, the condition resolves to true because the first operand evaluates to true, allowing the insertion to proceed.
  • AND Chains: If an expression checks attribute_not_exists(pk) AND attribute_exists(sk), it resolves to false because any failing sub-condition invalidates the entire expression.

Capacity and Error Handling

If a condition evaluates to false on a non-existent item, DynamoDB returns an HTTP 400 status code with a ConditionalCheckFailedException. In standard provisioned or on-demand modes, failed conditional writes still consume Write Capacity Units (WCUs)—typically 1 WCU for an item that does not exist—reflecting the work DynamoDB performed to attempt the write and verify the condition.
