How DynamoDB Transactions Guarantee ACID Compliance

Amazon DynamoDB provides native, fully managed support for multi-item, cross-table operations that require strict database guarantees through its transaction APIs. By utilizing TransactWriteItems and TransactGetItems, developers can coordinate up to 100 operations or 4 MB of data in a single transactional request. This overview explains the specific mechanisms DynamoDB uses to ensure Atomicity, Consistency, Isolation, and Durability (ACID) across multiple items and tables without requiring complex custom locking logic.

The Underlying Architecture: Managed Two-Phase Commits

To enforce ACID compliance across distributed storage nodes, DynamoDB uses an internal, highly optimized two-phase commit (2PC) protocol managed by transaction coordinators.

When a transaction request arrives:

  1. Coordination: A coordinator node is assigned to orchestrate the transaction.
  2. Phase 1 (Prepare): The coordinator validates permissions, checks pre-conditions, and acquires reservations (locks) on the targeted items across their respective storage partitions.
  3. Phase 2 (Commit): If all condition checks pass and no conflicts occur, the coordinator instructs the partitions to apply the changes simultaneously. If any single check fails or an item is locked by a competing transaction, the coordinator cancels the operation and releases all reservations.

How DynamoDB Enforces Each ACID Property

1. Atomicity

Atomicity dictates that a set of operations must either entirely succeed or entirely fail. DynamoDB enforces this through an "all-or-nothing" execution model:

  • If any condition check in a TransactWriteItems call evaluates to false, the entire transaction is rejected.
  • DynamoDB returns a TransactionCanceledException, indicating precisely which item caused the failure.
  • No partial updates are ever written to the database; the state remains unchanged as if the operation never occurred.

2. Consistency

DynamoDB transactions maintain system-wide consistency before and after execution:

  • Prerequisite Validation: Developers can attach condition expressions (such as verifying an account balance or checking item existence) to individual operations within the transaction.
  • Global Secondary Indexes (GSIs): While transaction writes are applied synchronously to base tables, updates to GSIs are updated asynchronously. However, the base table data remains strictly consistent across all replicas immediately upon transaction completion.

3. Isolation

DynamoDB provides serializable isolation, the highest isolation level defined by SQL standards:

  • Transactions are executed such that their concurrent execution produces the same state as if they were executed sequentially.
  • Read operations within TransactGetItems or writes within TransactWriteItems do not experience dirty reads, non-repeatable reads, or phantom reads.
  • Read-only transactions are isolated from simultaneous write transactions, ensuring the client receives a point-in-time snapshot of the requested items.

4. Durability

Durability guarantees that once a transaction completes, its updates persist even in the event of hardware or system failures:

  • DynamoDB stores items redundantly across multiple Availability Zones (AZs) within an AWS Region.
  • A transaction is acknowledged as successful to the client only after the updates have been committed to persistent storage across a quorum of storage nodes.

Preventing Duplicate Executions with Idempotency

Network timeouts can obscure whether a transaction succeeded. DynamoDB solves this by allowing clients to include a ClientRequestToken with any TransactWriteItems call.

If the client retries the exact same transaction with the same token within a 10-minute window, DynamoDB recognizes the operation as idempotent. It returns the success status of the initial execution without re-applying the operations, preventing unintentional double-writes or duplicate charges.
