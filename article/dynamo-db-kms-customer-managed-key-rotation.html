DynamoDB KMS Customer Managed Key Rotation

Amazon DynamoDB integrates natively with AWS Key Management Service (KMS) to encrypt data at rest using Customer Managed Keys (CMKs). When a KMS key rotates, DynamoDB handles the transition seamlessly through an envelope encryption model, ensuring that continuous read and write operations proceed without downtime, performance degradation, or the need to immediately re-encrypt existing datasets.

Envelope Encryption and Table Keys

To minimize latency and reduce direct KMS API costs, DynamoDB does not call AWS KMS for every individual item write or read. Instead, it implements envelope encryption using a hierarchy of keys:

  1. KMS Customer Managed Key (CMK): The root key stored and managed within AWS KMS.
  2. DynamoDB Table Key: A unique encryption key generated by DynamoDB, encrypted by the KMS CMK, and cached securely in memory.
  3. Data Encryption Keys: Ephemeral keys derived from the table key used to encrypt the actual partition blocks and data records.

Automatic Key Rotation

When automatic key rotation is enabled for a customer managed key in AWS KMS, KMS automatically creates a new cryptographic backing key every year while keeping the same Key ID, Amazon Resource Name (ARN), policies, and permissions.

Because the key ARN remains unchanged, DynamoDB requires no administrative configuration updates:

  • Handling Existing Data: AWS KMS retains all prior versions of the backing key material. When DynamoDB reads historical data encrypted under an older table key, KMS uses the appropriate historical backing key to decrypt it.
  • Handling New Writes: DynamoDB periodically refreshes its cached table keys. Once the table key is refreshed, DynamoDB requests a new data key from AWS KMS, which KMS encrypts using the latest backing key. All subsequent write operations use this new key material.
  • No Immediate Bulk Re-encryption: DynamoDB does not rewrite or re-encrypt the entire table upon rotation. Data is re-encrypted dynamically as records are updated or rewritten over time.

Manual Key Rotation

If organizational policies require changing the cryptographic key entirely (which creates a new Key ARN) rather than rotating the underlying key material, the process involves a configuration change:

  1. A new KMS CMK is created with a distinct Key ARN.
  2. The DynamoDB table is updated via the AWS Management Console, AWS CLI, or the UpdateTable API, pointing the SSESpecification parameter to the new KMS Key ARN.
  3. DynamoDB immediately switches to the new CMK to generate subsequent table keys. Existing data remains accessible while DynamoDB asynchronously establishes the new encryption context, without table locking or availability impact.

Operational and Cost Impacts

Because DynamoDB relies on cached table keys, key rotation produces virtually zero operational overhead:

  • Availability: Reads and writes remain fully available during rotation.
  • KMS Costs: Since DynamoDB caches table keys, rotating a KMS key does not trigger a spike in KMS Decrypt or GenerateDataKey API requests across table partitions.
  • Permissions: No policy updates are necessary for automatic rotation since the Key ARN remains identical; IAM policies and KMS key policies remain valid throughout the lifecycle.
