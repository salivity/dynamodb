DynamoDB GSI Projections: Impact on Read Costs

In Amazon DynamoDB, Global Secondary Index (GSI) attribute projections—KEYS_ONLY, INCLUDE, and ALL—directly dictate read costs by determining the byte size of indexed items and deciding whether your application requires secondary queries against the base table. Choosing the right projection balances the cost of reading larger payloads from the GSI against the cost of performing additional read operations to fetch non-projected attributes.

How GSI Read Capacity Units Are Calculated

DynamoDB bills GSI reads based on Read Capacity Units (RCUs). Because GSIs only support eventually consistent reads, one RCU provides two reads per second for items up to 4 KB in size (0.5 RCU per item up to 4 KB). When an item exceeds 4 KB, DynamoDB rounds up to the next 4 KB multiplier.

The projection type determines the physical size of the item stored in the GSI:

  • KEYS_ONLY: Projects only the partition key, sort key, and base table primary keys. This produces the smallest possible item footprint.
  • INCLUDE: Projects specified non-key attributes alongside the key schema, keeping item sizes controlled while providing needed data.
  • ALL: Copies every attribute from the base table into the index, resulting in the largest item footprints.

The Direct Cost: Item Size Multipliers

If you choose the ALL projection or include large attributes via INCLUDE, the index record inherits the full weight of those fields. For example, reading an item from a GSI with a 3 KB projection consumes 0.5 RCU. If projecting all attributes expands that same item to 9 KB, reading it requires 1.5 RCUs (rounded up to the nearest 4 KB increment). For high-volume query patterns, projecting unnecessary data scales up RCU consumption linearly with item size.

The Indirect Cost: Secondary Lookups (Base Table Fetching)

Under-projecting attributes creates a different, often more expensive read cost. If a query requires an attribute not present in a KEYS_ONLY or minimal INCLUDE projection, your application must execute a two-step read:

  1. Query the GSI to retrieve the base table’s primary keys (consuming GSI RCUs).
  2. Execute a BatchGetItem or sequential GetItem requests against the base table to fetch the missing attributes (consuming base table RCUs).

This pattern doubles the number of read requests. If you perform strongly consistent reads on the base table during the second step, you consume 1 RCU per 4 KB instead of the GSI's 0.5 RCU rate. The operational overhead of handling two round trips also adds latency and network overhead alongside increased billing.

Optimizing GSI Projections for Cost

To minimize read expenses:

  • Use INCLUDE for defined query patterns: Identify the exact subset of attributes your access patterns require and project only those. This prevents items from spilling over 4 KB boundaries while avoiding subsequent base table lookups.
  • Use KEYS_ONLY for existence checks: If an access pattern only needs to determine whether a record exists or count matching entries, KEYS_ONLY minimizes read costs by keeping items well within the base 4 KB limit.
  • Reserve ALL for wide data requirements: Use ALL only when queries consistently need the full object graph, making the single, larger GSI read cheaper than executing a secondary base table read.
