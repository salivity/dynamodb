How DynamoDB Partitions Scale as Data Grows

Amazon DynamoDB automatically manages data distribution across physical storage units called partitions. As your application writes more data and the total item count increases, DynamoDB dynamically adapts by splitting existing partitions and reallocating hash ranges to accommodate the increased volume and throughput demands. This article explains how DynamoDB's internal partition mechanics work, how partition splits occur when data volume grows, and how item assignment changes over the lifecycle of a growing table.

The Role of the Partition Key and Hash Function

When an item is stored in DynamoDB, the service passes the primary partition key value into an internal MD5-based hashing algorithm. The resulting hash value falls somewhere along a continuous 128-bit hash ring (0x00 to 0xFF...). DynamoDB divides this hash ring into distinct ranges, with each physical partition responsible for a specific, contiguous range of hash values. Regardless of how many items exist, an item’s destination partition is determined exclusively by where its partition key hash lands within these ranges.

Triggers for Partition Splitting

A single DynamoDB partition has hard physical boundaries: it can hold up to 10 GB of data, support up to 1,000 Write Capacity Units (WCU), and support up to 3,000 Read Capacity Units (RCU).

As item counts rise over time, the primary driver for partition changes is storage accumulation. Once the total size of items assigned to a single partition approaches the 10 GB limit, DynamoDB automatically initiates an asynchronous partition split. Splits can also be triggered if the read or write throughput required by items in that partition exceeds the physical throughput limits.

How Partition Splitting Modifies Assignment

When a partition reaches its capacity limit, DynamoDB does not simply append an extra partition to the end of the table. Instead, it performs the following steps:

  1. Range Bisecting: DynamoDB creates two new child partitions and divides the parent partition's hash key range between them.
  2. Data Redistribution: Items residing in the parent partition are allocated to one of the two child partitions depending on their specific hash values. Roughly half the items typically move to the first child partition, while the remaining items move to the second.
  3. Parent Decommissioning: Once the data migration is verified, the original parent partition is removed from active routing, and requests are directed to the new child partitions.

Because this split happens at the hash range level, items with different partition keys that once shared a single partition may now reside on different physical partitions. However, all items sharing the exact same partition key value will always hash to the identical value and therefore remain together on the same child partition.

The Monotonic Growth of Partitions

Partition splits are a one-way operation. As item counts grow and cause partition counts to increase, DynamoDB does not automatically merge partitions back together if you subsequently delete large numbers of items. The allocated partitions remain in place, each continuing to manage its assigned subset of the hash space.

Because throughput allocation and physical capacity scale with partition splits, maintaining a high-cardinality partition key is essential. High cardinality ensures that as partition boundaries multiply over time, items and read/write requests remain uniformly distributed across all available partitions rather than concentrating on a single split segment.
