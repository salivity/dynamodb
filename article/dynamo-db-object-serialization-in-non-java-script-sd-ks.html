DynamoDB Object Serialization in Non-JavaScript SDKs

Amazon DynamoDB stores data using low-level attribute type descriptors—such as {"S": "value"} or {"N": "123"}—which represent DynamoDB’s native data model. While JavaScript and TypeScript ecosystems often rely on the Document Client to translate standard JSON objects, non-JavaScript AWS SDKs handle object mapping through higher-level Object Persistence Models (OPMs), reflection-based mappers, and language-specific struct tags or annotations. These tools serialize native classes, structs, or domain objects into DynamoDB’s wire-format attribute maps and deserialize responses back into typed language constructs.

The Low-Level Wire Format vs. Domain Models

At the transport layer, the DynamoDB API does not accept plain JSON or arbitrary binary classes. Every write request (PutItem, UpdateItem) expects a map of attribute names paired with typed values (e.g., S for String, N for Number, B for Binary, M for Map, L for List, and sets like SS or NS). Non-JavaScript SDKs automate the translation between these rigid descriptors and language-native objects using distinct patterns tailored to each runtime.

Java: The DynamoDB Enhanced Client

In the AWS SDK for Java 2.x, serialization is primarily driven by the DynamoDB Enhanced Client.

  • Annotations and Schemas: Java maps POJOs (Plain Old Java Objects) using annotations such as @DynamoDbBean, @DynamoDbPartitionKey, @DynamoDbSortKey, and @DynamoDbAttribute.
  • Static Table Schemas: For immutable classes or scenarios avoiding reflection, the SDK provides the TableSchema builder, defining mapping rules programmatically.
  • Custom Converters: When a class contains an unsupported or nested third-party object, developers implement the AttributeConverter<T> interface. This interface defines two methods: transformFrom(T input) to convert the custom object into an AttributeValue, and transformTo(AttributeValue input) to reconstruct the original type.
  • Nested Objects: Sub-objects annotated with @DynamoDbBean automatically serialize into nested DynamoDB Maps (M).

.NET (C#): The Object Persistence Model

The AWS SDK for .NET includes a high-level DynamoDBContext that manages mapping via reflection.

  • Attributes: Properties and classes are decorated with attributes such as [DynamoDBTable], [DynamoDBHashKey], [DynamoDBRangeKey], and [DynamoDBProperty].
  • Custom Type Conversion: If a property cannot be implicitly mapped to standard primitive or collection types, the SDK requires an implementation of IPropertyConverter. This interface supplies ToEntry(object value) to produce a DynamoDBEntry and FromEntry(DynamoDBEntry entry) to hydrate the custom object back into the .NET class.
  • Complex Hierarchies: Nested classes can be serialized as JSON strings or flattened into nested maps depending on whether the [DynamoDBIgnore] or explicit conversion attributes are applied.

Python: Boto3 and PynamoDB

The official Python SDK, Boto3, handles serialization at two different layers:

  • Boto3 TypeSerializer/TypeDeserializer: The low-level client requires explicit dictionaries, but Boto3 includes the boto3.dynamodb.types.TypeSerializer and TypeDeserializer classes. These utilities convert native Python types (such as str, int, list, dict, and decimal.Decimal) to and from DynamoDB attribute values.
  • Manual Custom Serialization: Boto3 does not have a built-in ORM/ODM for custom Python classes. Custom objects must define standard serialization methods (such as to_dict() or asdict() from standard dataclasses) before passing data to the serializer.
  • Third-Party Mappers (PynamoDB): To achieve behavior similar to Java or .NET, Python developers commonly use libraries like PynamoDB, which define models using declarative attributes (UnicodeAttribute, MapAttribute) and provide custom serialization hooks via Attribute subclasses.

Go: The attributevalue Package

The AWS SDK for Go (v2) uses the feature/dynamodb/attributevalue package to bridge Go structs and DynamoDB data types.

  • Struct Tags: Go relies on struct field tags using the dynamodbav namespace (e.g., dynamodbav:"user_id,hash", dynamodbav:"created_at,omitempty").

  • Reflection-Driven Marshalling: Functions such as attributevalue.MarshalMap(interface{}) inspect struct fields and recursively generate map[string]types.AttributeValue.

  • Custom Marshalling Interfaces: To intercept and customize serialization for domain types, a custom struct must implement the attributevalue.Marshaler interface:

    MarshalDynamoDBAttributeValue() (types.AttributeValue, error)

    Deserialization uses the companion attributevalue.Unmarshaler interface:

    UnmarshalDynamoDBAttributeValue(types.AttributeValue) error

Handling Unsupported or Deeply Nested Custom Types

When an SDK encounters a custom type without a built-in primitive mapping or an explicit converter:

  1. Map Decomposition: If the object is composed of public fields or standard accessors, the SDK attempts to recursively serialize it into a native Map (M).
  2. String/Blob Fallback: If the structure is complex or opaque (such as third-party library classes), developers commonly serialize the object into a JSON string or Protocol Buffer byte array and map it to a String (S) or Binary (B) attribute.
  3. Null and Default Handling: Most non-JavaScript SDKs default to omitting null fields from writes rather than writing a null attribute (NULL: true), unless explicitly instructed via configuration settings or annotations.
