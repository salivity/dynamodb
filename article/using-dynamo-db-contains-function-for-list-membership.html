Using DynamoDB Contains Function for List Membership

Amazon DynamoDB allows you to evaluate whether a list attribute contains a specific element by using the contains(path, operand) function within a condition expression. This article explains how DynamoDB processes this function against List (L) data types, the exact matching rules it applies to list elements, its behavior with complex data types, and critical considerations regarding data types and performance.

How contains Operates on DynamoDB Lists

In DynamoDB condition and filter expressions, the contains function takes two parameters:

contains(path, operand)

When path references an attribute of type List (L), the function evaluates to TRUE if the specified operand matches any individual element within that list. Otherwise, it returns FALSE.

Unlike its behavior on String (S) attributes—where it looks for a substring—when applied to a List (L), contains looks for complete element equality.

Exact Match Evaluation Rules

DynamoDB adheres to strict element-level comparison semantics when scanning lists:

  • Complete Value Matching: The operand must match the target element entirely. For instance, if a list contains the string "database", contains(myList, :val) where :val is "data" will evaluate to FALSE.
  • Type Strictness: Lists in DynamoDB can be heterogeneous (containing mixed data types). DynamoDB requires that both the value and the underlying DynamoDB data type match. An operand of type Number ({"N": "100"}) will not match an element of type String ({"S": "100"}).
  • Case Sensitivity: For String elements within a list, comparisons are strictly case-sensitive. "DevOps" will not match "devops".

Handling Complex and Nested Data

DynamoDB lists can store complex data structures, including Maps (M) and nested Lists (L):

  • Exact Structure Equality: If a list contains maps, contains evaluates to TRUE only if the operand map matches the targeted map element exactly, including all keys, nested values, and types.
  • No Deep Searching: The contains function does not traverse into nested structures inside list elements. For example, you cannot use contains(myList, :nestedValue) to find a scalar value nested inside a Map element within that list; doing so requires targeting the specific nested path directly (e.g., myList[0].nestedKey = :val).

Example Condition Expression

Consider an item representing a project with an assigned user list:

{
  "ProjectId": {"S": "PRJ-001"},
  "TeamMembers": {
    "L": [
      {"S": "alice"},
      {"S": "bob"},
      {"S": "charlie"}
    ]
  }
}

To conditionally update the project only if "bob" is an existing member of the team, the condition expression is structured as follows:

  • Condition Expression: contains(#members, :user)
  • Expression Attribute Names: {"#members": "TeamMembers"}
  • Expression Attribute Values: {":user": {"S": "bob"}}

During evaluation, DynamoDB inspects the TeamMembers list element by element. When it encounters the second element ({"S": "bob"}), it finds an exact type and value match, short-circuits the list traversal, and resolves the condition to TRUE.

Performance and Read Capacity Impact

DynamoDB evaluates condition expressions on the server after reading the full item.

  • The contains check does not reduce the Read Capacity Units (RCUs) consumed for the operation. DynamoDB always consumes RCUs based on the total size of the item, regardless of whether the condition succeeds or fails.
  • For lists that grow significantly, traversing large lists repeatedly can add processing overhead. If your access pattern exclusively requires testing for item membership among unique scalar values, utilizing a Set (SS, NS, or BS) instead of a List is often preferred for data integrity, though evaluation mechanics for contains remain functionally similar.
