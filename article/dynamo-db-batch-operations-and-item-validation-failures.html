DynamoDB Batch Operations and Item Validation Failures

Amazon DynamoDB handles batch operation failures differently depending on whether the error stems from structural validation, transactional condition checks, or throughput limits. When an individual item within a standard batch request violates basic DynamoDB validation rules—such as schema mismatches or size limits—DynamoDB rejects the entire batch immediately without processing any items. Conversely, if operations fail due to capacity limits or if transactional APIs are used, DynamoDB applies distinct partial-success or all-or-nothing rollback mechanisms.

Payload and Request-Level Validation

Standard batch APIs, namely BatchWriteItem and BatchGetItem, perform synchronous validation on the entire request payload before attempting to process individual records. If any single item in the batch fails a core validation check, DynamoDB returns an HTTP 400 error (typically a ValidationException), and zero items are written or read.

Validation failures that reject the entire batch include:

  • Primary Key Violations: Supplying an item missing a partition key, omitting a required sort key, or using a data type that does not match the table's schema.
  • Size Limitations: Any single item exceeding the 400 KB limit, or the total batch request exceeding the 16 MB limit.
  • Batch Quantity Limits: Supplying more than 25 items in a BatchWriteItem call or more than 100 items in a BatchGetItem call.
  • Duplicate Keys: Supplying multiple operations targeting the same primary key within the same batch request.

Because DynamoDB evaluates these constraints prior to execution, request validation is strictly non-atomic and binary: the entire payload is rejected at the API gateway level.

Conditional Checks and Transactional Batches

Standard BatchWriteItem operations do not support condition expressions. If your workload requires individual item validation checks based on existing database state (such as checking if an attribute equals a certain value or ensuring an item does not already exist), you must use TransactWriteItems instead of BatchWriteItem.

When using TransactWriteItems:

  • All-or-Nothing Atomicity: If a single item fails its ConditionExpression, DynamoDB aborts the entire transaction.
  • Error Response: The operation throws a TransactionCanceledException. DynamoDB returns a CancellationReasons array detailing exactly which item failed its condition check and why (e.g., ConditionalCheckFailed).
  • State Preservation: None of the other items in the batch are committed, preventing partial updates when integrity constraints are breached.

Partial Processing: Validation vs. Provisioned Capacity

It is essential to distinguish between validation failures and throughput or transient operational failures. While validation errors terminate the request entirely, operational bottlenecks do not.

When executing BatchWriteItem or BatchGetItem, DynamoDB processes each valid item independently. If certain items cannot be processed due to transient issues or table throttling:

  • DynamoDB processes and commits the valid items that succeed.
  • Failed items are placed into the UnprocessedItems (or UnprocessedKeys) block of the response payload.
  • The API returns an HTTP 200 status code rather than an exception, signaling that the request itself was structurally valid even though execution was only partially complete.

Recommended Implementation Strategy

To handle DynamoDB batch operations reliably:

  1. Validate Client-Side: Ensure items match schema requirements, primary keys are populated, data types are correct, and payload limits are respected prior to sending the batch call.
  2. Handle UnprocessedItems: Always inspect the response of BatchWriteItem and implement an exponential backoff retry loop for any records returned in UnprocessedItems.
  3. Select the Right API: Use BatchWriteItem when maximizing write throughput for independent, non-conditional items. Switch to TransactWriteItems when you must enforce data consistency, uniqueness constraints, or conditional state validation across multiple records.
