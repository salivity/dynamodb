Enforce Tenant Isolation in DynamoDB Partition Keys

In a shared multi-tenant architecture using Amazon DynamoDB, tenant data isolation can be achieved within a single pooled table by designing the partition key around a unique tenant identifier and enforcing runtime permissions using AWS Identity and Access Management (IAM). This approach prevents cross-tenant data leakage by mathematically separating data placement across physical storage partitions while leveraging DynamoDB's fine-grained access control (FGAC) to reject unauthorized operations at the request layer.

1. Partition Key Design Patterns

To enforce tenant isolation, the tenant identifier must be an immutable component of the primary partition key (PK). There are two common patterns for structuring this key:

  • Prefix-Based Composite Keys: Concatenate the tenant identifier with the item's entity type and unique ID (e.g., PK = TENANT#12345#USER#67890). This allows multiple entity types for a single tenant to reside across partitions while maintaining strict namespace separation.
  • Tenant-Dedicated Partition Keys: Set the partition key exclusively to the tenant ID (e.g., PK = TENANT#12345) and use the sort key (SK) to identify the entity type and item ID (e.g., SK = USER#67890). This groups all items for a given tenant onto the same partition or logical partition set, which simplifies isolation logic but requires monitoring partition throughput limits (1,000 WCU / 3,000 RCU per partition).

Regardless of whether the key is purely the tenant ID or a composite prefix, every write operation must programmatically inject the authenticated tenant's identifier into the partition key attribute.

2. Fine-Grained Access Control with IAM Policy Conditions

Application-level checks are insufficient on their own; isolation must be enforced by AWS IAM. DynamoDB supports fine-grained access control through the dynamodb:LeadingKeys policy condition key. This condition evaluates the partition key value of every incoming GetItem, PutItem, UpdateItem, DeleteItem, BatchGetItem, BatchWriteItem, and Query request.

An IAM policy restricting access to a specific tenant looks like this:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:UpdateItem",
        "dynamodb:DeleteItem",
        "dynamodb:Query",
        "dynamodb:BatchGetItem",
        "dynamodb:BatchWriteItem"
      ],
      "Resource": "arn:aws:dynamodb:region:account-id:table/MultiTenantTable",
      "Condition": {
        "ForAllValues:StringLike": {
          "dynamodb:LeadingKeys": [
            "${aws:PrincipalTag/TenantId}*"
          ]
        }
      }
    }
  ]
}

By utilizing ${aws:PrincipalTag/TenantId}*, the condition validates that the partition key begins with the authorized tenant ID. If an operation attempts to read or write using a partition key with a different tenant prefix, DynamoDB evaluates the condition to false and returns an AccessDeniedException.

3. Dynamic Credential Generation via AWS STS

To make IAM policy enforcement scalable without creating separate IAM roles for thousands of tenants, use AWS Security Token Service (STS) to vend dynamic, short-lived credentials:

  1. Session Tagging: When an application authenticates a tenant (for example, through an Amazon Cognito User Pool or custom identity provider), it generates a JWT containing the tenant_id.
  2. AssumeRole: The application assumes an IAM role using sts:AssumeRole or sts:AssumeRoleWithWebIdentity, passing the tenant ID as a transient principal tag (TenantId).
  3. Scoped DynamoDB Client: The resulting temporary credentials are used to instantiate the DynamoDB client for that specific request execution. DynamoDB dynamically substitutes ${aws:PrincipalTag/TenantId} with the session tag value, enforcing isolation at the partition key without hardcoding policies per tenant.

4. Isolating Global Secondary Indexes (GSIs)

Partition key isolation must also extend to all Global Secondary Indexes (GSIs). If a GSI uses a partition key that does not include the tenant identifier (such as an index partitioned by a generic Status or CreatedAt attribute), any query to that index can expose cross-tenant data.

To prevent this:

  • Ensure that every GSI's partition key also uses a tenant-prefixed composite key (e.g., GSI1PK = TENANT#12345#STATUS#ACTIVE).
  • Include the GSI ARN in the IAM policy resource block, ensuring the dynamodb:LeadingKeys condition applies to index queries as strictly as base table operations.
