How DynamoDB Evaluates AND and OR Condition Expressions

Amazon DynamoDB allows developers to enforce granular write conditions using boolean operators like AND and OR. This article explains how DynamoDB parses and evaluates these compound condition expressions, detailing operator precedence, grouping rules, evaluation order, and how missing attributes impact conditional logic during write, update, or delete operations.

Operator Precedence in DynamoDB

When evaluating multiple conditions within a ConditionExpression, DynamoDB strictly adheres to standard boolean operator precedence:

  1. Parentheses (): Any expressions wrapped in parentheses are evaluated first, from the innermost set to the outermost set.
  2. NOT: Unary negation is evaluated next.
  3. AND: Conjunction operations are evaluated before disjunctions.
  4. OR: Disjunction operations have the lowest precedence.

When operators have equal precedence (such as multiple AND clauses chained together), DynamoDB evaluates them from left to right.

Example of Precedence in Action

Consider the following unparenthesized expression:

attribute_exists(userId) OR age > :minAge AND status = :active

Because AND takes precedence over OR, DynamoDB groups and evaluates the expression as:

attribute_exists(userId) OR (age > :minAge AND status = :active)

The operation will succeed if attribute_exists(userId) is true, regardless of what age or status evaluate to. To alter this evaluation order, explicit parentheses must be used:

(attribute_exists(userId) OR age > :minAge) AND status = :active

Boolean Logic and Short-Circuit Evaluation

DynamoDB evaluates condition expressions against the existing item stored in the table immediately before executing a write or update. The entire compound condition must resolve to a single boolean true value for the operation to proceed. If it resolves to false, the operation aborts and returns a ConditionalCheckFailedException.

DynamoDB uses standard short-circuit evaluation logic:

  • AND Logic: If the first operand evaluates to false, DynamoDB knows the entire AND block cannot be satisfied.
  • OR Logic: If the first operand evaluates to true, DynamoDB knows the entire OR block is satisfied.

Even with short-circuiting, all attribute names and values referenced in the expression must still be validly formed and defined in ExpressionAttributeNames or ExpressionAttributeValues.

Handling Non-Existent Attributes in Compound Expressions

A common source of errors in compound DynamoDB condition expressions is how missing attributes are treated:

  • If an expression references an attribute that does not exist on the targeted item (e.g., score > :minScore), that individual condition evaluates to false.
  • In an AND chain, if any condition checks a missing attribute without using attribute_not_exists(), the entire AND expression resolves to false.
  • In an OR chain, a missing attribute evaluating to false does not automatically fail the request; the operation can still succeed if the alternate condition evaluates to true.

For example, to safely update an item whether an attribute exists or not, you can combine checks using OR:

attribute_not_exists(viewCount) OR viewCount < :maxViews

If viewCount does not exist, the first clause resolves to true, satisfying the OR statement and allowing the write to succeed.

Expression Constraints and Limits

When constructing complex logic trees with AND and OR, keep the following constraints in mind:

  • Nesting Depth: DynamoDB allows expressions to be nested up to a depth of 100.
  • Expression Length: The maximum size of an individual condition expression string is 4 KB.
  • Consumed Capacity: Conditional writes consume write capacity units (WCUs) regardless of whether the condition succeeds or fails. DynamoDB reads the existing item first to evaluate the condition expression before executing the modification.
