How DAX Maintains Consistency on Base Table Writes

Amazon DynamoDB Accelerator (DAX) is a fully managed, highly available, in-memory cache designed to deliver microsecond response times for DynamoDB workloads. Maintaining cache consistency between DAX and the underlying base table depends heavily on whether writes are routed directly through DAX or bypass it entirely to write straight to DynamoDB. This article explores how DAX handles cache consistency during base table updates, detailing the write-through architecture, the limitations of direct DynamoDB writes, and the role of Time to Live (TTL) in cache invalidation.

Write-Through Caching via DAX

The primary mechanism DAX uses to maintain consistency is a write-through caching strategy. When an application performs write operations (PutItem, UpdateItem, DeleteItem) directly through the DAX client rather than the standard DynamoDB client:

  1. Synchronous Base Table Update: DAX forwards the write request to the underlying DynamoDB base table first.
  2. Cache Synchronization: Only after the base table successfully acknowledges the write does DAX update or invalidate the item in its internal cache.
  3. Success Acknowledgment: The client receives a success response only when both the base table write succeeds and the cache state is updated.

This ensures that any subsequent read directed to DAX immediately reflects the updated state of the base table, maintaining read-after-write consistency for item-level operations.

Writes That Bypass DAX (Direct Base Table Writes)

When writes are executed directly against DynamoDB bypassing the DAX cluster—such as by other microservices, batch jobs, or manual administrative changes—DAX has no native, real-time awareness of these changes. DAX does not monitor DynamoDB Streams to automatically invalidate or update cached items.

In this scenario, consistency is maintained via the following passive mechanisms:

1. Time-to-Live (TTL) Expiration

DAX relies on configurable TTL settings to limit data staleness when direct base table updates occur. DAX maintains two distinct caches:

  • Item Cache: Holds individual items fetched via GetItem or BatchGetItem. By default, items remain in the cache until the TTL expires (default is 5 minutes, configurable down to 0). Once the TTL expires, the next read results in a cache miss, prompting DAX to fetch the fresh item from DynamoDB and repopulate the cache.
  • Query Cache: Holds results from Query and Scan requests. This cache also uses a TTL. Writes to DynamoDB do not invalidate existing query result sets until their TTL elapses.

2. Least Recently Used (LRU) Eviction

When the DAX cluster experiences memory pressure, it automatically evicts items using an LRU algorithm. Evicted items that were modified directly in DynamoDB will be refreshed with current data from the base table on their next read.

Strong Consistency and Cache Bypass

If an application requires immediate, guaranteed consistency after a base table write has bypassed DAX, it can request a strongly consistent read.

DAX does not serve strongly consistent reads from its in-memory storage. Instead, passing a strongly consistent read request through DAX causes it to bypass both the Item and Query caches, forwarding the request directly to DynamoDB to retrieve the most up-to-date data. Note that strongly consistent reads do not refresh the DAX cache with the newly retrieved value.

Summary of Consistency Characteristics

  • Writes through DAX: Cache consistency is immediate for item-level reads via the write-through pattern.
  • Writes direct to DynamoDB: Cache becomes eventually consistent, bounded by the configured Item and Query Cache TTL values or LRU eviction.
  • Query and Scan operations: Even when writes are sent through DAX, complex queries may remain stale until the Query Cache TTL expires, as DAX does not compute whether a single item modification affects cached query result sets.
