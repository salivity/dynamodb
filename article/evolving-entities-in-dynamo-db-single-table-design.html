Evolving Entities in DynamoDB Single-Table Design

Managing structural evolution in Amazon DynamoDB single-table design requires handling schema changes at the application layer, as DynamoDB enforces schemas only on primary keys, not item attributes. This article explains how single-table design accommodates changing business requirements, detailing practical techniques such as additive attribute changes, entity versioning, index adaptation, and zero-downtime data migrations using DynamoDB Streams and lazy updates.

The Nature of Schema in DynamoDB

DynamoDB is inherently schemaless at the attribute level, meaning items in the same table can have entirely different attributes. However, in single-table design, the "schema" is strictly governed by access patterns modeled through generic primary keys (such as PK and SK) and Global Secondary Indexes (GSIs). Therefore, structural evolution does not typically mean running database migrations to alter columns; instead, it means evolving how entity attributes map to primary and secondary index keys.

Handling Additive and Non-Breaking Changes

The simplest evolution occurs when an entity requires new attributes that do not affect existing access patterns or index structures. Because DynamoDB does not enforce a uniform item shape:

  • Optional Fields: New attributes can be written directly to newly created or updated items.
  • Default Values: The application logic handles missing attributes on older items by assigning sensible defaults upon deserialization.
  • Deprecations: Unused attributes can simply be ignored by the application or removed gradually during write operations.

Entity Versioning

When an entity's structure changes fundamentally—such as restructuring nested objects or changing data types—entity versioning prevents read errors:

  • Schema Version Attributes: Include a version or schemaVersion attribute (e.g., "version": 2) on every item.
  • Polymorphic Deserialization: The application layer uses this attribute to route the raw JSON payload to the appropriate model parser.
  • In-Memory Upgrades: The application reads version 1, converts it in memory to version 2, and either uses it transparently or saves it back in the version 2 format.

Evolving Primary and Secondary Index Keys

Structural challenges arise when access patterns change, requiring updates to overloaded primary keys (PK/SK) or GSI partition and sort keys (GSI1PK/GSI1SK). Because primary keys cannot be updated in place, entities must be handled systematically:

  1. Composite Key Overloading Adjustments: If a new query pattern requires a new composite sort key (e.g., changing from STATUS#DATE to ORG#STATUS#DATE), the application begins populating the new format in a dedicated GSI attribute to avoid breaking legacy queries.
  2. Sparse Indexes for New Entity Types: Adding a new entity type or sub-structure often only requires populating GSI keys for those specific items. Because DynamoDB GSIs are sparse, items lacking these attributes will not be indexed, preventing index bloat.

Migration Strategies for Legacy Data

When existing records must be updated to conform to a new access pattern, two primary strategies are used:

1. Lazy Migration (Write-on-Read)

The application handles migration on an item-by-item basis:

  • The application reads the old item format.
  • If outdated, the application transforms the item into the new structure.
  • The application writes the transformed item back to DynamoDB (deleting and recreating if primary keys changed).
  • Over time, frequently accessed records are migrated without mass compute overhead.

2. Dual-Writing and Asynchronous Backfilling

For mission-critical systems requiring immediate consistency across all records:

  • Phase 1 (Dual-Writing): Update the application to write data in the new structure (or populate both old and new GSI fields) for all incoming writes.
  • Phase 2 (Backfilling): Run a background process—such as an AWS Glue job, an Amazon EMR cluster, or a custom script reading via parallel DynamoDB Scans—to update historical items with the new attributes.
  • Phase 3 (DynamoDB Streams for Edge Cases): Use DynamoDB Streams coupled with AWS Lambda to capture updates made during the backfill, ensuring no writes are overwritten with stale data.
  • Phase 4 (Cutover and Cleanup): Switch read operations to query the new keys, then remove the legacy attributes or old GSIs once traffic has shifted entirely.
