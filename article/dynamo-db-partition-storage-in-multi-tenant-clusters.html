DynamoDB Partition Storage in Multi-Tenant Clusters

Amazon DynamoDB manages partition storage capacity across its multi-tenant architecture by isolating data into distinct, fixed-capacity logical partitions distributed across shared physical storage nodes. While tenants share underlying hardware, DynamoDB strictly limits each individual partition to a maximum of 10 GB of data to ensure high availability, fast repair times, and consistent I/O performance. DynamoDB computes this capacity via continuous item-level metering on local partition replicas and automatically prevents node exhaustion through dynamic partition splitting and autonomous cluster rebalancing.

Logical Partitions and Multi-Tenant Storage Nodes

In DynamoDB, a table's data is divided into logical partitions based on partition key hash values. Each logical partition is maintained as a three-node replication group using the Paxos consensus algorithm across multiple Availability Zones.

Physical storage nodes host these partition replicas in a multi-tenant layout. A single physical machine runs a proprietary storage engine (historically based on specialized storage systems like B-trees and, more recently, optimized log-structured merge engines) hosting hundreds or thousands of partition replicas belonging to completely different AWS customer accounts. Multi-tenancy operates strictly at the physical layer, while logical boundaries are maintained per partition.

How Storage Capacity Is Computed

DynamoDB calculates storage consumption at the item level in real time. The storage size of a partition is the aggregate byte count of all its items, calculated as:

  • Attribute Names: The length of each attribute name in UTF-8 bytes.
  • Attribute Values: The raw binary, string (UTF-8 bytes), numeric, or set data sizes.
  • Per-Item Overhead: An internal overhead allocation (typically around 100 bytes per item) to account for indexing, system metadata, and document structure tracking.

Every write, update, and delete operation executed via Paxos evaluates this byte delta. The leader replica of the partition maintains an ongoing local counter of total stored bytes. Because deletions and overwrites can introduce internal fragmentation, DynamoDB's local storage engine tracks actual user data footprints rather than raw disk-block allocation when calculating against tenant storage quotas.

The 10 GB Boundary Enforcement

DynamoDB enforces an architectural limit of 10 GB per individual partition. This ceiling is selected to ensure that operational tasks—such as rebuilding a failed replica across the network, taking automated backups, or migrating data—can be completed in minutes rather than hours.

Storage capacity enforcement does not simply reject writes once 10 GB is reached. Instead:

  1. Monitoring Thresholds: As a partition's computed storage size approaches capacity (typically triggered once it crosses safe internal thresholds near 10 GB), an automated management event is generated by the partition manager.
  2. Partition Splitting: The partition splits into two new partitions. DynamoDB calculates a new midpoint in the partition key hash space, dividing the data roughly in half.
  3. Replica Relocation: The newly formed partitions can remain on the existing physical storage nodes or be migrated to new physical nodes elsewhere in the cluster to prevent localized disk saturation.

If an individual item collection (items sharing the exact same partition key in a table with a Local Secondary Index) reaches 10 GB, it cannot be split across partitions. In this specific scenario, DynamoDB will reject additional writes to that specific partition key with an ItemCollectionSizeLimitExceededException.

Cluster-Level Multi-Tenant Capacity Management

Because multiple tenants share disk space on the same physical storage nodes, overall drive utilization is managed independently of individual partition limits:

  • Proportional Placement: DynamoDB’s global request router and fleet placement systems evaluate physical node disk utilization before assigning new partition replicas.
  • Anti-Noisy-Neighbor Rebalancing: If multiple tenants on the same physical drive experience rapid, aggregate data growth, background fleet management services automatically migrate partition replicas to less-utilized storage nodes without downtime or performance degradation.
  • Storage vs. Throughput Decoupling: Storage capacity calculations are decoupled from provisioned or on-demand throughput calculations. A partition split triggered by hitting the 10 GB storage threshold reallocates data, resets the 10 GB ceiling for the two new child partitions, and redistributes allocated throughput across the new hash ranges.
