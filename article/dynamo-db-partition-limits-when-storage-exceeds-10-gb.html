DynamoDB Partition Limits When Storage Exceeds 10 GB

Amazon DynamoDB manages scalability automatically by distributing data across physical storage units known as partitions. This article explains how DynamoDB computes partition allocation, details the mathematical formulas triggered when a table's storage exceeds the standard ten-gigabyte threshold, and examines how partition splitting affects allocated throughput across your database architecture.

Partition Capacity Constraints

DynamoDB imposes strict capacity boundaries on each individual physical partition:

  • Maximum Storage: 10 GB
  • Maximum Read Throughput: 3,000 Read Capacity Units (RCUs)
  • Maximum Write Throughput: 1,000 Write Capacity Units (WCUs)

Whenever a table exceeds any of these operational thresholds, DynamoDB allocates additional partitions to maintain availability and performance.

Computing Partition Requirements

DynamoDB calculates the total number of partitions required for a table using two independent metrics: provisioned throughput and total data storage.

  1. Partitions by Throughput:
    \[\text{Partitions (Throughput)} = \frac{\text{Total RCUs}}{3000} + \frac{\text{Total WCUs}}{1000}\]

  2. Partitions by Storage:
    \[\text{Partitions (Storage)} = \frac{\text{Total Storage in GB}}{10\text{ GB}}\]

The overall number of partitions provisioned is determined by taking the ceiling of whichever calculation yields the higher number:

\[\text{Total Partitions} = \lceil \max(\text{Partitions (Throughput)}, \text{Partitions (Storage)}) \rceil\]

When storage exceeds 10 GB, the storage-based calculation increases. For example, if a table stores 25 GB of data with minimal throughput (e.g., 100 RCU and 100 WCU), the throughput calculation requires only one partition, but the storage calculation (\(\frac{25}{10} = 2.5\)) rounds up to require three partitions.

The Partition Splitting Process

When an existing partition reaches the 10 GB capacity limit, DynamoDB automatically initiates a partition split:

  • Key Space Segmentation: The 10 GB partition splits into two new child partitions. DynamoDB assigns roughly half of the parent partition's hash key range to the first child and the other half to the second child.
  • Data Redistribution: The existing items are reallocated to the respective child partitions based on their partition keys.
  • Throughput Division: The provisioned capacity previously allocated to the parent partition is split equally between the two new child partitions.

Architectural Implications

Partition allocation is a permanent, one-way process. If data volume later drops below 10 GB (via item deletion or Time to Live expiration), DynamoDB does not automatically merge partitions back together.

Because throughput divides evenly among all active partitions, storage-driven partition splits directly impact capacity distribution. A table split into multiple partitions to accommodate storage must have an evenly distributed access pattern; otherwise, high-frequency access to keys located on a single partition can lead to ProvisionedThroughputExceededException errors, commonly known as the "hot partition" problem.
