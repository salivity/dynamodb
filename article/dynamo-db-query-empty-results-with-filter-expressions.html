DynamoDB Query Empty Results with Filter Expressions

When querying Amazon DynamoDB, using a filter expression can frequently result in an empty list of items even when data matching the primary key exists. This article explains the two-step evaluation process of DynamoDB queries, why empty results still consume Read Capacity Units (RCUs), how pagination behaves when items are filtered out, and how to properly handle these responses in your application.

The Two-Step Query Evaluation Process

To understand why DynamoDB returns empty results, you must understand how query requests are evaluated. DynamoDB processes queries in two distinct phases:

  1. Read Phase (Key Condition Expression): DynamoDB locates the partition key and optional sort key criteria specified in the KeyConditionExpression. It reads up to 1 MB of matching data from disk (or up to the specified Limit parameter).
  2. Filter Phase (Filter Expression): DynamoDB takes the records read in step one and applies the FilterExpression. Attributes that do not match the filter criteria are discarded before the final response is constructed.

If none of the records read during the first phase satisfy the FilterExpression, the resulting Items array in the response will be empty ([]).

Metadata Indicators: ScannedCount vs. Count

When an empty result set occurs due to a filter expression, the API response contains metadata that explains what happened:

  • ScannedCount: The number of items DynamoDB actually evaluated from storage based on your KeyConditionExpression. This number will be greater than zero.
  • Count: The number of items remaining after the FilterExpression was applied. In this scenario, Count will be 0.

Capacity Unit Consumption

A common misconception is that an empty result set does not incur costs. In DynamoDB, consumed capacity is calculated based on the data evaluated, not the data returned.

DynamoDB charges Read Capacity Units (RCUs) based on the total size of items processed during the Read Phase (ScannedCount), rounded up to the nearest 4 KB for strongly consistent reads (or 8 KB for eventually consistent reads). Even if your query returns zero items to the client, you are charged for every byte read prior to filtering.

Handling Pagination and LastEvaluatedKey

The most critical consequence of this behavior involves pagination. If DynamoDB reaches its 1 MB read limit or hits the query's Limit threshold without finding any items that match your filter, it halts execution and returns an empty Items list along with a LastEvaluatedKey.

An empty Items array does not mean there are no matching items remaining in the table. As long as LastEvaluatedKey is present in the response, your application must continue to make subsequent query requests, passing ExclusiveStartKey = LastEvaluatedKey, until:

  1. Matching items are found, or
  2. LastEvaluatedKey is null or undefined, signifying that the entire key space has been evaluated.

Failing to loop through the pagination when Items is empty will cause your application to prematurely drop valid matching records.

How to Avoid Empty Filter Results

Relying heavily on filter expressions over large datasets is inefficient and increases latency. To avoid empty results and unnecessary read charges:

  • Use Sort Keys: Redesign your table schema so that frequently queried attributes are part of the composite primary key.
  • Create Global Secondary Indexes (GSIs): If you need to filter on non-key attributes across many items, create a GSI with the required attributes as the partition or sort key so DynamoDB can locate them during the initial Read Phase.
  • Sparse Indexes: Use GSIs that only project items containing the specific attribute you are filtering on, automatically excluding irrelevant records without read overhead.
