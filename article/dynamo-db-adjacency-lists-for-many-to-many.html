DynamoDB Adjacency Lists for Many-to-Many

This article explains how to model many-to-many (N:M) relationships in Amazon DynamoDB using the adjacency list design pattern. In a non-relational database, traditional join tables do not exist, making the adjacency list the standard pattern for representing graph-like connections within a single table. You will learn how to structure partition keys and sort keys, create relationship-defining edge items, and leverage Global Secondary Indexes (GSIs) to enable fast, bi-directional queries.

Understanding the Adjacency List Pattern

An adjacency list represents a graph structure where entities are "nodes" and the relationships between them are "edges." In DynamoDB, this pattern is implemented within a single table using composite primary keys: a Partition Key (PK) and a Sort Key (SK).

Every entity has a root item representing the node itself, while related items represent the edges connecting one entity to another.

Schema Structure for Adjacency Lists

To model a many-to-many relationship—such as Users and Groups, where a user can belong to multiple groups and a group can contain multiple users—the table requires:

  1. A Primary Key: PK (string) and SK (string).
  2. A Global Secondary Index (GSI): An inverted index where GSI1PK = SK and GSI1SK = PK.

Entity Items (Nodes)

Each user and group has a primary record defining its attributes:

PK SK Type Name / Details
USER#101 METADATA User Alice
USER#102 METADATA User Bob
GROUP#A METADATA Group Engineering
GROUP#B METADATA Group Design

Relationship Items (Edges)

Edges are created as separate items to connect the nodes:

PK SK GSI1PK (SK) GSI1SK (PK) Role / Edge Data
USER#101 GROUP#A GROUP#A USER#101 Admin
USER#101 GROUP#B GROUP#B USER#101 Member
USER#102 GROUP#A GROUP#A USER#102 Member

In this configuration:

  • The PK holds the identifier of the source entity (USER#101).
  • The SK holds the identifier of the target entity (GROUP#A).
  • Relationship-specific attributes (such as Role or JoinedDate) are stored directly on the edge item.

Querying the Adjacency List

The adjacency list combined with an inverted index enables efficient lookups in both directions using the Query API rather than costly table scans.

1. Fetching All Groups for a User

To find all groups that USER#101 belongs to, query the base table:

  • Key Condition Expression: PK = :userId AND begins_with(SK, :groupPrefix)
  • Values: :userId = "USER#101", :groupPrefix = "GROUP#"

This returns only the edge items representing USER#101's memberships.

2. Fetching All Users in a Group (Inverted Index)

To find all members belonging to GROUP#A, query the Global Secondary Index (GSI1):

  • Key Condition Expression: GSI1PK = :groupId AND begins_with(GSI1SK, :userPrefix)
  • Values: :groupId = "GROUP#A", :userPrefix = "USER#"

Because the GSI swaps the partition key and sort key, the relationship is read in reverse without duplicating write logic in the application.

Key Considerations

  • Data Duplication vs. Joins: Adjacency lists minimize data duplication by storing relationship metadata directly on edge items. If target entity attributes (like user names) are denormalized onto edge items to save read requests, application-level updates are required when those attributes change.
  • Item Size Limits: Because each relationship is an independent item, the pattern easily avoids DynamoDB's 400 KB item size limit, scaling to thousands of relationships per entity.
  • Transactional Writes: When creating relationships that require mutual validation or simultaneous updates, use TransactWriteItems to ensure all relevant edges and metadata remain consistent.
