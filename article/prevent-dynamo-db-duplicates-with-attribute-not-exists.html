Prevent DynamoDB Duplicates With attribute_not_exists

Amazon DynamoDB natively performs upsert operations, meaning a standard write command will overwrite an existing item if it shares the same primary key. To enforce data uniqueness and prevent duplicate records, developers use DynamoDB conditional writes powered by the attribute_not_exists function. This article explains how this function evaluates item keys before writing, how it triggers exceptions to halt unintended overwrites, and the best practices for implementing it effectively in distributed environments.

The Default Overwrite Behavior

In DynamoDB, the PutItem operation is non-idempotent regarding data state: if an item with the specified partition key (and sort key, if applicable) already exists, DynamoDB replaces the entire item with the new data. This default behavior frequently causes accidental duplicates or data loss in workflows where records should only be created once, such as user registrations, payment authorizations, or order processing.

How attribute_not_exists Enforces Uniqueness

The attribute_not_exists function acts as a conditional check evaluated on the server side immediately before a write operation executes. By pointing this function at the item's primary key attribute, DynamoDB guarantees atomic validation:

ConditionExpression = "attribute_not_exists(id)"

When this condition is attached to a PutItem request, DynamoDB performs the following steps:

  1. Target Identification: DynamoDB locates the partition where the target primary key belongs.
  2. Evaluation: The engine checks whether the specified attribute (e.g., id) exists on an item with that primary key.
  3. Execution or Rejection:
    • If the attribute does not exist (the item is entirely new), DynamoDB commits the write.
    • If the attribute does exist (a record with that key already exists), the write fails immediately.

Because this evaluation happens atomically inside the DynamoDB engine, it avoids race conditions (check-then-act bugs) without requiring distributed locks.

Handling ConditionalCheckFailedException

When attribute_not_exists evaluates to false, DynamoDB rejects the write request and returns a ConditionalCheckFailedException (HTTP status code 400).

Application logic should catch this specific exception to handle duplicates appropriately:

  • Idempotent APIs: If an identical request is sent twice (e.g., network retry), the exception confirms the record was already created, allowing the application to safely return a success or cached response instead of failing.
  • Conflict Resolution: For entity creation (such as a unique username), catching the exception allows the application to notify the client that the identifier is already taken.
  • Cost Efficiency: A rejected conditional write still consumes Write Capacity Units (WCUs) because DynamoDB reads and evaluates the record, but it prevents downstream inconsistency.

Composite Primary Key Considerations

For tables using a composite primary key (a Partition Key and a Sort Key), attribute_not_exists must be applied to the Sort Key:

ConditionExpression = "attribute_not_exists(sort_key_name)"

Checking the partition key alone is insufficient on a composite table because multiple items can share the same partition key as long as their sort keys differ. Targeting the sort key ensures the specific partition-and-sort combination does not already exist.

Scope and Limitations

The attribute_not_exists function only enforces uniqueness across primary key attributes. It cannot prevent duplicates across non-key attributes directly. If a non-key attribute (such as an email address) must remain globally unique while using a different primary key (such as a generated user_id), standard secondary indexes cannot enforce this constraint. In such scenarios, developers must use DynamoDB Transactions (TransactWriteItems) to write a secondary "lock" or mapping item alongside the primary item to ensure uniqueness.
