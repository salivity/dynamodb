How DAX Handles Write-Through and Write-Around

Amazon DynamoDB Accelerator (DAX) is a fully managed, highly available, in-memory cache designed to reduce DynamoDB response times from milliseconds to microseconds. When managing application writes, developers must balance data consistency, cache utilization, and write latency. This article provides an overview of how DAX natively executes a write-through caching strategy and how applications can implement a write-around approach to optimize performance for various workloads.

Understanding DAX Caching Architecture

DAX provides two primary caches:

  1. Item Cache: Stores individual items retrieved via GetItem or BatchGetItem calls.
  2. Query Cache: Stores collections of items retrieved via Query or Scan calls, along with the request parameters.

How DAX handles writes directly determines how these caches maintain consistency with the underlying DynamoDB tables.

Write-Through Caching in DAX

Write-through is the default and native behavior of DAX when an application directs write requests (PutItem, UpdateItem, DeleteItem, BatchWriteItem) directly to the DAX client endpoint.

How It Operates

  1. Application Write: The application sends a write operation directly to the DAX cluster.
  2. Synchronous Write to DynamoDB: DAX intercepts the call and simultaneously applies the change to the underlying DynamoDB table.
  3. Cache Update: Upon successful confirmation from DynamoDB, DAX updates or evicts the corresponding item in its own Item Cache.
  4. Response to Client: DAX returns a success code to the calling application only after the write to DynamoDB succeeds.

Effects on the Caches

  • Item Cache: The written item is immediately updated in or added to the Item Cache, ensuring that subsequent GetItem calls return the most current data without a cache miss.
  • Query Cache: DAX automatically invalidates the relevant Query Cache results. Because query results depend on complex filters and sort keys, DAX does not attempt to calculate how a single write alters query sets; it clears the query cache to prevent stale reads.

Advantages and Trade-offs

  • Pros: Minimizes read misses for newly written or updated data. It guarantees read-your-own-writes consistency through the DAX client.
  • Cons: Introduces slight write overhead because data must pass through both DAX and DynamoDB before returning a success response. It can also cause cache churn if frequently written data is rarely read.

Write-Around Caching with DAX

DAX does not have a native toggle for "write-around" caching; instead, write-around is an architectural pattern implemented at the application level by bypassing DAX for write operations.

How It Operates

  1. Dual Client Configuration: The application initializes two clients—a standard AWS DynamoDB SDK client and a DAX client.
  2. Direct Writes: The application routes write requests directly to the standard DynamoDB endpoint via the DynamoDB client, bypassing DAX entirely.
  3. Reads via DAX: The application routes read operations (GetItem, Query) to the DAX cluster.

Effects on the Caches

  • Item Stamping / Latency: DAX is completely unaware of the direct write to DynamoDB. Consequently, the existing entry in the DAX Item Cache remains unchanged until its Time-to-Live (TTL) expires.
  • Stale Reads: Any read request routed through DAX prior to TTL expiration will serve stale data. Once the TTL expires, the next read fetches the fresh item from DynamoDB and repopulates the DAX cache.

Advantages and Trade-offs

  • Pros: Ideal for write-heavy workloads where written data is not immediately read. It prevents high-volume writes (such as bulk data loads or real-time log ingestion) from flushing hot items out of the cache. It also minimizes write latency by eliminating the DAX middle layer.
  • Cons: Increases the risk of serving stale data. Applications must be tolerant of eventual consistency defined by the cache TTL settings.

Summary of Use Cases

  • Choose Write-Through (Native DAX): Best for read-heavy applications where newly created or updated items are read immediately (e.g., user profile updates, e-commerce shopping carts).
  • Choose Write-Around (Application Bypass): Best for bulk ingestion, batch updates, or audit logging where data is rarely read immediately after being written, preserving DAX cache space for genuinely hot items.
