DynamoDB Write Sharding to Prevent Hot Partitions

Amazon DynamoDB scales by distributing data across multiple physical partitions, but disproportionate traffic to a single partition key can trigger hot spots and throughput throttling. Write sharding mitigates this issue by appending randomized or calculated suffixes to partition keys, effectively dispersing write traffic across multiple storage partitions. This design pattern ensures consistent throughput, eliminates capacity bottlenecks, and enables DynamoDB tables to scale well beyond the standard limits of a single partition.

The Partition Hot Spot Problem

DynamoDB distributes table data across distinct physical storage nodes based on the hash value of the partition key. Each physical partition can provide a maximum of 1,000 Write Capacity Units (WCUs) per second.

When an application frequently writes data sharing the same partition key—such as a timestamp, a status flag, or a trending event—all of those operations target the same physical partition. If write operations exceed 1,000 WCUs on that partition, DynamoDB throttles the requests, throwing a ProvisionedThroughputExceededException. This throttling occurs even if the overall table has ample unused provisioned capacity or is configured with on-demand capacity mode.

How Write Sharding Works

Write sharding resolves partition hot spots by artificially expanding the cardinality of the partition key. Instead of writing all items to an identical partition key, the application appends a shard identifier (suffix) to the key before storing the item.

For example, instead of writing events directly to a partition key like OrderDate#2024-05-01, the application generates keys such as:

  • OrderDate#2024-05-01.1
  • OrderDate#2024-05-01.2
  • OrderDate#2024-05-01.N

Because DynamoDB hashes each distinct string to determine the target partition, each sharded key maps to a different physical partition. This splits high-volume traffic across multiple partitions, multiplying the total write capacity available for that logical dataset.

Sharding Strategies

There are two primary approaches to generating shard identifiers, each tailored to specific access patterns.

1. Randomized Sharding

In a randomized sharding model, the application selects an integer from a fixed range (for example, 1 to 10) using a random number generator and appends it to the base partition key.

  • Use Case: Best suited for high-volume ingest scenarios where write throughput is the primary concern, such as log aggregation or sensor data collection.
  • Trade-off: Reading all data for a specific logical key requires querying all \(N\) shards in parallel (a scatter-gather query) and merging the results in the application layer.

2. Calculated (Deterministic) Sharding

In calculated sharding, the application hashes a secondary attribute of the item (such as a UserId or DeviceId) and computes a modulo against the total number of shards to determine the suffix.

  • Use Case: Ideal when items need to be distributed evenly across partitions while still allowing deterministic lookups.
  • Advantage: When querying for a specific user's transactions on a given date, the application can recompute the exact shard key and fetch the item in a single direct read, avoiding scatter-gather operations.

Determining the Number of Shards

The number of shards (\(N\)) directly dictates the write throughput ceiling for a given logical partition key. Because each partition supports up to 1,000 WCUs, calculate \(N\) using the expected peak write volume:

\[N = \frac{\text{Peak Expected WCUs}}{1,000} \times \text{Safety Factor}\]

For an application expecting 8,000 writes per second for a specific key, selecting an \(N\) between 10 and 12 provides sufficient distribution and a buffer for uneven write distribution. Choosing an excessively large value for \(N\) should be avoided, as it increases read latency and cost when executing scatter-gather queries across all shards.
