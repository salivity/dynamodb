DynamoDB Batch Write with Duplicate Keys

Amazon DynamoDB rejects any batch write request that contains duplicate item keys within the same batch, failing the entire operation before processing any records. This article explains how DynamoDB identifies duplicate keys in a BatchWriteItem call, the specific error returned, the architectural reasons behind this behavior, and how to properly handle item deduplication on the client side.

The Behavior: Request Rejection

When using DynamoDB's BatchWriteItem API, you can specify up to 25 PutItem or DeleteItem requests across multiple tables, with an aggregate payload size limit of 16 MB. However, DynamoDB enforces a strict validation rule: a single batch request cannot contain multiple operations targeting the same primary key in the same table.

If your batch request includes duplicate primary keys—whether two PutRequest operations, two DeleteRequest operations, or a mix of both for the exact same partition key (and sort key, if applicable)—DynamoDB does not process any of the items in that batch. Instead, the service immediately aborts the call and returns an HTTP 400 error with a ValidationException:

ValidationException: Provided list of item keys contains duplicates

Because the failure occurs during the initial request validation phase, no partial writes take place. DynamoDB does not attempt to resolve the conflict, choose a "winner," or write the other valid items in the batch.

Why DynamoDB Disallows Duplicate Keys in a Single Batch

DynamoDB processes individual operations within a BatchWriteItem call in parallel across different partitions. To maximize throughput and minimize latency, the service does not guarantee the order of execution for items in a batch.

If DynamoDB permitted multiple operations on the same primary key in a single batch, concurrent execution would introduce a race condition. For example, if a batch contained both a PutRequest and a DeleteRequest for the same key, there would be no deterministic way to know whether the final state of the item should be created or deleted. Rejecting duplicate keys eliminates non-deterministic outcomes and preserves data consistency.

How to Prevent Duplicate Key Errors

To avoid ValidationException failures during batch operations, deduplicate your data on the client side before building the BatchWriteItem payload:

  1. Client-Side Deduplication: Use a hash map or dictionary keyed by the table's composite primary key (Partition Key + Sort Key). As you iterate through your data, overwrite or merge values so that only the final desired state of each key is included in the batch.
  2. Handle Sequences Separately: If you must apply sequential operations to the same item (such as an insert followed by an update or deletion), perform them in distinct, sequential API requests rather than packaging them into the same batch.
  3. Partition into Distinct Batches: If multiple updates to the same key are valid independent actions that must both occur, place them into separate BatchWriteItem calls and ensure the first batch completes before issuing the second.
