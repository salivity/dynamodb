How DynamoDB Point-in-Time Recovery Works

Amazon DynamoDB executes point-in-time recovery (PITR) by continuously backing up your table's data and transaction logs, allowing you to restore item-level data to any single second within the preceding 35 days. This article details the underlying architecture of PITR, explaining how DynamoDB captures state changes, provisions a new target table, and replays storage logs to reconstruct items exactly as they existed at a specific target timestamp.

Snapshot and Transaction Log Architecture

DynamoDB does not perform continuous full exports to maintain PITR. Instead, it uses a combination of automated storage-tier snapshots and continuous change log streams. At the storage layer, DynamoDB partitions constantly generate incremental checkpoints (snapshots) of storage nodes. Concurrently, every single mutation—including PutItem, UpdateItem, and DeleteItem requests—is sequentially recorded in durable, multi-Availability Zone transaction logs with microsecond-level timestamps.

The Restoration Execution Process

When a restore request is initiated with a specific target timestamp, DynamoDB executes the following sequence:

  1. New Table Allocation: DynamoDB creates an entirely new table. PITR never overwrites an existing table, protecting live production workloads from accidental data corruption and eliminating write-lock contention.
  2. Baseline Identification: The service determines the closest system snapshot taken immediately prior to the requested timestamp.
  3. Partition Provisioning and Data Hydration: DynamoDB provisions partition storage for the new table and copies the baseline data blocks directly into the new storage nodes.
  4. Log Replay to the Target Second: DynamoDB retrieves the differential transaction logs between the snapshot time and the target restore second. It replays these write-ahead operations sequentially across the partitioned data. Any mutations, condition checks, and deletions that occurred after the target timestamp are omitted.
  5. Metadata and Secondary Index Rebuilding: As data reaches the requested state, DynamoDB applies primary key schemas, Local Secondary Indexes (LSIs), and initiates asynchronous backfilling for specified Global Secondary Indexes (GSIs).

Operational Impact and Consistency

Because the restoration process runs purely against decoupled background storage replicas and journal logs, initiating a PITR restoration consumes no provisioned read or write throughput capacity from the source table. The resulting restored items reflect full ACID compliance matching the state of the database at that precise second.
