DynamoDB Exceeding Provisioned Write Capacity

When a write operation in Amazon DynamoDB exceeds the provisioned throughput limits for a table or index, DynamoDB actively throttles the request to protect system stability and resource availability. This event triggers an immediate ProvisionedThroughputExceededException error, prompting standard AWS software development kits (SDKs) to initiate automatic retries via exponential backoff. This guide breaks down the immediate mechanics of throughput throttling, the behavior of burst capacity, the impact on secondary indexes, and the primary strategies used to handle and prevent these bottlenecks.

The Immediate System Response: Throttling

DynamoDB allocates resources based on provisioned Write Capacity Units (WCUs). One WCU provides up to one write per second for an item up to 1 KB in size. When the rate of incoming write requests exceeds this allocated limit, DynamoDB rejects the excess requests with an HTTP 400 bad request error code alongside a ProvisionedThroughputExceededException.

Once this occurs:

  • The write operation is not executed or queued automatically by the database engine.
  • The consumed write request does not modify the table data.
  • Amazon CloudWatch records the throttled event under the ThrottledRequests and WriteThrottleEvents metrics.

Burst Capacity and Its Limits

DynamoDB provides temporary resilience against sudden spikes using burst capacity. If a table does not utilize its full provisioned throughput, DynamoDB banks the unused capacity for up to 300 seconds (5 minutes).

If a sudden burst of writes exceeds your provisioned rate, DynamoDB will automatically consume this banked capacity to complete the writes without throwing an error. However, burst capacity is not guaranteed, and sustained writes that exceed provisioned limits will quickly deplete the reserve, resulting in immediate throttling once exhausted.

Automatic Retries and Exponential Backoff

Most applications interact with DynamoDB through official AWS SDKs. When an SDK receives a ProvisionedThroughputExceededException, it handles the error automatically without immediate application-level failure:

  1. Wait and Retry: The SDK pauses for a short duration and retries the failed write request.
  2. Exponential Backoff: If subsequent attempts also fail, the SDK progressively increases the wait time between each retry attempt.
  3. Jitter: The SDK introduces randomized delays ("jitter") to prevent multiple simultaneous requests from hitting DynamoDB at the exact same millisecond.

If the sustained load is too high and the SDK exhausts its maximum retry attempts, the exception is passed up to your application code. At this stage, your application must handle the failure explicitly, or the write data will be lost.

Hot Partitions and Non-Uniform Access

A table may experience throttling even if its total consumed WCUs appear to be well below the total provisioned limit. DynamoDB divides table data across multiple physical partitions, distributing the total provisioned throughput equally among them.

If your application directs a disproportionate number of writes to a single partition key—a scenario known as a "hot partition"—that specific partition will exhaust its allocated share of WCUs. The operations hitting that specific partition will be throttled, regardless of how much idle capacity remains across the rest of the table.

Impact on Global Secondary Indexes (GSIs)

If a base table has one or more Global Secondary Indexes (GSIs), write operations to the base table also generate corresponding writes to those indexes.

If a GSI lacks sufficient provisioned write capacity to accommodate the updates, writes to the base table will be throttled, even if the base table itself has ample write capacity available. DynamoDB throttles the base table write to ensure that secondary indexes do not fall indefinitely behind the primary data set.

How to Prevent and Resolve Write Throttling

To prevent write operations from exceeding capacity limits, several architectural patterns and configuration options are standard:

  • Enable DynamoDB Auto Scaling: Set minimum and maximum capacity thresholds alongside a target utilization percentage. Auto Scaling monitors CloudWatch metrics and dynamically adjusts provisioned WCUs up or down as traffic patterns shift.
  • Switch to On-Demand Capacity Mode: For workloads with unpredictable, spiky, or unknown traffic patterns, On-Demand mode eliminates manual capacity planning by instantly accommodating workloads up to double the previous peak traffic without throttling.
  • Improve Partition Key Cardinality: Distribute writes evenly by choosing high-cardinality partition keys. If a natural key creates a hot partition, append random or calculated suffixes (write sharding) to spread the writes across multiple partitions.
  • Buffer with Queues: Place a message queue, such as Amazon SQS, directly in front of the DynamoDB write layer. The queue acts as a shock absorber during traffic spikes, allowing worker processes to ingest items and write to DynamoDB at a steady, controlled rate that stays within provisioned limits.
