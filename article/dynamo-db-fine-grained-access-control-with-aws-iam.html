DynamoDB Fine-Grained Access Control with AWS IAM

Amazon DynamoDB integrates with AWS Identity and Access Management (IAM) to enforce fine-grained access control (FGAC), allowing organizations to control security at the individual item and attribute levels rather than granting blanket table access. This article explains how DynamoDB uses IAM policy condition keys to restrict access to specific records based on user identity, limit visibility to individual attributes, and integrate with federated identity providers for secure multi-tenant architectures.

The Role of IAM Condition Keys in DynamoDB

Standard IAM policies grant permissions at the API action level (such as dynamodb:GetItem or dynamodb:PutItem) and resource level (the table or index ARN). Fine-grained access control extends this by evaluating the Condition block in an IAM policy. When an application or user requests access to a table, DynamoDB evaluates the parameters of the request against the conditions declared in the IAM policy to determine whether the operation is authorized.

DynamoDB provides specific context keys designed for item- and attribute-level enforcement:

  • dynamodb:LeadingKeys: Controls access to items based on their partition key value.
  • dynamodb:Attributes: Restricts which attributes (columns) a user can read or write.
  • dynamodb:Select: Controls the projection type allowed in query or scan operations (e.g., SPECIFIC_ATTRIBUTES).

Item-Level Access Control

Item-level security prevents users from accessing items that do not belong to them. It is commonly implemented using the dynamodb:LeadingKeys condition key, which matches the partition key value of the target item against an attribute of the requesting identity.

For example, when using Web Identity Federation or Amazon Cognito, an application receives an identity token containing a unique user ID (${cognito-identity.amazonaws.com:sub}). By embedding this variable in the IAM policy's dynamodb:LeadingKeys condition, DynamoDB ensures the caller can only read, write, or update items where the partition key matches their unique identifier.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:UpdateItem",
        "dynamodb:DeleteItem",
        "dynamodb:Query"
      ],
      "Resource": "arn:aws:dynamodb:us-east-1:123456789012:table/UserProfiles",
      "Condition": {
        "ForAllValues:StringEquals": {
          "dynamodb:LeadingKeys": [
            "${cognito-identity.amazonaws.com:sub}"
          ]
        }
      }
    }
  ]
}

Attribute-Level Access Control

Attribute-level control dictates which fields within an item can be viewed or modified. This is useful for protecting sensitive data, such as Personally Identifiable Information (PII) or internal administrative flags, while still permitting general access to the rest of the record.

Attribute access is managed using the dynamodb:Attributes key alongside permission modifiers:

  • Read Restrictions: To limit read operations, policies enforce that queries or gets must request only authorized attributes. The policy must also require dynamodb:Select to be set to SPECIFIC_ATTRIBUTES to prevent wildcards from returning unauthorized data.
  • Write Restrictions: For write operations, the policy restricts the attributes that can be passed in PutItem or UpdateItem requests, preventing unauthorized users from modifying privileged fields like isAdmin or accountBalance.

Identity Federation and Multi-Tenancy

In modern mobile, web, and SaaS architectures, fine-grained access control removes the need for intermediate backend authentication layers to broker database queries. By combining DynamoDB IAM policies with identity federation:

  1. A user authenticates through an OpenID Connect (OIDC) or SAML provider (e.g., Google, Amazon Cognito, Okta).
  2. AWS Security Token Service (STS) issues temporary AWS credentials linked to an IAM role.
  3. The IAM role contains policy conditions tied to session tags or identity provider claims (such as a tenant_id or user_id).
  4. DynamoDB validates these session variables against the target partition key on every request, isolating tenant or user data natively at the database layer.
