How DynamoDB DAX Writes Items to DynamoDB

Amazon DynamoDB Accelerator (DAX) maintains data consistency by acting as a write-through caching service. When your application writes data using the DAX client, the item is synchronously written to the underlying DynamoDB table first. Only after the primary table successfully acknowledges the write does DAX update its internal item cache and return a success response to the application, ensuring that the primary database remains the authoritative source of truth.

The Write-Through Workflow

When an application issues a write operation (such as PutItem, UpdateItem, DeleteItem, or BatchWriteItem) to a DAX cluster endpoint, the process follows these sequential steps:

  1. Client Request: The application sends the write request to DAX instead of communicating directly with DynamoDB.
  2. Forwarding to DynamoDB: DAX does not update its cache immediately. Instead, it forwards the request directly to the underlying DynamoDB table.
  3. Table Persistence: DynamoDB writes the item to storage, applies any conditional checks, and completes the operation.
  4. Cache Update: Once DynamoDB successfully acknowledges the write, DAX updates its item cache with the new or modified item (or removes the item, in the case of a DeleteItem request).
  5. Client Response: DAX returns the success response to the calling application.

Failure Handling and Consistency

If the write operation to the DynamoDB table fails—due to a condition check failure, provisioned throughput throttling, or an underlying service error—DAX does not update its item cache. The error returned by DynamoDB is passed directly back to the client application. This strict ordering prevents "phantom writes" and prevents the cache from holding data that was never committed to persistent storage.

Impact on Cache Types

DAX contains two separate caches, which behave differently during write operations:

  • Item Cache: The item cache stores individual items keyed by their partition and sort keys. On a successful write-through operation, DAX immediately populates or updates the item cache with the newly written item. Subsequent GetItem requests for this key are served directly from the cache.
  • Query and Scan Cache: The query and scan cache stores result sets from complex read operations. Because a single write can affect multiple query result sets, DAX does not update query or scan results during a write. Instead, it clears or invalidates the relevant entries in the query and scan cache to ensure stale result sets are not returned on subsequent queries.

Performance Implications

Because DAX writes through to DynamoDB synchronously, write operations do not see the microsecond latency benefits that DAX provides for read operations. Write latency through DAX is comparable to writing directly to DynamoDB, with the addition of a small network hop through the DAX cluster nodes. Applications requiring fast writes with eventual consistency typically write directly to DynamoDB or manage cache invalidations independently.
