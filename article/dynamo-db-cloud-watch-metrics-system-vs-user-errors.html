DynamoDB CloudWatch Metrics: System vs User Errors

Amazon DynamoDB integrates natively with Amazon CloudWatch to monitor database performance, throughput, and operational health. To differentiate between internal AWS failures and client-side application faults, CloudWatch provides two primary metrics: SystemErrors for 5xx-level service failures and UserErrors for 4xx-level client issues. Understanding the distinction between these metrics allows engineering teams to accurately diagnose issues, configure effective alarms, and maintain resilient data layers.

The SystemErrors Metric

The SystemErrors metric tracks the number of requests to DynamoDB that generate an HTTP 500 series status code (typically HTTP 500 Internal Server Error).

  • Cause: These errors represent internal issues within the DynamoDB service itself, such as transient infrastructure faults, internal network partitions, or service unavailability.
  • Responsibility: AWS is responsible for resolving the root cause of these errors.
  • Resolution: Client applications should implement exponential backoff with jitter to retry failed operations automatically. In production environments, the baseline for SystemErrors should ideally be zero; any sustained increase warrants setting a CloudWatch Alarm and contacting AWS Support if automated retries fail.

The UserErrors Metric

The UserErrors metric measures requests to DynamoDB that result in an HTTP 400 series status code (typically HTTP 400 Bad Request).

  • Cause: These errors are caused by client-side misconfigurations, invalid syntax, or failed constraints. Common scenarios include:
    • ValidationException: Attempting to write an attribute with an incorrect data type or exceeding item size limits.
    • ResourceNotFoundException: Querying a table or index that does not exist.
    • ConditionalCheckFailedException: Writing an item where a specified conditional expression evaluates to false.
    • AccessDeniedException: IAM permission issues preventing the identity from reading or writing data.
  • Responsibility: The client application developer is responsible for resolving these issues.
  • Resolution: Debug application code, verify data payloads, ensure correct IAM policies, and adjust query or write syntax.

Throttling Considerations

While throttled requests also produce an HTTP 400 status code (ProvisionedThroughputExceededException), DynamoDB provides dedicated metrics for capacity bottlenecks rather than relying solely on UserErrors:

  • ThrottledRequests: Tracks the total number of requests that exceeded the provisioned throughput or account-level limits.
  • ReadThrottleEvents and WriteThrottleEvents: Measure throttling specific to read and write activity on base tables and Global Secondary Indexes (GSIs).
