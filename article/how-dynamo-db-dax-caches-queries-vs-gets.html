How DynamoDB DAX Caches Queries vs Gets

Amazon DynamoDB Accelerator (DAX) optimizes read workloads by managing two separate in-memory caches: the Item Cache and the Query Cache. While point lookups (key-value gets) operate through the Item Cache to retrieve individual records with real-time write-through invalidation, search-based read operations (queries and scans) leverage the Query Cache to store entire result sets. Understanding how these two caching layers interact is critical to designing efficient, cost-effective, and consistent architectures with DynamoDB.

The Item Cache: Key-Value Gets

The Item Cache handles point-lookup API operations, specifically GetItem and BatchGetItem.

  • Storage and Indexing: Data is stored as individual items indexed strictly by their primary keys (partition key, or partition key plus sort key).
  • Cache Read Flow: When an application issues a GetItem request, DAX checks the Item Cache. If the key exists (cache hit), DAX returns the item immediately with microsecond latency. If the key does not exist (cache miss), DAX fetches the item from DynamoDB, writes it to the Item Cache, and returns it to the client.
  • Cache Invalidation on Writes: The Item Cache maintains write-through consistency. When data is modified via DAX using PutItem, UpdateItem, or DeleteItem, DAX writes the update to DynamoDB and immediately updates or invalidates the corresponding item in the Item Cache.
  • Eviction Policy: Items remain in the cache until they expire based on the configured Time to Live (TTL) or are evicted under memory pressure using a Least Recently Used (LRU) algorithm.

The Query Cache: Queries and Scans

The Query Cache handles collection-based operations, specifically Query and Scan.

  • Storage and Indexing: Instead of caching individual primary keys, the Query Cache stores the parameter sets of the request (the partition key condition, sort key condition, filter expressions, attributes, index names) mapped directly to the resulting list of items.
  • Cache Read Flow: When a Query or Scan is executed, DAX evaluates whether the exact set of request parameters exists in the Query Cache. If matched, it returns the cached result set. If not, DAX executes the operation against DynamoDB, stores the resulting list in the Query Cache, and sends it to the application.
  • Cache Invalidation on Writes: Unlike the Item Cache, the Query Cache is not updated or invalidated when write operations (PutItem, UpdateItem, DeleteItem) occur. Because calculating which queries are affected by an individual write is computationally expensive, DAX relies exclusively on the TTL to expire entries in the Query Cache, or LRU eviction when memory limits are reached. Consequently, queries may return stale data if underlying items are updated before the query's TTL expires.

Key Architectural Differences

  • Cross-Cache Isolation: The Item Cache and Query Cache do not populate or invalidate each other. Running a Query that returns ten items does not warm the Item Cache for those individual primary keys. Conversely, updating an item via PutItem updates the Item Cache, but any matching queries cached in the Query Cache will continue serving the previous result set until their TTL expires.
  • Staleness and Consistency: Applications heavily reliant on Query or Scan through DAX must be designed to tolerate eventual consistency and potential staleness governed by the Query Cache TTL. Point lookups via GetItem provide stronger consistency guarantees when updates pass through the DAX cluster.
  • TTL Configuration: DAX allows distinct TTL configurations for the Item Cache and the Query Cache. Setting a lower TTL on the Query Cache is a standard practice to mitigate the impact of stale query results while maintaining a longer TTL on the Item Cache for predictable key-value access.
