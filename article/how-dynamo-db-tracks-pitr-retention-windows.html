How DynamoDB Tracks PITR Retention Windows

Amazon DynamoDB point-in-time recovery (PITR) provides continuous, automatic backups that protect your tables against accidental write or delete operations. This article explains how DynamoDB tracks and manages its retention windows, detailing the underlying mechanics of transaction logging, restorable timestamp boundaries, and the automated pruning of historical data.

Continuous Transaction Logging and Micro-Checkpoints

DynamoDB does not use traditional daily snapshots to maintain PITR. Instead, once enabled, the service continuously records all table modifications to internal transaction logs and couples them with periodic baseline checkpoints of the storage partitions.

Every item creation, update, and deletion is recorded with an authoritative internal timestamp. Because these changes are tracked in continuous storage streams alongside partition data, DynamoDB can replay or reconstruct table states up to any designated second within the active retention window.

The Restorable Window Boundaries

DynamoDB programmatically exposes and monitors its recovery window using two primary timestamps: EarliestRestorableDateTime and LatestRestorableDateTime.

  • EarliestRestorableDateTime: This timestamp represents the oldest second to which the table can be restored. When you first enable PITR, this value is established shortly after activation (typically within a few minutes) once the initial baseline is secured. As the table operates, this value remains fixed until the table reaches the maximum 35-day (840-hour) threshold. Once reached, EarliestRestorableDateTime shifts forward continuously, maintaining an exact 35-day sliding window.
  • LatestRestorableDateTime: This timestamp indicates the most recent point in time to which a table can be safely restored. DynamoDB continually updates this value, maintaining a lag of only a few seconds behind the current time to account for log replication across multiple Availability Zones.

You can inspect both timestamps at any time using the AWS Management Console, the AWS CLI (describe-continuous-backups), or the DynamoDB API.

Rolling Retention and Automatic Pruning

DynamoDB automatically manages the retention lifecycle without consuming read or write capacity units from your table. As logs age beyond the 35-day retention boundary, the internal storage system expires and prunes the historical logs that precede the EarliestRestorableDateTime. This background garbage collection ensures you are only billed for the data within the active 35-day window.

If PITR is disabled on a table, the retention window is closed immediately. DynamoDB resets the tracking metadata, invalidates the continuous backup state, and deletes the recovery logs, preventing any further restoration to points in time prior to the deactivation.
