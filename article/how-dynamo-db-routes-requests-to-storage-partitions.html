How DynamoDB Routes Requests to Storage Partitions

Amazon DynamoDB uses a specialized architectural component known as the Request Router to direct incoming API requests to the correct physical storage partition. When a client performs a read or write operation, the request router evaluates the request, determines the specific partition hosting the target data using an internal hash mechanism, and forwards the operation to the appropriate storage node. This article explains the role of the Request Router, the step-by-step routing process, and how it enables DynamoDB’s high throughput and single-digit millisecond latency.

The Role of the Request Router

The Request Router is an internal, horizontally scalable fleet of stateless proxy servers that sit between incoming client requests and DynamoDB’s underlying physical storage nodes.

Its primary duties include:

  • Authentication and Authorization: Verifying AWS Identity and Access Management (IAM) credentials and request signatures.
  • Request Validation: Ensuring the API payload conforms to DynamoDB specifications.
  • Partition Lookup: Determining which storage partition holds the requested data.
  • Forwarding: Dispatching the request directly to the appropriate storage node hosting a replica of that partition.

How DynamoDB Routes API Calls Step-by-Step

When an application invokes an operation such as GetItem or PutItem, the Request Router carries out a specific sequence of actions to locate and modify the record:

  1. Hash Calculation: Every table in DynamoDB requires a primary key, which includes a partition key. The Request Router takes the partition key value from the API payload and runs it through an internal hashing algorithm (an MD5-based cryptographic hash function).
  2. Partition Map Consultation: The Request Router maintains an in-memory partition map that associates hash value ranges with specific physical storage partitions. DynamoDB partitions are mapped across an ordered 128-bit hash ring. By comparing the calculated hash value against the partition map, the router identifies the exact partition assigned to that hash range.
  3. Storage Node Resolution: Each logical partition in DynamoDB is replicated across three physical storage nodes in different Availability Zones (AZs) using the Paxos consensus algorithm. The Request Router consults its topology cache to locate the active leader node or follower replicas for that partition.
  4. Request Dispatch:
    • For Write Operations: The router sends the request directly to the Paxos leader node for that partition to coordinate the write across replicas.
    • For Strongly Consistent Reads: The router contacts the leader node to guarantee the latest data state.
    • For Eventually Consistent Reads: The router can query any of the three storage replicas, typically selecting the replica with the lowest latency or within the same Availability Zone.

Partition Map Updates and Scalability

As tables grow in data size or provisioned throughput, DynamoDB automatically splits partitions. When a partition split occurs, the central metadata service (the DynamoDB configuration service) updates the global partition topology.

Request Routers constantly synchronize with this service to update their local partition maps. If a router directs a request using stale topology data, the contacted storage node returns an error code instructing the router to refresh its cache and re-route the request, ensuring seamless scalability without client downtime.
