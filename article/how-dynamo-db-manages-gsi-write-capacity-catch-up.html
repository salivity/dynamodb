How DynamoDB Manages GSI Write Capacity Catch-Up

This article explains how Amazon DynamoDB handles write capacity consumption on Global Secondary Indexes (GSIs) during and after heavy write bursts on the base table. It covers the asynchronous replication model of GSIs, how DynamoDB utilizes burst capacity and replication buffers to catch up, and the critical backpressure mechanism that can throttle base table writes if a secondary index falls too far behind.

DynamoDB decouples the write capacity of base tables from that of Global Secondary Indexes. While Local Secondary Indexes (LSIs) consume write capacity directly from the base table synchronously, GSIs have their own provisioned or on-demand Write Capacity Units (WCUs) and are updated asynchronously. When an item is added, updated, or deleted on a base table, an internal change stream immediately routes the modification to all associated GSIs to project the changes.

During heavy write spikes on the base table, the GSI must process these incoming updates at a rate proportional to the write volume and the size of the projected attributes. If the incoming write rate to the GSI exceeds its allocated capacity, DynamoDB initially uses burst capacity. DynamoDB retains up to 300 seconds of unused read and write capacity per partition to absorb sudden bursts of traffic. If burst capacity is available on the GSI, the index utilizes these extra units to catch up on replication without throttling the incoming stream.

If the heavy write workload exhausts the GSI's burst capacity and the sustained volume remains higher than the GSI’s provisioned WCUs, DynamoDB stores pending updates in an internal storage queue. The GSI continuously drains this queue, consuming its maximum allowed write capacity until all updates are applied.

However, DynamoDB does not allow this internal replication queue to grow indefinitely. If the GSI lacks sufficient write capacity to keep pace and the replication lag threatens internal buffer limits, DynamoDB applies backpressure to the base table. In this state, DynamoDB throttles write requests directly on the base table—returning ProvisionedThroughputExceededException errors to client applications—even if the base table itself has ample unused write capacity. This protective behavior prevents unbounded replication lag and ensures the eventual consistency of the index does not drift excessively far behind the primary dataset.

In on-demand capacity mode, DynamoDB mitigates catch-up bottlenecks by automatically scaling the GSI's write capacity up to twice the previous peak traffic instantaneously. In provisioned mode, enabling DynamoDB Auto Scaling helps prevent backpressure by dynamically raising the GSI’s provisioned WCUs in response to elevated target utilization metrics, allowing the index to catch up quickly and return to normal operation.
