How to Avoid DynamoDB Hot Partition Keys

DynamoDB relies on horizontal scaling to deliver consistent single-digit millisecond latency, but uneven traffic to a specific partition key can create "hot keys" that lead to request throttling and degraded performance. This article outlines the primary architectural strategies used to avoid hot partition keys, focusing on data distribution techniques such as key sharding, selecting high-cardinality attributes, combining composite values, and offloading heavy reads.

Understand the Cause of Hot Keys

A hot key occurs when a disproportionate volume of read or write requests targets a single partition key within a short time window. Because DynamoDB allocates throughput per partition, exceeding the partition limit (1,000 write capacity units or 3,000 read capacity units per second) triggers throttling, even if your total allocated table capacity is not fully utilized.

1. Select High-Cardinality Attributes

The foundational defense against hot keys is choosing partition keys that naturally offer high cardinality—meaning they contain a large number of distinct values distributed evenly across requests.

  • Ideal attributes: user_id, device_id, order_id, or UUID.
  • Attributes to avoid as sole partition keys: status (e.g., "active"/"pending"), gender, binary flags, or broad categories that concentrate massive amounts of data into a few physical partitions.

2. Implement Write Sharding (Adding Salt)

When an application must write heavy traffic to a single logical entity (such as tracking real-time votes, global counters, or daily logs), write sharding distributes that traffic across multiple physical keys by appending a suffix (a "salt").

Random Suffixing

Append a random integer from a fixed range (e.g., 1 to N) to the partition key value:

  • Format: EventDate_2026-03-30.# (e.g., EventDate_2026-03-30.1, EventDate_2026-03-30.2).
  • Use case: Scenarios where write throughput is the primary bottleneck and writes do not need to be read via a single query. Reads can aggregate data by querying all shards in parallel.

Calculated Suffixing

Append a deterministic value derived from another attribute in the item, such as a hash of a transaction ID or user ID:

  • Format: Department_Sales.[Hash(EmployeeID) % 10].
  • Use case: Scenarios where you need to distribute write load across partitions while retaining the ability to predict which partition contains a specific record for targeted reads.

3. Construct Composite Partition Keys

Combine multiple attributes into a single partition key string to increase distinctness without losing logical grouping.

For example, instead of using tenant_id as the partition key—which causes a multi-tenant system to throttle when a large customer experiences high traffic—use a composite key such as tenant_id#date or tenant_id#region. This distributes that single customer's traffic across multiple physical partitions based on time or location while maintaining tenant isolation.

4. Isolate Time-Series Workloads

In time-series designs, applications frequently write to a partition representing the "current" minute, hour, or day, creating an intense hot spot on the newest partition.

  • Pre-allocate daily or hourly shards: Combine the timestamp with an identifier (e.g., SensorID#YYYY-MM-DD-HH).
  • Use separate tables for time intervals: Create daily or weekly tables for high-volume ingest, then lower the provisioned capacity or transition older tables to on-demand pricing once traffic drops.

5. Offload Read Hot Spots with Caching

If read operations—rather than writes—are causing partition throttling due to a popular item (a "celebrity" record), key redesign alone may not solve the problem without complicating query patterns.

Deploy an in-memory cache, such as Amazon DynamoDB Accelerator (DAX) or an external Redis layer, to serve repeated read requests. This absorbs high read frequencies directly from memory and prevents repeated hits to the underlying DynamoDB partition.
