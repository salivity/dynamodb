How DynamoDB Streams Captures Changes in Order

Amazon DynamoDB Streams provides a time-ordered log of item-level modifications made to a DynamoDB table. Whenever an application creates, updates, or deletes an item, DynamoDB Streams automatically generates a stream record capturing the before-and-after state of that item. By organizing stream records into partitioned storage units called shards and routing operations according to item partition keys, DynamoDB guarantees that modifications to any single item are serialized and delivered in the exact chronological sequence in which they occurred.

Write-Ahead Logging and Stream Record Creation

The ordering process begins at the storage tier. When an item modification request—such as PutItem, UpdateItem, or DeleteItem—is committed to DynamoDB’s underlying storage nodes, a corresponding stream record is created almost simultaneously.

Each stream record contains metadata about the operation, a timestamp representing when the operation was committed, and the actual item data based on the chosen stream view type (KEYS_ONLY, NEW_IMAGE, OLD_IMAGE, or NEW_AND_OLD_IMAGES).

Sharding and Partition Key Routing

DynamoDB Streams achieves high throughput while preserving order through sharding:

  • Key-Based Allocation: DynamoDB partitions stream data into individual containers called shards. All mutations affecting items with the identical partition key are routed to the exact same shard.
  • Per-Shard Serialization: Within a single shard, incoming stream records are appended sequentially to an internal log. Because records for a specific partition key are never split concurrently across multiple shards, their relative chronological order is permanently preserved.
  • Sequence Numbers: DynamoDB assigns a unique, monotonically increasing sequence number to every record within a shard. Consumers can use this sequence number to verify ordering and to resume processing from a specific checkpoint.

Maintaining Order During Shard Splits

As write throughput or data volume increases, DynamoDB automatically scales by splitting shards into child shards:

  • Parent-Child Lineage: When a shard splits, it closes to new writes and transitions into a read-only state. Two new child shards are provisioned to accept subsequent stream records.
  • Lineage Tracking: Every child shard retains a pointer to its parent shard.
  • Ordered Consumption Rule: To guarantee end-to-end chronological consistency, consumers—such as AWS Lambda or the DynamoDB Streams Kinesis Adapter—must exhaustively process all records from the parent shard before reading records from the corresponding child shards. This strictly prevents newer writes in child shards from being processed before older writes from the parent shard.

Granularity of the Ordering Guarantee

DynamoDB Streams guarantees strict chronological order at the individual item level (or across items that share the same partition key).

Because different partition keys may map to different shards running in parallel, DynamoDB does not guarantee the global chronological ordering of modifications between two completely unrelated partition keys. However, for any single item or partition key group, the sequence of updates in the stream will precisely mirror the sequence of writes applied to the table. Records remain accessible in the stream for 24 hours, after which they are automatically trimmed.
