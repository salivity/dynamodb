CloudWatch Metrics for DynamoDB Throttling

Amazon DynamoDB relies on Amazon CloudWatch to report real-time operational data, allowing administrators to detect performance bottlenecks before they impact end users. This guide breaks down the essential CloudWatch metrics used to identify read and write throttling in DynamoDB, explains why these throttling events occur, and covers how to monitor associated secondary indexes and capacity utilization.

Primary Throttling Metrics

When a DynamoDB table or index exceeds its configured provisioned throughput or encounters partition throughput limits (even in on-demand mode), DynamoDB throttles the offending requests. CloudWatch provides three direct metrics to track these occurrences:

  • ReadThrottleEvents: Measures the number of read requests that were throttled because they exceeded the provisioned read capacity units (RCU) for a table or a Global Secondary Index (GSI). It is emitted as a count metric.
  • WriteThrottleEvents: Measures the number of write requests that were throttled because they exceeded the provisioned write capacity units (WCU) for a table or GSI. Like read throttles, this is emitted as a count metric.
  • ThrottledRequests: Captures the total count of requests that exceeded the provisioned throughput limits and resulted in an HTTP 400 ProvisionedThroughputExceededException. While ReadThrottleEvents and WriteThrottleEvents track throttles at the storage layer per operation, ThrottledRequests reflects the actual exceptions surfaced to your application.

Associated Capacity Metrics

To understand why throttling occurs, compare throttle events with your overall capacity consumption metrics:

  • ConsumedReadCapacityUnits and ConsumedWriteCapacityUnits: Track the total throughput consumed over a given period.
  • ProvisionedReadCapacityUnits and ProvisionedWriteCapacityUnits: Display the assigned throughput capacity for tables running in provisioned capacity mode.

Comparing consumed units against provisioned limits indicates whether a table needs a higher capacity threshold or target-tracking auto-scaling adjustments. If throttling occurs while consumed capacity appears well below the provisioned capacity, the issue is typically a "hot key" or partition-level bottleneck, where traffic is concentrated on a single storage partition exceeding 1,000 WCU or 3,000 RCU.

Monitoring Global Secondary Indexes (GSIs)

In DynamoDB, writes to a base table are replicated asynchronously to all associated Global Secondary Indexes. If a GSI lacks sufficient write capacity, it will throttle incoming writes. To prevent the index from falling indefinitely behind, DynamoDB throttles writes on the base table itself.

To catch GSI-induced throttles:

  • Check the WriteThrottleEvents metric filtered by the GlobalSecondaryIndexName dimension.
  • Ensure that every GSI has provisioned write capacity that equals or exceeds the write capacity of the base table.

Recommended CloudWatch Alarms

To proactively manage throttling:

  1. Direct Throttling Alarms: Create CloudWatch alarms on ReadThrottleEvents and WriteThrottleEvents where Statistic = Sum and the threshold is greater than zero (> 0) over a 1-minute or 5-minute period.
  2. Capacity Utilization Alarms: Set up high-utilization alarms comparing ConsumedReadCapacityUnits and ConsumedWriteCapacityUnits against their provisioned counterparts (typically triggering around 80% sustained usage) to adjust auto-scaling rules before request throttling occurs.
