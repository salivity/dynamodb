DynamoDB Conflict Resolution in Global Tables

Amazon DynamoDB Global Tables provide fully managed, multi-Region, active-active database replication designed to deliver low-latency reads and writes to globally distributed applications. When multiple applications write to the same item across different Regions concurrently, conflicts are inevitable. DynamoDB resolves these concurrent update conflicts automatically using a deterministic "Last-Writer-Wins" (LWW) strategy based on internal system timestamps. This article explains how the LWW mechanism functions, how timestamp ties are settled, the inherent limitations of this model, and strategies to prevent unintended data loss.

The "Last-Writer-Wins" (LWW) Mechanism

DynamoDB uses an asynchronous replication model across Regions. When an item is updated in one Region, the update is committed locally first and then propagated to replica tables in other Regions, typically within one to two seconds.

To resolve write conflicts:

  1. System Timestamps: DynamoDB attaches a precise, system-level timestamp to each write operation at the moment it is committed to the local storage node. This timestamp relies on Amazon Time Sync Service (a fleet of redundant, satellite-synchronized reference clocks) to maintain low clock drift.
  2. Comparison: When an incoming replicated update arrives at a target Region, DynamoDB compares the timestamp of the incoming update with the timestamp of the existing item in the target Region.
  3. Overwriting: If the incoming update has a newer timestamp, it replaces the existing item. If the existing item in the target Region has a newer or identical timestamp that wins the tie-break, the incoming update is discarded.

Tie-Breaking for Identical Timestamps

In rare cases where two updates occur at the exact same physical millisecond in different Regions, DynamoDB must resolve the conflict deterministically so that all replicas eventually converge to the identical state.

DynamoDB breaks ties by evaluating internal metadata attributes, typically favoring a deterministic hash or Region identifier associated with the transaction. Regardless of the specific internal tie-breaker applied, the rule is consistent across all Regions: every replica evaluates the conflict identically, ensuring eventual consistency throughout the global infrastructure.

Item-Level vs. Attribute-Level Resolution

A critical aspect of DynamoDB’s conflict resolution is that it operates at the entire item level, not the attribute level:

  • If Region A updates attribute_1 and Region B simultaneously updates attribute_2 on the same item, the update with the later timestamp overwrites the entire item.
  • The earlier write is discarded completely. The attributes are not merged automatically.

Without careful data modeling, this behavior can lead to "lost updates," where valid field-level changes are wiped out by concurrent writes elsewhere.

Managing and Preventing Concurrency Conflicts

Because DynamoDB relies purely on LWW without native support for Conflict-free Replicated Data Types (CRDTs), developers must design around this limitation when concurrent write conflicts cannot be tolerated:

  • Item Segregation: Separate concurrently updated attributes into distinct DynamoDB items using unique partition or sort keys. For example, store user profile data and user preferences in separate items to prevent one from overwriting the other.
  • Regional Affinity: Route all write traffic for a specific entity (such as a specific customer or tenant) to a designated primary Region. Use other Regions strictly for read traffic, shifting writes only during Regional failover events.
  • Application-Level Timestamps and Versioning: Implement an explicit version number or timestamp in the application payload. While DynamoDB's native conditional writes (attribute_exists, version = :current) only validate conditions against the local table at write time—not during cross-Region replication—application-level checks can still assist in auditing and identifying discarded updates.
  • Append-Only Event Sourcing: Instead of updating state in place, write sequential immutable events. An asynchronous processor can aggregate these events in a deterministic order across Regions.
