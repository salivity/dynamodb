DynamoDB GSI Limitations for Existing Tables

Adding a Global Secondary Index (GSI) to an existing Amazon DynamoDB table provides significant query flexibility, but it introduces distinct operational constraints and performance trade-offs. This article outlines the core limitations to consider, including index creation concurrency limits, read and write throughput consumption during backfilling, immutability of index schemas, and table-level service quotas.

Single Concurrent Index Operation

DynamoDB allows only one GSI to be created, updated, or deleted at a time per table. If you need to add multiple GSIs to an existing table, each index must be created sequentially. The table remains in an updating state until the current GSI finishes backfilling and transitions from the CREATING state to ACTIVE. Any attempt to initiate a second GSI creation while one is underway will result in a ResourceInUseException.

Base Table Throughput Consumption

When a new GSI is added to an existing table, DynamoDB scans the entire base table to backfill data into the new index.

  • Read Capacity Units (RCUs): The backfilling process consumes read capacity from the base table. If the base table is using Provisioned capacity mode without sufficient headroom, this scan can throttle regular application read traffic.
  • Write Capacity Units (WCUs): The GSI must be allocated adequate write capacity to absorb the backfill load alongside ongoing write operations. If the GSI's write capacity is too low, the backfill process slows down significantly, and incoming writes to the base table may be throttled to prevent the GSI from falling too far behind.

Backfill Duration and Monitoring

Backfill duration is proportional to the size of the base table and the provisioned throughput of both the base table and the GSI. For tables containing terabytes of data, backfilling can take several hours or even days. During this period:

  • The GSI cannot be queried.
  • The GSI cannot be modified or deleted until the build phase completes or fails.
  • Live writes to the base table during the backfill are also propagated to the new index, consuming additional GSI write capacity.

Immutable Index Definitions

Once a GSI creation request is submitted, its primary key schema (partition key and sort key) and projected attributes cannot be altered. If you omit an attribute from the projection list that your queries require, or if you select the wrong data type for the index key, the index cannot be patched. You must wait for the GSI to become ACTIVE, delete it, and create a new GSI with the correct schema, restarting the entire backfill process.

Quota and Size Limits

  • Maximum GSIs per Table: By default, DynamoDB permits up to 20 GSIs per table. While this soft limit can be increased by requesting a quota increase from AWS, high index counts multiply the write capacity required for every base table write.
  • Item Size Constraints: While GSIs allow sparse indexing (items without the index partition key are ignored), items that exceed the 400 KB limit cannot be written to the base table or the index. Large projected attribute sets increase storage costs and write unit consumption.
