DynamoDB TTL on Non-Numeric Data Types

Amazon DynamoDB Time-to-Live (TTL) automatically deletes expired items from tables to reduce storage costs and manage data lifecycles. This article explains how DynamoDB processes items when the configured TTL attribute contains non-numeric data types, highlighting the validation mechanics, runtime behavior, and best practices to avoid unexpected data retention.

Expected Data Format for TTL

DynamoDB TTL requires the designated expiration attribute to be formatted strictly as an Amazon DynamoDB Number (N) data type. Furthermore, the numeric value must represent the expiration timestamp in seconds elapsed since the Unix epoch (January 1, 1970, 00:00:00 UTC).

How Non-Numeric Data Types Are Handled

When DynamoDB evaluates an item for expiration, it inspects the designated TTL attribute. If the attribute contains any data type other than a Number—such as String (S), Binary (B), Boolean (BOOL), Map (M), List (L), or Null (NULL)—DynamoDB simply ignores the attribute.

Key behaviors include:

  • No Automatic Deletion: Because the TTL processor does not recognize non-numeric values as valid epoch timestamps, the item is completely bypassed by the background TTL cleanup process. The item will remain in the table indefinitely unless manually deleted or updated.
  • No Write-Time Validation: DynamoDB is a schemaless database. Writing an item with a non-numeric TTL attribute via PutItem, UpdateItem, or BatchWriteItem will succeed without throwing an error or validation exception. The database does not enforce schema constraints on TTL fields during write operations.
  • No CloudWatch TTL Error Metrics: DynamoDB does not emit dedicated error metrics or CloudWatch alarms for skipped non-numeric items. The items are silently excluded from TTL processing.

Common Scenarios and Pitfalls

A frequent mistake in DynamoDB implementations is passing formatted date strings or string-encoded numbers into the TTL attribute.

  • ISO-8601 Date Strings: Storing dates in human-readable formats (such as "2026-03-30T12:00:00Z") requires a String data type. DynamoDB ignores these entries entirely.
  • String-Encoded Epoch Values: If an epoch timestamp is wrapped in quotes (such as "1774872000"), the AWS SDK transmits it as a String (S) rather than a Number (N). Even though the content represents a numeric timestamp, DynamoDB treats it as non-numeric and ignores it.
  • Nested Attributes: DynamoDB TTL only inspects top-level attributes. Storing a timestamp inside a nested Map or List results in the TTL evaluator skipping the item, even if the nested value itself is a Number.

Resolving and Preventing Non-Numeric TTL Issues

To ensure items are properly removed by TTL:

  1. Enforce Type Conversion at the Application Layer: Ensure your application logic converts all expiration timestamps to integer values representing Unix epoch time in seconds before sending write requests.
  2. Scan for Malformed Types: Identify existing items with invalid types by running a table scan with the attribute_type filter expression (for example, attribute_type(ttl_attribute, 'S') to find String values).
  3. Correct Existing Records: Update identified items by converting the attribute to the Number data type containing the appropriate Unix timestamp in seconds.
