How LSI Updates Impact DynamoDB Provisioned Capacity

When modifying items in an Amazon DynamoDB table that has Local Secondary Indexes (LSIs), changes to indexed or projected attributes directly consume the base table's provisioned Write Capacity Units (WCUs). Because LSIs do not have independent throughput allocations, any index updates caused by base table mutations automatically draw from the base table's provisioned capacity pool. This article explains the shared capacity model of LSIs, the exact write cost incurred when modifying attributes, and how attribute projection choices determine overall throughput consumption.

The Shared Capacity Architecture

Unlike Global Secondary Indexes (GSIs), which have independently provisioned or on-demand throughput settings, Local Secondary Indexes share the provisioned Read Capacity Units (RCUs) and Write Capacity Units (WCUs) of the base table. Every write operation applied to the base table that also requires an update to one or more LSIs subtracts capacity directly from the base table’s allocated capacity.

Write Cost Mechanics of Updating Attributes

The write capacity consumed when updating an attribute depends strictly on whether the modified attribute is part of the index structure:

  • Updating an LSI Sort Key: If an update modifies the attribute that acts as the sort key for an LSI, DynamoDB must perform two operations within the index: deleting the existing index entry with the old sort key value and writing a new index entry with the updated value. This consumes write capacity for both the delete and the put operation in the index, in addition to the write operation performed on the base table itself.
  • Updating a Projected Attribute: If an update modifies an attribute that is not the index sort key but is projected into the LSI (via INCLUDE or ALL), DynamoDB must update the entry within the index to reflect the new value. This consumes write capacity on the base table proportional to the size of the updated index item.
  • Updating a Non-Projected Attribute: If the updated attribute is neither the LSI sort key nor projected into the index (via KEYS_ONLY or an omitted attribute in INCLUDE), the LSI is unaffected. In this scenario, DynamoDB only consumes the base table's standard WCU for the base item update, with zero additional WCU consumed by the index.

Item Size and Capacity Calculation

The throughput consumed by an index update is calculated based on the size of the index entry, not the full size of the base table item. An LSI item entry consists of:

  • The base table partition key value.
  • The base table sort key value.
  • The LSI sort key value.
  • Any attributes explicitly projected into the index.

The sum of these attributes determines the size of the index record. DynamoDB calculates the required WCUs by rounding up the index entry size to the next 1 KB increment. If multiple LSIs contain the modified attribute, each affected index independently consumes write capacity based on its respective item size.

Throttling Implications

Because write operations across all LSIs draw from a single provisioned WCU pool, frequent updates to indexed or heavily projected attributes can deplete the base table's available write capacity much faster than anticipated. If the combined write volume of the base table and all affected LSIs exceeds the provisioned limit, DynamoDB rejects the entire request with a ProvisionedThroughputExceededException, causing base table operations to throttle even if base table updates alone would have remained within capacity limits.
