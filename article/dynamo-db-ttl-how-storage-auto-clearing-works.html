DynamoDB TTL: How Storage Auto-Clearing Works

Amazon DynamoDB Time to Live (TTL) automates storage management by identifying and deleting expired items from tables without consuming provisioned throughput. By defining a specific timestamp attribute on records, DynamoDB continuously scans data in the background, invalidates out-of-date records, and removes them to optimize storage costs and maintain clean datasets.

Defining the Expiration Attribute

DynamoDB requires the user to designate a specific table attribute as the TTL metric. This attribute must be formatted as a Number data type containing a Unix epoch timestamp in seconds. During normal table operations, you populate this field with the exact future time at which the item becomes obsolete. Any record lacking this attribute, or containing an invalid format (such as string timestamps or millisecond precision), is ignored by the TTL mechanism and remains in the database indefinitely.

The Background Scanning and Deletion Process

DynamoDB uses an internal, distributed background process to manage the eviction of expired records:

  • Asynchronous Scans: Dedicated background threads continuously scan storage partitions to compare the designated TTL timestamp against the current epoch time.
  • Deletion Window: Once an item’s timestamp passes the current time, DynamoDB typically deletes the item within 48 hours. The exact timing depends on the partition size, volume of expired items, and overall system workload.
  • Zero Throughput Cost: Background deletions do not consume provisioned Read Capacity Units (RCUs) or Write Capacity Units (WCUs). This ensures that standard application traffic is neither throttled nor financially penalized by maintenance tasks.

Physical Storage Reclamation

When a background process deletes an expired item, the data is removed from the storage partition, immediately freeing up the raw storage space associated with the item's payload. This reduction is reflected in the cumulative table size metric reported in Amazon CloudWatch, which directly reduces ongoing storage costs. Additionally, the deletion automatically updates any Local Secondary Indexes (LSIs) and Global Secondary Indexes (GSIs) associated with the table, clearing the corresponding index entries across all partitions without additional capacity unit consumption.

Query and Scan Behavior During Deletion Lag

Because TTL deletion is asynchronous, records that have mathematically expired may still appear in read requests prior to physical removal. If an application requires strict enforcement of expiration, read operations (GetItem, Query, Scan) should use filter expressions to exclude records where the TTL attribute is less than or equal to the current epoch time.

Integration with DynamoDB Streams

TTL deletions are captured by DynamoDB Streams if streaming is enabled on the table. Each TTL-driven deletion generates an event marked with the REMOVE operation type. These events contain a distinct metadata identity flag (principalId: dynamodb.amazonaws.com), allowing downstream consumers, such as AWS Lambda, to differentiate between manual user deletions and automated TTL evictions. This enables systems to archive expired records to cold storage solutions like Amazon S3 before permanent data loss occurs.
