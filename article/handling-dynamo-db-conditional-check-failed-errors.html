Handling DynamoDB Conditional Check Failed Errors

When a conditional write operation in Amazon DynamoDB evaluates to false, the service rejects the request to prevent unintended data overwrites or mutations. DynamoDB communicates this failure by returning a specific client-side error, allowing applications to detect concurrency conflicts, apply fallback logic, or retry operations. Understanding how this error is structured across single-item writes and transactional requests is essential for building resilient distributed systems.

Standard Error Response: ConditionalCheckFailedException

For single-item write operations—including PutItem, UpdateItem, and DeleteItem—a failed condition expression causes DynamoDB to reject the operation and return an HTTP 400 Bad Request status code.

Along with the HTTP status, DynamoDB returns an exception type of ConditionalCheckFailedException. The JSON payload returned by the service includes:

  • __type: com.amazonaws.dynamodb.v20120810#ConditionalCheckFailedException
  • message: The conditional request failed

Because this is a 4xx client error, AWS SDKs do not automatically retry the request. The application code must catch this specific exception to determine the next action, such as refreshing local state or notifying the user of a conflict.

Inspecting Item State with ReturnValuesOnConditionCheckFailure

By default, a ConditionalCheckFailedException does not include the existing attributes of the item that caused the check to fail. Resolving the conflict typically required a subsequent GetItem call.

To eliminate this round-trip, DynamoDB supports the ReturnValuesOnConditionCheckFailure parameter. When set to ALL_OLD, DynamoDB includes the item's current attributes directly inside the error response payload:

  • If the condition fails and the item exists, the response populates the Item field with the current item data.
  • If the condition fails because the item does not exist (for example, when using attribute_exists), the Item field remains empty.

Consuming this data directly from the error response reduces latency and decreases overall read capacity unit (RCU) consumption.

Behavior in Transactional Writes

When using TransactWriteItems, DynamoDB handles conditional failures differently to preserve ACID guarantees:

  1. Transaction Cancellation: If a condition check on any single item within the transaction fails, the entire transaction is canceled, and no changes are committed.
  2. Exception Type: DynamoDB returns an HTTP 400 Bad Request with a TransactionCanceledException.
  3. CancellationReasons List: The error response includes a CancellationReasons array matching the order of the operations submitted in the request. The specific operation that violated the condition will have a code of ConditionalCheckFailed, while unaffected operations typically display None.

If ReturnValuesOnConditionCheckFailure is specified in a transactional write, the attributes of the failed item are attached to that operation's entry inside the CancellationReasons list.

Recommended Application Handling Patterns

Applications encountering conditional check errors should handle them based on the underlying access pattern:

  • Optimistic Locking: When updating records using a version number attribute, catch the ConditionalCheckFailedException, fetch the updated item, apply business logic to the new state, and re-attempt the write.
  • Idempotent Inserts: When using attribute_not_exists(partition_key) to avoid overwriting existing records, treat ConditionalCheckFailedException as a signal that the record is already created, bypassing the write without failing the workflow.
  • Atomic State Transitions: If using conditions to enforce state machine transitions (such as status moving from PENDING to PROCESSING), catch the exception to gracefully abort the process if another worker has already acquired the task.
