DynamoDB Batch Operations Over Throughput Limits

When an Amazon DynamoDB table exceeds its maximum provisioned throughput limit during batch operations, requests are throttled rather than completely dropped. Instead of rolling back the entire operation, DynamoDB partially processes the batch, fulfilling only the items that fall within the available capacity and returning the remaining records in the response payload. This article outlines how DynamoDB handles throughput exhaustion during BatchWriteItem and BatchGetItem calls, the nature of partial failures, and the engineering strategies required to manage throttled requests.

Partial Batch Failures and Unprocessed Items

DynamoDB batch operations are not atomic transactions. When you send a BatchWriteItem or BatchGetItem request, DynamoDB processes each individual put, delete, or get action independently.

If the table's provisioned read capacity units (RCUs) or write capacity units (WCUs) are fully consumed mid-batch, DynamoDB processes what it can and returns an HTTP 200 OK status. Inside the response object, it populates:

  • UnprocessedItems for BatchWriteItem calls, containing the specific put or delete requests that were throttled.
  • UnprocessedKeys for BatchGetItem calls, containing the primary keys that could not be read due to capacity constraints.

If the table is so severely throttled that none of the items in the batch can be processed, DynamoDB returns a 400 Bad Request error with a ProvisionedThroughputExceededException.

Automatic SDK Retries vs. Application Logic

Most AWS SDKs implement default retry behavior with exponential backoff for low-level throttled requests. However, SDK behavior varies when handling partial batch responses:

  • Automatic Retries: If the entire call fails with a ProvisionedThroughputExceededException, the SDK automatically retries the operation based on its configured retry policy.
  • Manual Retries Required: If DynamoDB returns an HTTP 200 with an UnprocessedItems or UnprocessedKeys payload, the SDK does not automatically re-submit those unprocessed items in a new request. The calling application must inspect the response, extract the remaining items, and retry them explicitly.

Failing to programmatically inspect and retry unprocessed items will result in silent data loss for writes or missing datasets for reads.

Systemic Impacts of Exceeding Throughput

Reaching provisioned limits causes downstream operational impacts:

  • Increased Latency: Implementing retry loops with exponential backoff and jitter introduces delays, increasing the end-to-end latency of the batch job.
  • Hot Partition Throttling: Even if total provisioned throughput across the entire table is high, individual partitions are capped at 1,000 WCUs and 3,000 RCUs. If a batch concentrates requests on a single partition key, that specific partition will throttle the operation while global capacity appears underutilized.
  • Thread and Connection Exhaustion: Long-running retry loops can tie up application threads and database connection pools, potentially propagating backpressure to upstream services.

Best Practices for Handling Batch Limits

To prevent and manage throughput exhaustion during batch workflows:

  1. Implement Exponential Backoff with Jitter: When reprocessing UnprocessedItems, pause execution using a progressively longer randomized backoff interval to avoid overwhelming the table immediately after a capacity spike.
  2. Enable DynamoDB Auto Scaling: If using Provisioned Mode, configure Auto Scaling to automatically raise capacity limits when sustained utilization crosses target thresholds.
  3. Evaluate On-Demand Capacity Mode: For workloads with unpredictable, high-volume traffic bursts, On-Demand mode dynamically accommodates traffic without manual provisioning.
  4. Distribute Partition Keys Uniformly: Ensure batch items do not target the same partition key repeatedly, which helps distribute the load across multiple internal partitions.
  5. Regulate Ingestion with a Message Queue: Place an Amazon SQS queue in front of batch write processes to buffer incoming data and rate-limit workers to match the table's provisioned limits.
