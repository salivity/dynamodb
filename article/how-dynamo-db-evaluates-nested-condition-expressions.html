How DynamoDB Evaluates Nested Condition Expressions

This article explains how Amazon DynamoDB processes condition expressions targeting nested attributes within document data types such as Maps and Lists. It details document path syntax, the step-by-step evaluation lifecycle against the existing item state, the behavior of common functions when parent or child keys are missing, and how conditional failures are handled during write operations.

Document Path Resolution

DynamoDB uses document paths to navigate complex, nested JSON-like structures (Maps and Lists). When evaluating a condition expression on nested attributes, the engine first resolves the path hierarchy:

  • Maps (Objects): Accessed using dot notation (e.g., Address.City or #parent.#child with Expression Attribute Names).
  • Lists (Arrays): Accessed using zero-based bracketed integer indexes (e.g., PhoneNumbers[0] or Preferences.Colors[2]).

To prevent issues with reserved keywords or special characters (such as hyphens or dots in map keys), DynamoDB requires or strongly advises the use of Expression Attribute Names placeholders (such as #a.#b) to define the traversal path.

Evaluation Lifecycle and State Checking

Condition expressions are evaluated against the current state of the item stored in DynamoDB immediately before a write operation (PutItem, UpdateItem, or DeleteItem) is committed.

  1. Read Target Item: DynamoDB reads the existing item from the partition. If the item does not exist, the evaluation treats all attributes as non-existent.
  2. Path Traversal: The evaluation engine follows the path from the root attribute down to the target node.
  3. Expression Application: The operator (=, <>, <, >, BETWEEN, IN) or built-in function (attribute_exists, attribute_not_exists, begins_with, contains, size) is applied to the resolved value.
  4. Commit or Abort: If the full expression evaluates to true, the write operation proceeds atomically. If it evaluates to false, the operation is aborted, and DynamoDB returns a ConditionalCheckFailedException.

Handling Missing Attributes and Partial Paths

A critical aspect of nested condition evaluation is how DynamoDB handles broken paths, where an intermediate parent node or the final leaf node does not exist in the item:

  • Comparison Operators (=, >, <, etc.): If any element in the path chain is missing (for example, evaluating User.Profile.Age > 18 when Profile does not exist), the path cannot be resolved. The expression evaluates to false.
  • attribute_exists(path): Evaluates to true only if every element in the document path exists down to the final target attribute. If any intermediate parent or the target leaf itself is missing, it evaluates to false.
  • attribute_not_exists(path): Evaluates to true if the final attribute is missing, or if any ancestor along the path does not exist. For example, attribute_not_exists(Metadata.Audit.Timestamp) returns true if Metadata is missing, if Audit is missing, or if Timestamp is missing.
  • Functions (size(), begins_with(), contains()): These functions require the target attribute to exist and be of the expected data type. If the attribute does not exist or the intermediate path is absent, the function cannot execute, causing the condition expression to evaluate to false.

Data Type Matching in Nested Checks

DynamoDB strictly enforces type checks during condition evaluation:

  • Evaluating a numeric comparison against a nested string value evaluates to false.
  • Using list-index traversal on a map attribute (e.g., MapAttribute[0]) or dot-notation traversal on a list attribute results in a ValidationException during request validation, aborting the request before condition evaluation occurs.
  • When evaluating arrays via size(ListPath), the target must explicitly resolve to a List, Set, Map, or String. If the path leads to a primitive number or boolean, the evaluation yields false.
