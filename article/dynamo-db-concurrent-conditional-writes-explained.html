DynamoDB Concurrent Conditional Writes Explained

When multiple clients attempt concurrent conditional writes targeting the same primary key, Amazon DynamoDB handles them through optimistic concurrency control and serialized execution at the storage replica level. DynamoDB evaluates conditional expressions directly against the latest committed state of an item. Because writes targeting the same partition key are strictly serialized, the first request evaluated will succeed if its condition is met, while subsequent concurrent requests are evaluated against the updated state and will fail with a ConditionalCheckFailedException if that condition is no longer valid.

The Serialization Process

DynamoDB distributes data across storage partitions, each managed by a three-node replication group using the Paxos consensus protocol. For any specific primary key, one node acts as the leader replica responsible for processing all write operations.

When multiple conditional write operations—such as PutItem, UpdateItem, or DeleteItem with a ConditionExpression—target the same partition key simultaneously:

  1. Request Queueing: The leader replica receives the incoming write requests. Even if requests arrive concurrently over the network, the leader sequences them into a deterministic, chronological queue.
  2. Atomic Evaluation and Commit: The leader evaluates the ConditionExpression of the first request against the item's current state. If the condition holds true, the leader writes the change to the local log and initiates a Paxos write quorum across the peer replicas.
  3. Sequential Execution: The subsequent request is not evaluated until the prior operation finishes committing (or failing). The leader then evaluates the second request against the newly updated state produced by the first request.

Handling Race Conditions and Failures

Because execution is strictly serialized on the partition leader, true simultaneous execution does not exist inside the storage engine. There are two primary outcomes for concurrent operations:

  • Condition Remains Valid: If the first write updates an attribute that is unrelated to the second write's condition, the second write will also evaluate to true and succeed.
  • Condition Is Invalidated: If the first write modifies or deletes data in a way that breaks the condition of the second write, DynamoDB rejects the second write. The service aborts the operation without committing any changes and immediately returns an HTTP 400 error containing a ConditionalCheckFailedException.

The Optimistic Locking Pattern

The most common use case for concurrent conditional writes is implementing optimistic locking using a version number or timestamp attribute.

Consider two clients, Client A and Client B, reading an item simultaneously at version = 1:

  1. Both clients prepare an update setting version = 2 under the condition that version = 1.
  2. Client A's request reaches the leader replica fractionally earlier. The condition version = 1 evaluates to true. DynamoDB updates the item, incrementing version to 2.
  3. Client B's request is evaluated immediately after. The leader checks the condition version = 1, but the item's version is now 2.
  4. Client B receives a ConditionalCheckFailedException. No data is overwritten or corrupted.

Client-Side Mitigation Strategies

Applications designed for high-concurrency DynamoDB workloads must anticipate and handle ConditionalCheckFailedException errors natively:

  • Read-Modify-Write Retries: Upon catching the exception, the client should fetch the latest state of the item, re-apply the business logic, increment the new version, and attempt the conditional write again.
  • Backoff and Jitter: When multiple workers repeatedly contend for the same primary key, immediate retries can lead to a "thundering herd" problem. Implementing truncated exponential backoff with full jitter spreads the retry attempts over time, reducing contention and allowing operations to succeed in sequence.
