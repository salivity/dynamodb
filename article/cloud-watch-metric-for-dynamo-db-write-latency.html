CloudWatch Metric for DynamoDB Write Latency

Monitoring write performance in Amazon DynamoDB is essential for ensuring application responsiveness and diagnosing performance bottlenecks. Amazon CloudWatch tracks this performance using the SuccessfulRequestLatency metric filtered by specific write operations. This article explains how SuccessfulRequestLatency works, how to isolate write operations, and how to effectively monitor and interpret DynamoDB write latency data.

The Primary Metric: SuccessfulRequestLatency

The primary CloudWatch metric used to monitor the time latency of DynamoDB write operations is SuccessfulRequestLatency.

This metric measures the time, in milliseconds, that DynamoDB takes to successfully respond to a request. Because SuccessfulRequestLatency captures all request types across your database, you must filter the metric using CloudWatch dimensions to isolate write actions.

Filtering by Write Operations

To view only write latency, combine the SuccessfulRequestLatency metric with the following dimensions:

  • TableName: Specifies the DynamoDB table you are evaluating.
  • Operation: Defines the API call executed. For write activity, select write-specific operations, including:
    • PutItem
    • UpdateItem
    • DeleteItem
    • BatchWriteItem
    • TransactWriteItems

Filtering by Operation allows you to see the exact latency for individual write APIs rather than an aggregate of both read and write traffic.

Recommended Statistics for Monitoring

When analyzing write latency in CloudWatch, using the appropriate statistic is critical for accurate performance analysis:

  • Average: Provides a general baseline for standard operation latency over time.
  • p95 and p99 (Percentiles): Most recommended for identifying outliers and tail latency. Averages often mask intermittent latency spikes caused by hot partitions, large item sizes, or provisioned throughput throttling.

Service Latency vs. Client-Side Latency

SuccessfulRequestLatency measures only the time spent processing the request inside DynamoDB. It does not include:

  • Network round-trip time between your application and DynamoDB.
  • Request queuing within client SDKs.
  • DNS resolution times.

If your application reports high write latency while the CloudWatch SuccessfulRequestLatency metric remains low, the delay is occurring outside of the DynamoDB service itself, such as in the network path, client-side resource exhaustion, or SDK connection pool settings.
