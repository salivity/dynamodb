How DynamoDB Handles Batch Write Partial Failures

This article explains how Amazon DynamoDB processes BatchWriteItem operations when a partial failure occurs. You will learn why DynamoDB treats individual operations within a batch independently, how the service signals partial failures through its response payload, the common causes behind these failures, and the standard retry strategies required to ensure all items are successfully written.

Non-Atomic Execution of Batch Operations

When you execute a BatchWriteItem request, DynamoDB does not treat the batch as a single, atomic transaction. A single call can accept up to 25 put or delete requests, with a total payload limit of 16 MB. DynamoDB evaluates and executes each put or delete request individually.

Because execution is non-atomic, the overall operation can succeed partially. Some items may be written successfully to their respective partitions, while other items within the same batch fail to write.

The HTTP 200 Status and UnprocessedItems

When a partial failure occurs, DynamoDB does not throw a system-level error or return a 4xx or 5xx HTTP status code. Instead, it returns an HTTP 200 OK response. This indicates that the batch request itself was well-formed and that the service processed as much of the batch as possible.

The response payload contains two key attributes:

  • Responses: Details about the operations that completed successfully (if requested or applicable depending on the SDK).
  • UnprocessedItems: A map containing every item that DynamoDB could not process. Each entry in this map includes the table name, the operation type (PutRequest or DeleteRequest), and the item attributes.

If the UnprocessedItems map is empty, every item in the batch succeeded. If it contains data, your application must take responsibility for those specific items.

Why Partial Failures Occur

Partial failures typically occur due to transient issues rather than validation errors. If a batch contains invalid parameters—such as an improperly formatted primary key or a request exceeding payload limits—the entire BatchWriteItem operation fails immediately with a 400-series client error, processing zero items.

Partial failures instead occur due to:

  • Provisioned Throughput Exceeded: One or more target partitions have exceeded their allocated Write Capacity Units (WCUs) or burst limits.
  • On-Demand Throttling: In on-demand mode, a sudden spike in traffic exceeding double the previous peak write throughput can throttle specific items.
  • Transient System Errors: Brief internal DynamoDB latency or network anomalies that prevent individual partition writes from finishing in time.

Recommended Handling Strategy

Because DynamoDB isolates the failed items in UnprocessedItems, handling partial failures involves an iterative retry loop rather than re-sending the entire original batch.

  1. Check for Unprocessed Items: After receiving the response, check if UnprocessedItems is populated.
  2. Back Off: Do not retry immediately. If the failure was caused by partition-level throttling, an immediate retry will likely fail again. Apply an exponential backoff algorithm with full jitter to space out retry attempts and smooth traffic spikes.
  3. Resubmit Failed Items: Pass the UnprocessedItems object directly into a subsequent BatchWriteItem request.
  4. Loop Until Complete: Continue the retry loop until UnprocessedItems is completely empty or until a predefined maximum retry limit or timeout is reached.
  5. Implement a Fallback: If retries are exhausted and items remain unprocessed, route those items to a Dead Letter Queue (DLQ) or log them to an error storage system for manual inspection and alerting.

While higher-level AWS SDK abstractions often perform automatic retries for transient errors, they may eventually exhaust their configured retry limit under sustained throttling. Writing robust logic to explicitly inspect and handle UnprocessedItems ensures no data is dropped during high-load periods.
