DynamoDB Global Tables 2019 Conflict Resolution

Amazon DynamoDB Global Tables (version 2019.11.21) provides a fully managed, active-active multi-region replication architecture that automatically synchronizes data across selected AWS regions. When concurrent writes target the same item in different regions, DynamoDB relies on a native, deterministic "last writer wins" strategy to reconcile differences. This article explains how this conflict resolution model operates, how DynamoDB evaluates competing writes, the structural scope of these updates, and architectural practices for managing concurrent writes.

The "Last Writer Wins" Mechanism

DynamoDB resolves all concurrent write conflicts in Global Tables using the Last Writer Wins (LWW) model. Under this rule, if two write operations update the same item in different regions almost simultaneously, DynamoDB evaluates the time of each update and applies the latest write across all replicas. The earlier write is discarded.

This reconciliation mechanism is automatic and fully managed. Developers do not need to configure custom conflict resolvers, reconciliation Lambdas, or consensus protocols at the database tier.

How Timestamps Determine the Winner

To determine which write occurred last, DynamoDB tracks internal metadata for every write operation:

  1. System-Generated Timestamps: When a write request is committed to a local regional replica, DynamoDB attaches an internal UTC timestamp to the update.
  2. Clock Synchronization: AWS uses the Amazon Time Sync Service across its infrastructure to keep server clocks synchronized to within milliseconds of UTC.
  3. Replication Evaluation: When an update is replicated asynchronously to peer regions, DynamoDB compares the timestamp of the incoming update with the timestamp of the existing item in the destination table.
  4. Application of the Win: If the incoming update has a newer timestamp than the existing item, it replaces the local item. If the incoming update has an older timestamp, it is ignored by the destination region.

Item-Level Replacement

A critical characteristic of conflict resolution in DynamoDB Global Tables is that it operates at the item level, not at the attribute level.

If an application updates Attribute A in Region 1 and simultaneously updates Attribute B in Region 2:

  • DynamoDB does not merge Attribute A and Attribute B into a single composite state.
  • The write with the latest timestamp completely replaces the item in all participating regions.
  • The attribute modification from the earlier write is lost entirely.

Because updates are applied to whole items rather than individual fields during cross-region sync, concurrent regional writes to different parts of the same item result in data overwrites.

Asynchronous Replication and Consistency

DynamoDB uses asynchronous replication to propagate writes across regions. A write returns success to the client as soon as it is committed to the local region; it then replicates across global replicas, typically in under a second.

During the propagation window:

  • Strongly consistent reads are supported only within the local region where the item was modified.
  • Reads across remote regions are eventually consistent.
  • A client reading from a remote region may temporarily observe stale data until the winning update arrives and overwrites older state.

Best Practices for Handling Conflicts

To prevent unintended overwrites and manage the limitations of Last Writer Wins, consider the following patterns:

  • Regional Routing (User Affinity): Route user requests to a single primary region based on user ID or partition key. If updates to a specific entity always originate in the same region, cross-region write conflicts are eliminated entirely.
  • Granular Item Design: Break large items containing multiple independently modified attributes into smaller, separate items. This prevents concurrent attribute updates from overwriting each other at the item level.
  • Idempotent Operations: Design operations to be idempotent so that replaying or overwriting an update does not leave the system in an invalid state.
  • Append-Only Event Streams: Instead of performing in-place updates across regions, record modifications as discrete, immutable events in a ledger pattern. A single worker or deterministic process can then materialize the final state.
