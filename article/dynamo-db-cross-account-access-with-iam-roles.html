DynamoDB Cross-Account Access with IAM Roles

Enabling cross-account access to an Amazon DynamoDB table allows applications and users in one AWS account to securely read from or write to a table hosted in another account. This is accomplished by establishing an IAM role in the account that owns the DynamoDB table, granting that role the necessary table-level permissions, and configuring its trust policy to permit an external AWS account to assume it. Using the AWS Security Token Service (STS), entities in the trusted account request temporary credentials to assume the role, enabling secure, credential-free cross-account delegation.

Core Architecture and Workflow

Cross-account access relies on two distinct AWS environments:

  • Account A (Resource Account): Owns the DynamoDB table and defines the IAM role.
  • Account B (Requesting Account): Contains the IAM user, application, Lambda function, or EC2 instance requiring access to Account A's DynamoDB table.

The process functions through four fundamental stages:

[Account B: Identity] 
       │ 
       ▼ (1. Calls sts:AssumeRole)
[AWS STS] 
       │
       ▼ (2. Issues Temporary Credentials)
[Account B: Identity] 
       │
       ▼ (3. Executes DynamoDB APIs with Temporary Credentials)
[Account A: DynamoDB Table]

Step 1: Create the IAM Role in Account A

Account A must host an IAM role that delegates access. This role requires two distinct policies: a Trust Policy and an Identity-based Permissions Policy.

1. The Trust Policy

The trust policy defines who is allowed to assume the role. It specifies Account B's root account ID (or a specific IAM principal within Account B) as the trusted entity.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::ACCOUNT_B_ID:root"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}

2. The Permissions Policy

Attached directly to the role, this policy determines what actions the role can execute against Account A's DynamoDB resources.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:UpdateItem",
        "dynamodb:Query",
        "dynamodb:Scan"
      ],
      "Resource": "arn:aws:dynamodb:REGION:ACCOUNT_A_ID:table/TargetTable"
    }
  ]
}

Step 2: Grant AssumeRole Permissions in Account B

By default, identities in Account B cannot assume roles in other accounts. An administrator in Account B must attach an inline or managed IAM policy to the specific user, group, or execution role (such as a Lambda execution role) that needs access.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::ACCOUNT_A_ID:role/RoleNameInAccountA"
    }
  ]
}

Step 3: Assume the Role Using AWS STS

The client application running in Account B uses the AWS SDK or CLI to call the STS AssumeRole API endpoint.

When invoking AssumeRole, the client provides:

  • The Amazon Resource Name (ARN) of the role in Account A (RoleArn).
  • A custom identifier for the session (RoleSessionName).
  • An optional external ID (ExternalId) to mitigate the confused deputy problem if third-party access is involved.

AWS STS returns a set of temporary security credentials comprising:

  • AccessKeyId
  • SecretAccessKey
  • SessionToken
  • Expiration Timestamp

Step 4: Access DynamoDB Using the Temporary Credentials

The application in Account B instantiates a new DynamoDB client using the temporary credentials provided by STS instead of its local credentials. All subsequent API calls (GetItem, PutItem, etc.) made by this client are signed with the temporary credentials, evaluate against the permissions policy assigned to Account A's role, and successfully execute against Account A's DynamoDB table.

Key Considerations

  • Resource-Based Policies vs. IAM Roles: While DynamoDB supports resource-based policies for direct cross-account access without assuming a role, cross-account IAM roles remain the standard architecture when centralized credential rotation, cross-account auditing, or strict session duration limits are required.
  • Session Durations: STS session durations range from 15 minutes to 12 hours. Applications must refresh or renew expired credentials to prevent API authorization failures.
  • Service Control Policies (SCPs): If either account is part of an AWS Organization, ensure that an SCP does not explicitly deny sts:AssumeRole or DynamoDB actions across account boundaries.
