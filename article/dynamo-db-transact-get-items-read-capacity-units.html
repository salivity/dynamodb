DynamoDB TransactGetItems Read Capacity Units

Amazon DynamoDB uses the TransactGetItems API operation to perform atomicity, consistency, isolation, and durability (ACID) compliant read transactions across multiple items. This article explains how DynamoDB computes consumed Read Capacity Units (RCUs) for multi-item transactional gets, detailing the mathematical formulas, per-item rounding behaviors, and practical examples to help you optimize and forecast table capacity costs.

The Baseline Pricing Rule for Transactional Reads

Transactional read requests provide atomicity and isolation, ensuring that you read the latest committed version of each item without encountering dirty or non-repeatable reads. Because of the coordination overhead required to guarantee ACID properties, transactional reads consume twice the capacity of standard strongly consistent reads.

  • Standard Strongly Consistent Read: 1 RCU per item up to 4 KB.
  • Transactional Read (TransactGetItems): 2 RCUs per item up to 4 KB.

Per-Item Size Rounding

When computing capacity for a TransactGetItems operation, DynamoDB does not aggregate the total size of all requested items together. Instead, it evaluates each item in the transaction independently:

  1. Size Measurement: The item’s size in bytes is determined (including attribute names and values).
  2. Rounding Up: The item size is rounded up to the nearest 4 KB increment.
  3. Multiplier Application: Each 4 KB increment consumes 2 RCUs.

The formula for each item in the transaction is:

\[\text{RCUs per item} = 2 \times \left\lceil \frac{\text{Item Size in Bytes}}{4096} \right\rceil\]

The total capacity consumed by the transaction is the sum of the RCUs calculated for each individual item:

\[\text{Total RCUs} = \sum_{i=1}^{n} \left( 2 \times \left\lceil \frac{\text{Size of Item } i}{4096} \right\rceil \right)\]

Handling Non-Existent Items

If a requested item in a TransactGetItems call does not exist, DynamoDB still performs the read operation to verify that absence. A non-existent item read is treated as a 0 KB to 4 KB payload and consumes 2 RCUs.

Calculation Example

Consider a single TransactGetItems request that reads three items from one or more tables:

  • Item A: 2.5 KB
  • Item B: 5.8 KB
  • Item C: Not found (0 KB)

The RCU consumption is calculated as follows:

  • Item A (2.5 KB): Rounds up to 4 KB.
    \[2 \times 1 = 2 \text{ RCUs}\]
  • Item B (5.8 KB): Rounds up to 8 KB (two 4 KB increments).
    \[2 \times 2 = 4 \text{ RCUs}\]
  • Item C (0 KB): Evaluated up to 4 KB.
    \[2 \times 1 = 2 \text{ RCUs}\]

Total Consumed Capacity: \(2 + 4 + 2 = 8 \text{ RCUs}\).

On-Demand vs. Provisioned Capacity Modes

The consumed capacity logic applies uniformly across DynamoDB billing modes:

  • Provisioned Mode: Consumes standard RCUs allocated to the table. If consumption spikes above your provisioned limits (and burst capacity is exhausted), the request will throw a ProvisionedThroughputExceededException.
  • On-Demand Mode: Consumes Read Request Units (RRUs). The pricing rule matches the provisioned model: one transactional read consumes 2 RRUs per 4 KB increment per item.
