How DynamoDB Manages Index Storage Overhead

Amazon DynamoDB manages storage overhead for index structures through architectural separation, selective attribute projection, and sparse indexing techniques. By treating secondary indexes as specialized, automated tables, DynamoDB gives developers granular control over the footprint of secondary access patterns. This article explains how DynamoDB minimizes and calculates index storage costs across Global Secondary Indexes (GSIs) and Local Secondary Indexes (LSIs), detailing the mechanics of sparse entries, projection types, and per-item metadata overhead.

Decoupled Storage Architecture

DynamoDB handles secondary indexes—particularly Global Secondary Indexes (GSIs)—as independent tables behind the scenes. When an item is written to the base table, DynamoDB asynchronously replicates the relevant data to the GSI storage partitions. Because GSIs do not reside within the exact same physical storage partitions as the base table, their storage overhead scales completely independently based on the specific attributes copied over rather than the total size of the parent item.

Local Secondary Indexes (LSIs), by contrast, reside on the same physical storage partition as the base item's partition key, governed by a strict 10 GB partition limit. To prevent index structures from breaching this limit, DynamoDB uses strict space accounting for every LSI update.

Attribute Projections

The primary mechanism for controlling storage overhead is the index projection policy. When defining an index, you specify which attributes are copied from the base table into the index structure:

  • KEYS_ONLY: Projects only the base table partition key, the base table sort key (if present), and the index partition and sort keys. This yields the lowest possible storage overhead, ideal for existence checks or lightweight lookups that subsequently fetch base table items if full attributes are needed.
  • INCLUDE: Projects only the primary keys plus a defined list of non-key attributes. This balances storage overhead with query performance, preventing over-allocation of disk space for large, rarely queried attributes (such as long text blobs or JSON payloads).
  • ALL: Clones the entire base table item into the index. While this eliminates the need for table fetches during queries, it doubles the raw data storage footprint for indexed items.

Sparse Indexing

DynamoDB inherently uses sparse indexes to eliminate overhead for irrelevant items. An item only occupies space in an index if that item contains both the partition key and sort key defined by the index schema.

If a base table contains millions of items, but only a fraction contain the attributes defining a secondary index, DynamoDB only writes those specific items to the index storage partition. Items lacking the index keys consume zero bytes of storage overhead in that index, allowing applications to create highly targeted, cost-effective index patterns without paying for empty records.

Metadata and Byte-Level Overhead Calculation

In addition to the raw size of projected attributes, DynamoDB applies structural overhead to each indexed entry to maintain internal B-tree-like routing and partition integrity:

  • Base Overhead: Each index entry incurs approximately 100 bytes of system overhead to store metadata, index pointers, and partition tracking information.
  • Key Storage: The index must store the base table primary keys (partition key and sort key) alongside the index primary keys, even in KEYS_ONLY configurations.
  • Total Calculation: The storage consumed by an indexed item equals the size of the base table primary keys + the size of the index keys + the size of projected non-key attributes + 100 bytes of overhead.

By leveraging sparse entries and restricting projected attributes to the minimum required dataset, DynamoDB ensures that the physical storage overhead of secondary indexes remains predictable, compact, and isolated from base table expansion.
