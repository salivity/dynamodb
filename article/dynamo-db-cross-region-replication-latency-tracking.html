DynamoDB Cross-Region Replication Latency Tracking

Amazon DynamoDB Global Tables provide fully managed, active-active cross-region data replication to deliver fast local read and write performance for globally distributed applications. To ensure operational visibility and data consistency across geographic boundaries, DynamoDB continuously monitors and tracks cross-region replication latency. This article details the underlying mechanisms DynamoDB uses to measure replication delays, the metrics it exposes via Amazon CloudWatch, and how time synchronization ensures accuracy across regions.

The Underlying Replication Architecture

DynamoDB cross-region replication is built on DynamoDB Streams. When an item is written, updated, or deleted in a source table, the modification is recorded in an ordered, near-real-time changelog. DynamoDB manages background replication fleets that read these change records from the source region's stream and apply them asynchronously to replica tables in the target regions.

Because replication is asynchronous, a slight delay occurs between the moment an item is committed locally and the moment it is committed in a remote replica. Tracking this delay is vital for applications that require bounded staleness or need to detect network partition events.

How Replication Latency Is Measured

DynamoDB measures replication latency using metadata timestamps embedded directly within stream records:

  1. Write Timestamping: When a write operation completes successfully in the source region, DynamoDB assigns a millisecond-precision server-side timestamp indicating when the update was committed to storage.
  2. Transit and Application: The replication worker retrieves the record from the stream and sends it to the target region.
  3. Latency Calculation: Upon successfully committing the update to the target replica table, the target region's replication coordinator compares the current system time in the destination region with the original timestamp recorded in the source region. The difference represents the elapsed replication time.

Clock Synchronization via Amazon Time Sync Service

Calculating latency using timestamps generated in different physical locations requires synchronized clocks. If clocks between AWS regions drift, latency measurements become inaccurate.

AWS resolves this using the Amazon Time Sync Service. This service utilizes a redundant fleet of satellite-connected reference clocks and atomic clocks deployed within each AWS region. By keeping host clocks synchronized within microsecond-level accuracy to Coordinated Universal Time (UTC), DynamoDB ensures that cross-region timestamp comparisons accurately reflect true transit and application delays rather than clock drift.

CloudWatch ReplicationLatency Metric

DynamoDB aggregates these latency measurements and publishes them to Amazon CloudWatch under the ReplicationLatency metric.

  • Dimensions: The metric is emitted per table and split across source and destination regions (e.g., TableName, ReceivingRegion).
  • Interpretation: ReplicationLatency represents the elapsed time (expressed in milliseconds) for an item updated in a source region to appear in the destination region's replica.
  • Statistical Tracking: Because network conditions and write volumes vary, latency is evaluated using percentiles (such as p90, p99, and maximum) rather than simple averages. Monitoring p99 latency allows teams to identify transient network congestion or throttling events that affect tail-end performance.

Handling Empty Streams and Idle Periods

When a table experiences low or zero write traffic, calculating latency based purely on user data is impossible because no stream records exist to measure. To maintain continuous tracking and health checks, DynamoDB's internal replication system generates periodic heartbeat markers. These internal records traverse the replication pipeline like standard writes, ensuring that ReplicationLatency remains accurate and updated even during periods of low application activity.
