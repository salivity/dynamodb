DynamoDB Soft Deletes Before TTL Sweeps Explained

Amazon DynamoDB includes a native Time to Live (TTL) mechanism that marks items for deletion once a specified epoch timestamp passes, but the physical deletion can take up to 48 hours to execute. This article details how to implement automated soft deletion patterns in DynamoDB to ensure applications immediately treat expired data as deleted before the background sweep purges the physical records.

The TTL Lag and the Need for Soft Deletion

DynamoDB TTL operates as a background maintenance process. When an item’s TTL timestamp expires, it remains physically present on the partition until DynamoDB's internal sweep reclaims the storage space. Because this sweep occurs asynchronously without consuming read or write throughput, there is an operational window where expired data remains readable unless the application actively accounts for it.

DynamoDB does not provide a native, built-in "soft delete" state out of the box; instead, soft deletion before the background sweep requires architectural patterns that combine TTL attributes with client-side filters, application flags, and DynamoDB Streams.

Pattern 1: Query-Time Filtering via Filter Expressions

The most common approach to achieve an instantaneous soft delete is by filtering expired items at the read layer. Because the item contains an epoch timestamp attribute used for TTL, read requests can compare that attribute against the current system time.

  • Implementation: Add a FilterExpression to Query and Scan operations:

    FilterExpression: "attribute_not_exists(#ttl) OR #ttl > :current_epoch"

  • Behavior: Even if an item is still physically stored on the partition awaiting the TTL sweep, DynamoDB evaluates the condition and excludes it from the result set returned to the client.

  • Trade-off: DynamoDB consumes read capacity units (RCUs) for the items evaluated before applying the filter, but the application layer never sees the stale item.

Pattern 2: Explicit Soft Deletes with Automated Hard Deletion

When an application needs an item marked as deleted immediately across all read patterns (including GetItem requests that do not support filter expressions), you can use an explicit soft-delete flag paired with a TTL timestamp:

  1. Write the Soft Delete: When a delete action occurs, the application updates the record rather than issuing a DeleteItem request. It sets an is_deleted attribute to true and sets the ttl attribute to an epoch timestamp (either immediate or set to a retention buffer, such as 30 days).
  2. Conditional Reads: Applications check is_deleted on direct key lookups (GetItem). If is_deleted is true, the application treats the item as a 404/Not Found.
  3. Automated Hard Sweep: When the ttl epoch passes, DynamoDB's background sweep automatically performs the physical deletion, eliminating the need for a separate batch-deletion script or worker.

Pattern 3: Event-Driven Soft Deletions Using DynamoDB Streams

If downstream systems or secondary data stores need to register the soft-deleted state before the item disappears permanently, DynamoDB Streams provides the necessary event hooks.

When DynamoDB's TTL process finally deletes an item, it writes a REMOVE event to the DynamoDB Stream. The event contains a system identity field:

"userIdentity": {
  "type": "Service",
  "principalId": "dynamodb.amazonaws.com"
}

An AWS Lambda function processing the stream can inspect this identity:

  • If principalId equals dynamodb.amazonaws.com, the deletion was caused by a TTL sweep.
  • The Lambda function can then archive the record to Amazon S3, notify downstream caches, or record an audit log confirming the final expiration.

Handling Consistency Considerations

DynamoDB's strongly consistent reads do not bypass unpurged TTL items. If a client performs a GetItem with ConsistentRead: true on an item that passed its TTL timestamp but has not yet been swept, the expired item will still be returned. Implementing read-time verification (either checking the TTL timestamp against Date.now() or validating an is_deleted boolean) remains mandatory across all read paths until the background process completes.
