DynamoDB WCU for Nested Updates vs Item Overwrites

This article explains how Amazon DynamoDB calculates Write Capacity Units (WCUs) when performing partial nested map updates compared to full item overwrites. While developers often expect granular updates to consume fewer write resources, DynamoDB determines write consumption based on the total size of the item rather than the size of the modified attribute. Understanding this behavior is essential for optimizing database costs, designing efficient data models, and preventing unexpected throttling in high-throughput applications.

How DynamoDB Calculates Write Capacity

DynamoDB measures write capacity in Write Capacity Units (WCUs) for provisioned tables or Write Request Units (WRUs) for on-demand tables. One write capacity unit represents one standard write per second for an item up to 1 KB in size.

If an item exceeds 1 KB, DynamoDB rounds up the total item size to the next 1 KB boundary. For example:

  • An item sized at 800 bytes consumes 1 WCU.
  • An item sized at 1.5 KB consumes 2 WCUs.
  • An item sized at 4.1 KB consumes 5 WCUs.

Transactions double these requirements, consuming 2 WCUs per 1 KB.

Nested Map Updates (UpdateItem)

When you use the UpdateItem API to modify, add, or delete an attribute inside a nested map (for example, using the update expression SET info.address.zip = :val), DynamoDB does not meter the write based only on the changed attribute.

Instead, DynamoDB meters the operation based on the larger of the two item sizes:

  1. The total size of the item before the update.
  2. The total size of the item after the update.

Even if you modify a single 4-byte integer deep within a nested map, DynamoDB reads and rewrites the entire item internally. If the item is 9.5 KB prior to the update and remains 9.5 KB after changing the nested value, the update consumes 10 WCUs.

Furthermore, if an update reduces the item size—such as using REMOVE info.largeList to shrink an item from 8 KB to 1 KB—DynamoDB still charges for the 8 KB pre-update representation (consuming 8 WCUs).

Entire Item Overwrites (PutItem)

When performing an entire item overwrite using the PutItem API, you replace all existing attributes with a new payload under the same partition (and sort) key.

For full overwrites, DynamoDB meters capacity based strictly on the size of the new item being written, rounded up to the nearest 1 KB.

Unlike UpdateItem, a PutItem operation does not inspect the previous item’s size for capacity billing unless you configure a conditional expression that requires evaluating the existing item's contents. If an existing 8 KB item is overwritten with a new 1 KB item via PutItem, DynamoDB charges only 1 WCU.

Direct Comparison

Scenario UpdateItem (Nested Map) PutItem (Full Overwrite)
Data modified Individual nested keys via SET/REMOVE Entire item payload
Calculation basis Greater of pre-update or post-update item size Size of the newly written item
4 KB item, 20-byte change Consumes 4 WCUs Consumes 4 WCUs
Shrinking 10 KB item to 2 KB Consumes 10 WCUs Consumes 2 WCUs

Architectural Recommendations

Because nested updates consume capacity for the entire item, storing frequently updated nested attributes inside large items leads to inefficient capacity utilization.

  • Separate dynamic attributes: If an item contains large, static data (such as product descriptions or metadata) alongside high-frequency updates (such as counters or status flags), separate them into two distinct items or tables.
  • Flatten structures when appropriate: If a map grows indefinitely, it increases the cost of every subsequent write to that item. Consider modeling dynamic list or map elements as separate items with a shared partition key and distinct sort keys.
  • Choose PutItem for radical shrinkage: When replacing an item with a drastically smaller payload, a standard PutItem call is more cost-efficient in WCUs than an UpdateItem with multiple REMOVE actions.
