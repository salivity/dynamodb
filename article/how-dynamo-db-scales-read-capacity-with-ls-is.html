How DynamoDB Scales Read Capacity with LSIs

In Amazon DynamoDB, Local Secondary Indexes (LSIs) do not have their own dedicated throughput; instead, they share the read and write capacity provisioned for the base table. Scaling read capacity for an LSI is therefore achieved entirely through the capacity management of the parent table, whether managed via On-Demand mode, provisioned capacity with Auto Scaling, or manual adjustments. Understanding this shared capacity model, along with read consistency choices and partition limits, is essential for maintaining performance and avoiding throttling when querying LSIs.

The Shared Capacity Architecture

Unlike Global Secondary Indexes (GSIs), which maintain independent read and write capacity allocations, an LSI always consumes the Read Capacity Units (RCUs) of the underlying base table. When an application queries or scans an LSI, DynamoDB deducts the necessary RCUs directly from the base table’s allocated pool.

Because capacity is shared, any operation scaling the base table directly scales the available throughput for its LSIs:

  • On-Demand Capacity Mode: DynamoDB automatically scales read throughput up or down based on incoming request volume. When queries to an LSI surge, DynamoDB accommodates the traffic instantly without manual configuration, billing read request units against the base table.
  • Provisioned Capacity with Auto Scaling: DynamoDB Auto Scaling dynamically modifies the base table's provisioned RCUs in response to CloudWatch metrics. As query volume on the LSI increases, the overall table utilization rises, triggering an automatic scale-up of the base table's read capacity.
  • Manual Provisioning: Administrators can manually increase the base table's RCU threshold to provide sufficient headroom for expected spikes in LSI read operations.

Factors Affecting LSI Read Capacity Consumption

The actual rate at which an LSI consumes read capacity depends on consistency settings and attribute projection:

  • Read Consistency: LSIs support both eventually consistent and strongly consistent reads. An eventually consistent read consumes 0.5 RCUs for items up to 4 KB, whereas a strongly consistent read consumes 1 RCU for items up to 4 KB. Selecting the appropriate consistency model directly halves or doubles read capacity consumption on the base table.
  • Attribute Projections: An LSI can project KEYS_ONLY, INCLUDE (specific attributes), or ALL base table attributes. If a query requests attributes that are not projected into the LSI, DynamoDB must perform an additional read against the base table to fetch the missing data. This action incurs extra RCU consumption, doubling the read cost for that query.

Partition Constraints and Adaptive Capacity

An LSI uses the same partition key as the base table, grouping data into what DynamoDB calls an "item collection." While overall read capacity scales with the base table, individual partitions have hard performance boundaries:

  • Partition Limits: A single partition in DynamoDB can supply a maximum of 3,000 RCUs. Because all LSI items with the same partition key reside on the same storage node as the base item, queries targeting an LSI for a specific partition key draw from that partition's 3,000 RCU limit.
  • Adaptive Capacity: If read operations disproportionately target a specific LSI partition, DynamoDB’s adaptive capacity feature automatically allocates unused capacity from other partitions to the high-traffic partition to prevent throttling, provided the total traffic does not exceed the single-partition physical ceiling.
  • Item Collection Size Limit: Any table with one or more LSIs imposes a strict 10 GB limit per item collection (all base table items and LSI items sharing a single partition key). Exceeding this boundary halts further writes, though reads remain operational up to partition throughput limits.
