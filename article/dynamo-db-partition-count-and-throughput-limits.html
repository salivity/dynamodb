DynamoDB Partition Count and Throughput Limits

In Amazon DynamoDB, table throughput and storage are distributed across physical partitions, making partition count a critical factor in performance management. DynamoDB allocates provisioned Read Capacity Units (RCUs) and Write Capacity Units (WCUs) uniformly across all active partitions. Consequently, as the number of partitions increases due to growing data volume or high throughput demands, the throughput allocated to each individual partition decreases proportionally, which directly affects how workloads handle access spikes and key distribution.

How DynamoDB Determines Partition Count

DynamoDB calculates the number of physical partitions allocated to a table based on two constraints: storage volume and total provisioned throughput. A single physical partition has hard performance and storage limits:

  • Maximum storage: 10 GB
  • Maximum read throughput: 3,000 RCUs
  • Maximum write throughput: 1,000 WCUs

DynamoDB uses the following formula to allocate partitions:

  • Partitions based on capacity = (Total Provisioned RCUs / 3,000) + (Total Provisioned WCUs / 1,000)
  • Partitions based on size = Total Table Size in GB / 10 GB
  • Total Partitions = Max(Capacity Partitions, Size Partitions), rounded up to the nearest integer.

Once partitions are allocated, they never decrease, even if provisioned throughput or stored data decreases.

The Division of Provisioned Throughput

DynamoDB divides total provisioned throughput equally among all physical partitions. The available throughput per partition is governed by:

\[\text{Throughput per Partition} = \frac{\text{Total Provisioned Throughput}}{\text{Partition Count}}\]

For example, if a table is provisioned with 1,000 WCUs and fits on a single partition, that partition can utilize the full 1,000 WCUs. If the table grows to 45 GB, DynamoDB automatically provisions 5 partitions to satisfy the storage requirement. The 1,000 WCUs are then divided equally among the 5 partitions, granting each partition a base allocation of 200 WCUs.

Impact on Hot Partitions and Throttling

Because capacity is distributed evenly, a higher partition count significantly lowers the baseline capacity allocated to any single partition. If application access patterns concentrate heavily on a small set of partition keys—a scenario known as a "hot partition"—the table can experience throttling errors (ProvisionedThroughputExceededException), even if the overall table capacity is substantially underutilized.

Using the previous example, an individual key on a 5-partition table cannot consume more than 200 WCUs consistently without triggering throttling, despite the table having an overall limit of 1,000 WCUs.

Adaptive Capacity Mitigations and Limitations

DynamoDB includes a feature called Adaptive Capacity to mitigate uneven traffic distribution. Adaptive Capacity automatically shifts unused capacity from quiet partitions to actively loaded partitions and uses burst capacity for short-term spikes.

However, Adaptive Capacity cannot bypass the hard physical limits of a single partition. Regardless of how high total table throughput is provisioned or how much spare capacity exists across the table, an individual physical partition can never exceed 3,000 RCUs or 1,000 WCUs for sustained workloads. As a result, maintaining a uniform partition key distribution with high cardinality is necessary to prevent partition counts from constraining overall application throughput.
