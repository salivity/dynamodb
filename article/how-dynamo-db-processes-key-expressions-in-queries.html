How DynamoDB Processes Key Expressions in Queries

This article explores how Amazon DynamoDB evaluates and executes key condition expressions during a query operation. When querying a table or secondary index, DynamoDB relies on key expressions to locate items without scanning the entire dataset. Understanding this internal workflow—from hash routing and sort key evaluation to physical data retrieval and read capacity calculation—enables developers to design high-performance, cost-effective schemas.

1. Partition Key Routing

The query process begins with the partition key specified in the KeyConditionExpression. DynamoDB requires an exact match (=) for the partition key.

When the query request reaches the DynamoDB request router, the router takes the partition key value and processes it through an internal hash function. The resulting hash value maps directly to a specific partition—a physical storage node (and its replicas) managed by DynamoDB. Because the partition key identifies the precise storage node, DynamoDB skips the vast majority of the table and targets only the partition that holds the matching data.

2. Sort Key Evaluation

Once the target partition is identified, DynamoDB evaluates the sort key portion of the key condition expression, if one is provided. Unlike partition keys, sort keys support range comparisons and functions:

  • Equality: =
  • Range comparisons: <, <=, >, >=
  • Subsets: BETWEEN
  • Prefix matching: begins_with()

Within each physical partition, items sharing the same partition key are stored in an ordered structure (such as a B-tree), sorted in ascending order by their sort key values. DynamoDB uses the sort key condition to find the starting and ending boundaries of the requested dataset within the index structure.

3. Sequential Data Retrieval

Because items with the same partition key are stored contiguously and pre-sorted by their sort key, DynamoDB can read the matching records sequentially from physical storage.

If no sort key condition is specified, DynamoDB retrieves all items associated with that partition key. If a sort key condition is present, the storage engine jumps directly to the first matching entry and reads sequentially until it encounters an item that no longer satisfies the condition.

Key attributes of this phase include:

  • Scan Direction: By default, items are read in ascending order. If the ScanIndexForward parameter is set to false, DynamoDB traverses the sorted structure in reverse order.
  • Limit Evaluation: If a Limit parameter is defined, DynamoDB stops reading as soon as the specified number of items are evaluated or the result set reaches 1 MB of raw data, whichever comes first.

4. Filter Expressions and Capacity Calculation

It is important to distinguish the key condition expression from a filter expression. DynamoDB processes the key condition expression first to retrieve the target slice of data.

Read Capacity Units (RCUs) are billed based on the total size of all items read using the key condition expression, rounded up to the nearest 4 KB chunk. If a FilterExpression is also applied to non-key attributes, it runs in memory after the key expression retrieval. Non-matching items are discarded before returning the response to the client, but the read capacity consumed remains based on the initial key-based retrieval.

5. Returning the Result

Finally, DynamoDB packages the matching items into the response payload. If the query hit the 1 MB data limit or evaluated the maximum number of items specified by Limit before finishing the key range, the response includes a LastEvaluatedKey. The client application can pass this key back in a subsequent query as the ExclusiveStartKey to resume processing exactly where the previous query left off.
