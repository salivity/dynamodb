DynamoDB Filter Expressions and Read Capacity Usage

This article examines how DynamoDB filter expressions impact Read Capacity Unit (RCU) consumption during Query and Scan operations. While filter expressions are effective for reducing network payload sizes and client-side processing, they do not decrease the number of RCUs consumed by a request. Understanding this distinction is essential for optimizing Amazon DynamoDB architecture, predicting operational costs, and designing efficient table schemas.

How DynamoDB Processes Read Operations

When executing a Query or Scan operation with a FilterExpression, DynamoDB performs the request in two sequential stages:

  1. Read Stage: DynamoDB identifies and reads the items from storage based on the request parameters. For a Query, it reads all items matching the KeyConditionExpression. For a Scan, it reads all items within the scanned partition space or segment up to the specified limit (or 1 MB max).
  2. Filter Stage: DynamoDB applies the FilterExpression to the items retrieved in the read stage. Items that do not match the filter criteria are discarded before the final response is returned to the client.

Because read capacity measurement occurs during the first stage, the filtering logic has zero impact on the volume of data initially read from disk.

The Direct Impact on Read Capacity Units (RCUs)

DynamoDB calculates consumed RCUs based on the total size of all items evaluated before applying the FilterExpression.

  • Strongly Consistent Reads: 1 RCU per 4 KB of data evaluated.
  • Eventually Consistent Reads: 0.5 RCU per 4 KB of data evaluated.
  • Transactional Reads: 2 RCUs per 4 KB of data evaluated.

For example, if a Query operation matches 100 items totaling 400 KB via the partition and sort keys, DynamoDB reads all 400 KB into memory. If a FilterExpression subsequently excludes 99 of those items, the client receives only a single 4 KB item. Despite the tiny response payload, DynamoDB charges for the full 400 KB evaluated, consuming 50 eventually consistent RCUs (or 100 strongly consistent RCUs).

The 1 MB Limit Constraint

DynamoDB limits individual read operations to a maximum of 1 MB of evaluated data per request. Because the FilterExpression is applied after this 1 MB boundary is read, an operation can return an empty result set while still consuming full read capacity and returning a pagination token (LastEvaluatedKey). Applications must handle pagination to evaluate subsequent items, further accumulating RCU costs.

Benefits of Filter Expressions

Although they do not reduce database-level read costs, filter expressions provide several distinct architectural advantages:

  • Reduced Network Latency and Bandwidth: By discarding unwanted attributes or items on the server side, DynamoDB transfers significantly smaller payloads over the wire to your application.
  • Lower Client-Side Compute: Applications do not need to spend CPU cycles or memory filtering large arrays of objects in code.
  • Simplified Application Logic: Developers can write cleaner client code without implementing custom filtering routines.

Best Practices to Actually Reduce RCUs

To lower read capacity usage and associated AWS costs, filtering must occur before data retrieval:

  • Optimize Partition and Sort Keys: Design sort keys that allow narrow ranges using operators like begins_with, between, and relational comparisons directly in the KeyConditionExpression.
  • Implement Global Secondary Indexes (GSIs): Create targeted GSIs with alternative partition and sort keys that isolate the exact items you need to query.
  • Use Sparse Indexes: Project only the items containing specific attributes into a GSI. If an item lacks the GSI's key attributes, it is not written to the index, effectively pre-filtering the dataset at zero query-time read penalty.
