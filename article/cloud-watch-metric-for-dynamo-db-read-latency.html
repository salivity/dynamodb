CloudWatch Metric for DynamoDB Read Latency

This article explains the specific Amazon CloudWatch metric used to monitor DynamoDB read latency, how it is recorded, and how to filter it for distinct read operations. Amazon CloudWatch tracks the performance of Amazon DynamoDB tables automatically, allowing developers and administrators to monitor service-side processing time, detect performance degradation, and optimize read throughput.

The primary Amazon CloudWatch metric that measures the latency of DynamoDB read requests is SuccessfulRequestLatency. This metric captures the time DynamoDB takes to process a successful request, measured in milliseconds on the service side.

Because SuccessfulRequestLatency applies to both read and write operations across DynamoDB, it must be filtered by the Operation dimension to isolate read activity. The read operations tracked under this metric include:

  • GetItem: Latency for retrieving a single item using its primary key.
  • BatchGetItem: Latency for retrieving up to 100 items across one or more tables.
  • Query: Latency for retrieving multiple items sharing the same partition key.
  • Scan: Latency for reading every item in a table or a secondary index.

To monitor this data effectively, view SuccessfulRequestLatency with the TableName and Operation dimensions in the CloudWatch console. While the Average statistic provides a baseline of typical response times, percentile statistics such as p95 or p99 are recommended for identifying latency spikes and tail-latency issues affecting end users.

It is important to note that SuccessfulRequestLatency reflects server-side latency only. It measures the duration from when DynamoDB receives the request until it finishes processing it. Network transit time, DNS resolution, and client-side processing are not captured by this metric; monitoring full round-trip latency requires client-side metrics via the AWS SDK.
